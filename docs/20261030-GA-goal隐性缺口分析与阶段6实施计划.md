# GA Goal 隐性缺口分析与 Phase 6 实施计划

> 日期：2026-10-30
> 范围：`genericagent/`（核心）、`frontends/ink`、`frontends/terminal`、`frontends/web`
> 前置：Phase 5（`edf7af4`）已落盘 SDK 元数据 / 只读卡片 / 本地遥测 / 默认关闭 nudge / 会话累计输出 token。
> 本文先做根因分析，再给修复方案与测试矩阵；随后按 §5 顺序实施，不 push。

---

## 1. 结论先行

Phase 5 把「goal 元数据 + 卡片 + 遥测」做到了可用，但还有 **6 个隐性缺口**，它们不影响主链路「设置目标 → Stop 门禁 → 达成自动清除」，却会破坏 **可恢复性、可发现性、审计完整性、弱模型健壮性、多前端一致性**。逐项核实如下：

- 都是**独立小改动**，互相不阻塞，可整体作为 Phase 6 一批做。
- 风险集中在 **恢复路径**（缺口 1）与 **hooks 行为**（缺口 4）；其余为 UI/遥测/文案级。
- 缺口 1 还牵出一个隐藏依赖：`session_output_tokens` 未持久化，恢复后归零，会让「tokens spent」出现负差被截断成 0 —— 必须一起修。

## 2. 缺口总览

| # | 缺口 | 落点 | 影响面 | 严重度 |
| --- | --- | --- | --- | --- |
| 1 | resume 后 goal 丢失 | `transcripts.py` load_v2 / restore_agent_session | 恢复会话失去卡片与门禁；tokens 计算错位 | 高 |
| 2 | `/goal` 不在补全与帮助 | `slashCommands.ts` / `App.tsx::helpText` | 用户敲 `/` 看不到 goal | 中 |
| 3 | 覆盖旧 goal 无 superseded 记录 | `app.py::_set_goal` / `_clear_goal` | 审计缺一条；`goal_cleared` 不区分原因 | 中 |
| 4 | 求值器非法 JSON 不重试 | `hooks/runner.py::_prompt_execute` | 弱模型偶发误判放行 | 中 |
| 5 | 元数据不随 ready/重连重发 | `app.py::_notify_goal_metadata` / `bridge.py` | 重连后卡片消失，需再变一次才回来 | 中 |
| 6 | 只有 Ink 消费 goal metadata | `terminal/web/bots/acp` | CLI/Web 无 goal 只读展示 | 低 |

## 3. 逐项根因与方案

### 缺口 1：resume 后 goal 丢失

**根因（已核实的代码坐标）**

- `genericagent/core/transcripts.py:1042` 的 `load_v2`：
  ```python
  elif kind in {"session_start", "resumed_from", "workflow_started",
                "workflow_completed", "workflow_failed", "goal_status",
                "active_goal"}:
      continue
  ```
  `active_goal` / `goal_status` 被**直接丢弃**，既没有解析出「当前 goal」，也没有进入 `LoadedSession`。
- `LoadedSession`（同文件 `:51`）没有 goal 字段。
- `restore_agent_session`（同文件 `:1291`）只恢复 backend.history / working_state / identity，**不重建 `agent.active_goal`，也不重新注册 `goal:stop` hook**。
- 追加发现：`record_active_goal`（`:660`）落盘的 payload**缺 `tokens_at_start`**（只写 condition/iterations/set_at/origin/last_reason），恢复后无法还原 token 锚点。
- 追加发现：`append_working_state`（`:285`）**不保存 `session_output_tokens`**，`restore_agent_session` 也不恢复它。恢复会话后累计输出 token 归零，而 goal 的 `tokens_at_start` 是旧值 → `tokens_spent` 被 `max(0, …)` 截成 0，指标失真。

**方案**

1. `record_active_goal` 的 payload 补 `tokens_at_start`（int）、`deferred_since` / `checkin_count` 等可选字段（先只补 `tokens_at_start`，其余保持向前兼容）。
2. `load_v2` 不再无脑 skip：新增对 `active_goal` 的最小解析，记录**最后一条** `active_goal` 事件的 `goal` payload 到局部变量 `latest_active_goal`；同时记录**最后一条非 sentinel、带 met/failed 的 terminal `goal_status`** 作为「终态徽标」（可选）。
3. `LoadedSession` 增 `active_goal: dict | None = None` 与 `terminal_goal: dict | None = None`。
4. `restore_agent_session`：
   - 若 `loaded.active_goal` 有 condition：构造 `goal_core.ActiveGoal`，赋给 `agent.active_goal`；调用 `goal_evaluator.register_goal_hook(agent, condition)` 重注册 Stop 门禁；把 `agent._last_goal_metadata` 清空以便重发。
   - 若没有 active_goal 但有 terminal_goal：仅保留用于一次性徽标推送（不重建 hook）。
   - 恢复 `backend.session_output_tokens`（从 working_state 读）。
5. `append_working_state` 增 `session_output_tokens` 字段；`_record_agent_turn_v2` 落盘时写入；`restore_agent_session` 读回。
6. bridge 在 resume 成功后调用 `agent._notify_goal_metadata(force=True)`（见缺口 5）主动推一次快照。

**取舍**：以「最后一条 active_goal 事件」为准（同 session 单 goal，最新即真相）。不重放历史 `goal_status`，只用于可选徽标，避免把已清除目标误恢复成 active。

### 缺口 2：`/goal` 不在命令补全与帮助

**根因**

- `frontends/ink/ui/src/slashCommands.ts` 的 `SLASH_COMMANDS` 无 `/goal`。
- `frontends/ink/ui/src/App.tsx::helpText()`（`:591`）无 `/goal` 行。
- 后端 `app.py::_handle_slash_cmd` 已经支持 `/goal`（`:1039` 一带），只是 UI 没暴露。

**方案**

- `slashCommands.ts` 增加 `{ name: '/goal', description: 'Show, set, or clear the session goal', requiresArgs: true }`（requiresArgs 让它先补全成 `/goal ` 再执行，和 `/workflow` 一致）。
- `helpText()` 增加 `/goal [condition] - set a stop-condition goal; /goal clear - remove it`。

### 缺口 3：覆盖旧 goal 无 superseded 记录

**根因**

- `app.py::_set_goal`（`:1134`）直接 `self.active_goal = ActiveGoal(...)`，旧 goal 被覆盖，既不写 `goal_cleared` 遥测也不写清理事件，设计 9.3 的 `superseded` 未落地。
- `_clear_goal`（`:1152`）的 `goal_telemetry.EVENT_CLEARED` 目前不区分「用户清除」和「被覆盖」。
- `goal_telemetry.record` 已支持 `outcome` 字段（`goal_telemetry.py` 白名单里已有 `outcome`）。

**方案**

- `_set_goal` 开头：若当前已有 active_goal，先走一次内部清理（不改 hook，只记事件 + 遥测 `EVENT_CLEARED outcome="superseded"`），并写一条 `goal_status`（met=False, reason="superseded"，sentinel=True）。
- `_clear_goal` 增参数 `outcome`（默认 `None` → 按 met/failed/cleared 推断）：用户 `/goal clear` 传 `outcome="user_cleared"`；superseded 路径传 `outcome="superseded"`；met/failed 保持 `met`/`failed`。
- `goal_telemetry.record(EVENT_CLEARED, …, outcome=...)` 把 outcome 落盘，`goal_cleared` 从此可区分原因。

### 缺口 4：求值器非法 JSON 不重试

**根因**

- `hooks/runner.py::_prompt_execute`（`:282`）对带 `outputSchema` 的 handler 走 `_parse_structured`（`:264`），解析失败即 `invalid_output` 返回，无重试。
- 「弱模型返非 JSON → 只记 evaluator_error 放行」在冒烟里已出现一次（文档已列已知限制）。

**方案（局部、只对 goal 生效）**

- `HookHandler` 增只读属性 `retry_on_invalid_output`（读 `options["retryOnInvalidOutput"]`，bool，默认 False）。
- `goal_evaluator.build_goal_handler_spec` 增加 `"retryOnInvalidOutput": True`。
- `_prompt_execute`：当 `schema is not None` 且 `retry_on_invalid_output` 且首次 `_parse_structured` 得到 `invalid_output` 时，**再跑一次 prompt_runner**，提示结尾追加强化指令（严格只输出 JSON、不要 prose/code fence），第二次结果再次 `_parse_structured`，仍失败才返回 invalid_output。
- **不改全局 hooks 行为**：普通 hooks 不设该选项，仍是单次严格解析。
- 重试上限固定 1 次（避免放大延迟与费用）；两次都失败仍走 `onFailure=continue`（goal 不锁死会话）。

---

### 缺口 5：元数据不随 ready/重连重发

**根因**

- `app.py::_notify_goal_metadata`（`:1078`）用 `goal_metadata.differs(previous, meta)` 去重，只在**状态变化**时推。
- bridge 重连、UI 重挂、`ready` 握手后，若 goal 未变，`hook_emit` 再也拿不到快照 → 卡片不回。

**方案**

- `_notify_goal_metadata(force=False)`：`force=True` 时跳过 `differs` 去重，无条件 emit（仍更新 `_last_goal_metadata`）。
- bridge：
  - `run_jsonl_loop` 发 `ready` 后调用 `bridge.emit_goal_snapshot()`；
  - `resume_session` 成功后调用同一个方法；
  - `new_session` 后不推 goal（已是 None），但前端 `history_replace(resetSession=True)` 要清空卡片/徽标/nudge。
- `state.ts`：`history_replace` 在 `startsNewSession` 时把 `goalMetadata/goalTerminal/goalNudge` 清空（补上当前遗漏）。

### 缺口 6：只有 Ink 消费 goal metadata

**根因**

- 只有 `frontends/ink/bridge.py:403` 设置 `agent.hook_emit = self.emit`；terminal/web/bots/acp 都没有把 `agent.active_goal` 展示出来。
- 设计 10.3 要求「Ink/CLI 正常渲染」，CLI 侧缺只读展示。

**方案（最小只读，不要每个前端都实现 hook_emit）**

- 新增共享纯函数 `genericagent/core/goal_metadata.py::active_goal_line(active_goal)` → 返回单行文本（如 `◎ Goal: <condition> (N turns)`），无 goal 返回 `""`。纯函数，各前端可复用于轮询展示。
- `frontends/terminal/tuiapp_v2.py`：`_refresh_topbar` 读 `s.agent.active_goal`，有值时在顶栏追加 goal 段（`render_topbar` 增可选参数 `goal_line`）。
- `frontends/web/stapp2.py`：在现有 `st.caption` 附近增加一行 goal 只读 caption（读 `agent.active_goal`）。
- `bots/acp`：ack 层不做卡片（消息渠道不适合常驻状态）；仅在 `/goal` 命令回执里已有文本结果。**明确记为「非目标」**，避免过度扩张。

- 恢复路径改动最敏感：任何异常都必须 best-effort，不能让 `restore_agent_session` 抛出（goal 恢复失败最多丢卡片，不能丢会话历史）。

## 附录 A：CC 283/303「resume 后 goal」的真实行为（源码核对）

结论：**CC 在 resume 时不会弹「继续执行 goal / 让 goal 暂停」的二选一对话框**，而是**自动静默恢复**。

证据链（283，可读化副本）：

- resume 会话选择器 `onSelect` 里调用恢复函数：`reconstructed/deminified/m1761_0xdf76d60.js:884`（`async function onSelect`）→ 第 `1023` 行 `BJn(o.messages, O, Xe)`。
- `BJn`（`m1585_0xdd20cb1.js:16`）是唯一职责就是“resume 时恢复 goal”：
  1. `yLt(s)`（`m0161_0xc2b67b6.js:25`）从消息流末尾找**最近一条未达成/未失败的 `goal_status`** 的 condition；
  2. `_Lt()`（`m0161:76`）做**门禁**：`hooks_gate`（hooks 被禁用/受限）或 `trust_gate`（非可信工作区）→ 返回错误；
  3. 有 condition 且门禁通过 → `add(Stop, {type:"prompt", prompt:condition})` 重新挂 Stop hook，并把
     `activeGoal = {condition, iterations:0, setAt:Date.now(), origin:"restored", tokensAtStart:Lp()}`；
     埋点 `tengu_goal_restored_on_resume`。
  4. 没有未决 condition，或门禁不通过 → `activeGoal: void 0`；若此前有 activeGoal，记 `f6(t,"resume_swap")`（`tengu_goal_cleared reason=resume_swap`）。
- 注意：恢复是**重新武装**——`iterations` 归零、`setAt` 取当前、`tokensAtStart` 取当前 `Lp()`，`origin` 改 `restored`；**不是**还原原来的迭代计数与 token 锚点。

「暂停」相关文案的真实归属（**不是** resume 对话框）：

- `m0560_0xcd966cc.js:2843-2850` 的 `Goal paused · ... · send a message to continue` 是**会话进行中**“中断自动重试 streak”耗尽后的提示；自动重试 3 次（`Us=[60000,300000,900000]`）后 `:2891` 记 `gave_up`、`:2917` 记 `paused`。属于“中断自动重试”语义（GA 阶段 3），与 resume 无关。

**与 GA 当前实现的差异（待决策）**

- GA 现在（Phase 6 缺口 1）从持久化的 `active_goal` 事件**精确还原**原 `iterations / tokens_at_start`，且不检查 hooks/trust 门禁。
- CC 是“**重新武装**”：`iterations=0 / setAt=now / tokensAtStart=当前` + `origin=restored` + `hooks/trust` 门禁失败则清空。
- 二者都对“目标继续生效”，但语义不同：GA 保留历史进度，CC 视恢复为新一段。若要严格对齐 CC，应改 GA 为：resume 恢复时 `iterations=0、setAt=now、tokens_at_start=当前会话累计`、`origin="restored"`，并在 hooks 禁用/非可信工作区时不恢复；同时 `active_goal` 恢复来源应改为“最近未决 `goal_status`”（GA 现已同时记录 `active_goal` 与 `goal_status`，可取后者）。

## 附录 B：resume 后「不想继续」或「换新 goal」——CC 怎么做

结论：**没有“resume 时”专门的取消/替换交互**。resume 是静默自动恢复（附录 A），用户改变主意时用的是**任何时候都可用的 `/goal` 命令**：

### B.1 不想继续 → `/goal clear`

`/goal` 命令实现（`m1713_0xde785b0.js` 的 `call`）：
- `h6e(e)` 命中 clear 词表 `clear|stop|off|reset|none|cancel` → 调 `_6e(o)`（`m0161_0xc2b67b6.js:143`）：
  - 用 `mCe(registry, session)` 找出**所有** goal Stop prompt hook 并逐个 `remove`；
  - 若 `activeGoal !== void 0` → 记 `f6(activeGoal, "user_clear")`（`tengu_goal_cleared reason=user_clear`）；
  - `activeGoal: void 0`；
  - `applyMessageOp append` 一条 **`goal_status` 附件 `Jln(met:true, sentinel:true, condition)`**（关键：写成 met=true）；
  - 返回 `"Goal cleared: <prompt>"`（无目标则 `"No goal set"`）。

### B.2 换新 goal → 直接 `/goal <新条件>`

`y6e(e,o)`（`m0161:104`）：
1. 门禁 `_Lt()`（hooks/trust 不过则报错不设）；
2. 若已有 `activeGoal` → `f6(old, "superseded")`（`tengu_goal_cleared reason=superseded`）；
3. `mCe` 找出并移除旧 goal Stop hook，再 `add` 新 hook；
4. 重置 `activeGoal = {condition:新, iterations:0, setAt:now, origin, tokensAtStart:Lp()}`；
5. append 一条 `goal_status` 附件 `Jln(met:false, sentinel:true, 新condition)`；
6. 返回 `{type:"query", value:"Goal set: ...", prompt: Qln(e)}`——把 kickoff prompt 作为**下一次模型输入**发出去，让模型立刻开跑。

### B.3 关键点：为什么 clear 写成 `met:true` 哨兵

- `yLt(messages)`（找“最近未决 goal_status”）判定标准是“最近的 goal_status 尚未 met/failed”。
- set 写 `met:false`、clear 写 `met:true`，于是 clear 之后 `yLt` 立刻认为“没有未决目标” → resume 时就不会再把已清的 goal 恢复回来。这是 CC 用**消息流里哨兵的正负翻转**来表达“目标是否还挂着”的机制，与内存里的 `activeGoal` 双轨一致。

### B.4 GA 现状对照

- 两条命令 **GA 已支持**：`/goal clear`（`_clear_goal(... outcome="user_cleared")`）与 `/goal <新>`（本批已加 `superseded` 审计）。resume 之后照样可用，因为它们不依赖 resume 流程。
- 差异（可选对齐项）：GA 用户清除时 `_clear_goal` 写的是 `goal_status met=False`（非哨兵 met:true）；CC 写 `met:true` 哨兵。当前 GA 的 resume 走 `active_goal` 事件（clear 时写 `active_goal: null`），所以不误恢复；但若将来把 resume 改为“最近未决 goal_status”口径（与 CC 完全一致），就必须把 clear 的 `goal_status` 改成 `met:true` 哨兵，否则 set 时那条 met:false 会被误判为仍挂着。
