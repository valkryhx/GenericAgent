| 变量 | 作用层 | 实测表现 |

| `GA_PROJECT_ROOT` | 项目身份（project_root → projectKey） | `agent.tool_cwd` = `D:\test20260416`；projectKey=`test20260416-20dabfb9b58b106f` |

## 3. 修复一：GA_PROJECT_ROOT 污染用户项目

### 现象

首次真实运行后，`D:\test20260416` 顶层凭空出现 `assets/`、`skills/`、`memory/`、`temp/`（共 25 个 GA 自身文件）。

### 根因

`genericagent/paths.py` 里 `runtime_root()` 返回 `PROJECT_ROOT if is_source_checkout() else user_data_dir()`，而 `PROJECT_ROOT` 会被 `GA_PROJECT_ROOT` 覆盖。于是 `TEMP_DIR/ASSETS_DIR/SKILLS_DIR/MEMORY_DIR` 全部指向用户项目，`ensure_runtime_dirs()` 把 GA 资源播种进去。

代码里 `RUNTIME_ROOT` 上方注释本来就写着“runtime state is writable user state, **not the user's project checkout**”，实现与注释自相矛盾。

### 修复

新增 `_checkout_root() = PACKAGE_ROOT.parent.resolve()`，`runtime_root()` 改为从**包所在位置**推导，忽略 `GA_PROJECT_ROOT`：

- 源码检出：运行时目录固定在 GA 仓库根（与历史行为一致）；
- 安装包：仍走 `GA_DATA_DIR / user_data_dir()`。

这样 `GA_PROJECT_ROOT` 只承担“项目身份”，符合三变量的原始设计意图。回归测试见 `tests/test_llm_config_paths.py::test_runtime_root_ignores_ga_project_root_in_source_checkout`。

## 4. 修复二：源码模式下 agent team 子进程无法导入 GA

### 现象

`spawn_agent(team_mode=True)` 返回 `startup_exited`，`returncode=1`，子进程 `stderr.log`：

```
python.exe: Error while finding module specification for 'genericagent.core.app'
(ModuleNotFoundError: No module named 'genericagent')
```

### 根因

`SubagentManager._child_popen_kwargs()` 用 `python -m genericagent.core.app` 启动子进程，`cwd` 是用户项目（或其数据桶）。源码模式下包未 `pip install`，且子进程环境没有 `PYTHONPATH`，所以父进程能 `import genericagent`，子进程却不行。

### 修复

`_child_popen_kwargs()` 在子进程环境里把 `paths.PACKAGE_ROOT.parent` 前置加入 `PYTHONPATH`（幂等、保留既有值）。源码/安装包两种形态都安全：安装形态下该路径本就随 site-packages 可导入，前置一项不改变解析。

回归测试：`tests/test_subagent_manager.py::test_child_launch_puts_ga_package_on_pythonpath_for_source_checkout`。
