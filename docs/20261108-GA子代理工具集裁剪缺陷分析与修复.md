# GA 子代理工具集裁剪缺陷分析与修复（2026-11-08）

## 0. 一句话结论

GA 的工具授权是**加法模型**：`role_tools` 为空列表时允许集合就是空集，子代理几乎拿不到任何
工具。CC 319 是**减法模型**：默认把全部工具给子代理，再用 `disallowedTools` 减去不该有的。
两者在其他任何地方都可以等价，唯独在"调用方没显式指定工具"这个最常见的场景下结论相反。

用户那次 4 个子代理全部空转报阻塞，就是加法模型收到的输入是 `[]` 而不是 `None` 的结果。

## 1. 现场复现（实测，不是推演）

用真实的 `assets/tools_schema.json`（34 个工具）跑真实的
`build_subagent_capability_profile`：

| 调用方式 | 修复前允许工具数 | 实际工具集 |
| --- | --- | --- |
| 普通子代理（`role_tools=None`） | 15 | file_read/file_write/code_run/... 正常 |
| 子代理 + `team_mode=True`，`role_tools=None` | 21 | 正常 15 + 协作 6 |
| 子代理 + `role_tools=['file_read','code_run']` | 3 | 显式指定，符合旧预期 |
| **子代理 + `role_tools=[]`（空列表）** | **1** | **只有 `no_tool`** |
| **子代理 + `team_mode=True` + `role_tools=[]`** | **7** | **`no_tool` + `send_message` + `task_create/get/update/list` + `team_status`** |

最后一行就是用户报告的现象，逐字吻合：

> 工具集只有 `task_*` / `send_message` / `team_status`

复现脚本：`tests/probes/python/_probe_subagent_toolset.py`。

## 2. 为什么 `role_tools` 会是 `[]` 而不是 `None`

`core/handler.py:1657-1674`：

```python
requested_role_tools = args.get("tools") or args.get("capability_tools")
if requested_role_tools is None and role is not None:
    requested_role_tools = list(role.tools)     # ← 内置角色 tools 默认是空 tuple
...
capability_options = {
    "role_tools": (
        None if requested_role_tools is None
        else [str(item) for item in requested_role_tools if str(item).strip()]
    ),
    ...
}
```

`agents/roles.py` 里 `SubagentRole.tools: tuple[str, ...] = ()`——所有内置角色
（explore / plan / review）的 `tools` 都是空 tuple。于是：

```
spawn_agent(agent_type="explore", team_mode=True)
  → role.tools = ()
  → requested_role_tools = []          # list(())
  → role_tools = []                    # 不是 None！
  → capabilities: allowed = set()      # 空集
  → team_mode 分支再 update(TEAMMATE_TOOLS)
  → 最终只有协作工具
```

实测确认（`tests/probes/python/_probe_role_tools_derivation.py`）：

```
plain spawn, no role, no tools              role_tools=None
plain spawn, team_mode=True                  role_tools=None
agent_type='explore' (builtin, tools=())     role_tools=[]      ← 陷阱
agent_type='explore' + team_mode             role_tools=[]
```

**关键点：内置角色不声明 `tools` 的意思是"不额外限制"，不是"什么工具都不给"。**
现在的代码把它读成了后者。

## 3. CC 319 是怎么设计的（源码坐标）

工具解析函数 `cI`（`m0779_0x12409ec4.js:6933`）的判定顺序：

```js
// 1) 先跑默认过滤器 pp()：决定"子代理默认能有哪些"
H = y ? tools_14 : pp({ tools: tools_14, isBuiltIn, agentType, isAsync,
                        isTeammate, permissionMode, agentDepth, subagentMemoryMode })

// 2) 再用 disallowedTools 减
G = H.filter(item => !isToolDisallowed_2(item))

// 3) 只有当 agent 定义里显式声明了 tools，才做白名单收窄
ie = nEe(tools_13)
if (tools_13 === void 0 || ie) {
  return { hasWildcard: !0, resolvedTools: le() ? ca(G, y) : G, ... }   // 全部
}
```

三个要点：

1. **`tools` 未声明（`undefined`）→ `hasWildcard: true` → 保留全部**。这就是默认全给。
2. `pp()`（`m0779:6722`）才是真正决定子代理默认面的地方，它按条件**减**：
   ```js
   if (ht(item, hi) && (isTeammate_2 || !Fy())) return !1;   // 子代理/teammate 去掉某类
   if (ht(item, ft)) return agentDepth < iR();                // 嵌套深度控制 Agent 工具
   if (isAsync && !Mv(item, bDt)) { ... return !1; }          // 异步任务再收窄
   return !0;                                                 // 默认保留
   ```
3. 只有 `tools_13` 显式给了值，才走白名单（`validTools` / `invalidTools` 分支）。

**CC 的模型：默认允许，显式收窄，disallowed 减去。GA 的模型：默认空集，靠白名单加。**

## 4. 失败的两种表现

| 输入 | 当前 GA 行为 | 用户看到的 |
| --- | --- | --- |
| `role_tools=[]`（内置角色） | 只有 `no_tool` | 子代理说"没有任何工具" |
| `role_tools=[]` + `team_mode=True` | 只有协作工具 | 子代理说"只有 task_*/send_message/team_status" |

第二种更隐蔽：**它看起来像是有工具的**，只是所有工具都跟干活无关。子代理会真的去尝试
用 `task_list` 找工作，然后报阻塞——这比空工具集更难排查。

## 5. 修复设计

### 5.1 核心改动：能力改为 opt-out，`role_tools` 不再是白名单

`agents/capabilities.py:build_subagent_capability_profile`：

```python
# 修复前
role = None if role_tools is None else {normalize(x) for x in role_tools}
allowed = set(available) if role is None else set(role)     # ← 空列表 → 空集

# 修复后
allowed = set(available) if available else set()             # 全给
# role_tools 只保留在签名里做兼容，不再参与计算
```

**为什么不只是"把空列表当 None"**：那只堵住当前这一条路径。真正的问题是
**能力是 opt-in 的**——任何一处调用方忘了传、或传了个空，子代理就失去工作能力，
而失败方式是"子代理回来说我没工具"，不是一条能立刻定位的错误。

改成 opt-out 之后，**忘记传参数不再有惩罚**，唯一的收窄途径是显式 `denied_tools`
或权限档。这与 CC 的 `hasWildcard` 一致：默认全给，只有明确说"不要"才减。

### 5.2 内置角色不再预设限制

`agents/roles.py`：`explore` / `plan` / `review` 三个内置角色**移除
`permission_profile=READ_ONLY`，也保持 `tools=()`**。

角色从此只是**提示词**（做什么、怎么汇报），不改变能力。理由：

1. **角色不该是沙箱。** 一个角色如果硬编码只读档，等于 harness 在执行一条调用方
   没要求、也看不见的边界。任务恰好需要写一次时，失败在工具调用处，解法（"换个角色"）
   只能靠读宿主源码才能发现。
2. **它是本轮 bug 的入口。** `role.tools=()` 被 `list()` 成 `[]`，进而清空工具集。
   保留 `tools` 字段就保留了复发路径。
3. **原来还有一层"猜意图然后拒绝"。** `_team_role_capability_mismatch` 用正则从任务
   描述里猜"这是不是要写文件/跑脚本"，然后因为角色是只读而拒绝整个 spawn。
   猜错的代价是任务被无理由拒绝——这条路径已整个删除。

**唯一保留的硬边界是"子 agent 不能再编排 agent"**，由
`capabilities.ORCHESTRATION_TOOLS` 统一扣掉，对所有子代理一视同仁，不需要任何角色。

### 5.3 什么样的收窄仍然有效

| 手段 | 是否仍生效 | 说明 |
| --- | --- | --- |
| `denied_tools=[...]` | ✅ | 唯一推荐的收窄方式，只会减 |
| `permission_profile: read_only`（显式传） | ✅ | 调用方主动选择时仍然执行期生效 |
| 角色文件里声明 `permission_profile` / `tools` | ✅ | 项目自定义角色仍可自我约束 |
| 内置角色的 `tools=()` | ❌ 不再解释为"不给工具" | 这是本次修复的核心 |

### 5.4 只读档仍然存在，但不再默认施加

`workflow/permissions.py` 的 `READ_ONLY` 档没删——它是**调用方可选**的边界，
`spawn_agent(permission_profile="read_only")` 依然在执行期拒绝
`file_write` / `file_patch` / `code_run` / `web_execute_js`。

区别在于：**它现在只能由调用方显式要求，不会因为选了个角色而被悄悄加上。**

## 6. 顺带修掉的资源浪费

`_resolve_subagent_isolation` 里"只读档不建 worktree"的判断**保留**。
这不是能力问题，是资源问题：worktree 要 checkout 一整棵树 + 建分支，而一个不会写的
子代理产不出任何需要隔离的改动。保留 `read_only_permission_profile` 与
`inherited_read_only_permission_mode` 两条降级，只在调用方确实要求了只读时才触发。
