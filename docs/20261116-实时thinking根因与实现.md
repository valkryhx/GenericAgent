## 1. 为什么不能改 yield 契约

这是本次实现最重要的一个判断，也是对 resume 文档里「需要改 yield 契约」的直接修正。

`ToolClient.chat()` / `NativeToolClient.chat()` 的 yield 流有两个消费者：

1. `loop.py` 的 `agent_runner_loop` → `_drain_agent_stream` → `display_queue` →
   `assistant_delta` → 前端 `ChatMessage.text`
2. 同一份 `full_resp` 还用于 `handler.last_assistant_message`、transcript 的
   `assistant_text`、以及 Stop hook 的 `last_assistant_message`

如果把 reasoning 混进 yield：

- transcript 的 `assistant_text` 会含推理，而 resume 侧刚按「`assistant_text` 只装
  prose」的契约实现完（`_message_text_from_blocks` 只收 `type == "text"`），两边打架
- 压缩摘要会把推理当正文喂给模型
- 工具 chip 的行首解析（`isToolChipRow` 认 `● name(`）会与推理文本混淆
- `do_no_tool` 的截断重试判据是 `'max_tokens !!!]' in content[-100:]`，推理插入会改变尾部

所以走**带外通道**：会话级回调，和既有的 `on_retry_status` 完全同构。

## 2. 实现

### 2.1 解析层：`genericagent/llm/core.py`

新增 `_notify_thinking(sess, text)`，与 `_notify_retry_status` 并列：

```python
def _notify_thinking(sess, text):
    if not text or not str(text).strip():
        return
    callback = getattr(sess, "on_thinking", None)
    if not callable(callback):
        return
    try:
        callback({"text": str(text)})
    except Exception:
        pass
```

三个发出点，都遵循「**块完成时发出，且必须在正文之前**」：

| wire | 发出位置 | 说明 |
|---|---|---|
| anthropic | `content_block_stop` 时块为 `thinking` | 结构化边界，最干净 |
| anthropic | 流中断时的兜底 | 没收到 `content_block_stop`，已到达的推理仍值得显示 |
| chat_completions | **首个 content delta 之前**（惰性） | 无块边界，推理是扁平 delta 流；必须在正文开始前发 |
| chat_completions | 流结束时兜底 | 纯工具轮没有 content delta，不会触发上面那条 |
| responses | 同上两条 | 新增 `response.reasoning_summary_text.delta` / `response.reasoning_text.delta` 采集——**这条 wire 之前完全没采 reasoning** |
| 非流式 json（三条 wire） | 解析完即发 | 见 `_parse_claude_json` / `_parse_openai_json` |

`BaseSession.__init__` 增加 `self.on_thinking = None`；`MixinSession._BROADCAST_ATTRS`
加入 `on_thinking`，故障转移时各子会话都能收到。

### 2.2 协议层

```ts
| { type: 'assistant_thinking'; taskId: number; text: string }
```

与 `assistant_delta` 并列，但**语义完全不同**：它不是回复正文的增量。

### 2.3 转发层：`frontends/ink/bridge.py`

`_bind_thinking(agent)` 与 `_bind_retry_status(agent)` 并列，在同一个初始化点调用：

```python
def _on_llm_thinking(self, payload: dict) -> None:
    text = str(payload.get("text") or "")
    if not text.strip():
        return
    self.emit({"type": "assistant_thinking", "taskId": int(self._task_seq), "text": text})
```

### 2.4 状态层：`frontends/ink/ui/src/state.ts`

每个推理块落成**一条独立的 done 消息**，追加到末尾：

```ts
if (event.type === 'assistant_thinking') {
  if (!event.text.trim()) return state
  // 先关掉未完成的 user，保持 Static 前缀约束（与 assistant_delta 一致）
  ...
  messages: [...messages, {
    id: `a-${event.taskId}-thinking-${thinkingSeq(messages, event.taskId)}`,
    role: 'assistant', text: '', done: true,
    taskId: event.taskId, thinking: [event.text],
  }]
}
```

**为什么不做成 live 消息上的字段**（这是本轮唯一的设计取舍，值得记下来）：

流式正文每超过 8 行就被 `commitStreamingAssistantMessages` 切成
`a-{taskId}-c0`、`a-{taskId}-c1`… 提交给 `<Static>`。这些已提交段排在 live 消息
**之前**。若 thinking 挂在 live 消息上，一旦发生切分，推理行就会跑到「发生在它
之后」的正文下面。独立消息 + `done: true` 让它的位置在创建时就被钉死。

### 2.5 渲染层：`frontends/ink/ui/src/messageWindow.ts`

复用 resume 侧已经写好的 `appendThinkingRows()`，只补一个分支：**reasoning-only
消息不再产出空白正文行**。

```ts
const reasoningOnly = !hasBody && (message.thinking?.some(t => t.trim() !== '') ?? false)
const body = reasoningOnly ? '' : formatAssistantText(message.text, ...) || ' '
const nextChannel = reasoningOnly ? channel : appendAssistantBodyRows(...)
```

原先 `formatAssistantText('') || ' '` 在 done 的 reasoning-only 消息上会画出一行
纯空白，reasoning 与正文之间因此出现两个空行。探针
`frontends/ink/ui/probes/live_thinking_rows.ts` 抓到了这个（当时 3 个空行），
修完是 1 个，与对照组同级。

## 4. 分析边界

- **「推理在正文之上」依赖一个时序事实**：thinking 块在正文 delta 之前完成。
  这被 `_notify_thinking` 的四个调用点主动保证（都是「首个正文 delta 之前」），
  不是碰巧。能力上支持 interleaved thinking 的模型若在正文之后继续推理，
  那一部分会在流结束的兜底里发出，位置落在正文之后——按发生顺序，这是对的。
- **response.reasoning_summary_text.delta 与 response.reasoning_text.delta 同时
  出现时取并集拼接**，实测的 GPT-5 类端点只发前者。两者是否会同时出现在同一
  响应里，未在真机上验证。
- **`MockResponse.thinking` 早就有值这件事，本轮用真机确认了**（zhanlu-ds
  781 字）。但 `native_claude_config_100x` 那把 key 实测 HTTP 401
  `INVALID_API_KEY`，anthropic wire 的真实链路只用合成 SSE 验证过，未跑真模型。
- CC 319 侧只读了 `lio()`（`latestThinkingSummary`）及其调用点，未通读它的
  完整 reasoning 渲染栈。GA 用的是「每块一行摘要 + Ctrl+O 展开」，形状对齐但
  不是逐像素复刻。
