# 20261020-GenericAgent hooks 设计与实现方案（对标 Claude Code 2.1.303）

> 目标：把 Claude Code（下称 CC）的本地 hooks 机制复刻进 GenericAgent（下称 GA），先实现可稳定落地的 `command` hooks，并用 `Stop` beep 作为第一条端到端验收链路。
> 适用范围：GA 本地会话、Ink/CLI/其他本地前端、workflow 子 agent、agent team；**不包含 CC 云端会话、device forwarding、cloud hook 策略**。
> 依据：本文第 11 节的源码调研文档索引。源码事实、本机实例、设计取舍分节标注。

## 1. 结论先行

### 1.1 CC hooks 是六层组合，不是几个零散回调

```text
配置层
  settings / plugin hooks / session hooks / builtin hooks
        |
收集与排序层
  source 收集 -> 去重/排序 -> matcher 过滤 -> handler 级 if 过滤
        |
输入协议层
  公共字段 + hook_event_name + 事件专属字段，以 JSON 写入 stdin
        |
执行层
  command / prompt / agent / http / mcp_tool
  timeout / abort / async / asyncRewake / exit code
        |
输出协议层
  stdout JSON 校验 -> decision / permissionDecision / additionalContext /
  updatedInput / updatedOutput / systemMessage / block / preventContinuation
        |
事件消费层
  把 hook 结果接回工具守卫、prompt 注入、主循环停止、UI 进度和日志
```

### 1.2 GA 现有能力与缺口

| GA 位置 | 现有能力 | 与 CC 的关系 | 缺口 |
| --- | --- | --- | --- |
| `genericagent/core/loop.py:199-272` `agent_runner_loop` | 每次 LLM/tool 迭代、工具批处理、turn_end_callback | 可挂 `PreToolUse` / `PostToolUse` / `PostToolBatch` 的物理位置 | “turn” 是内部 step，不是 CC `Stop` |
| `genericagent/core/handler.py:367-481` `dispatch` | capability、permission、PathACL、工具执行 | 已有本地守卫，但硬编码 | 还没有可配置 hook dispatcher |

| `genericagent/core/app.py:964-1161` `GenericAgent.run()` | 一轮用户请求的完整生命周期 | 最接近 CC 的“用户回合” | 没有 `UserPromptSubmit` / `Stop` 派发点 |
| `genericagent/core/app.py:985-1014` | 每轮创建 handler | 可注入 hook runtime | 无统一配置加载 |

| `genericagent/core/app.py:1546-1809` `run_task_worker_loop` | 进程型 subagent 生命周期 | 可映射 `SubagentStart` / `SubagentStop` | 无独立 hook 协议 |
| `genericagent/core/transcripts.py:98-134` | JSONL 会话事件 | 可追加 hook 事件 | 无统一 hook audit 事件类型 |

### 1.3 第一版必须做对的三条

1. **`Stop` 必须挂在 `GenericAgent.run()` 的用户回合终态，不挂在 loop 的每个 `Turn N`。**
2. **hook 输入走独立 JSON 协议，输出走 stdout JSON；不要让 hook 往主对话或 tool_result 里乱写。**
3. **第一版 `command` handler 必须支持 exec form；GA 的 beep 用 `command=python, args=[脚本路径]`，不拼 shell。** 这与 CC 的 `m0062:2640` 语义一致，也避开 Windows 中文路径、引号、反斜杠、PowerShell hook 历史兼容问题。

## 2. CC hooks 的加载链与触发链（源码级）

### 2.1 加载

CC 的 settings 结构：

```json
{
  "hooks": {
    "<EventName>": [
      {
        "matcher": "<optional pattern>",
        "hooks": [
          { "type": "command", "command": "...", "args": ["..."], "timeout": 10 }
        ]
      }
    ]
  }
}
```

`matcher` 是 **entry 级**；handler 内的 `if` 是另一层 permission-rule 过滤。GA 必须保留这个分层，否则“先 spawn 再判断”会把大量进程白白拉起。

来源：

```text
userSettings    ~/.claude/settings.json
projectSettings <repo>/.claude/settings.json
localSettings   <repo>/.claude/settings.local.json
policySettings  managed policy
pluginHook      plugin 的 hooks/hooks.json
sessionHook     内存临时注册
builtinHook     内部注册
```

对应源码：`m0353:13717-13746`、`m0353:13748-13783`。

### 2.2 `Stop` 的触发语义

`Spe()`（`m0459:156588`）构造输入时：

```text
主 agent：hook_event_name = "Stop"
子 agent：hook_event_name = "SubagentStop"
公共停止字段：
  stop_hook_active
  last_assistant_message?
  background_tasks?
  session_crons?
```

主循环的 `gl()`（`m0671:3167`）在准备结束回合时创建 `Spe(..., "blockable_turn_end")`，并消费结果：

- `message`：hook 进度/附件/错误消息；
- `blockingError`：转成 meta user message，阻止本回合结束并继续 loop；
- `additionalContext`：追加到继续运行时的上下文；
- `preventContinuation`：阻止继续；
- `timedOut`：超时；
- `hook_success` / `hook_non_blocking_error` / `hook_error_during_execution`：记录与 UI 展示。

`blockingError` 路径见 `m0671:8946-9023`。默认连续阻断上限 8（`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`）。

### 2.3 beep hook 为什么合法且安全

本机脚本的核心行为：

```python
import sys

def main() -> None:
    try:
        sys.stdin.buffer.read()
    except Exception:
        pass
    try:
        import winsound
        winsound.Beep(800, 300)
    except Exception:
        try:
            sys.stderr.write("\a")
            sys.stderr.flush()
        except Exception:
            pass

if __name__ == "__main__":
    main()
```

为什么它不会阻断 `Stop`：

- 读完 stdin，不造成管道写端挂起；
- exit code 0；
- stdout 完全空；
- 没有 `decision: "block"`、`preventContinuation`、`additionalContext`；
- timeout 10 秒覆盖 300 ms 蜂鸣。

因此 CC 将它视为成功、无控制输出的 hook。Stop hook 的正常成功在 UI 上通常无感，这正是预期行为。

### 2.4 `Stop` 不是 `PostToolUse`，也不是 GA 的内部 turn

```text
CC PostToolUse    = 单个工具调用后
CC Stop           = 主 agent 结束一个用户回合
CC SubagentStop   = 子 agent 停止
GA loop Turn N    = 单个用户请求内部第 N 次 LLM 调用（可能很多次工具）
```

所以 beep 在 GA 中必须挂在：

```text
GenericAgent.run()
  ├─ 用户 prompt 进入                      -> UserPromptSubmit
  ├─ agent_runner_loop 内部多次 Turn N      -> Pre/PostToolUse、PostToolBatch
  └─ 本次 run 成功/失败/中止的最终收尾      -> Stop / StopFailure
```

## 3. GA hooks 的目标架构

### 3.1 新模块布局

```text
genericagent/hooks/
  __init__.py
  models.py          # HookConfig, HookEntry, HookHandler, HookContext, HookResult
  config.py          # 配置发现/合并/校验、来源与顺序
  matcher.py         # event entry matcher + handler if 过滤
  runner.py          # command executor、timeout、abort、stdout/stderr 捕获
  runtime.py         # 注册表、并发、结果聚合、审计
  protocol.py        # 输入/输出 JSON schema 与版本
  audit.py           # JSONL 审计与 UI 事件适配
```

接入点：

```text
genericagent/core/app.py
genericagent/core/loop.py
genericagent/core/handler.py
genericagent/core/transcripts.py
genericagent/workflow/child_agent.py
genericagent/agents/manager.py
```

### 3.2 配置路径与合并顺序

第一版采用 GA 独立命名空间，避免误读/误触发 CC 配置：

```text
~/.genericagent/settings.json              # user
<project>/.genericagent/settings.json      # project
<project>/.genericagent/settings.local.json # local
<project>/.genericagent/hooks.json          # project hook file (optional)
~/.genericagent/hooks.json                  # user hook file (optional)
```

显式环境变量：

```text
GA_HOOKS_CONFIG=<path>        # 只加载指定文件，最高优先级；测试/CI 用
GA_HOOKS_DISABLED=1           # 全禁 configured hooks
GA_HOOKS_DEBUG=1              # 输出详细执行诊断到 stderr/日志
```

如果希望兼容 CC 现有 `settings.json`，作为**后续适配层**读取 `.claude/settings.json`；第一版不要默认读取，避免 GA 与 CC 的 hook 互相触发。

优先级建议：

```text
builtin < plugin < project < local < user < session < GA_HOOKS_CONFIG
```

CC 的精确排序证据在 `m0353:13794-13806`；GA 第一版按上述显式顺序执行，并在测试中固定。后续若做严格兼容，再逐事件核对覆盖/合并语义。

### 3.3 第一版支持的 handler

只实现 `command`：

```json
{
  "type": "command",
  "command": "python",
  "args": ["C:/Users/drago/.genericagent/hooks/beep_on_stop.py"],
  "timeout": 10,
  "statusMessage": "Beep",
  "onFailure": "continue",
  "once": false,
  "async": false
}
```

为什么第一版只做 `command`：

- 可覆盖 beep、日志、通知、格式化、简单守卫等 80% 高价值场景；
- 输入/输出协议与 CC 同构，便于后续扩展 `prompt` / `agent` / `http` / `mcp_tool`；
- 避免一开始把模型调用、HTTP、MCP、async worker 全部混进来导致协议不稳定。

### 3.4 handler 字段

| 字段 | 第一版 | 语义 |
| --- | --- | --- |
| `command` | 必填 | 可执行文件或 shell 命令 |
| `args` | 推荐 | 存在时 exec form，不经 shell；逐元素替换占位符 |
| `shell` | 可选 | 无 `args` 时的 shell；Windows 默认 `bash` 优先，否则 `powershell` |
| `timeout` | 可选 | 秒；默认 10 秒，上限 600 秒 |
| `statusMessage` | 可选 | UI spinner 文案 |
| `onFailure` | 可选 | `continue`（默认）/ `block`；Stop 类事件第一版忽略 `block` |
| `once` | 可选 | 成功执行后从 session registry 移除 |
| `async` | 延后 | 第一版拒绝或降级同步执行，并写警告 |
| `asyncRewake` | 延后 | 第二版实现 |
| `if` | 第二版 | 复用 GA permission-rule 匹配器 |


CC 对应公共字段见 `m0120:6796-6807`。GA 保留 `hook_event_name`、`session_id`、`transcript_path`、`cwd`、`permission_mode`；增加 `schema_version`、`hook_run_id` 便于审计。

### 4.2 `Stop` 输入

```json
{
  "hook_event_name": "Stop",
  "stop_hook_active": false,
  "last_assistant_message": "最终回复全文",
  "background_tasks": [],
  "session_crons": [],
  "task_id": 42,
  "exit_reason": "completed",
  "source": "user"

```

| 字段 | 含义 |
| --- | --- |
| `stop_hook_active` | 当前是否因 Stop hook 的 blocking 而续跑；防无限阻断 |
| `last_assistant_message` | 本次用户回合最终回复；用于通知/摘要 hook |
| `background_tasks` | 尚未结束的后台任务快照 |
| `session_crons` | 计划唤醒任务快照 |
| `task_id` | GA bridge 的任务序号 |
| `exit_reason` | `completed` / `failed` / `aborted` / `max_turns` |
| `source` | `user` / `subagent` / `sdk` / `schedule` |

### 4.3 其他第一版事件

| CC 事件 | GA 事件同名 | 接入点 | 第一版用途 |
| --- | --- | --- | --- |
| `SessionStart` | 是 | `ensure_agent_session` / agent 初始化 | 初始化通知、记录环境 |
| `UserPromptSubmit` | 是 | `GenericAgent.run()` 拿到 `raw_query` 后 | 注入上下文、阻断请求 |
| `PreToolUse` | 是 | `GenericAgentHandler.dispatch` 入口 | allow/deny/ask、改写 `updatedInput` |
| `PostToolUse` | 是 | `dispatch` 返回前 | 追加上下文、日志、格式化 |
| `PostToolUseFailure` | 是 | 工具异常/错误结果 | 失败通知、补充诊断 |

| `StopFailure` | 是 | `run()` 异常终态 | 失败通知、诊断 |

## 5. 输出协议

### 5.1 顶层字段

```json
{
  "continue": true,
  "decision": "block",
  "reason": "why",
  "systemMessage": "shown to user",
  "hookSpecificOutput": {
    "hookEventName": "Stop",
    "additionalContext": "..."
  }
}
```

第一版 GA 支持：

| 字段 | 行为 |
| --- | --- |
| `continue: false` | 停止后续处理/阻止继续 |
| `decision: "block"` | 对守卫事件阻止；对 Stop 转为 blocking 续跑 |
| `reason` | 给用户/模型的原因 |
| `systemMessage` | 仅 UI 提示，不进 transcript |
| `hookSpecificOutput.additionalContext` | 追加进模型上下文 |
| `hookSpecificOutput.permissionDecision` | `PreToolUse` 的 allow/ask/deny |
| `hookSpecificOutput.updatedInput` | 替换工具参数（第一版只允许安全合并） |

### 5.2 exit code

| exit | 语义 |
| --- | --- |
| `0` | 成功；stdout 可为空或一个 JSON object |
| `2` | 阻塞；stderr / stdout 作为阻断原因 |
| 其它 | 非阻塞失败；记录诊断，不阻止主流程 |

`onFailure: "block"` 仅对 PreToolUse/PermissionRequest 等守卫事件生效；`Stop` 默认忽略，防止 beep 脚本故障导致会话无法结束。

### 5.3 stdout 规则

- stdout 必须是**单个 JSON object**或空；
- 如果 stdout 非空且不是合法 JSON：守卫事件且 `onFailure: block` -> 阻断；其它情况 -> 非阻塞错误，写审计；
- stderr 不参与协议，只进日志/UI；
- 单个输出上限自建，建议 `maxOutputChars=20000`；超限持久化到 `temp/hooks/<hook_run_id>.stdout.txt` 并只回传 preview；
- 不照抄 CC 未证实的 `Yqs=24576`。

## 6. 执行与聚合

### 6.1 执行顺序

```text
事件发生
  -> 收集当前事件的所有 entry
  -> entry matcher 过滤
  -> handler.if 过滤（第二版）
  -> 按来源顺序 + 声明顺序执行
  -> 每个 handler 独立 timeout / abort / stdout / stderr
  -> 校验输出
  -> 聚合
  -> 写审计事件
  -> 应用结果到业务路径
```

### 6.2 并发

第一版 `command` hooks 可以并行，但必须设上限：

```text
GA_HOOKS_MAX_CONCURRENCY=4
```

理由：

- CC 的总并发上限是 12（`m0459:155262`），GA 第一版以稳定性优先；
- 并行缩短多个通知/日志 hook 的总时延；
- 结果按**声明顺序**聚合比按完成顺序更容易复现实验，第一版采用声明顺序；这与 CC 的“完成顺序 yield”不同，是 GA 的有意取舍，需写入测试；
- 如果后续需要严格 CC 兼容，再切换为完成顺序 + 稳定排序键。

### 6.3 聚合规则

```text
permissionDecision: deny > ask > allow
additionalContext: 按声明顺序拼接
systemMessage: 按声明顺序拼接（去重）
continue=false: 任一 hook 设置即 false
decision=block: 任一 hook 设置即 block
updatedInput: 后声明覆盖先声明，但记录审计
```

不要笼统使用“last-write-wins”。

### 6.4 审计事件

每次 hook 执行写一条 JSONL：

```json
{
  "type": "hook_executed",
  "hook_run_id": "hook_...",
  "event": "Stop",
  "source": "userSettings",
  "handler_index": 0,
  "command": "python",
  "args": ["C:/Users/drago/.genericagent/hooks/beep_on_stop.py"],
  "status": "success",
  "exit_code": 0,
  "duration_ms": 312,
  "stdout_preview": "",
  "stderr_preview": "",
  "blocking": false
}
```

落盘：

```text
<project>/temp/hooks/events-YYYYMMDD.jsonl
<project>/temp/hooks/outputs/<hook_run_id>.stdout.txt
<project>/temp/hooks/outputs/<hook_run_id>.stderr.txt
```

## 7. 接入点精确设计

### 7.1 `UserPromptSubmit`

位置：`GenericAgent.run()`，在 `_handle_slash_cmd` 之后、构造 `messages` 之前。

```text
raw_query
  -> 构造 UserPromptSubmit 输入
  -> 运行 hooks
  -> 合并 additionalContext
  -> 若 decision=block：直接输出 reason，任务终止
  -> 否则继续 agent_runner_loop
```

### 7.2 `PreToolUse`

位置：`GenericAgentHandler.dispatch`，在 capability/permission/PathACL 之后、真正调用 `do_<tool>` 之前。

原因：

- 现有 capability 和 permission 是硬安全边界，不能被 hook 放宽；
- hook 只能在安全边界内进一步收紧或补充；
- `PreToolUse` 的 `updatedInput` 只能修改已通过安全校验的参数，修改后必须重新跑路径校验。

```text
capability deny?
  -> permission deny/ask?
  -> PathACL deny?
  -> PreToolUse hook
      allow / ask / deny
      updatedInput
  -> 对 updatedInput 重新跑 PathACL
  -> 工具执行
```

### 7.3 `PostToolUse`

位置：`dispatch` 拿到 `ret` 后、返回前。

- 成功：写审计、合并 `additionalContext`；
- `updatedOutput` 第一版不启用；
- hook 失败不改变工具结果。

### 7.4 `PostToolBatch`

位置：`agent_runner_loop` 的 `batch_outcomes` 完成之后。

GA 已有 `_batch_tool_calls`（`loop.py:59-68`）和 `_run_parallel_tools`（`loop.py:139-197`），这是天然接入点。

### 7.5 `Stop`

位置：`GenericAgent.run()` 的 `finally` 之前，在 `display_queue.put({'done': ...})` 与 transcript 记录之后。

```python
def _finalize_turn_success(...):
    # record transcript
    # run Stop hooks
    # emit status

def _finalize_turn_failure(...):
    # record failed transcript
    # run StopFailure hooks
    # emit status
```

注意：

- 用户主动停止 -> `Stop`，`exit_reason="aborted"`；异常 -> `StopFailure`。
- `Stop` 不阻塞 UI done；blocking hook 需要重新进入 loop，第一版先只支持“通知型 Stop”，blocking Stop 放到第二版。
- beep 在第一版必须属于“非阻塞通知型 Stop”，因此先实现并验收。

### 7.6 `SubagentStop`

位置：

- 进程型 subagent：`run_task_worker_loop` 的 `agent_exited` / `agent_shutdown` / `agent_error` 分支；
- workflow child：`WorkflowChildAgent` 的 `_build_handler` 所在任务收尾处。

第一版只做审计和通知，不允许 `SubagentStop` blocking 父 agent。

### 7.7 `SessionStart` / `SessionEnd`

位置：

- `ensure_agent_session` 创建/恢复后；
- `GenericAgent` 关闭/`SessionEnd` 前。

第一版只做日志和通知。

```json
          }
        ]
      }
    ]
```

### 8.2 GA 脚本

```text
C:/Users/drago/.genericagent/hooks/beep_on_stop.py
```

与 CC 本机脚本保持一致：

```python
import sys

def main() -> None:
    try:
        sys.stdin.buffer.read()
    except Exception:
        pass
    try:
        import winsound
        winsound.Beep(800, 300)
    except Exception:
        try:
            sys.stderr.write("\a")
            sys.stderr.flush()
        except Exception:
            pass

if __name__ == "__main__":
    main()
```

### 8.3 验收断言

| 层级 | 断言 |
| --- | --- |
| 脚本 | `echo '{"hook_event_name":"Stop"}' \| python beep_on_stop.py` exit 0、stdout 为空 |
| runner | 构造 `Stop` 输入，exec form 可运行，exit 0，审计写入 |
| 单回合 | 一个用户请求内部有 >=2 次 LLM turn / 多次工具，只响一次 |
| 多回合 | 连续两次用户请求，各响一次 |
| 失败隔离 | 脚本抛异常/超时，主回合仍正常结束 |
| 子代理 | workflow 有 3 个子 agent，主 `Stop` 只响一次，`SubagentStop` 不触发 beep（配置只在 `Stop`） |
| UI | 响铃不污染 Ink 输入框、不产生额外 assistant 文本、不重复状态 |

### 8.4 为什么第一版不应把 beep 放在 `handler.turn_end_callback`

`handler.turn_end_callback` 是 GA loop 每次内部迭代都调用：

```text
agent_runner_loop:
  Turn 1 -> tools -> turn_end_callback
  Turn 2 -> tools -> turn_end_callback
  Turn 3 -> no_tool -> turn_end_callback
```

一个复杂任务可能响 10 次。CC 的 `Stop` 一个用户回合只响一次。GA 的 beep 必须挂外层 `run()`。

## 12. 风险与边界

| 风险 | 处理 |
| --- | --- |
| hook 拖慢主流程 | 第一版只做通知型；默认 timeout 10s；可配置超时 |
| hook 阻塞 Stop | Stop 忽略 `onFailure: block`；blocking Stop 第二版 |
| 子代理重复响铃 | beep 只配 `Stop`，不配 `SubagentStop` |
| hook 修改工具参数绕过权限 | hook 后重新跑 capability/PathACL |
| 多来源 hook 顺序不稳定 | 显式来源优先级 + 声明顺序 + 审计 |
| stdout 污染协议 | stdout 只允许单个 JSON；日志走 stderr |
| 输出过大 | `maxOutputChars` + 持久化 preview |
| Windows shell 差异 | 优先 exec form；不依赖 PowerShell hook |
| 误读 CC 配置 | GA 第一版使用 `.genericagent/`，不默认读 `.claude/` |
| 云端误入 | **复刻 hooks 时暂时不需要参考 Claude Code 云端会话实现**；不做 cloud/device forwarding |
