# 20261028-GenericAgent goal 模式设计与实施方案（对标 Claude Code 2.1.303）

> 目标：把 Claude Code（下称 CC）2.1.303 的 goal 模式复刻进 GenericAgent（下称 GA），让 GA 能“设一个会话目标，
> 持续工作直到条件达成”。设计依据见同目录、同日期调研文档
> `docs/../..` 侧已落盘：`D:/git_codes/claudecode283_hack/docs/20261028-CC-goal模式实现调研.md`。
> 本文只落盘在 GA 仓库 `docs/`，标注 GA 侧改动落点（`genericagent/` 具体文件/函数），并给出分阶段实施与 DoD。
> 不实现 CC 云端会话、device forwarding、cloud hook 策略；仅本地会话 / Ink / CLI / workflow child / agent team 可用范围内。

## 1. 结论先行

CC 的 goal 模式本质不是独立子系统，而是**“会话级 Stop hook + 活跃目标状态机 + 只读模型求值器”**三件套：

- 设目标 = 往当前会话 hooks 注册表塞一条 `Stop` 事件下的 `prompt` 型 hook，prompt 即条件文本，同时维护 `activeGoal` 状态；
- 做法成检测 = 每次“回合要结束”时对这条 prompt hook 跑一次**工具隔离、只读转录**的模型调用，返回 `{ok, reason, impossible?}`；
- 未满足 → **阻塞停止**、把 `reason` 注回会话并让回合继续；满足 / 判定不可达成 → 摘掉目标 hook、写 `goal_status`；
- 后台任务在跑时求值推迟 + 定时 check-in；用户中途打断自动重试注入。

GA 已有 hooks 引擎（`command/prompt/agent/http/mcp_tool` 五种、`Stop/SubagentStop/StopFailure` 事件、工具隔离的
prompt 运行器），**goal 模式可以直接复用这条“Stop + prompt hook”缝**，不必另造轮子。

### 1.1 本文一句话方案

**在 GA 的回合结束门禁处（`agent_runner_loop` 要 break 的时机）加一个“目标守卫”——复用阶段 A 的 `handler.run_stop_gate()`，goal 只注册一条 `Stop` 会话 hook 并做三态记账（§4.1）**：

```text
回合想要结束（CURRENT_TASK_DONE / EXITED / MAX_TURNS）
   │   有 activeGoal 吗？ 无 → 正常结束
   ▼
   │   后台任务在跑？ 是 → 推迟求值 + 记录 deferredSince + 定时 check-in
   ▼
prompt-hook 求值（工具隔离模型，读会话转录，问 {ok, reason, impossible?}）
   ├─ ok:true          → 清 activeGoal + 落 goal_status{met:true} + 正常结束
   ├─ impossible:true  → 清 activeGoal + 落 goal_status{met:false,failed:true} + 正常结束
   ├─ ok:false         → 注入 reason（用户元消息）+ **不结束，继续下一轮**
   └─ timeout/error    → 记遥测 + 按 cancelled/error 处理（不阻塞死循环）
```

### 2.1 关键映射决策：goal 复用“阶段 A 门禁 + 阶段 B 会话 Stop hook”（20261029 修订）

**旧稿曾主张“在 `agent_runner_loop` 里另插一个 `handler.goal_guard` 专属状态机”。阶段 A 落地后该说法作废**：
`loop.py` 的 break 前已经有 `handler.run_stop_gate()` 这道可阻塞门禁，goal 若再造一套门禁会与它重复触发、双写状态。

正确做法（对齐 `docs/20261029-...（goal与mods前置）.md` §5.5 的“只做三件事”）：

1. `/goal <条件>` → `add_session_hook("Stop", {type:"prompt"|"agent", prompt:<条件+求值契约>, model:<求值模型>, outputSchema:{ok,reason,impossible?}}, key="goal:stop")`；
2. 门禁在 `turn_end` 跑该 hook：`ok:false` → `blocked` → 现有 loop 已注入 reason 继续；`ok:true` / `impossible:true` → 不阻塞；
3. goal 薄层读取门禁返回的 aggregate，把结果解释为 met / failed / not_met，维护 `ActiveGoal.iterations / last_reason` 并写 `goal_status`，met / failed 时 `remove_session_hook("goal:stop")`。

也就是说 goal 只增加“设定/清除 + 状态记账 + 转录”的薄层，**求值、阻塞、续跑、防死循环全部复用 A/B/D**。

## 3. 目标数据模型与状态

### 3.1 `ActiveGoal` 结构（对齐 CC `m0274` `activeGoal`）

```python
@dataclass(frozen=True)
class ActiveGoal:
    condition: str            # 目标条件（也是目标 stop prompt）
    iterations: int = 0       # 已求值轮数
    set_at: float = field(default_factory=time.time)   # 设置时刻（结算 durationMs）
    origin: str = "user"      # "user" | "proposal_direct" | "proposal_approved"
    tokens_at_start: int = 0  # 起始 token（结算 tokens 用）
    last_reason: str | None = None          # 最近一次“未满足”的 reason
    deferred_since: float | None = None     # 后台推迟起点
    checkin_count: int = 0                  # 已 check-in 次数（退避）
    last_deferral_pass_at: float | None = None
    idle_checkin_count: int = 0             # 空闲 check-in 上限计数(3)
```

存放位置：建议放会话级对象，例如 `GenericAgent` 实例上的 `self.active_goal: ActiveGoal | None`，
外部借 `app.py` 的状态对象透传给工具上下文（对齐 CC `toolUseContext.options.activeGoal`，`m0609:4674`）。

### 3.2 会话/转录里的 `goal_status` 事件（对齐 CC `VVn/COr`）

向 `transcripts.py` 增加一类事件 `goal_status`，字段对齐 CC：

```json
{ "type": "goal_status", "met": true|false, "failed": false,
  "condition": "...", "reason": "...",
  "iterations": 3, "durationMs": 1234, "tokens": 2000, "sentinel": false }
```

- `sentinel:true`：设置/清除时写，仅作标记、前端不渲染（对齐 CC `m1556:7324` sentinel 分支）；
- `Met`：有 activeGoal → 写 `met:false`；activeGoal 被摘掉但转录里仍有该条件 → 写 `met:true`（对齐 `m0459:140117`）。

### 3.3 来源（`queuedGoalOrigin`）

`ProposeGoal` 工具提议（直设 / 审批通过）时，先把来源记到会话临时位，再 enqueue `/goal <条件>`；
真正设置时按“条件匹配”取回来源（对齐 CC `m0274:120-143` 的 `O` 与 `SFs`）。GA 可在 `self._queued_goal_origin` 上实现。

## 4. 核心设计：goal 复用回合结束门禁（20261029 修订）

### 4.1 不新增门禁，改为薄封装阶段 A 的 Stop gate

阶段 A 已把 `loop.py:276-305` 的 break 前逻辑改成：

```python
# loop.py，agent_runner_loop 内，break 之前（已落地，勿再插新门禁）
if len(next_prompts) == 0 or exit_reason:
    if exit_reason.get('result', '') == 'EXITED':
        break
    if handler._done_hooks:
        next_prompts.add(handler._done_hooks.pop(0))
    else:
        stop_gate = handler.run_stop_gate(exit_reason)   # 阶段 A
        if stop_gate[0] == 'continue':      # blocked -> 注入 reason 继续
            next_prompts.add(stop_gate[1]); exit_reason = {}
        elif stop_gate[0] == 'stop':        # preventContinuation -> 停止
            ...; break
        else:                                # none -> 正常结束
            break
```

`handler.run_stop_gate()`（`handler.py:448`）内部已经做了这些事，goal **不再复制**：
- `_stop_gate_count` 连续阻断上限（对齐 CC `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`：默认 8、可配置、`<=0` 关闭）→ 防死循环；goal 与普通 Stop hook 共用这同一个 cap（CC 把 `goal_active` 只当遥测字段）；
- `stop_hook_active = count > 0` → 供 hook 区分“已因门禁续跑过”；
- `phase='turn_end'`、`last_assistant_message`、`exit_reason` 载荷；
- 汇聚 `Stop` 事件的所有静态 + 会话动态 hook（`run_hook_event`），`preventContinuation` 优先、`blocked` 次之、错误放行。

因此 goal 阶段 1 的改动**只有**：注册一条 `Stop` 会话 hook（§4.2 的 handler），并给门禁 aggregate 加一层“解释为 met/failed/not_met”的薄封装。
**禁止**在 `agent_runner_loop` 再插一个 `goal_guard` 专属状态机（旧稿 §4.1 的写法）——那会与阶段 A 门禁重复触发并双写 `ActiveGoal`。

### 4.2 goal 的 Stop handler 与三态解释（复用阶段 D）

注册（goal 设置时）：

```python
add_session_hook(
    "Stop",
    {
        "type": "prompt",              # 或 agent（同样的严格 schema 通道）
        "prompt": GOAL_EVAL_PROMPT + "\n\nGOAL CONDITION:\n" + condition,
        "outputSchema": {
            "type": "object",
            "required": ["ok", "reason"],
            "properties": {
                "ok": {"type": "boolean"},
                "reason": {"type": "string"},
                "impossible": {"type": "boolean"},
            },
        },
        "timeout": <goal_eval_timeout>,
    },
    key="goal:stop",
)
```

阶段 D 已经把这个 handler 的结果解析成严格三态（`models.py:351`）：

| 求值器输出 | 阶段 D 在 aggregate 上的效果 | goal 薄层的解释 | Aggregate 消费方（阶段 A 门禁） |
| --- | --- | --- | --- |
| `{ok:true, reason}` | 不置 blocked（仅记 `reason`） | met：清目标、写 `goal_status{met:true}` | `run_stop_gate` → `none` → 正常结束 |
| `{ok:false, impossible:true, reason}` | 不置 blocked（记 `reason`） | failed：清目标、写 `goal_status{met:false,failed:true}` | `none` → 正常结束 |
| `{ok:false, reason}` | `decision='block'` → `aggregate.blocked` | not_met：`iterations+1`、`last_reason=reason`，保留目标 | `continue` → 注入 reason、继续下一轮 |
| 无有效 JSON / 不合 schema | `status=invalid_output` | 记 `evaluator_error`，不当作 met | Stop 属“失败忽略”事件（`runner.py:474`）→ 不阻塞 → 放行 |
| 运行错误 / 超时 | `status=error/timeout` | 记 `evaluator_error/timeout`，不当作 met | 同上 → 放行 |

> 关键：`impossible:true` 与 `ok:true` 在 Stop 上都是“不阻塞”，所以**仅靠门禁返回值无法区分 met / failed**。
> goal 薄层必须读取门禁返回的 aggregate（`handler.last_hook_aggregate`，或让 `run_stop_gate` 直接返回 aggregate 三元组）
> 去拿到 `ok/impossible` 原文，才能记账与写 `goal_status`。这就是“薄封装”的具体位置。

### 4.3 落地与转录（对齐 CC `m0671` 与 `m0459 Met`）

- met：`remove_session_hook("goal:stop")`；`active_goal = None`；`transcripts.record_goal_status({met:true, condition, reason, iterations, duration_ms, tokens})`；
- impossible：同上但 `met:false, failed:true`；
- not_met：保留目标、更新 `iterations/last_reason`，写 `goal_status{met:false, reason}`；不额外动作（继续由门禁 `continue` 完成）。

### 4.4 phase 门禁与 fetch 兜底

同一 `Stop` 事件有两个发射 phase，goal 求值**只能对 `turn_end` 生效**：

- `turn_end`（`handler.run_stop_gate`，每次模型想收尾）→ goal 求值在这里；
- `user_turn_end`（`app.py:1319` 兜底，整个用户回合收尾，aggregate 不消费）→ goal 必须**跳过求值**，否则同一回合求值两次、`iterations` 双增。

因为阶段 B 的 `add_session_hook` 的 `matcher` 只匹配 `tool_name/agent_type/task_type`（`matcher.py:14`），**无法按 `phase` 过滤**。
所以 goal 侧二选一（阶段 1 落地时定，推荐后者）：

1. goal 的 Stop handler 在 `prompt` 里要求模型看到 `user_turn_end` 载荷时直接返回 `{ok:false, impossible:true}`——不推荐，污染语义；
2. 给 `run_stop_gate`/`run_hook_event` 增加一个 `skip_dynamic_keys` 或 `phases` 过滤（**最小改 `handler.py`/`runtime.py`**），
   让 `phase='user_turn_end'` 时跳过 `goal:stop` 这条动态 hook；这是首选，改动局部且不破坏静态 Stop（如 beep）。

## 5. 两个入口

### 5.1 `/goal` 命令（对齐 CC `m1247` + `m1927`）

GA 的斜杠命令需新增 `goal`：支持 `status / <condition> / clear` 三形态。

```text
/goal                → "Goal active: {condition} ({n} turns){lastReason}"   | "No goal set."
/goal clear|stop|off|reset|none|cancel
                     → omt() 成功 ? "Goal cleared: {condition}" : "No goal set"
/goal <condition>    → 长度 ≤ 4000：设置并回 "Goal set: {condition}" + kickoff 注入
                       > 4000：拒绝 "Goal condition is limited to 4000 characters (got N)"
```

- clear 词表：`{"clear","stop","off","reset","none","cancel"}`（对齐 `m0274:80`）；
- 长度上限：用户手输 4000；模型提议 500（对齐 `GNt=4000` / `Vjn=500`）；
- 设置走 `_set_goal(condition, origin)`：先过门禁（§9），再 `active_goal = ActiveGoal(...)`，
  并把 kickoff 文本作为后续模型输入的元消息注入：
  > A session-scoped goal is now active with condition: "...". Continue working toward the condition; the evaluator
  > will block turn-end until it holds. It auto-clears once met (do not ask the user to clear after success).
- 命令可挂在 `app.py` 的斜杠分发处（与现有命令同一入口），非交互模式（`--print`）走 `supportsNonInteractive` 直读。

### 5.2 `ProposeGoal` 工具（模型提议，对齐 CC `m1718` + `m0418`）

在 GA 工具集市新增 `propose_goal` 工具：

- 输入：`{condition: string(1..500), ask_user?: boolean}`；输出：`{condition, ask_user}`；
- 工具 `is_enabled()` 门禁（对齐 `m1718:173-181` + `m0062` 设置）：
  - 非交互 / 非本地会话 → 禁用；
  - feature flag `tengu_propose_goal`（对应 GA 内部开关，默认关）→ 禁用；
  - `model_proposed_goals == "disabled"` → 禁用；
  - Plan mode 激活 → 调用时拒绝（“plan 完成后才可提议”）。
- `call()`：
  - 规范化条件（折叠 `\r\n\u2028\u2029` 为空格、reject 纯空白/超长/clear 词）；
  - `model_proposed_goals == "alwaysAsk"` 或 `ask_user !== false` → 走“一键审批对话框”（GA Ink 侧
    `goal_proposal` 对话框，payload `{condition}`，result `{approved, explicit?}`）；
  - 审批通过/直设 → `_queued_goal_origin = "proposal_approved"|"proposal_direct"`，再 enqueue `/goal <condition>`
    （与 CC 一致，工具不直接设，靠命令路径落 `active_goal`）；
  - 不阻塞当前工作：`should_defer=true`，返回“已展示/已直设，继续工作勿等 kickoff”。

### 5.3 一致性

两入口殊途同归到 `_set_goal/clear_goal`，来源（user / proposal_direct / proposal_approved）写进 `ActiveGoal.origin`，
供遥测与 UI 展示。

## 6. 求值器实现（复用 GA prompt-hook runtime + 阶段 D 严格通道）

### 6.1 复用点（20261029 修订：不得走宽解析）

GA `hooks/runtime.py:41` 已有工具隔离模型运行器 `_default_prompt_runner(agent)`（`client.chat(..., tools=None)`）。
goal 求值器**不新建 runner**，而是注册一条带 `outputSchema` 的 `prompt`/`agent` Stop hook（§4.2）：

- 模型底座：`_default_prompt_runner`（工具隔离、只读）；
- **结构化输出：必须走阶段 D 的严格通道**（`runner.py:_prompt_execute` + `_parse_structured`）。
  `handler.output_schema` 非空时，模型回复必须是与 schema 匹配的 JSON，否则 `status=invalid_output`，**绝不回退 `additionalContext` 宽解析**；
  `models.py:351` 再把 `{ok,reason,impossible?}` 解释成 block / 非阻塞。
- **旧稿 §6.1 说“直接复用 `_default_prompt_runner` 的宽解析”是错的**：那会继承 `allow_text=True`，重演 `f1a69959` 的 JSON 静默失败。
  正确做法是“复用其运行器 + 阶段 D 的严格 schema 通道”，二者缺一不可。

### 6.2 系统提示词（goal 专用，写进 handler 的 `prompt`）

`_default_prompt_runner` 的 system 文案是固定的 hook 文案，因此 goal 的求值契约要写进 handler `prompt`（会成为 user 消息）：

```text
You are evaluating a stop-condition goal in GenericAgent. Read the conversation transcript in <hook_input>,
then judge whether the user-provided condition is satisfied.

Your response MUST be a single JSON object matching this schema:
- {"ok": true, "reason": "<quote evidence from the transcript that satisfies the condition>"}
- {"ok": false, "reason": "<quote what is missing or what blocks the condition>"}
- {"ok": false, "impossible": true, "reason": "<explain why the condition can never be satisfied>"}

Always include "reason", quoting specific text whenever possible. If the transcript lacks clear evidence,
return {"ok": false, "reason": "insufficient evidence in transcript"}. Only use "impossible" when the
condition is genuinely unachievable in this session (self-contradictory, depends on an unavailable resource,
or all reasonable approaches exhausted and independently confirmed). When in doubt, return {"ok": false}
without "impossible". Do not wrap the JSON in prose or code fences.

GOAL CONDITION:
<condition>
```

（沿用 CC `Xe` 语义：只读对话、无工具、reason 要引用文本、拿不准不判达成、impossible 要独立确认。）

### 6.3 结构化结果（由阶段 D 产出，goal 薄层只做三态解释）

阶段 D 已把模型 JSON 严格解析并校验 schema（`runner.py:_parse_structured`），随后 `models.py:351` 消费三态。
goal 薄层看到的最终语义见 §4.2 的表，这里只补“异常分支”的处置：

| 求值器情况 | 阶段 D 状态 | goal 侧处理 | 对齐 CC |
| --- | --- | --- | --- |
| `ok:true` | success | met：清目标 + `goal_status met:true` | success / met |
| `ok:false, impossible:true` | success（非阻塞） | failed：清目标 + `goal_status met:false failed:true` | success / impossible |
| `ok:false` | blocking | not_met：注入 reason、保留目标、`iterations+1` | blocking / not_met |
| 无有效 JSON / 不合 schema | `invalid_output` | 记 `goal_met=evaluator_error`，不当作 met | hook error |
| 运行错误 | `error` | 记 `goal_met=evaluator_error`，不当作 met | hook error |
| 超时 | `timeout` | 记 `goal_met=evaluator_timeout`，按 cancelled 处理 | cancelled / timedOut |

> Stop 属“失败忽略”事件（`runner.py:474` 的 `ON_FAILURE_IGNORED_EVENTS`），`invalid_output/error/timeout` 不会升级为 block，
> 门禁 `run_stop_gate` 会 `none` 放行、turn 正常结束——**坏求值器不锁死会话**。这与 CC“Stop 类忽略 onFailure=block”一致。

### 6.4 转录裁入（goal 薄层要补，阶段 D/A 未提供）

`_default_prompt_runner` 当前只把 `prompt` 当 user 消息、把 hook payload 附到 `<hook_input>`；
它**不会**自动带上会话转录。goal 求值需要“截至当前回合的会话转录”，因此 goal 阶段 1 必须：

- 在注册/调用前，把转录（去除工具大输出、保留对话+摘要）序列化进 payload，或改 runner 接受 `transcript` 字段；
- 超预算时按 0.5×上下文预算截断，并在最前面插入：
  > [Earlier conversation truncated to fit the evaluator's context window — N earlier messages omitted. Evaluate the
  > condition against the recent transcript; if the required evidence may be in the omitted prefix, return
  > {"ok": false, "reason": "insufficient evidence in transcript"}.]

### 6.5 防死循环（复用阶段 A 的上限，goal 侧不再自建）

- 门禁每次触发都走 `_stop_gate_count`，超过 cap 自动放行（`handler.py:462`；cap 对齐 CC `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`，默认 8、可配置、`<=0` 关闭，goal 不单独设值）——goal 不需再维护独立计数器；
- `stop_hook_active` 由门禁按 `count > 0` 置位，goal handler 可据此在提示里要求“若已续跑多次仍无进展，倾向判 impossible”；
- `max_turns` 与门禁上限天然给续跑封顶；timeout/error 一律放行，避免求值器故障锁死用户会话。

## 7. 后台 deferral 与 goal check-in（对齐 CC `m0671:128-338`）

当 GA 里存在正在跑的**后台任务**（agent / shell / monitor，见 `_run_parallel_tools` 产生的在途任务）且目标是 active 时，
`goal_stop_gate`（goal 对阶段 A 门禁的薄封装）不立即求值，而进入“推迟求值”：

- 记录 `g = replace(g, deferred_since=now)`，并调度一个 `check-in` 定时器；
- 定时器到点（默认 30 分钟，`CLAUDE_CODE_GOAL_CHECKIN_MINUTES` 可覆盖）：若目标仍 active 且后台仍在跑
  → 向主模型注入一条 check-in 元消息：
  - 后台已清 → “Goal check-in: background work no longer running… Continue toward the goal.”
  - 后台仍在 → 列出每个任务 `- id · type · description`，提示“check on progress… waiting / fix or stop, continue”。
- 退避：`delay = 30min * 2 ** min(checkin_count, 2)`；idle 上限 3 次后只重排不再注入
  （“idle check-ins paused until your next message”，对齐 `Lu=3` / `dr` / `ju`）。

**关键：推迟不等于放行收尾。** 后台任务在跑时确实不 block，但一旦后台清空且回合又到结束点，`goal_stop_gate` 会重新求值。

## 8. 中断与自动重试（对齐 CC `m0671:3763-3860`）

用户可能在某回合中手动 Stop（abort / 清空队列命令 / usage limit）。目标仍 active 时，GA 应“自动续跑”而不是默默结束：

- 维护 `goal_interruption_streak`：`{goal_set_at, retries, announced}`；
- retry 间隔 `[60s, 300s, 900s]`（+小抖动），最多 3 次（`Ds=3`）；
- 到点注入：`"Goal check-in: continuing after the last turn ended early — {condition} is still active. The last turn
  ended before the goal could be evaluated: {cause}. Continue toward the goal."`；
- retries 到 3：注记 `"Goal paused after 3 automatic retries · {cause} · send a message to continue"`（warning），不再自动续；
- 用户主动发新消息 / 显式 EXITED → 清 streak。

> 收发与 `app.py` 的 abort 路径衔接：`stop_sig`（用户停止）时若目标 active，走 §8 的重试调度；这与 CC 的
> `goalInterruptionStreak` + `Qu` 重试注入一致。

## 9. 门禁与设置（对齐 CC `m0062` / `m0274 Dsn` / `m1134 Uxn`）

### 9.1 设置 `model_proposed_goals`

取值/默认：`auto`（缺省）/ `alwaysAsk` / `disabled`；consent-affecting → 只读 trusted sources（user/policy/flag），
忽略 workspace 内 project/local。由 `ProposeGoal.is_enabled()` 与 `call()` 消费（§5.2）。

### 9.2 设置/求值门禁 `_goal_applicable(session)`

在 `_set_goal` / `goal_stop_gate` 入口统一判：

1. hooks 未被禁用/受限（对齐 `kae()`：GA 若 `disableAllHooks` / `allowManagedHooksOnly` 打开 → 拒绝/跳过）；
2. 会话设置在可信工作区（GA 的 trust 判定），非交互且非可信 → 拒绝；
3. Plan mode 激活时（`permissions.policy` 的 plan 相应判定）→ 允许 `/goal` 存在但**禁止 ProposeGoal 提议**
   （求值器仍可在 plan 结束后命中，对齐 CC `m1718:217`）；
4. 求值器仅在“回合要结束”触发，且非用户显式 EXITED，避免抢占用户控制权。

### 9.3 并发与重入

- 同一会话同一时刻最多一个 activeGoal；新目标覆盖旧目标（记 `superseded`）；
- 一个 `ProposeGoal` 请求在途时拒绝再次提议（`tool_state` 标记，对齐 `m1718:226`）；
- 求值器跑在后台线程/独立 runner，与主消息循环解耦，避免阻塞 UI 渲染。

## 13. 修订记录（20261029，对齐 hooks 阶段 A–E）

本文写于 hooks 语义补全之前。阶段 A–E 落地后，以下三处与实现不符，已按“复用 A/B/D、不另造轮子”修订：

2. **§6.1（求值器解析）**：旧稿说“直接复用 `_default_prompt_runner` 的宽解析”。这会继承 `allow_text=True`，重演 `f1a69959` 的
   JSON 静默失败。改为“复用运行器 + 阶段 D 的 `outputSchema` 严格通道”（§6.1 / §4.2）。

   `met` 与 `failed` 在 Stop 上都不阻塞，必须靠 aggregate 原文区分（§4.2 表）。
