# CC 319 如何处理 Windows 长路径：一个反向结论

> 目的：回答「GA 的 workflow 在深路径下静默失败，是不是该给 `atomic_write_json` 套 `\\?\` 前缀」。
> 方法：只读阅读 `D:/git_codes/claudecode283_hack/reconstructed319/deminified/`（CC v2.1.319 反混淆源码）。
> **本文不改任何代码**，只记录证据与结论。
>
> 结论先说：**CC 从不主动加 `\\?\` 前缀，反而在校验层把该前缀判为"必须拒绝"的形式。**
> 我们要学的不是"怎么加前缀"，而是 CC 那三条让路径根本不会长到超限的设计。

## 1. CC 侧证据：前缀是被拒绝的输入，不是修复手段

### 1.1 路径校验明确禁止设备命名空间前缀

`reconstructed319/deminified/m0094_0x112cc57f.js:7214`（win32 分支的错误文案原文）：

```
path must be in normalized form: no "." or ".." segments, no doubled or trailing
separators, no component ending in "." or a space, no ":" outside the drive letter,
no device-namespace (\\?\) prefix, no drive-relative (\dir or C:name) or UNC
(\\server\share) form
```

CC 把 `\\?\` 前缀与 `..`、重复分隔符、8.3 短名、NTFS 备用流并列为
**"windows 可疑路径模式"**，出现在权限校验里：

`m0094_0x112cc57f.js:2981`：
```
${path} is a device-namespace path, which can't be checked for links to a network
location. Give it without the \\?\ or \\.\ prefix.
```

即：**用户传进来的路径如果带前缀，CC 拒绝并要求去掉它**。

### 1.2 校验层主动把前缀"剥掉"再比较

`m0037_0x11233d43.js:485-491`：

```js
function Jv(t) {
  if (t.startsWith("\\\\?\\UNC\\")) return "\\\\" + t.slice(8);
  if (t.startsWith("\\\\?\\") && t.length >= 7 && t[5] === ":") return t.slice(4);
  return t;
}
```

`\\\\?\UNC\server\share\...` → `\\server\share\...`
`\\\\?\C:\...`            → `C:\...`

这是"canonical form"归一化：**内部比较、去重、白名单匹配都用去前缀后的形式**，
这样同一个文件无论从哪个命名空间进来都判定为同一路径（避免前缀成为绕过权限的通道）。

`m0094_0x112cc57f.js:561-563` 的权限判定里也专门检测前缀变体，
包括正斜杠写法 `//?/C:/...` 与 `//./C:/...`。

### 1.3 前缀判定函数

`m0037_0x11233d43.js:986-992`：

```js
function R0(t) {
  return ct.test(t) || t.includes("??") && ct.test(At(t));
}
var ct = /^[\\/]\?\?[\\/]/;
function At(t) {
  return V.win32 ? V.win32.normalize(t) : t;
}
```

注意 `t.includes("??") && ct.test(At(t))`：连 "路径里出现 `??` 再 normalize 后才暴露前缀"
都算，说明 CC 把前缀视为**必须识破的混淆形式**。

### 1.4 长度上限用的是 32767，不是靠加前缀解决

`m0037_0x11233d43.js:77`：

```js
var Ot = 32767;
function Aoa(t) {
  if (t.length > Ot) return "named";
  ...
}
```

CC 在**语义层**（路径分类）认的最大长度是 32767 —— 即 long path 完全启用后的上限。
它并不试图在 260 附近做任何加前缀的兜底。

## 2. CC 真正的三条设计（这才是可借鉴的部分）

### 2.1 tmp 名字极短：`.tmp.` + 8 位 hex

`m0067_0x11295438.js:151-158`：

```js
function fP(t) {
  return `${t}.tmp.${ee(4).toString("hex")}`;      // 例: foo.json.tmp.a1b2c3d4
}
function jA(t, e) {
  let n = `${e}.tmp.`;
  return t.startsWith(n) && /^[0-9a-f]{8}$/.test(t.slice(n.length));
}
function GFr(t) {
  return /\.tmp\.(?:[0-9a-f]{8}|\d+\.[0-9a-f]{12})$/.test(t);
}
```

对比 GA：

| | 临时名 | 相对目标文件多出 |
| --- | --- | --- |
| CC | `<name>.tmp.<8 hex>` | **13 字符** |
| GA | `.<name>.<pid>.<tid>.tmp` | **约 13-19 字符**（`.10732.17192.tmp` = 18 字符，且前面还多一个点） |

差别不大，但方向不同：CC 把**唯一性标识放在后缀最末且定长**，且用随机 hex 而非
pid+tid —— 后者在线程数增长时位数会增加，是不定长。

> 这一条单独不足以解决问题（13 vs 18 只差 5 字符），但它是"路径预算"意识的一部分。

### 2.2 有 `stagingDir` 机制：临时区可以外置

`m0067_0x11295438.js:586-612`、`430-448`：

```js
async function me(t, e) {          // t = 目标路径, e = stagingDir
  return t;                        // ← 当前版本直接返回，机制已停用
  try { await (await I(e, O_RDONLY | O_DIRECTORY | O_NOFOLLOW)).close(); }
  catch (error) { ... return t; }  // 不可用时退回目标目录
}
```

`Kt(path, e, { stagingDir, ... })` 会把临时文件写到 `stagingDir`，再 `rename` 到目标。
**这条路径当前被 `return t` 短路掉了**（CC 自己停用），但设计意图明确：
临时文件的位置是**可配置的**，不必与目标同目录。

对 GA 的意义：`atomic_write_json` 的临时文件完全可以写到 `<temp>/atomic-staging/`
再 `os.replace` 过去 —— 前提是同一卷（跨卷 `os.replace` 会失败）。

### 2.3 原子写有多级降级，且失败**不静默**

`m0067_0x11295438.js:586-720` 的 `Kt()` 结构：

1. 正常路径：写临时文件 → `renameFn(staging, target)`
2. `rename` 失败且 errno 在 `qt` 集合内（`ENOENT/ENOTDIR/ELOOP/EMLINK/EFTYPE/EISDIR/ENAMETOOLONG/EINVAL`）
   → 检查是否可走 **in-place arm**（`lt`）：直接 `O_WRONLY|O_CREAT` 打开目标、`truncate(0)`、写入
3. in-place 也失败 → 依据快照判定文件处于 `untouched / replaced / restored / removed / partial`，
   并把该状态**抛给调用方**（`_(error, d, state)`）

关键是第 3 步：临时文件创建被拒绝时（`inPlaceOnTempCreateRefused`），
若 errno 是 `EACCES` 且目标可写，会**降级为原地写**而不是放弃：

```js
if (k(error) !== "EACCES") throw error;
if (!(await ae(path_3).then(() => !0, () => !1))) throw error;
await lt(void 0);   // in-place arm
return;
```

`ENAMETOOLONG` 被列进"可尝试降级"的集合（`qt`），意味着**CC 遇到长路径时的行为是换一种写法继续，
而不是抛出**。GA 现在是：`open(tmp)` 抛 `FileNotFoundError` → `workflow_draft` 吞掉 → 静默空 runId。

> 这一步是 CC 与 GA 最大的行为差异：同样是"临时文件写不了"，CC 有 fallback 且把结果状态上报，
> GA 没有 fallback 且把异常吞了。

## 3. 关键对照表

| 维度 | CC 2.1.319 | GA 现状 |
| --- | --- | --- |

## 4. 结论：该学什么，不该学什么

### 不该做

**不要给 `atomic_write_json` 套 `\\?\` 前缀。** 理由：

1. CC 自己不用这个手段，用了反而在校验层把它当危险形式
2. 前缀会**关掉 Win32 四类规范化**（`temp/probe_prefix_semantics.py` 实测）：
   - 正斜杠 → `FileNotFoundError`
   - 相对路径 → `FileNotFoundError`
   - 含 `..` → `OSError`
   - 结尾的点不裁剪 → **静默写到另一个文件**（最危险）
3. GA 里路径来源多样（workspace 可由 `GA_WORKFLOW_WORKSPACE_ROOT`、`args.workspacePath`
   等外部输入决定），无法保证每条都是干净绝对路径
4. 前缀写出的文件，**下游任何未加前缀的读取都会 `FileNotFoundError`**（实测：
   `os.path.exists` 返回 False、`os.listdir` 抛异常），等于把问题从"写失败"改成"读失败"

### 该做（按收益排序）

1. **临时文件名缩短** —— 改为 `<name>.tmp.<8hex>` 形式，去掉 pid/tid，把 18 字符降到 13；
   同时长度定长，不随线程数增长
2. **写失败不再静默** —— `workflow_draft` 的 `except Exception` 必须把
   `FileNotFoundError/WinError 206` 与普通错误区分开，作为 `workflow_draft_failed` 事件上报，
   而不是返回空 runId 让上层以为"用户没提交"
3. **临时文件落 `temp/` 下同卷 staging 区** —— 学 CC 的 `stagingDir` 思路，
   把临时文件挪出深路径，`os.replace` 再落到目标（需保证同卷）
4. **加一条路径预算断言** —— 在 `create_run` 里检查目标路径长度，超限时给出
   **明确的、可诊断的**错误，而不是让 `open()` 抛一个看起来像"文件不存在"的异常

## 6. 一句话

CC 的思路不是"把路径撑开"，而是**缩短临时名 + 归一化 + 失败降级**，
并让长路径在语义层（32767）而非 260 附近被认知。

GA 真正该修的是**静默吞异常**：用户看到的是"workflow 不启动"，
而实际是一个 `FileNotFoundError` 被 `except` 吃掉了 —— 这比路径长度本身更难排查。
