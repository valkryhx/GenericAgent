# GA 真实 LLM 测试策略：过程断言优先，别用结果给过程背书

日期：2026-11-03
定位：专门针对「需要真实 LLM API 的测试」的策略与红线。它和
`docs/20261030-GA-goal多智能体协同测试方法论.md` 互补——那份讲并发窗口、
真实 Ink 抓帧、Windows 写文件坑；这份讲**怎么防止真实 LLM 测试走捷径、怎么保证
测到「过程」而不是只看「结果」**。
触发场景：任何要调真实模型、且行为带有「回合 / 工具调用 / 多步执行」的测试。

---

## 0. 一句话总纲

> **真实 LLM 测试的价值不在「最后对没对」，而在「过程有没有真的发生」。
> 只断言结果的测试，会被一个「什么都没做但结果看起来对」的 bug 骗过去。**

本文的全部内容，都是为了落实这一条。

---

## 1. 本案复盘：测试全绿，却漏掉 `/goal` 空转

用户输入 `/goal <目录> 写一个 8 皇后 html`，界面显示 `0 turns · <1s · 0 tokens`，
文件没生成。但此前「各种测试都通过」。翻回上一版（`e48dbae`）的测试可以清楚看到失误：

| 层 | 当时的写法 | 为什么没抓到 |
| --- | --- | --- |
| 单测 | `_run()` 直接调私有 `_handle_goal_command()`，断言 `q[-1]['done'] == 'Goal set: ...'` | 断言的就是「塞一条终结性 done 就地结束」——**把 bug 固化成了期望**，且完全绕过了分发层 `_handle_slash_cmd()` 和主循环 `run()` |
| 真实 e2e | 全部「两段式」：先 `/goal <谓词>` 设目标，**再单独发一条消息干真活** | `/goal` 那轮 0 动作、<1s 结束也会被后面真正干活的轮次圆回来，goal 最终照样 met；「任务直接写进一条 `/goal`」的形态从没跑过 |
| 覆盖对象 | 几十个测试都在测 `_set_goal`/Stop hook/defer/resume/metadata | 测的是「goal 判据系统」，从没测「命令分发是否进入模型回合」这个**入口契约** |
| 源码对照 | 读 CC 时看到 `/goal` 返回 `{type:"query", shouldQuery:true}` | 读了契约却没把它落成断言 |

**根因一句话**：结果导向（最终 met 就算过）掩盖了过程导向（有没有真的起回合、真的在干活），
而测试的抽象层一直停在「goal 判据」，从没下沉到「命令分发 → 是否进入模型回合」。

由此提炼三个最致命的**测试反模式**，下面逐条给对策。

---

## 2. 反模式 A：只测最终结果，不测过程

**错误写法**（本次就是）：

```python
# 只看最后 goal 是否 met、文件是否存在
r = run_turn(agent, "/goal 主目录下必须有 child_done.txt")
run_turn(agent, "好的，开始干活，把文件建出来")   # 偷偷补一条真正干活的
assert agent.active_goal is None and marker.exists()
```

问题：`/goal` 本身空转、`<1s`、`0 turns`，也会因为第二条消息把活干了而「通过」。
**结果对了，但被测的那条路径根本没被验证。**

**正确写法**：既断言结果，也断言**只有真正跑过才会有**的过程证据：

```python
t0 = time.time()
dq = agent.put_task("/goal <条件>")          # 只发这一条，之后不再补发任何消息
done = drain_until_done(dq)
secs = time.time() - t0

assert secs > 5,                      "本地命令会 <1s，真回合不可能这么快"
assert done and len(done) > 0,        "必须有一条 assistant 正文"
assert agent_turn_count(agent) >= 1,  "必须真的走了模型回合"
assert produced_file_content == "OK", "结果也要对"
```

> 判据：**每一条「过程断言」都要问一句——「如果是那个 bug（什么都没做），这条会不会也过？」**
> 会过，就说明它不是过程断言，只是结果断言。

---

## 3. 反模式 B：为了好写，偷偷「补一条消息」把 bug 绕过去

真实 LLM + 多步任务时，最省事的写法就是「先设目标/先设状态，再补一条命令让它干」。
但这恰恰会掩盖「第一步本身是否有副作用（是否起回合）」的 bug。

**错误写法**：

```python
run_turn(agent, "/goal 必须有 x.txt")     # 只想要「设置」这个副作用
run_turn(agent, "现在去把 x.txt 建出来")   # 补一条干活，掩盖了第一步空转
```

**正确写法**：**先明确这条测试到底测的是「设置语义」还是「端到端语义」，两者分开写。**

- 测「设置语义」（不需要模型）：直接、显式地在测试里 `agent._set_goal(...)`，
  并在注释里写明「本用例只测设置/判据，不测触发回合」。这是**合法的**，前提是**别冒充端到端**。
- 测「端到端语义」：**必须只用一条真实 `/goal` 输入，条件里就带任务，之后不再补发任何消息**。
  —— 这正是本次新增的 `tests/real_goal_slash_kickoff_e2e.py` / `real_goal_slash_8queens_e2e.py`。

> 红线：任何声称「验证用户操作」的用例，**用户实际会敲的输入必须原样出现在测试里，且是唯一
> 启动这次任务的输入**。不许用「内部 API 预置 + 补发消息」去拼出一个用户根本不会有的操作序列。

---

## 4. 反模式 C：测试抽象层停在「机制」，从没覆盖「入口契约」

goal 有几十个测试，全在 `_set_goal`/Stop hook/defer 这一层。它们都对，但**入口层
（斜杠命令分发 → 是否进入模型回合）从未被断言**，而 bug 正好在入口层。

**正确写法**：功能上线时，先画出「用户输入 → 分发 → 执行 → 结果」的链路，
**每一跳至少一条断言，尤其是「分发后是否真的启动了执行」这一跳**：

```python
# 入口分发层单测（不需要模型，快、确定）
assert agent._handle_slash_cmd("/goal 做某事", q) is not None   # set 必须返回 kickoff -> 起回合
assert agent._handle_slash_cmd("/goal", q) is None               # status 本地结束
assert agent._handle_slash_cmd("/goal clear", q) is None         # clear 本地结束
```

> 规则：**「命令 / 入口类」功能，必须有一层专门测「分发与执行启动」，不许混进底层机制测试。**
> 底层机制（判据、持久化、渲染）各自单测，但它们通过不代表入口会把用户带进这套机制。

## 5. 真实 LLM 测试的「过程证据」清单（照抄）

一个「输入 → 回合 → 工具 → 产物」的真实 LLM 测试，**至少**采集以下过程证据，
并逐条断言。缺哪条，就从「端到端」降级为「结果冒烟」，不能当回归门禁。

| # | 过程证据 | 为什么它能杀死「空转/假成功」 |
| --- | --- | --- |
| 1 | **耗时** `elapsed_secs` | 本地命令/空转 <1s；真实回合通常 >5s，量级明显不同 |
| 2 | **回合真的起来了**：`status=running` 出现过；`agent.is_running` 曾为真 | 只设置状态、没起回合时不会出现 running |
| 3 | **模型步数 / turn 计数** ≥1 | `0 turns` 是空转的直接指纹 |
| 4 | **至少一条 assistant 正文**（非空 `assistant_done`） | 没进模型就不会有模型正文 |
| 5 | **token 用量 > 0** | 真调用了模型才会产生 token；`0 tokens` = 没调用 |
| 6 | **工具/副作用的发生轨迹**（文件 mtime 在本次窗口内、事件日志新增条目） | 产物可能是上一次留下的；要看「本次新增」 |
| 7 | **终点状态**：goal_met/achieved、active_goal 清空等 | 结果正确性（但不能单独作为通过条件） |
| 8 | **没有重复/异常事件**（如 system 通知只出现 1 次） | 捕获「同一通道发两次」这类重复 bug |

可复用的采集骨架（从 `tests/real_goal_slash_kickoff_e2e.py` 抄）：

```python
events = []
bridge = GenericAgentBridge(emit=lambda e: events.append(e))
# ...
t0 = time.time(); dq = agent.put_task("/goal <条件>")   # 唯一输入
done = drain(dq)                                        # 收 done 与中途 system
secs = time.time() - t0

running_seen   = any(e["type"]=="status" and e.get("status")=="running" for e in events)
system_notes   = [e["text"] for e in events if e["type"]=="system"]
assistant_text = done or ""
new_goal_events = [e for e in goal_events()[before:]]   # 只看本次新增

check("耗时像真回合", secs > 5, secs)
check("出现过 running", running_seen)
check("有 assistant 正文", len(assistant_text) > 0)
check("goal 事件是本次新增", any(e["event"]=="goal_met" for e in new_goal_events))
check("产物是本次写入", mtime(marker) >= t0)
```

> 关键：`before = 记录日志行数`、`mtime(marker) >= t0` 这类「取差值/看新增」，
> 是为了防止**上一次运行的残留**让本次假通过。测试目录最好每次用带时间戳的独立子目录。

## 6. 真实 LLM 测试的工程纪律（防止「偶发绿」和「假绿」）

1. **每次跑在全新、带时间戳的目录 + 独立 session**：`temp/<feature>/run_<TAG>`，
   并在 `setup_env()` 里清掉 `GA_PROJECT_KEY/…_SESSION_ID/GA_TEAM_KEY` 等，避免串味。
   （详见 20261030 方法论 §5.6。）
2. **断言「本次新增」而非「当前存在」**：日志看行数差、文件看 mtime ≥ t0。
3. **不把「模型随机性」塞进精确断言**：要确定性瞬态，用「受控 gate」层（20261030 §2.1）。
   真实 LLM 层只证明「这条路能走通」，不承担精确时序断言。
4. **重试不掩盖失败**：真实 LLM 偶发失败可以重跑，但**重跑前必须先确认这次是「模型偶发」
   还是「代码真 bug」**。连续两次同点失败先当 bug 处理，不许「再跑一次就绿了」了事。
5. **一次只测一个「发起动作」**：一个回合塞太多（既起 A 又起 B 还内联长脚本），
   模型容易写错引号/超步数，失败原因混在一起分不清是能力问题还是代码问题
   （20261030 §5.4）。
6. **保留可复盘的落盘证据**：每次 e2e 写一份 `summary_<TAG>.json`（含各 check 的 ok/detail、
   耗时、token、goal 事件序列），失败时能直接看到「哪条过程断言挂了」，而不是只有一句 FAIL。

## 7. 提交前的「真实 LLM 测试」自检清单

新增/修改任何真实 LLM 相关功能，合并前逐条打勾：

- [ ] 存在一条「**只用一条用户会敲的输入**」就能跑通的端到端用例（不靠内部 API 预置 + 补发消息）
- [ ] 该用例断言了**过程证据**：耗时、running、assistant 正文、token>0 至少各一条
- [ ] 断言了**本次新增**（日志行数差 / 文件 mtime ≥ t0），排除上次残留
- [ ] 入口分发层有独立单测（`_handle_slash_cmd` 之类：该起回合的返回非 None，纯本地命令返回 None）
- [ ] 至少有一个「反例/回归」用例：能复现原 bug 的输入形态，且修复前会红、修复后会绿
- [ ] 没有「永远为真」的断言（grep `=> true` / `placeholder` / `assertTrue(True)`）
- [ ] 失败时落盘了 `summary_*.json`，能定位到具体哪条过程断言失败
- [ ] 不依赖外部已设的环境变量/开关；默认关闭的特性测试里自行打开
- [ ] 若用了「先设状态再补消息」的两段式，**明确标注这是设置层测试，不代表端到端**

---

## 8. 一句话收尾

> **结果对了不算数，要能证明「过程真的发生过」才算数。
> 一个测试如果换成那个 bug 版本也能通过，它就不是这个 bug 的测试。**
