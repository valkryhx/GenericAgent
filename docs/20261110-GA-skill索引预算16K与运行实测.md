# skill 索引预算 8000 → 16384：效果与真实运行实测（2026-11-10）

> 承接第 3 轮（`docs/20261110-GA-skill渐进式披露对照与第3轮优化.md`）：
> 索引已经"一个都不丢"了，但 8000 字符的预算在本机 51 个 skill 上仍然会把
> 19 行压成只剩名字。本轮把默认预算提到 **16384**（CC 默认的 2 倍），
> 然后用真实模型重跑一遍，看运行速度、token 占用和 skill 加载是否正常。

---

## 0. 结论先行

| 指标 | 8K 预算 | **16K 预算** |
| --- | --- | --- |
| L1 行数 | 51 | 51 |
| 只剩名字的行（描述被预算挤掉） | **19** | **0** |
| 描述被单条上限压缩的行 | 6 | 9（长描述仍按 400 字符压，但触发器句保留） |
| L1 清单字符 | 8,302 | 12,779 |
| skills 段落字符（含引导句） | 8,766 | 13,237 |
| 整个 system prompt 字符 | 18,975 | 23,446 |
| 首次 API `input` token（同题 A/B） | 21,591 | 22,651 |
| 真实模型：写 skill 任务 | 99.3s / 12 调用 / `load_skill=write-a-skill` | 96.6s / 23 调用 / `load_skill=write-a-skill` |
| 真实模型：前端页面任务 | 110.2s / 4 调用 / `load_skill=design-taste-frontend` | 62.4s / 2 调用 / `load_skill=frontend-design` |

**16384 是把"描述"补齐，不是把"全文"塞进来**：51 份 SKILL.md 全文合计
424,122 字符（≈10.6 万 token），索引只有 12,779 字符（≈3.2K token）——**约 33 倍**。

## 1. 改动（两行代码 + 一条测试）

`genericagent/core/skills.py`：

```python
SKILL_LISTING_CHAR_BUDGET_ENV = "GA_SKILL_LISTING_CHAR_BUDGET"
DEFAULT_SKILL_LISTING_CHAR_BUDGET = 16384          # 原 8000

def format_skill_listing(
    skills: Iterable[SkillSpec],
    char_budget: int = DEFAULT_SKILL_LISTING_CHAR_BUDGET,   # 原字面量 8000
    *,
    for_model: bool = True,
) -> str:
```

`tests/test_skills_runtime.py` 新增 `test_listing_default_budget_is_the_module_constant`：
默认预算必须等于模块常量（防止以后又漂成两处字面量），并断言 16384。

改动只影响"索引能装多少描述"，不影响加载逻辑：L2 的 `load_skill`、L3 的
`file_read` 引用读取、compact 后的 `invoked_skills` 回注都原样未动。

## 2. 成本账：渐进式披露到底省不省 token

同一台机器、同一批 51 个模型可见 skill：

| 口径 | 字符 | 约合 token（4 字符≈1 token） |
| --- | --- | --- |
| 全部 51 份 SKILL.md 全文 | 424,122 | ≈ 106,000 |
| 16K 预算的 L1 索引 | 12,779 | ≈ 3,200 |
| 实际发生的 L2 加载（`write-a-skill`） | 3,003 | ≈ 750 |

也就是说：**索引 ≈ 全文的 1/33**，真正的加载只发生在命中的那一份。
GA 的提示词里也有明确的"只读需要的那一份"的指令（`load_skill_content()` 的第 2 行）：

```text
Attached files live under this base directory. Read only the reference you need with file_read.
```

补一句实话：GA 的 base prompt（`assets/sys_prompt.txt`）**没有**一条"省着用 token"的通用要求，
省 token 是**结构上**做到的（三层 + 按需加载），不是靠一句口号。这也是和 CC 一致的做法：
CC 的 skill 引导同样只有一句"列表里的才可用，别猜"。

## 3. 怎么测的

三组证据，全部可复现：

1. **纯本地**：同一批 skill 分别按 8K / 16K 预算生成清单，数"只剩名字的行"和总字符。
2. **真实模型（同任务、不同预算）**：`temp/prompt_ab_probe.py` 进程内起真实 Agent，
   模型固定 `zhanlu-ds`，只改 `GA_SKILL_LISTING_CHAR_BUDGET`，记录耗时、工具调用序列、
   `load_skill` 命中，以及运行时的 `[Debug] Current context: ~N tokens` 与
   `[Cache] input / cached` 行。
3. **L2 直测**：直接调 `load_skill_content('write-a-skill')`，确认返回全文 + `Base directory` 首行。

## 4. 真实模型实测（zhanlu-ds，同两个任务，只改预算）

| 任务 | 8K 预算 | 16K 预算 |
| --- | --- | --- |
| A 做一个有质感的注册页 `index.html` | 110.2s，4 次工具调用，`load_skill=design-taste-frontend` | **62.4s**，2 次调用，`load_skill=frontend-design` |
| B 给仓库写一个 CHANGELOG→发布说明 skill | 99.3s，12 次调用，`load_skill=write-a-skill` | 96.6s，23 次调用，`load_skill=write-a-skill` |

能说的和不能说的都写清楚：

- **skill 加载正常**：两个预算下任务 B 都命中 `write-a-skill`（它在 8K 下本来就在索引里）。
  16K 这次还额外读了仓库里已有的 `workflow-authoring/SKILL.md` 与
  `genericagent/core/skills.py`，然后才动手写。
- **速度**：A 快了 47.8s，B 基本持平（-2.7s）。单样本、真实网络的模型调用，
  不足以证明"预算越大越快"；**能下的结论只是"没有变慢"**。
- **调用次数**：A 从 4 降到 2，B 从 12 升到 23。B 的 23 次里有一半是在仓库里探路
  （找已有 skill 约定、确认 CHANGELOG 是否存在），属于任务本身的不确定性，不是预算造成的。
- **一个副作用（已清理）**：16K 这次把 `SKILL.md` 写进了仓库真实的
  `skills/release-notes/`，而不是工作区 `temp/ab_code_task4/`。这是探针环境的问题
  （AGENTS 允许 model 用绝对路径），不是产品缺陷；跑完已删除，工作区干净。

### 4.1 同题 A/B：同一任务、同一模型，只改预算

任务 B（写 CHANGELOG→release notes 的 skill），单轮：

| 指标 | 16K 预算 | 8K 预算 |
| --- | --- | --- |
| 首次 API `input` token | **22,651** | **21,591** |
| 耗时 | 119.4s | 78.3s |
| 工具调用 | 23 | 20 |
| `load_skill` | `writing-skills` | `write-a-skill` |

- **确定性结论**：16K 索引每轮多 **1,060 token**。这与系统提示字符差
  （18,975 → 23,446，即 +4,471 字符 ≈ 1.1K token）完全对得上。
- **不能下的结论**：耗时。这组是 16K 更慢（119.4 vs 78.3），但上一组两轮实验里
  16K 反而更快（A：62.4s vs 110.2s）。**单样本、真实网络的模型调用，耗时波动远大于
  1K token 的影响**，只有 token 这一项是可重复的。
- **两种预算下模型都加载了 skill**（`writing-skills` / `write-a-skill`），
  说明渐进式披露的 L2 路径正常；选哪个是模型自己的判断，不是预算决定的。

## 6. 取舍与风险（如实说明）

1. **索引翻倍 = 每轮系统提示多约 1.1K token**（18,975 → 23,446 字符）。
   换来的是 19 个 skill 从"只有名字"变成"有完整描述"。对 200K 窗口的模型这是零头；
   但对小窗口模型（32K 级）就不划算，用 `GA_SKILL_LISTING_CHAR_BUDGET=8000` 可以退回旧预算。
2. **子 agent 也吃这份索引**（`workflow/child_agent.py` 同样调 `build_skill_prompt()`），
   所以每个子 agent 也多 ~1.1K token。若以后并发很多子 agent，可以按角色给不同预算。
3. **单条 400 字符上限仍是硬约束**：预算提到 16K 后，9 条长描述仍在压缩
   （`archify` 652、`ui-ux-pro-max` 928 这类），只是触发器句被保住了。
   想更完整就调 `_SKILL_DESC_CAP`，但那是"用预算换细节"的另一笔账，本轮没动。
4. **16384 是拍的值**：不是从窗口推出来的（CC 是按 `窗口 x 4 x 0.01` 算）。
   按 CC 的公式，200K 窗口给的就是 8000；GA 选择 2 倍，是因为本机 skill 数（51）
   明显多于 CC 的典型场景。真正的自适应留到以后（按模型窗口推导）。

## 7. "省 token"这件事，直接回答

- **结构上省**：51 份全文 ≈ 10.6 万 token，索引 ≈ 3.2K token，实际只加载命中的 1 份（≈750 token）。
  这就是渐进式披露的收益，和预算 8K/16K 无关——预算只决定"索引写多详细"。
- **提示词里没有"省 token"这句话**：`assets/sys_prompt.txt` / `sys_prompt_en.txt` 里没有任何
  token 相关的措辞；`[Available Skills]` 段的引导语说的是"索引只是索引，加载的才是权威"。
  唯一的节约指令在 L2：`Read only the reference you need with file_read.`
- **模型也没有"报账"**：实测两轮 transcript 里模型没有说"我省了多少 token"，
  它只是照 L2/L3 的方式按需读（任务 B 读了 3 个文件就收手，没有把整个仓库读一遍）。
  想统计真实的省量，得看 `[Cache] input=... cached=...` 这类运行时数字（见 §4）。
