# 工作流 Schema 安全渲染调研与实施

日期：2026-10-02

## 背景

真实运行任务“使用 5 个 subagent 搜索 OpenAI 利用 GPT 模型解决数学猜想的新闻，交叉验证真实性，最后形成 docx 文档”时，DeepSeek 生成的计划包含如下 schema 引用：

```json
{
  "schemas": {
    "research/source_1.json": { "type": "object" }
  },
  "schemaRef": "research/source_1.json"
}
```

GA 原渲染器把 schema key 直接拼进 JavaScript 变量声明：

```js
const research/source_1.json = { ... }
```

这会在任何 subagent 启动前触发 `SyntaxError: Missing initializer in const declaration`，因此问题不是 DeepSeek 响应速度，也不是 Tavily 调用失败，而是计划脚本渲染边界没有把模型字符串当作不可信数据处理。

## 对 Step-Code workflow 的调研结论

Step-Code 的 `WorkflowAgentOptions` 直接接收 `schema?: unknown`。schema 作为 JSON 数据进入 workflow runtime，不会把 schema 名称拼成 JavaScript 标识符。runtime 负责结构化输出提示、JSON Schema 校验、最多 3 次有界重试，并在最终失败时让 workflow 失败。其原则是：

> schema 是数据，不是代码标识符。

Step-Code 还使用 JSON-only workflow 契约、显式 schema、边界 runtime 校验和失败闭环；提示词只是指导，不是安全边界。

## 方案决策

### 1. 渲染器采用 schema registry

GA 生成一个对象注册表：

```js
const __workflowSchemas = Object.freeze({
  "research/source_1.json": { "type": "object" }
})
```

agent 调用使用：

```js
schema: __workflowSchemas["research/source_1.json"]
```

schema key 可以包含路径、中文、空格、连字符和点号；它们只作为对象属性名使用。原始 `schemaRef` 不被改写成 JavaScript 标识符。

### 2. validator 负责契约完整性

计划校验继续严格检查：

- `schemaRef` 必须是非空字符串；
- `schemaRef` 必须存在于 `schemas` registry；
- schema 必须是 JSON 可序列化的对象或布尔 schema；
- schema 数量和大小应受限；
- 未知 schema 引用必须在执行前拒绝。

不要因为 key 看起来像文件路径就拒绝；路径型 key 在 registry 访问模式下是安全的。

### 3. 提示词作为软约束

planner 提示明确要求使用逻辑 schema 名称（如 `SOURCE_SCHEMA`、`VERIFICATION_SCHEMA`），不要把 artifacts、writeScope 或 deliverables 路径当作 schemaRef。但提示词不能替代渲染器和 validator 防护。

### 4. 执行前脚本检查

最终计划脚本应在进入 workflow worker 前做语法预检；至少要保证 schema registry 引用、变量声明和脚本大小合法。当前首要修复先消除 schema key 进入 JS 标识符的根因，再补充脚本编译预检。

## 验收标准

1. 任何包含 `research/source_1.json`、中文或带空格 schema key 的计划都能生成合法 JavaScript。
2. 不存在的 schemaRef 在计划阶段得到 `undefined_schema`，不会进入 runtime。
3. schema 仍由 runtime 进行结构化输出校验，不能通过改名绕过。
4. 真实 Ink UI 测试中，5 个 Tavily research agent、交叉验证 agent 和 DOCX writer 均实际执行。
