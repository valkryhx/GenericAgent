## 1. 背景与问题

当前 GA 的「运行配置」有三种形态，各自读取方式不同：

1. **YAML 配置文件**：`llm.yaml` —— 已有成熟解析（`paths.resolve_llm_config_path()` / `llm_config_candidates()`），
   顺序为 `GA_LLM_CONFIG` 显式路径 → 源码仓库根 → 每用户配置目录（Windows `%APPDATA%/GenericAgent`），
   且支持字符串值里的 `${ENV_VAR}` 插值。这是**最规范的样例**，env 文件化应尽量对齐它。
2. **JSON 设置文件**：`settings.json` / `hooks.json` / `mcp.json` —— `hooks/config.py::discover_hook_files()`
   有多级发现（project `.genericagent/`、user `~/.genericagent/` 等）；`model_proposed_goals` 也读 `settings.json`。
3. **散落的进程环境变量**：50+ 个 `GA_*` 开关/参数，靠各模块直接 `os.environ.get("GA_XXX")` 读取，
   **没有统一注册、没有单一事实源、没有统一的 `.env` 载体**。`GA_PROPOSE_GOAL_ENABLED` 就是这一类的新增者。

问题：

- 功能开关/配置散落在业务代码字符串里，**难发现、难审计、难对外文档化**；
- 发布包（wheel 安装）后，用户缺少一个「明确的、相对安装位置解析」的地方去设置这些开关；
- 同类开关命名/默认/解析规则不统一，容易各写各的。

## 2. 现状盘点

### 2.1 配置来源优先级（现状）

| 类别 | 显式覆盖 | 源码仓库 | 发布包（wheel） | 备注 |

### 2.2 散落的 GA_* 环境变量（抽样，实际 50+）

### 2.3 发布链路（现状）

- `scripts/build_release.ps1`：把 `assets/` 逐文件**镜像**到 `genericagent/resources/assets`（只拷贝已存在于
  resources/assets 的文件，避免把大资产打进 wheel），再 `python -m build` 出 wheel。
- `pyproject.toml [tool.setuptools.package-data]`：`genericagent.resources` 已包含 `assets/*.json`、

- 结论：**新增的 env 模板若要随包发布，必须进 `genericagent/resources/` 且登记进 `package-data`**，
  并在 `build_release.ps1`/audit 里校验其存在。

## 3. 目标设计（方案）

### 3.1 单一配置入口：一个 `.env`（分层）

引入**一个统一 `.env` 文件**作为「运行开关/配置」的载体，同时保留「进程环境变量优先」的顶层覆盖语义：

优先级（高 → 低）：
1. **真实进程环境变量**（进程内已存在，最高；便于 CI/临时覆盖，不落盘）；
2. **显式指定的 env 文件**：`GA_ENV_FILE=/abs/or/relative/path.env`（相对路径按「当前工作目录」解析）；
3. **用户级 env 文件**：`<user_config_dir>/ga.env`（Windows `%APPDATA%/GenericAgent/ga.env`）；
4. **随包发布的默认模板/默认值**：`genericagent/resources/ga.env.example`（**只作示例/文档，不自动加载**）。

> 与既有 `llm.yaml` 发现顺序同构：显式覆盖 → 用户目录；`.env` 取代「散落 env」，不取代 `llm.yaml`
> （`llm.yaml` 是结构化多值配置，继续走 YAML；`.env` 只放 K=V 型开关/标量）。

### 3.2 读取实现：集中一层 `genericagent/config/env.py`

新增一个薄模块（名字待定），职责只有一个：**加载并缓存 env 文件，把值注入 `os.environ`（不覆盖已存在项）**，
再暴露 `get(name, default)` / `get_bool` / `get_int` / `get_float` 访问器。

- 加载时机：在 `paths.py` 被导入之后、任何业务模块读取 `GA_*` 之前（建议在 `genericagent/__init__.py`
  或 `ga_cli` 启动早期调用一次 `load_env_files()`）；也可在图省事时于访问器首次调用时惰性加载。
- **不覆盖已存在的进程环境**（`os.environ.setdefault` 语义），保证「进程 env 覆盖 .env」。
- 解析规则对齐常见 `.env`：`#` 注释、`KEY=VALUE`、可选引号、行尾 `\r` 清理；**不支持**复杂 shell 展开
  （保持简单、可预测；需要插值就写清楚）。
- **相对路径明确读取**：`GA_ENV_FILE` 若为相对路径，`(Path.cwd()/value).resolve()`；并支持相对「仓库根/安装根」。

### 3.3 哪些变量进 `.env`、哪些不进

- **进 `.env`（可配置开关/标量）**：功能开关、阈值、超时、并发、调试开关等，例如
  `GA_PROPOSE_GOAL_ENABLED`、`GA_WORKFLOW_GUARD_STRICT`、`GA_HOOKS_DISABLED`、`GA_MCP_DEBUG` 等。
- **不进 `.env`（运行期注入 / 身份类）**：`GA_PROJECT_ROOT`、`GA_DATA_DIR`、`GA_WORKFLOW_WORKSPACE_ROOT`、
  `GA_CONFIG_DIR`、`GA_TOOL_CWD`、`GA_PARENT_SESSION_ID`、`GA_TASK_ROOT`、`GA_TEAM_KEY`、`GA_LAUNCH_CWD` 等
  —— 这些由启动器/父进程/子进程按运行上下文注入，写进 `.env` 反而会造成身份错乱。在纪要里明确白名单/黑名单两类。

### 3.4 迁移原则

1. **只迁移「配置型常量」，不动「运行期注入型」**（见 §3.3 黑名单）。
2. **保留进程 env 的完全兼容**：迁移后 `os.environ.get("GA_X")` 仍能读到（因为加载层把 `.env` 注入 `os.environ`），
   故可**逐模块渐进迁移**，不必一次改 50 个点。
3. **业务代码不直接读裸字符串**：新代码改用 `env.get_bool("GA_X", default)`；老代码先不动，后续按模块清理。
4. **默认值集中在注册表**：在 `env.py` 里维护一张 `KNOWN_CONFIG` 表（name → 类型/默认/说明），作为文档与校验单一事实源。
5. **`GA_PROPOSE_GOAL_ENABLED` 作为第一个试点**：默认关（已定），迁到 `.env` 载体，但**行为不变**。

## 5. 发布包可读性保证（重点）

1. `ga.env.example` 必须进 `genericagent/resources/`，并登记 `package-data`（否则不进 wheel）。
2. `build_release.ps1` 第 5 步 wheel 审计的 `required` 集合硬校验该文件存在。
3. 运行期查找顺序（发布包场景）：`GA_ENV_FILE` → `%APPDATA%/GenericAgent/ga.env`；
   **绝不**把 `.env` 写进 site-packages（只读、且升级会被覆盖）—— 与 `llm.yaml` 现状一致。
4. 升级 wheel 不得覆盖用户 `ga.env`（它本就位于用户配置目录，不在包内）。
5. 交付前必做：干净 venv 安装 → 写入 `ga.env` → 断言生效（见 E3）。

## 6. 风险与取舍

- **兼容风险**：迁移只读取访问器、不删除旧 `os.environ` 用法，风险低；但若某处 `os.environ["GA_X"]` 走 KeyError 硬取，
  需逐个改为 `.get`。
- **相对路径歧义**：`GA_ENV_FILE` 相对路径需明确「相对 cwd 还是相对安装根」，本计划取 **相对 cwd**（显式、可预期），
  并在文档写死；仓库内开发时默认查仓库根，安装后默认查用户配置目录。
- **安全**：`.env` 可能含密钥；`ga.env` 放**用户配置目录**、加进 `.gitignore`，示例模板里不写真实密钥。
- **不做过度设计**：不引入第三方 `python-dotenv`（除非确有需要），自写 ~80 行解析即可，避免新依赖进发布包。
- **与 `settings.json` 的关系**：`model_proposed_goals` 这类「同意类设置」继续走 `settings.json`（与 CC 对齐），
  `.env` 只承载「运维开关/标量」，两者不混。
