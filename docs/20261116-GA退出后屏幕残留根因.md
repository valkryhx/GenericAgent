# `ga` 退出后屏幕不干净 —— 根因与修复（2026-11-16）

**状态：** ✅ 已修复并真机验证（863 tests + typecheck PASS）
**主修复：** `frontends/ink/ui/src/App.tsx`（`cleanupTerminalOnce` 顺序）、`frontends/ink/ui/src/stdoutCursorPark.ts`（`dispose` 不再清空 buffer）
**探针：** `tests/probes/python/_probe_exit_screen_residue.py`、`frontends/ink/ui/probes/exit_path_trace.ts`

---

## 0. 结论先行

> **退出清理序列一直没写出去，而且写出去的那一份还会在「回到主屏之后」再把光标挪走。**

两个独立缺陷叠在一起，都出在 `cleanupTerminalOnce()` 的**顺序**上：

1. 旧顺序是 `unpark → flush → dispose → 写清理序列 → flush`。
   `CursorParkWriter.flush()` 在 `disposed === true` 时**直接丢弃缓冲区**，于是
   `ESC[?1049l`（回主屏）、`ESC[?1006l`（关鼠标）、`ESC[?25h`（显示光标）
   **一个都没到终端**。
2. 即使把它们写出去，用的是 `flush()`（默认 `park = true`），会在
   `ESC[?1049l` 之后再发 `ESC[4A ESC[5G`——**在主屏上把光标挪到 composer 那一行**。

用户看到的两句话——「光标没回退到最前面」「输入框下边的线短了一截」——正好对应这两条。

---

## 1. 症状

用户描述（Windows Terminal，`ga` 默认 fullscreen 模式）：

| 现象 | 实际含义 |
|---|---|
| 退出后光标没回到最前面 | 光标停在主屏的 composer 行（`ESC[?1049l` 之后被 park 挪过去） |
| 输入框下边的线短了一截 | alt-screen 里的内容没被 `1049l` 清掉，残留在主屏上 |
| 画面不整洁 | 上一行的组合 |

「Claude Code 好像也是这样」——用户观察到的可能是**不同的原因**（CC 有它自己的退出
路径），本轮只负责 GA。

## 2. 真机测量

### 2.1 探针

`tests/probes/python/_probe_exit_screen_residue.py`：真 PTY 起 `./ga`，输入 `abc`，
按两次 Ctrl+C（GA 的语义：一次提示、二次退出），然后用 pyte 回放整段输出，
读回**终端最终状态**。

为什么不看 GA 自己的写入日志：ConPTY 会改写序列（见
`docs/20261116-GA-中文输入法光标不跟输入框根因.md` §2.1），只有回放才知道屏幕上是什么。

### 2.2 修复前

```
[D 第二次 Ctrl+C 之后（应已退出）]
  光标 = (35, 6)          ← 停在 composer 行，不是主屏首行
  含边框行 = 2            ← 「────」两行还留在屏上
  非空行 = 6

=== 退出序列证据 ===
  回到主屏 ESC[?1049l    出现 0 次     ← 关键：一次都没有
  进备用屏 ESC[?1049h    出现 1 次
```

`1049l` 出现 **0 次**，等于「进得去、出不来」：终端以为还在 alt-screen，而内容已经
画在主屏上了。

### 2.3 修复后

```
[D 第二次 Ctrl+C 之后]
  光标 = (0, 0)           ← 主屏首行首列
  含边框行 = 0
  非空行 = 0

  回到主屏 ESC[?1049l    出现 1 次
```

### 2.4 关键补充：不能为了「干净」清掉用户的历史

同一轮还测了「启动前主屏已有内容」的场景（临时脚本，已清理）：

```
[A TUI 运行中]  PRE-EXISTING 行=0   composer边框=2
[B 退出后]      PRE-EXISTING 行=2   composer边框=0   光标=(2,0)
    PRE-EXISTING-LINE-A
    PRE-EXISTING-LINE-B
```

用户原有的两行**完好保留**，光标落在它们之后。**这是正确行为**：退出时把主屏
`ESC[2J` 一把清掉，会连带毁掉用户自己的终端历史。

所以本次**不**加「退出时清屏」。用户看到的「不整洁」是 alt-screen 泄漏造成的假象，
修好泄漏后画面自然干净。

## 3. 修复

### 3.1 `App.tsx` 的 `cleanupTerminalOnce`

```diff
- cursorPark?.unpark()
- cursorPark?.flush()
- cursorPark?.dispose()
- ...写 clear / cleanup...
- cursorPark?.flush()        // 已 disposed → 被丢弃

+ cursorPark?.unpark()       // 先把光标移回帧底
+ ...写 clear / cleanup（含 1049l）...
+ cursorPark?.unpark()       // = flush(false)：写出去，但不 park
+ cursorPark?.dispose()
```

注释里写清了每一步的理由与实际字节证据（`\u001b[?1049l \u001b[4A\u001b[5G` 这个
顺序就是「主屏光标被挪走」的直接证据）。

### 3.2 为什么用 `flush(false)` 而不是 `flush()`

`flush(true)` 会在帧末 park。退出时终端状态已经交还，再移动光标就是越权——而且
`1049l` 之后的行号是**主屏**的行号，park 用的却是 alt-screen 的相对位移，
两者根本不是一个坐标系。

### 3.3 `dispose()` 的语义澄清

`dispose()` 仍然丢弃未写出的 buffer（单测 `dispose stops parking and drops buffered
bytes` 钉的就是这一条——退出瞬间没渲染完的帧不该再污染屏幕），只是注释里说明了
**清理序列必须在 dispose 之前 flush**，否则会被这条规则吞掉。

## 4. 回归测试

`stdoutCursorPark.test.ts` 新增 `flushUnpark writes the buffered cleanup bytes without
parking`，同时钉住两条不变量：

- 清理序列**必须**出现在终端字节里（旧缺陷 1）；
- 清理序列之后**不得**出现 `ESC[nA ESC[mG`（旧缺陷 2）。

这两条任何一条回归，真机上的画面就会退回「光标不回位 / 下边线短一截」。

## 6. 方法论

1. **「没写出去」和「写出去了但写错」是两种 bug，症状很像。** 第一次看到
   「光标停在 composer 行」，直觉会去查 park 的坐标；实际是清理序列整段被丢了。
   先用探针确认**目标字节在不在**，再查它的内容对不对。

2. **顺序 bug 只有真机能抓。** 单测里 `flush()` 在被 dispose 后丢弃 buffer 是
   刻意设计（有测试保护），`cleanupTerminalOnce` 的调用顺序错了却没有任何单测覆盖
   —— 因为它是「多个正确组件的错误组合」。这是集成层的盲区，只能靠端到端回放。

3. **「让画面干净」和「别毁用户的东西」会冲突。** 最省事的修法是退出时 `ESC[2J`，
   但那会连带清掉用户滚上去的历史。**先问「用户的原有关内容该不该保留」**，
   再决定要不要清屏。本轮实测证明保留是对的。

---

## 7. 分析边界

- 只在 Windows Terminal / ConPTY 上验证；其它终端的 alt-screen 语义未逐一实测。
- `ESC[?1049l` 之后仍会写一次 `ESC[?25h`（显示光标），这是 `terminalCleanup.ts`
  既有行为，无害。
- 未改 `terminalCleanup.ts` 的序列内容，只改了写出时机与是否 park。
