## 3. 关键事实订正（务必先读，避免重复犯错）

**错误说法（已纠正）：** “GA 的 `spawn_agent` 是同步的、没有异步后台模型，所以阶段 2 无意义。”

**源码核实后的正确事实：**
1. `spawn_agent` **默认 `background=True`**，立即返回 `{"status":"started", pid, run_id, task_dir, state_path, ...}`（`genericagent/core/handler.py::do_spawn_agent`）。GA **本来就有异步后台子 agent**。
2. GA **有中断信号**：`GenericAgent.abort()` 置 `stop_sig=True` 并 `cancel_current_request()`；`run()` 主循环 `if self.stop_sig: break` 退出；另有 `_stop` 文件 watcher 触发 abort（`consume_file(task_dir,'_stop')`）。
3. **在途查询现成**：`SubagentManager.list_descendants(parent_session_id)`；状态字段 `turn_status ∈ {pending,running}`、`process_status ∈ {alive,exited}`（`genericagent/agents/manager.py`）。

**所以：** 阶段 2/3「建立在异步后台任务 / 中断事件之上」这个前提，GA **是满足的**。真正的门槛不是“有没有异步任务/中断”，见 §4。

## 4. 阶段 2/3 的真实依赖分析（关键决策依据）

CC 的阶段 2-B（定时 check-in）和阶段 3（中断后自动续跑）本质相同：**到点主动往会话塞一条消息，让模型在没有用户输入时再跑一轮**。

GA 的 `run()` 是「每用户回合同步」模型：`task_queue.get()` 等用户下一条消息 → 起一个 handler → 跑 `agent_runner_loop` → 回合结束。**GA 没有“无用户消息也能定时唤醒模型”的调度器。**

因此依赖要拆开看：

| 子项 | 依赖 | 成本 | 判断 |
| --- | --- | --- | --- |
| **阶段 2-A**：Stop 门禁检测「本会话有在途后台子 agent」→ **跳过本轮求值、放行回合结束** | 仅需 `list_descendants(session_id)` 判断 `turn_status∈{pending,running} & process_status==alive` | 小、可单测 | **建议先做**。不做则后台子 agent 还在跑时，goal 求值会误判 not-met 把主模型卡住（阶段 1 的真实缺陷） |
| 阶段 2-B：定时 check-in 注入（CC `Du=30min`、退避 `2^min(count,2)`、idle 上限 3） | 需要「定时唤醒调度器」：后台线程/定时器在到点时 `put_task` 或直接注入下一轮 | 大（新增唤醒通路 + 退避状态机 + 生命周期/取消） | 暂缓，待单独架构决策 |
| 阶段 3：中断后自动续跑（CC `Us=[1,5,15]min`、最多 3 次） | 同样需要「定时唤醒调度器」；且 GA 里 abort 是**用户主动停**，自动续跑与用户意图冲突，UX 需先定 | 大 + 方向未定 | 暂缓，待方向确认 |

**一句话：** 2-A 是阶段 1 的正确性补丁（该做）；2-B/3 是“无消息唤醒”调度器的功能（先设计再动）。

## 5. 阶段 2-A 已落地（实现要点 + 一个真实 bug 修复）

已实现落点（4 处代码 + 1 个测试文件）：

1. `genericagent/core/goal_evaluator.py`
   - 新增 `_IN_FLIGHT_TURN_STATUSES={pending,running}`、`_TERMINAL_PROCESS_STATUSES={exited,shutdown,killed}`、
     `is_in_flight_agent_state(state)`、`has_in_flight_agents(agent, handler=None)`。
   - 判定口径：`process_status` 不在终态、且 `turn_status in {pending,running} or process_status == 'alive'` 即为在途。
   - 任何异常一律返回 False（fail-open，绝不让查询 bug 永久 defer 把会话卡死）。
2. `genericagent/core/handler.py::run_stop_gate`
   - `goal_active` 时先判 `goal_defer = has_in_flight_agents(agent, self)`；
     defer 则置 `data['goal_defer']=True`、调 `agent._record_goal_deferred()`、**不注入 transcript**；
     `if goal_active and not goal_defer` 才做阶段 1 的三态记账。
3. `genericagent/hooks/runtime.py::run_event`
   - `skip_dynamic = event=="Stop" and (phase=="user_turn_end" or payload.get("goal_defer") is True)`
     —— 在途时连 `goal:stop` 动态 hook 都不跑（静态 Stop 如 beep 不受影响）。
4. `genericagent/core/app.py::_record_goal_deferred`
   - 写 `goal_status(met=False, reason='deferred', iterations=当前值)`，不改 `active_goal`、不 bump iterations。
5. `tests/test_goal_phase2a.py`（11 passed）：状态判定 / manager 查询 / defer 不阻塞 / 非 defer 正常求值 / runtime 跳过。

⚠️ **本会话发现并修复的真实 bug（很关键，否则整个 2-A 是死代码）**：
`run_stop_gate` 里 `agent = self._hook_agent()` 拿到的是 `GenericAgent`，而 subagent manager 工厂
`_get_subagent_manager()` 实际挂在 `GenericAgentHandler` 上（它需要 per-session 的 `session_data_dir` 与 team 身份）。
原实现只对 `agent` 取工厂 → 永远拿不到 manager → `has_in_flight_agents` 恒为 False，defer 从不触发。
修复：`has_in_flight_agents(agent, handler)` 优先从 `handler` 取工厂、`session_id` 回退到 `handler.parent.session_id`，
`run_stop_gate` 调用点传入 `self`；并新增两条单测锁定「工厂在 handler、agent 上没有」的线上形态。

真实 LLM 验证（`tests/real_goal_2a_stop_gate_e2e.py`，默认 `deepseek-v4.1-flash`，9/9 通过）：
真实 `GenericAgent` + 真实后台子 agent（`spawn_agent(background=True)`，子进程 sleep 45s）在途时直接调 `run_stop_gate`：
- 在途：`action='none'`（不阻塞）、prompt_runner 调用次数 0（真没求值）、jsonl 落 `goal_status(reason='deferred')`、`active_goal` 保留；
- 子任务结束后：`action='continue'`、prompt_runner 调用 0→1（真求值）、无 `evaluator_error`、产出可解析 verdict。

另一个真实探针 `tests/real_goal_2a_defer_e2e.py`（同类探针已并入） 验证 `has_in_flight_agents` 对真实 live 子进程：
spawn 后立即/5s 均为 True（turn=running, proc=alive），子任务完成转 `completed/waiting_reply` 后为 False。

**注意（沿用）**：不要动静态 Stop（beep）。只在“goal:stop 会话级 hook + 在途”时跳过。

> 说明：上一条所记的「整回合 e2e 跑 `put_task` 让模型自己 `spawn_agent`」路径不稳定（模型行为 + 回合时长不可控），
> 故 2-A 的验收以「真实 LLM + 真实子进程 + 直接驱动真实 `run_stop_gate`」为准，能精确命中 defer 分支且可重复。

### 7.1 阶段 2-B：deferral 定时 check-in（303 `m0671:120-340`）

- 常量：`Du=30`（默认 30 分钟，可被 `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` 覆盖）、`Uu=2`、`Lu=3`（idle 上限）。

- `Bi(condition, deferredMs, tasks)` 生成 check-in 文案：
  “Goal check-in: background work still running …” / “… no longer running … Continue toward the goal.”
- `ji()` 维护 `deferredSince / checkinCount / isNewRun`；`fn/as/Wu` 是 idle 定时器：到点 `deliver(checkinText)`，
  `idleCheckinCount+1`，达到 `Lu=3` 后只重排 tick、并附
  “idle check-ins paused until your next message … Claude Code won't wake this session for another check-in…”。
- 遥测：`tengu_goal_checkin_injected`、`goal_checkin`（含 `idle_cap_reached / fire_failed / plan_failed / arm_failed`）。
- 开关：`tengu_saffron_wren`（默认开）+ `ls()`。

### 7.2 阶段 3：中断后自动重试（303 `m0671:340-390` + `Yi()`）

- 常量：`Us=[60000,300000,900000]`（1/5/15 分钟）、`Ds=Us.length=3`（最多 3 次）。
- `Yi()`：回合以 `kind==="retry"` 结束（如 `image_error / malformed_tool_use_exhausted / api_error(rate_limit)`）时，
  `$i → Ki → setTimeout(Qu, delay)` 排 `pendingGoalReprompt`。
- `Qu()`：到点注入 “Goal check-in: continuing after the last turn ended early” +
  `${condition} is still active. The last turn ended before the goal could be evaluated: ${cause}. Continue toward the goal.`，
  记 `goal_interruption`。
- `retries >= Ds` → `Goal paused after 3 automatic retries · {cause} · send a message to continue`（`gave_up`）；
  非 retry 类（model_error / hook_stopped / 各类 usage/rate limit）→ `Goal paused · {cause} · send a message to continue`（`paused`）。
- 开关：`ls()`；非交互会话不自动续。

### 7.3 为什么 GA 暂缓（依赖没变）

2-B 与 3 本质相同：**在没有用户消息时，定时把一条消息塞回会话让模型再跑一轮**。
GA 的 `agent.run()` 是“每用户回合同步”：`task_queue.get()` → 跑一个 handler → 回合结束，**没有“无消息定时唤醒”的调度器**。
所以二者都需要先补一个可取消、有 idle 上限、opt-in 的唤醒调度器（建议 `GA_GOAL_WAKE` 开关），是独立架构项，不是小补丁。
2-A（defer-skip）已做，是“有后台任务时**别误判**”，与 2-B/3 的“主动**唤醒**”是两回事。
