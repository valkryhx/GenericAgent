# CC 2.1.303 的会话 / 生成物按目录存放机制 vs GA 现状调研

> 目标读者：GA 维护者。本文回答两个问题，并对照 GA 现状指出差距：
> 1. **Claude Code（以 2.1.303 为准）怎样把 session 按项目分开存放？是什么机制？**
> 2. **CC 的「生成物」（计划、workflow、子 agent 产物、shell 快照等）怎样按目录区分？**
>
> 证据基准：`D:\git_repos\claude_hack\reconstructed303\deminified\`
> （303 去混淆产物；行号可 `grep -n` → `sed -n` 回查）。
> 读法遵守 claude_hack 仓库 `AGENTS.md` §10：只做「grep 定位 → sed 取窗口」。
>
> 结论先行：**CC 的模型是「一份全局配置目录 + 按 cwd 派生 projectKey 分桶」**，
> 会话正文、子 agent 转录、workflow 运行数据**全部**落在 `projectKey` 目录下；
> 而 plans / workflows(定义) / shell-snapshots / memory / teams 等处**是全局的**，
> 不按项目分。GA 现在把「会话 + 一切产物」平铺在一个安装目录的 `temp/` 下，
> 既没有按项目分桶，也没有区分「全局」与「项目级」。

## 1. 一句话总览

```text
<CLAUDE_CONFIG_DIR 或 ~/.claude>/          ← 全局配置根（config home）
├── projects/                              ← 「按项目」分桶的根
│   └── <projectKey>/                      ← 由 cwd 派生
│       ├── <sessionId>.jsonl              ← 主会话转录（每会话一个文件）
│       └── <sessionId>/
│           └── subagents/
│               ├── agent-<agentId>.jsonl  ← 子 agent 转录
│               └── workflows/<runId>/…    ← workflow 运行数据
├── plans/                                 ← 全局（不分项目）
├── workflows/                             ← 全局（workflow 定义/脚本）
├── shell-snapshots/                       ← 全局
├── memory/personal/                       ← 全局
├── teams/                                 ← 全局
└── …
```

**关键点：projectKey 只由「当前工作目录」决定**，不是用户手动选的项目，
也不是安装路径。换到另一个目录启动 CC，就会自动读到另一个 `projects/<projectKey>/`。

## 3. projects/ 与 projectKey：会话按项目分桶的核心机制

### 3.1 projects 目录

**源码**：`m0081_0xe583228.js:746-750`、`m0282_0xe97ca62.js:21-23`

```js
function Vm() { return S(Pe(), "projects"); }          // m0081:746
function Xp() { return i(Pe(), "projects"); }          // m0282:21-23
```

`iS(cwd, projectsDir)`（`m0081:756`）= `join(<projectsDir>, cE(cwd))`：**一条会话转录的目录 =
projects/ + projectKey**。

### 3.2 projectKey = 清洗后的 cwd

**源码**：`m0081_0xe583228.js:695-707`

```js
var $he = 200;

function k(e)  { return e.replace(/[^a-zA-Z0-9]/g, "-"); }   // 非字母数字 → "-"

```

**实例**：cwd = `D:\git_repos\ga\GenericAgent`
→ `k()` → `D--git-repos-ga-GenericAgent`（盘符后的 `:\` 变成 `--`）。
这不是猜测：`~/.claude/projects/` 下的真实目录名就是 `D--git-repos-...` 这种形态。

| 规则 | 证据等级 | 坐标 |
| --- | --- | --- |
| 非 `[A-Za-z0-9]` 全部替换为 `-`（含 `/`、`\`、`:`、`.`, 空格、中文） | S | `m0081:701` |
| 名字 ≤200 字符原样；超长 → 前 200 字符 + `-` + cwd 哈希 base36 | S | `m0081:695-706` |
| 清洗**不**做大小写折叠：大写异写的同一目录会得到不同 key；跨大小写视为同一目录由 §3.4 的比较函数做，key 生成本身不保证 | S | `m0081:701` |

### 3.3 派生确实基于 **realpath(cwd)**

**源码**：`m1407_0xfd5b0eb.js:2347-2367`

```js
function Jt(e) { let s = pn(e ?? "."); try { n = dn(s); } catch { n = s; } return $n(n); }

```

- `Jt` 先 `path.resolve`，再 `fs.realpathSync`（`m1407:2351 import realpathSync`），
  **软链接/短路径别名会归一到同一 key**；
- 失败时回退到 resolve 结果（fail-open，不抛错）。

### 3.4 覆盖变量 `CLAUDE_CODE_PROJECT_DIR_NAME` 与「固定项目目录」

**源码**：`m0020_0xe47a7e6.js:74-83`

```js

  I = /^(?:con|prn|aux|nul|com[0-9]|lpt[0-9])$/i;
```

| 规则 | 证据等级 | 坐标 |
| --- | --- | --- |
| 覆盖值须匹配 `^[A-Za-z0-9_-]{1,64}$` | S | `m0020:75` |
| 拒绝 Windows 设备名 `con/prn/aux/nul/comN/lptN` | S | `m0020:76` |
| **只有设置了 `CLAUDE_CONFIG_DIR` 才认这个覆盖**（`o() || BQ()`） | S（推导） | `m0020:83` |
| 非法值 → 静默回退到 cwd 派生 key | S | `m0020:79-81` |

→ 设计意图是「**共享配置根**（多人/多容器同一 CLAUDE_CONFIG_DIR）时，各端用显式名字
而不是各自机器上不同的 cwd 去落桶」；单机默认情况下**从不使用**这个名字。

| 事实 | 证据等级 | 坐标 |
| --- | --- | --- |

`function eye(){ let e=m(); return e ? e.sessionProjectDir : n().identity.projectDir(); }`），
resume 时用**会话记录的那个目录**，而不是「现在正好在哪个 cwd」。
这保证 `cd` 到别处后 resume 旧会话不会「另起一份」。

### 3.6 同 key 撞车检测（清洗是有损的）

`k()` 把 `/` `.` `:` ` ` `_` **全部**映射为 `-`，因此 `a/b` 与 `a-b`、`a_b` 会得到同一个 key。
CC 显式处理了这种情况（`m0081_0xe583228.js:709-735`）：

```js

  return pGe(r, t) !== pGe(i, t);        // 归一化后仍不同 → 是撞车而不是同一目录
}
async function RBr(e, n, t, r, i) {      // 用 realpath 再确认
  if (!N(e, n, t)) return !1;
  ...
  let o = await $_(n, i);

```

| 事实 | 证据等级 | 坐标 |
| --- | --- | --- |
| 先比清洗后的 key，再比「保留分隔符」的路径，两者都同才算**不是**同一目录（即判断为撞车） | S | `m0081:711-717` |
| 调用方可要求比较时统一小写（`t` 由调用方传入，非函数内自行判断平台） | S | `m0081:708-710,715` |
| 再经 realpath 复核（`m0081:718-734`），失败一律返回「不是同一目录」 | S | `m0081:718-734` |

这一层对 GA 的意义：**照抄 CC 的清洗规则就同样会撞车**，实现时要么加同款检测，
要么改用「可逆/带哈希」的编码（见设计文档 §4.2）。

## 4. CC 的「生成物」怎么放：分两类

CC 的产物**不是统一一个目录**，而是按「跟不跟项目走」分两类。

### 4.1 项目级：随 projectKey 走

| 产物 | 路径 | 证据等级 | 坐标 |
| --- | --- | --- | --- |
| 主会话转录 | `<projects>/<key>/<sessionId>.jsonl` | S | `m0282:63-68` |
| 子 agent（Task / in-process teammate）转录 | `<projects>/<key>/<sessionId>/subagents/agent-<id>.jsonl` | S | `m0282:78-88` |
| agent 转录的命名空间存储（SQLite 后端的同构表示） | `namespace:"transcript", projectKey, sessionId, agentId` | S | `m0282:106-125` |
| workflow 运行数据 | 挂在会话 `subagents` 之下（`subagents/workflows/<runId>`） | A（283 既有剖析，303 未逐行复核） | `claudecode283/extracted/dynamic-workflow-internals.md:514-562`；303 侧对应容器见 `m0282:78-88` |

要点：**子 agent / workflow 不另建一套「项目根」**，它们一律挂在
「该项目 → 该会话」下面。因此「同一项目第二次开新会话」看到的子 agent 转录
天然只属于那个会话；`/workflows` 列表要跨会话看，就按 `projectKey` 聚合。

### 4.2 全局级：与 cwd 无关，全部落在 config home 根下

| 产物 | 路径 | 证据等级 | 坐标 |
| --- | --- | --- | --- |
| 计划文件（plan mode） | `<config>/plans/` | S | `m0285:503`、`m0800:941` |
| workflow 定义 / 脚本 | `<config>/workflows/` | S | `m1063:134` |
| shell 快照（bash 环境持久化脚本） | `<config>/shell-snapshots/` | S | `m0459:168724`、`m0800:1335` |
| 个人记忆 | `<config>/memory/personal/` | S | `m0154:2663` |
| 团队 | `<config>/teams/` | S | `m0020:72-73`（`function fet(){ return u(Pe(), "teams"); }`） |

**为什么这些不分项目**：它们的生命周期/语义本来就跨项目——计划可以跨仓库讨论，
workflow 是可复用的定义，shell 快照是「同一台机器上同一个用户」的环境。
把它们放进 projectKey 桶里会制造重复。

### 4.3 CC 没有「产物输出目录」这回事

CC 里 agent 的代码执行与文件写入**直接落在当前 cwd（用户的项目目录）**，
CC 不另设 `cwd = <某 temp 目录>`。CC 自己的运行时文件则走 §4.1 / §4.2。
换句话说，CC 的划分是：

```text
用户项目目录  ← 工具/代码在这里读写（= cwd）
~/.claude     ← CC 自己的所有运行时数据（产物、计划、快照…）
```

GA 的做法是把「工具 cwd」和「运行时数据」混在同一个 `temp/` 里（见 §5），
这恰好是两者都丢掉了项目语义。

## 5. GA 现状：会话与产物都平铺在安装目录的 `temp/`

### 5.1 路径模型（`genericagent/paths.py`）

```python
RUNTIME_ROOT = PROJECT_ROOT if is_source_checkout() else user_data_dir()   # paths.py:70-73
TEMP_DIR     = RUNTIME_ROOT / "temp"                                       # paths.py:74
SESSIONS_DIR = TEMP_DIR / "sessions"                                       # paths.py:83
```

- 源码运行时 `RUNTIME_ROOT = PROJECT_ROOT`（`GA_PROJECT_ROOT` 或包所在仓库）；
- wheel 安装时 `RUNTIME_ROOT = %LOCALAPPDATA%/GenericAgent`。

**不论哪种形态，`RUNTIME_ROOT` 都是「GA 自己住在哪」，与「用户此刻在哪个项目目录」无关。**
而 `PROJECT_ROOT` 恰恰会被设成用户的项目目录（见 5.3），二者的含义在代码里混用。

### 5.2 实际落盘位置

| 内容 | 现状路径 | 坐标 |
| --- | --- | --- |
| 会话转录 | `temp/sessions/session_<uuid>.jsonl`（**单一扁平目录**） | `transcripts.py:17,90-91` |
| 会话列表 / resume | `temp/sessions/` + `.listing_cache.json` | `transcripts.py:332-375` |
| workflow 运行存储（run 索引、产物目录） | `temp/sessions/` 下（`WorkflowStore` 以 SESSIONS_DIR 为根） | `workflow/store.py:41,99`；`frontends/ink/bridge.py:281` |
| workflow 运行 workspace | `temp/workflow-runs/<runId>`（`default_workspace_root()`） | `workflow/workspace.py:30` |
| 隔离子 agent 工作区 | `temp/workflow_child_agents/<runId>/<jobId>` | `workflow/child_agent.py:39` |
| 模型原始响应日志 | `temp/model_responses/model_responses_*.txt` | `core/app.py:619`；`llm/core.py:1268` |

`ensure_runtime_dirs()` 只会建 `TEMP_DIR`、`temp/model_responses`、`SESSIONS_DIR`
（`paths.py:202-206`）——全部是「一个目录，所有项目共用」。

### 5.3 更隐蔽的问题：`PROJECT_ROOT` 的含义被拉成了两重

- `ga_cli/cli.py:19-30,72-89`：启动时把 `env["GA_PROJECT_ROOT"] = PROJECT_DIR`，
  其中 `PROJECT_DIR` 在「源码运行」下是**GA 仓库目录**，在「wheel 运行」下是**调用者的 cwd**；
  随后把 cwd 切到 `frontends/ink/ui`。
- `paths._discover_project_root()`（`paths.py:33-53`）直接读 `GA_PROJECT_ROOT`。

后果：

1. 从源码跑 `ga`：`PROJECT_ROOT` = GA 仓库，**无论用户在哪个目录启动**，会话与产物都进 GA 仓库的 `temp/`；
2. wheel 版：`PROJECT_ROOT` = 启动时的 cwd，于是「GA 安装」与「用户项目」被混成一个变量，
   `RUNTIME_ROOT`（= `user_data_dir()`）与 `PROJECT_ROOT` 在代码里被当成「同一个东西」交替使用；
3. `frontends/common/chatapp_common.py:3`、`frontends/terminal/continue_cmd.py:5,15,17` 用
   `RUNTIME_ROOT` 拼 `temp/sessions`；`frontends/desktop/fsapp.py:6-8,35` 用 `PROJECT_ROOT` 拼 `temp/`，
   并且 `fsapp` 启动时 `os.chdir(PROJECT_ROOT)`——**同一套目录，两种根，取决于哪个前端**。

### 5.4 工具 cwd 与「生成物」的关系

- 主会话 handler：`GenericAgentHandler(self, self.history, str(paths.TEMP_DIR), workspace_root=str(paths.PROJECT_ROOT))`
  （`core/app.py:1046`），系统提示里直接告诉模型
  `cwd = <TEMP_DIR> (./; tool scratch/output dir)`（`core/handler.py:2332-2333`）。
- 于是模型写文件的相对路径落在 **GA 安装目录的 `temp/`**，而不是用户项目；
  同时 `workspace_root = PROJECT_ROOT`，在源码形态下就是 GA 仓库——**用户的项目根本没参与**。
- 子 agent：`cwd=parent.task_dir, workspace_root=parent.task_dir`（`child_agent.py:971,990`），
  默认 `task_dir` 是 `temp/workflow_child_agents/...`。

### 5.5 `os.getcwd()` 在 GA 里不可靠

`transcripts.create_session(cwd=None)` 时写 `os.getcwd()`（`transcripts.py:107-117`）；
`ensure_agent_session` 也是 `cwd=os.getcwd()`（`transcripts.py:420`）。
但 Ink 前端启动时 `os.chdir(frontends/ink/ui)`（`cli.py:89`），所以会话里记下的 `cwd`
可能是 **GA 的 UI 目录**，而不是用户的项目目录。记录字段存在（`session_start.cwd`），
但**它没有被用来做分桶**，也没有被用来在 resume 时回到原目录。

| 会话落盘 | `<config>/projects/<key>/<sid>.jsonl` | `temp/sessions/<sid>.jsonl`（全局扁平） | 不分项目 |
| 子 agent 转录 | `<key>/<sid>/subagents/agent-<id>.jsonl` | 子 agent 共用父会话记录，无独立转录子目录 | 结构缺失 |
| workflow 运行数据 | 项目/会话下 | `temp/sessions/`（WorkflowStore 根） | 随会话一起平铺 |
| workflow 产物 | 运行专属目录 | `temp/workflow-runs/<runId>` | 不分项目 |
| 计划 / shell 快照 / 记忆 | 全局（`<config>/plans` 等） | 计划无独立目录；记忆 `RUNTIME_ROOT/memory`（全局 ✓） | 大体一致 |
| 工具 cwd | 用户项目目录（cwd） | `temp/`（GA 安装目录下） | 产物不进用户项目 |
| `workspace_root` | 无此概念；越界靠权限 | `PROJECT_ROOT`（源码=GA 仓库） | 语义混淆 |
| 项目名覆盖 | `CLAUDE_CODE_PROJECT_DIR_NAME`（校验 + 条件生效） | 无 | 可选补齐 |
| 撞车处理 | key 相等后再比原路径 + realpath | 无（因为还没分目录） | 实现时必须处理 |

## 7. 结论

1. **CC 按项目分桶的唯一钥匙是「当前工作目录」**：`realpath(cwd)` 清洗成 `projectKey`，
   会话、子 agent 转录、workflow 运行数据都进 `projects/<projectKey>/`。
   用户不需要「选项目」，换目录启动就是换项目。
2. **CC 同时保留了「全局层」**：plans、workflows(定义)、shell-snapshots、memory、teams
   放在 config home 根下，不按项目分。**项目级 / 全局级是两套目录，不是一套目录里的子目录名。**
3. **CC 的产物输出就是用户的 cwd**，CC 不替用户另设 scratch 目录；
   自己的运行时数据全在 `~/.claude`。GA 现在把这两者合成 `temp/`，两边都丢语义。
4. GA 的具体问题（按影响排序）：
   - **会话不分项目**：`temp/sessions` 扁平，`/resume` 看到所有项目的会话混在一起；
   - **产物不进用户项目**：工具 cwd = GA 安装目录的 `temp/`，模型写出的文件与用户项目脱节；
   - **`PROJECT_ROOT` / `RUNTIME_ROOT` 双根混用**，前端各自拼路径，行为随前端/安装形态而变；
   - **`os.getcwd()` 被 Ink 的 `chdir` 污染**，会话里的 `cwd` 记录不可信。
5. 修复方向（详见设计文档）：引入 GA 的「项目键」层——由**用户启动目录**决定
   （显式 `GA_PROJECT_ROOT` 优先），运行时数据改为
   `<数据根>/projects/<projectKey>/…`，全局数据留在 `<数据根>/` 根下；
   工具 cwd 与 `workspace_root` 归一到用户项目目录。
