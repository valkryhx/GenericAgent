# GA goal × 多智能体协同：测试方法论与踩坑手册

日期：2026-10-30
定位：这是"怎么把 goal × workflow × agent-team 这类复杂并发场景测扎实"的**方法沉淀**，
不是结论清单。结论见 `docs/20261030-GA-goal-workflow-agentteam协同设计与测试基线.md` §11。
后续新增任何一个"后台 + goal"的组合，都应该先读本文再动手写测试。

---

## 1. 为什么这类场景不能只测一层

"goal + 后台任务"天然是**跨层**的：它同时涉及
- 会话状态（active_goal、Stop 门禁）
- 后台执行（workflow 线程 / 子进程）
- 回合生命周期（何时结束、何时 handoff、何时再求值）
- 前端渲染（卡片、状态栏、overlay 面板）

只测一层会漏掉另一层的真实 bug。本项目实际就是"单测全绿、真实跑却空转 9 步"——
因为单测用 mock 把"后台在飞"直接设 True，而真实世界里 workflow 根本不在 SubagentManager 里。
所以方法论第一条：

> **每一层用一个"只有它能杀死"的风险来定义，层与层之间不重复覆盖同一个风险。**

---

## 2. 四层测试阶梯（本次采用）

| 层 | 依赖 | 能杀死的风险 | 本次文件 |
| --- | --- | --- | --- |
| L1 单元 | 无网络、假对象 | 判定逻辑本身（状态集合、fail-open、标签合并、flag 重置） | `tests/test_goal_workflow_coop.py` |
| L2 受控 gate | 真实 bridge + 真实后台，但**自己调用 gate** | "两通道同时在飞时，Stop 门禁确实 defer / settle 后确实求值" | `tests/real_goal_workflow_team_gate_e2e.py` |
| L3 纯模型全链 | 真实 LLM 自主发起 | "模型自己发起的两个后台通道，回合能否正常结束、产物对不对、goal 最终对不对" | `tests/real_goal_workflow_team_combo_e2e.py` |
| L4 真实 UI 渲染 | 真实 bridge + 真实模型 + 真实 Ink | "四类表面（goal 卡片/状态栏/team 面板/workflow 面板）真实显隐、互斥、恢复、宽度" | `frontends/ink/ui/scripts/real_ink_goal_workflow_team_combo_e2e.ts` |

关键点：**L2 是最容易被跳过、但性价比最高的一层。** 它用真实后台、真实 gate，但因为
"gate 由测试代码直接调用"，所以不受模型随机性影响，能确定性拿到"两通道同时在飞"这个瞬态。
L3 才有模型随机性——它证明"模型也能走通"，但不适合用来做精确的瞬态断言。

### 2.1 为什么 L2 要单独存在（而不是直接上 L3）

L3 里"两通道同时在飞"这个窗口是**模型行为决定的**：模型可能先起 workflow 再起 team，
也可能慢一步让快的先跑完；脚本还可能有引号错误让回合拖长到后台任务早已结束。
所以 L3 很难**稳定**断言"此刻两者都在飞"。L2 把"发起"和"观察"解耦：
测试自己 spawn workflow + spawn team，然后在 `sleep 5` 后自己调 `run_stop_gate()`。
这样瞬态窗口是测试构造的，确定性 100%。

## 3. 构造"并发窗口"的稳定套路

### 3.1 先起慢通道，再起快通道

这是本轮最重要的经验。目标状态是"两个后台通道同时存活"，但两个通道的**启动耗时**不同：
- workflow 要 `load_skill` + 校验脚本 + 起线程 + 子 agent 首次 LLM 调用，往往十几秒；
- team 子 agent 也要起子进程 + 首次 LLM 调用，十几到几十秒。

如果在**同一个回合**里让模型先起 workflow 再起 team，等 team 真正跑起来时，workflow 可能已经
跑完（尤其脚本很"快"时），并发窗口就消失了。反之亦然。

**稳定做法**：分两个回合，且**先发起的那个通道故意跑得更慢**：
```
turn A: 起 team 子 agent，脚本 sleep 120   （慢通道先起，保证后面几十秒都在）
turn B: 起 workflow，脚本 sleep 30          （快通道后起，此时慢通道必然还活着）
立刻检查: 两通道是否都在飞
```
`tests/real_goal_workflow_team_combo_e2e.py` 就是 120s vs 30s 这个配比，实测稳定并发。

### 3.2 "慢"要慢在后台进程里，不是慢在模型思考里

sleep 必须放在**子 agent 真正执行的命令**里（`python -c "time.sleep(N); ..."`），
不要指望"模型会思考很久"。模型可能秒回，也可能纠结很久——都不可控。
把 sleep 放进后台命令，等于把"并发窗口时长"变成一个你完全掌控的数值。

### 3.3 用绝对路径 + 正斜杠，产物落在可断言的位置

两条硬规则：
1. **goal 条件里写的路径 = 产物实际落盘的路径**。workflow 子 agent 默认写 run 自己的
   workspace（`<target>/workflow-runs/<runId>/`），不是用户给的根目录。若 goal 条件指根目录，
   必须在脚本命令里用**绝对路径**写到根目录，否则会出现"workflow 成功但 goal 判文件不存在"的假阴性。
2. **路径一律用正斜杠**（`D:/xxx/yyy`）。Windows 反斜杠穿过 Python→JS 模板→shell 多层时极易
   被当转义吃掉，是这类测试最常见的莫明失败源（见 §5.2）。

### 3.4 断言"在飞"要用真实的结构数据，不要用日志文本

判断"后端有没有在飞"，用真实对象：
```python
ge.has_in_flight_agents(agent, handler)          # 合并两通道后的总判定
ge._workflow_runs_in_flight(agent)               # workflow 通道标签
mgr.list_descendants(session_id)                 # 子 agent 通道状态
```
不要 grep 日志里有没有 "running" 字样——那既可能误命中历史文本，也覆盖不到"通道根本没注册"这种
真实故障（本次 bug 正是"日志看着都在跑，但 gate 看不到 workflow"）。

## 4. 真实 Ink UI 抓帧方法（L4）

### 4.1 用"假 TTY 的 CaptureWriteStream"承接 Ink 输出

Ink 是逐步写 ANSI 帧到 stdout 的（diff 渲染），无法直接拿到"一张完整屏幕"。做法：
- 用一个 `EventEmitter` + `write()` 收集所有 chunk 的 `CaptureWriteStream` 当 stdout；
- 用 `FakeReadStream` 模拟 stdin（能 `send('\r')` / `send('\u001b')` / 方向键）；
- `render(<App .../>, { stdout, stderr, stdin, patchConsole:false, debug:true })` 挂真实 App；
- 每个 chunk `stripAnsi()` 后，按"含 `Enter send` / `Running ·` / `GenericAgent` / `────`"筛出
  **chrome 帧**（底栏帧），取 `.at(-1)` 作为"当前屏幕"。

### 4.2 断言要"等到出现"，不要"写完立刻断言"

Ink 渲染是异步、多次 diff 的。必须在 `waitForFrame(predicate)` 里轮询直到某帧满足条件（带超时），
而不是 `typeInput` 之后立刻读 `.at(-1)`。否则会偶发拿到旧帧导致假失败。

### 4.3 断言要贴"该表面独有"的文本，防假阳

- `/team` 面板：断言 `Team … lead …` + `Task board`（面板独有）。
- `/workflows` 面板：断言 **`Dynamic workflows`**（这是面板标题常量，`workflowPanel.ts` 里写死）。
  早期我用 `/workflows|Enter view|.../` 这种宽正则——但"workflow 状态栏"本身就含 `/workflows`，
  会**假阳**（状态栏还在、面板没开也通过）。收紧成 `frame.includes('Dynamic workflows')` 才是真验证。
- "overlay 隐藏 goal 卡片"：断言该帧 **不含** `Goal active`，且同时断言 overlay 独有文本出现，
  两个条件一起，避免"帧是空的所以不含 Goal active"的错误通过。

### 4.4 宽度校验用 stringWidth，不用 length

中文、emoji、全角符号的显示宽度 ≠ 字符数。逐行 `stringWidth(line) < columns`（严格小于，
留 1 列余量）才是"不超宽"的正确判据。要覆盖**所有**捕获帧，不是只看最后一帧。

## 5. 本轮踩过的坑 & 解决法（最值钱的部分）

### 5.1 Windows/Git Bash heredoc 吞反斜杠（最高频）

**现象**：往 `.ts` / `.py` 里写含 `\` 的代码（正则 `\u001B`、路径 `C:\`、`replace(/\/g,'/')`），
落盘后变成单反斜杠甚至半个正则，Node 报 `Invalid regular expression: ... Unterminated group`、
esbuild 报 `Expected ")"`。

**根因**：heredoc 内容经过 PowerShell here-string → Git Bash `-lc` 多层传递，反斜杠被逐层消耗。

**解决（按可靠性排序）**：
1. **完全避免在源码里写反斜杠字面量**。例：路径转正斜杠不要 `p.replace(/\/g,'/')`，
   改用 `p.split(String.fromCharCode(92)).join('/')`（92 就是反斜杠码点，源码里没有 `\`）。
   拼接多行不要 `'a\n' + 'b'`，改用 `String.fromCharCode(10)`。
2. 需要正则时，从**已存在的正确文件**里用 Python 脚本 `re` 抽取整段函数，覆盖进目标文件
   （本次 `stripAnsi` 就是直接从 `goalUiRender.test.ts` 抽过来，零手写反斜杠）。
3. 用 Python 字节级脚本 `chr(92)` 构造并替换（`open(...,'rb')` 读、`replace`、`wb` 写）。
4. **不要**原样重试同一条被吞的命令——只会重复损坏。

> 判定经验：只要一段 heredoc 写完，立刻用 `python -c "import ast;ast.parse(...)"`（py）或
> `npx tsc --noEmit`（ts）过一遍语法；语法错基本就是反斜杠被吞了。

### 5.2 中文在 Windows 控制台"显示"乱码 ≠ 文件坏了

**现象**：`cat` / `print` 出来一堆 `Ŀ¼` `��`，以为文件写坏了。

**真相**：Windows 控制台代码页是 GBK，UTF-8 中文被错误解码显示。**文件本身可能是好的。**

**验证法（看字节不看回显）**：
```python
b = open(p, "rb").read()
assert b[:3] != b"\xef\xbb\xbf"      # 无 BOM
assert b.count(b"\r") == 0           # 无 CRLF
b.decode("utf-8")                    # 不抛异常即合法 UTF-8
```
本次所有 md / 源码写完后都跑了这套校验。另外注意 `print` 中文到 GBK 控制台会直接抛
`UnicodeEncodeError`，要看中文得 `sys.stdout.buffer.write(text.encode("utf-8"))`。

### 5.3 占了位却永远是 true 的"假断言"

**现象**：写测试时留了 `rec('...', events.some(() => true) ? true : true)` 这种占位，忘了替换——
测试"全绿"但那一行什么都没验证。

**解决**：本轮专门 grep `placeholder` / `=> true` 清理了这类行，并把每条断言落到真实谓词。
**规则：任何永远为真的断言都是负资产，提交前必须 grep 掉。**

### 5.4 单回合塞太多 + 多层嵌套引号

**现象**：最早一版想让模型"一个回合里同时起 workflow 和 team"，还让它把
`python -c "import time;time.sleep(30);open(...).write(...)"` 这种命令嵌进 workflow 的 JS 模板串。
结果模型花 10 步、122 秒都没把引号写对，脚本根本没跑起来，回合 `done=false`。

**解决**：
1. **一个回合只做一件"发起"的事**（分 turn 起 team / 起 workflow），模型负担小、成功率高。
2. **复杂脚本落盘，用 `scriptPath` 传**，不要让模型在对话里内联一大段带引号的 JS。
3. 脚本里需要 shell 命令时，命令字符串用变量拼、路径用正斜杠，减少嵌套层数。

### 5.5 等后台任务"真正 settle"再断言，而非"文件出现就完事"

**现象**：marker 文件出现了就去断言"goal 已求值"，但此时 workflow run 的 status 可能还是
running（刚写完结果、还没落终态），`has_in_flight` 仍为 True，goal 自然不会求值 → 假失败。

**解决**：等待条件用"多条件与"：
```
marker_wf 存在  AND  marker_team 存在  AND  workflow run.status ∈ 终态集合
```
再加一个 `sleep 6~8s` 让子进程状态落盘，然后才断言 `has_in_flight == False` 与"求值发生"。

### 5.6 浏览器/后端无关，但通用的：测试要"自包含环境变量"

每个真实 e2e 的 `setup_env` 都显式设 `GA_PROJECT_ROOT/GA_DATA_DIR/GA_WORKFLOW_WORKSPACE_ROOT/
GA_LAUNCH_CWD/GA_ORIGINAL_CWD/GA_LLM_CONFIG`，并清掉可能串味的 `GA_PROJECT_KEY/..._SESSION_ID/
GA_TEAM_KEY` 等。否则上一次运行的会话/团队/项目标识会污染这一次（比如 team 复用了旧的 task board）。
另外本次还补了：`GA_PROPOSE_GOAL_ENABLED` 之类默认关闭的开关，测试要自己打开，不能依赖外部已设。

## 6. 断言清单模板（新增组合测试时照抄）

一个"goal + 后台X"的组合，至少覆盖：

- [ ] 发起回合 `done == true`（回合能正常结束，不空转）
- [ ] 发起回合 `last_goal_defer == true`
- [ ] 发起回合模型步数 `<= 合理上限`（防空转）
- [ ] 后台通道确实 in-flight（用结构化数据，不是日志）
- [ ] defer 期间 evaluator **未被调用**（`prompt_runner` 计数不变）
- [ ] transcript 里有 `goal_status(reason='deferred')`
- [ ] 后台 settle 后 `has_in_flight == false`
- [ ] settle 后 evaluator **被调用**（计数 +1），且出现非 deferred 的 goal_status
- [ ] 所有预期产物按**精确路径**落盘、内容正确
- [ ] goal 最终 met / 合理 not_met（不误判）
- [ ] （UI 层）每个表面用**独有文本**断言、overlay 隐藏次要带、关闭恢复、逐帧宽度
- [ ] 提交前 grep `placeholder` / `=> true` / `TODO` 无残留

（手写最容易被 §5.1 的反斜杠和 §4.2 的异步时序坑到）。

## 8. 一句话总纲

> **执行正确性用"受控 gate"拿确定性证据；模型能力用"纯模型全链"证明走得通；
> 渲染正确性用"真实 Ink 抓帧 + 独有文本断言"；瞬态窗口靠"先慢后快 + 后台 sleep"构造；
> 所有路径正斜杠、所有中文看字节、所有断言不许永远为真。**
