
# GA 的 skill 渐进式披露：对照 CC 319 与第 3 轮优化（2026-11-10）

> 用户问："CC 有渐进式披露，GA 有吗？听说这个方式可以逐步加载 skill 原文，
> 不用一下子把 Skill 的所有内容都加载进去。"
>
> 答案：**GA 早就实现了三层结构**（L1 清单 / L2 `load_skill` 读全文 / L3 按需读 references），
> 连 compact 之后的 `invoked_skills` 回注都有。真正缺的是 L1 在**超预算时的降级策略**：
> 旧实现会**静默丢掉 skill**，本机 51 个模型可见 skill 里只列出 38 个，
> 另外 13 个（含 `ui-ux-pro-max`、`writing-skills`、`using-superpowers`）模型**根本看不见**，
> 也就永远不可能匹配。本轮修的就是这个。

## 0. 结论先行

| 能力 | CC 319 | GA（本轮前） | GA（本轮后） |
| --- | --- | --- | --- |
| L1 常驻索引 | 名称 + 描述 + when_to_use | ✅ 同 | ✅ 同 |
| L1 预算 | 窗口×4×0.01（200k → 8000），env 可覆盖 | ✅ 8000，**env 不可覆盖** | ✅ 8000，`GA_SKILL_LISTING_CHAR_BUDGET` 可覆盖 |
| L1 超预算 | 整行降级成 `- name`，**一个都不丢** | ❌ 先降级、放不下就 `break`，**丢掉后面所有 skill** | ✅ 整行降级成 `- name`，一个都不丢 |
| 单条描述上限 | 1536 字符硬截 | ❌ 250 字符硬截，砍掉句尾的 `Use when …` 触发器 | ✅ 400 字符，**保留触发器句**（`_compact_description`） |
| L2 按需加载 | `Skill` 工具返回 SKILL.md 全文 + base dir | ✅ `load_skill` 返回全文 + base dir | ✅ 同 |
| L3 references | 正文里指路，模型自己 `Read` | ✅ 首行就写"Read only the reference you need with file_read" | ✅ 同 |
| compact 后回注 | `invoked_skills` 提醒 | ✅ `context.py` 已实现 | ✅ 同 |
| 覆盖状态 | `on` / `name-only` / `user-invocable-only` / `off` | ✅ 同名四态（env `GA_SKILL_OVERRIDES` + frontmatter） | ✅ 同 |

**为什么这件事重要**：本机 51 个模型可见 skill，L1 索引原始长 14,257 字符；
如果把 51 份 SKILL.md 全塞进上下文是 **424,122 字符（约 10.6 万 token）**，
是索引的 **29.7 倍**。只加载命中的那一份，正是渐进式披露的全部意义。
所以 L1 的完整性不是细节——**L1 里不出现的 skill 等于不存在**。

## 1. CC 319 的三层是怎么实现的

细节见 `D:/git_codes/claudecode283_hack/docs/20261017-CC-skill渐进式披露调研.md`，这里只留用于对照的坐标：

| 层 | 机制 | 源码坐标 |
| --- | --- | --- |
| L1 | `The following skills are available for use with the Skill tool:` + 名称/描述逐行 | `claudecode319` 对应区（283 为 `m0591:228783`） |
| L1 预算 | `sOt()`：`skillListingBudgetFraction(0.01) × contextWindow × 4`（200k → 8000），env `SLASH_COMMAND_TOOL_CHAR_BUDGET` 覆盖 | 319 `m0591_0x11be624e.js:110719` |
| L1 单条上限 | `j5t()` → `rRr = 1536`；`aRr()` 盲切 `desc.slice(0, 1535) + "…"`（不看句义） | 319 `m0591:110718`、`m0591:110815` |
| L1 降级 | `Q_n()`：先算总长；超预算就进 `"priority"` 模式——**先扣每个 skill 的描述长度**，名字（`nameLength + 2`）一个都不扣，被扣描述的记进 `budgetTruncatedSkills` | 319 `m0591:110759` |
| L2 | `Skill` 工具调用 → 返回 SKILL.md 全文，首行是 `Base directory for this skill: …` | `m0357` |
| L3 | 正文里指路 `references/*.md`，模型按需 `Read` | skill 作者约定 |
| 回注 | compact 后注入 `invoked_skills` 提醒（"不要重复执行、不要当成新请求"） | `m0357` |

CC 的取舍很清楚：**预算只花在"描述"上，名字永远保留**。因为一个 skill 被裁掉描述，
模型仍可能从名字猜出用途；名字都没了，就彻底失联。

值得注意的是，CC 自己的 1536 上限也是**盲切**（`aRr()` 直接按字符数 slice，不看句子边界）。
GA 的索引更长（51 个 skill、还要装 Claude/Codex 的技能），所以 GA 比 CC 多做了一步：
压缩时把 `Use when …` 这类触发器句保住（见 §4.2）。

## 2. GA 现状：三层都在，缺的是"别丢"

GA 的对应实现在 `genericagent/core/skills.py`：

| 层 | GA 实现 |
| --- | --- |
| L1 | `build_skill_prompt()` → `format_skill_listing()`，输出 `[Available Skills]` 段，每行 `- name: desc [source]` |
| L2 | `load_skill_content()`：返回 `Base directory for this skill: …` + `Attached files live under this base directory. Read only the reference you need with file_read.` + 全文 |
| L3 | 同上那句就是 L3 的指路；模型用 `file_read` 只读需要的那一份 references |
| 回注 | `genericagent/core/context.py:132 _collect_invoked_skills()` / `:169 _append_invoked_skills()` → `<invoked_skills>` |
| 四态覆盖 | `effective_skill_state()`：`on` / `name-only` / `user-invocable-only` / `off` |
| 计量 | `SkillSpec.always_on_chars` / `on_invoke_chars`：每个 skill 的 L1 成本与 L2 成本 |

也就是说，"逐步加载"这件事 GA 一直是这么做的；用户感觉"GA 不用 skill"，
另有原因（第 2 轮已定位为主因：隐性任务不触发扫描；本轮补上第二个原因：**索引不完整**）。

## 3. 实测：索引不完整到什么程度

用本机真实的 skill 集合（51 个模型可见）跑旧算法与新算法对比：

```text
model-visible=51   old_rows=38  new_rows=51
old_chars=7994     new_chars=8302
旧算法丢掉的 13 个：
  ui-ux-pro-max, using-git-worktrees, using-superpowers, verification-before-completion,
  write-a-skill, writing-plans, writing-skills, imagegen, openai-docs, review-agent,
  skill-creator, skill-installer, 技术报告撰写
旧算法里被 250 字符硬截的行：17 行
新算法里被压缩但保留触发器句的行：6 行
```

两点都直接命中用户抱怨的现象：

1. **丢掉的 13 个里有 6 个是 superpowers 的流程技能**
   （`using-superpowers` / `writing-plans` / `writing-skills` / `write-a-skill` /
   `verification-before-completion` / `using-git-worktrees`），
   还有 `ui-ux-pro-max` 这种前端设计大件。
   **模型在 L1 里看不到它们，就不可能匹配** —— 这解释了为什么"写计划 / 写 skill / 前端设计"
   这类任务 GA 从来不加载对应 skill。
   注意排序是按发现顺序（本地 skill → `~/.claude/skills` → `~/.codex/skills`），
   被丢掉的全是**排在后面**的，与质量无关。
2. **17 行被砍在 250 字符处**，而 skill 描述的"何时使用"几乎总在句尾。举例：

   ```text
   OLD  ...motion, and PNG/JPEG/WebP/SVG/WebM export. Accept plain-language re
   NEW  ...PNG/JPEG/WebP/SVG/WebM export. ... Use when the user asks to visualize system
        architecture, infrastructure, cloud/security/network topology, technical workflows, ...
   ```

   旧行在 `Accept plain-language re` 处断掉，恰好在 `Use when the user asks to visualize …` 之前。
   隐式匹配唯一能用的判据就这样被砍没了。

## 4. 本轮改动（`genericagent/core/skills.py`）

### 4.1 L1 永不丢 skill（对齐 CC）

```python
extra = len(line) + (1 if lines else 0)
if lines and used + extra > char_budget:
    # Degrade the whole row to `- name` -- never drop the skill.
    line = f"- {name}"
    extra = len(line) + (1 if lines else 0)
```

旧实现是"降级一行 → 还放不下就 `break`"，相当于把剩余 skill 从模型世界里删掉。
新实现只降级、不退出：预算耗尽后每一行都是 `- name`，名字始终可见。

### 4.2 描述压缩保留触发器句

- 单条上限 `_SKILL_DESC_CAP = 400`（CC 是 1536；GA 索引还要装 Claude/Codex 的 skill，压得更狠但要保命）。
- `_split_description_sentences()` 切句：中文按 `。！？；`（中文句末**不带空格**，只按空白切会把整段当成一句），
  英文按 `.!?` + 空白（避免把 `e.g.` / `1.5` 切开）。`_SKILL_TRIGGER_RE`（忽略大小写）匹配
  `use when / use this / when the user / trigger / do not use / 使用 / 触发 / 当用户 / 用来`。
- `_compact_description()`：触发器在句尾时，**保留头部若干句 + 拼接触发器句**；
  触发器本来就在第一句时，退化为正常的前部填充（不拼接，避免出现难看的行首 `...`）。

实测效果（本机 51 个 skill，6 行触发压缩）：

```text
- archify: Create polished, validated architecture, ... PNG/JPEG/WebP/SVG/WebM export.
  ... Use when the user asks to visualize system architecture, infrastructure, ...
- create-theme: Use this skill when the user wants to create, draft, author, or extract a
  slide theme in this open-slide repo. Triggers on phrases like "create a theme", ... [claude]
```

### 4.3 预算可配置（对齐 CC 的 `SLASH_COMMAND_TOOL_CHAR_BUDGET`）

```python
SKILL_LISTING_CHAR_BUDGET_ENV = "GA_SKILL_LISTING_CHAR_BUDGET"
DEFAULT_SKILL_LISTING_CHAR_BUDGET = 8000
def _skill_listing_budget() -> int: ...   # env 覆盖，非法值回落默认
def build_skill_prompt(char_budget: int | None = None) -> str: ...
```

保留函数参数的显式优先：调用方传了就按传的来，没传才读 env。
小上下文模型可以 `GA_SKILL_LISTING_CHAR_BUDGET=3000`，索引仍然完整（只是描述更省）。

### 4.4 测试（`tests/test_skills_runtime.py`）

新增 4 条，全部**先红后绿**，并做了反向确认（`git stash` 掉实现后重新变红）：

| 测试 | 断言 | 反向确认 |
| --- | --- | --- |
| `test_listing_never_drops_a_skill_when_over_budget` | 8 个 skill、预算 40，仍然 8 行且顺序正确 | 旧实现只剩 1 行 → 红 |
| `test_truncated_description_keeps_the_trigger_sentence` | 500+ 字符描述被压到 <500 且 `Use when the user asks to visualize` 仍在 | 旧实现 250 硬截 → 红 |
| `test_listing_budget_env_override_is_honoured` | `GA_SKILL_LISTING_CHAR_BUDGET=12345` 真的传进 `format_skill_listing` | 旧实现恒 8000 → 红 |
| `test_cjk_descriptions_keep_their_trigger_too` | 中文描述（句间无空格）压缩后仍保留 `用来在交付评审会上 …` | 仅按空白切句 → 丢触发器（monkeypatch 实测）|

## 5. 复测：真实模型第一次就命中了"旧索引里不存在"的 skill

模型固定 `zhanlu-ds`（真实 LLM），跑两个任务（`temp/prompt_ab_pd_skills.json`）：

| 任务 | 目标 skill | 旧索引里可见？ | 结果 |
| --- | --- | --- | --- |
| A 做一个有质感的注册页 `index.html` | `design-taste-frontend` / `ui-ux-pro-max` | 前者可见，后者**不可见** | 110.2s，4 次工具调用，`load_skill=design-taste-frontend` |
| B 给仓库写一个 CHANGELOG→发布说明的 skill | `write-a-skill` / `writing-skills` / `skill-creator` | **三个全都不可见** | 99.3s，12 次工具调用，`load_skill=write-a-skill` |

任务 B 是本轮的关键证据：`write-a-skill` / `writing-skills` / `skill-creator`
在旧算法下**一个都没进 L1**，模型不可能知道它们存在；base prompt 又明确要求
"只用 Available Skills 里出现过的名字"，所以旧实现下这条任务只能瞎猜。
修复后首次运行即命中：

```text
load_skill {"skill": "write-a-skill"}
file_glob  {"pattern": "skills/**/SKILL.md", "path": "D:\git_codes\GenericAgent"}
file_read  {"path": "...\skills\workflow-authoring\SKILL.md"}
file_glob  {"pattern": "**/CHANGELOG*.md"}
file_write {"path": "skills/release-notes/SKILL.md", ...}
code_run   {"script": "import subprocess; subprocess.run(['git','status','--porcelain','--','skills'])"}
```

它按 `write-a-skill` 的流程走：先读仓库里已有 skill 的约定 → 再起草 → 写完用
`git status -- skills` 确认没动仓库里已有的 skill（任务里明确要求"不要修改已有 skill"）。

**没有破坏红线**：两个任务各只加载 1 个 skill，索引变大并没有导致滥加载；
任务 A 的答案也不是"我建议你用某某风格"，而是真的探测环境（Playwright / 字体 / 网络）后落页面。

关于证据强度，如实说明：这不是 token 级的同题 A/B（旧算法已经不存在了，
但它的输出可以直接复算，见 §3 的 38 行 / 13 个丢失名字）。这里证明的是
**"L1 里没有 → 不可能用"** 这条结构性因果，以及修复后同类任务确实会用上。

## 7. 未做 / 下一轮候选

1. **预算是软上限**：名字保底后可能略超（本机 51 个名字约 1.2K，总长 8,302 / 8,000）。
   这是刻意的——CC 的选择也是"名字优先"，宁可超一点，不让 skill 失联。
2. **8000 是定值**：CC 按 `窗口 × 4 × 0.01` 推导。GA 可以按当前模型的上下文窗口算，
   换小窗口模型时自动收紧（现在只能靠 env 手工设）。
3. **子 agent 拿的是同一份完整索引**（`workflow/child_agent.py:1319` 也调 `build_skill_prompt()`）。
   好处是子 agent 也能用 skill；代价是每个子 agent 多 ~8K 字符。是否给子 agent 单独预算待评估。
4. **skill 扫描仍不可观测**（第 2 轮遗留）：只有 `load_skill` 调用能当证据，
   "扫描了但没加载"没有记录，统计误加载率只能靠人工看 transcript。
5. **相关性收敛未做**：53 个 skill 全量在索引里，按 cwd / 仓库类型筛选会更省，
   但也可能把该用的 skill 筛掉，优先级低于前几项。
6. **`_SKILL_DESC_CAP = 400` 是经验值**：CC 用 1536。可以先放到 600–800 观察索引总量，
   在"描述更完整"和"索引别太长"之间找平衡。
