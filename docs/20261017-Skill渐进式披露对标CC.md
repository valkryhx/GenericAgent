# GA Skill「渐进式披露」对标 CC —— 现状 + 实施方案

> 目标：把 CC v2.1.283 的 skill 渐进式披露机制对齐到 GA，**尤其是把越来越大的 SKILL.md 瘦身**。
> CC 侧证据见 `D:/git_codes/claudecode283_hack/docs/20261017-CC-skill渐进式披露调研.md`（逐条模块坐标）。
> 背景根因：`load_skill('workflow-authoring')` 一次返回 ≈17.7KB，触发上游渠道 guardrail
> （`Upstream access forbidden`），伪装成"LLM 空回复"。修复见 commit `caa42f1`（错误已可见），
> **本文是根因侧的优化**。

---

## 0. 现状：GA 已经有什么（先别重复造）

`skills_runtime.py`：

| 函数 | 作用 |
| --- | --- |
| `SkillSpec(name, description, source, root, path, body, when_to_use, allowed_tools, version)` | skill 元数据 |
| `discover_skills()` | 扫 roots：`<repo>/skills`、`~/.claude/skills`、`~/.codex/skills`、`GA_SKILL_PATHS` |
| `format_skill_listing(skills, char_budget=8000)` | **L1 清单**：`- name: desc - when_to_use [source]`，desc 截 250 字，超预算降级 `- name` |
| `build_skill_prompt(char_budget=8000)` | 注入 `[Available Skills]` + "The listing is only an index; load the full SKILL.md before following it" |
| `load_skill_content(name, ...)` | **L2**：返回 `Base directory for this skill: <dir>` + 正文全文；替换 `${CLAUDE_SKILL_DIR}`/`${CODEX_SKILL_DIR}`/`${GA_SKILL_DIR}`/`$ARGUMENTS` |

注入点：`agentmain.py:496` `"skills": build_skill_prompt()`；工具：`ga.py::do_load_skill`。

## 1. 差距（对标 CC）

| 维度 | CC | GA | 差距 |
| --- | --- | --- | --- |
| L1 清单 | 名字 + desc + when_to_use；预算 = ctx×4×0.01；超预算降级 `- name` | 已有；固定 8000；desc 截 250；额外带 `[source]` | **基本对齐**（可微调） |
| L2 加载 | 调用时载入 SKILL.md **全文** | 同（`base_dir` + body） | **已对齐** |
| L3 附带文件 | 正文瘦 + `references/` 按需 Read | **无约定**；`workflow-authoring/SKILL.md` = 17.3KB 单体 | **主要缺口** |
| 压缩后回注 | `invoked_skills` 提醒 | 无 | 缺口 |
| 覆盖状态 | `on`/`name-only`/`user-invocable-only`/`off` + `disable-model-invocation` | 无 | 可选 |

**关键认知修正（避免做错方向）**：CC 的 L2 **也是载入全文**，它并没有把 SKILL.md 切片按需加载。
渐进披露的杠杆是 ①清单常驻 ②**正文本身要瘦**（重内容放附带文件）。
→ 所以 GA 的修法重点是**重构大 skill 的正文结构**，而不是改加载协议。

### 1.1 追加实证：CC 的 17K workflow authoring 正文如何加载

> 2026-10-17 复核结论。CC 侧完整证据见
> `D:/git_codes/claudecode283_hack/docs/20261017-CC-skill渐进式披露调研.md` §7。

**主路径不是常驻 17K，而是“约 3.3K 工具描述 + 按需 load skill”。**

- `m1502_0xdb4a986.js`：
  - `t` = Workflow 工具短描述，约 **3,078 字符**；
  - `i` = 185 字符指针：`Before writing a script, load the workflow-authoring skill ...`；
  - `Anr()` = 完整 authoring reference，约 **17,526 字符**；
  - `xnr(e)`：`e === true` 时返回 `t + i`；`e === false` 时返回 `t + Anr()`。
- `m1503_0xdb4fec6.js`：把 `Anr()` 注册为内置 skill `workflow-authoring` 的
  `getPromptForCommand()` 返回值。
- `m1065_0xd342694.js`：`fSe(tools)` 判断 workflow-authoring skill 是否可用且 Skill 工具已挂载。
- `m0357_0xc63ba04.js`：Skill 调用后，`TAt(...)` 取 `getPromptForCommand()` 的全文 `w`，
  构造 `Ce({ content: w, isMeta: true, ... })`，作为**独立 user message** 注入。
- `m0517_0xcd36592.js`：Skill 工具的 `tool_result` 仍然只有
  `Launching skill: <name>`（约 30-40 字符）。

因此正常路径的真实消息形态是：

```text
assistant: tool_use Skill { skill: "workflow-authoring" }
user:      tool_result  "Launching skill: workflow-authoring"   ← 极小
user:      isMeta: true  content = 17.5K authoring reference    ← 正文在这里
```

**为什么这样不出问题：**

1. 17.5K 正文不是 tool_result JSON，而是合法的独立 user text；
2. tool_result 保持极小，避免大 payload 被渠道 guardrail 拒绝；
3. 正文只在 Skill 被调用时加载，不常驻、不每轮重复；
4. 字节级重复调用会被替换为短 `isMeta` 提醒；
5. compact 后若旧副本被截断，重调用会先加“之前副本被 compaction 截断，完整指令随后”的提示。

**不是“Claude 上下文大所以可以一次塞 17K”。** 17.5K 字符约 4.4-5K tokens，
模型确实装得下；但 CC 的关键设计是**按需加载 + 正文/工具结果分通道**。
如果常驻或塞进 tool_result，依然会造成浪费和渠道风险。

**GA 当前差异：** GA 的 `load_skill` 把 `base_dir + body` 放在返回 dict 里，
最终整体进入 `tool_result`；因此 17.7KB 正文既是大 payload，又是嵌套 JSON。
对齐 CC 时应优先做到：

- Workflow 工具描述保持短，只提示 `load_skill('workflow-authoring')`；
- `load_skill` 的 tool_result 只返回“已加载”确认；
- skill 正文作为下一轮独立注入内容（GA 可先复用 `next_prompt`，不必先改底层 API 协议）；
- 正文瘦身，重内容放 `references/`；
- 重复加载去重；compact/续跑后做 `invoked_skills` 回注。


### 1.2 GA 侧涉及哪些修改（对标 CC 的通用 tool_result 策略）

> CC 侧证据见 `D:/git_codes/claudecode283_hack/docs/20261017-CC-skill渐进式披露调研.md` §8。

**先纠偏：不是“JSON 不能用”。**

CC 的 tool_result 本身也是结构化协议；小型 JSON/结构化结果完全可以。
真正的问题是**单个 tool_result 的 content 字符串过大**。CC 在
`m0297_0xc5de28c.js` 用 `maxResultSizeChars` 做统一预算：

- 未超预算：原样返回；
- 超预算：先持久化到文件，返回 `<persisted-output>` + preview + 文件路径；
- 无法持久化：退化为 `<truncated-output>` + 前 N 字符；
- `image` / `document` 不计入这个字符预算。

具体工具也不是“把 dict 原样塞进去”：

- `Write` 返回短确认文本；
- `Read` 有自身 `maxSizeBytes` / `maxTokens` / offset / limit；
- `Bash` 返回 stdout/stderr 文本，大输出用 `persistedOutputPath`；
- `Grep` 返回文本；
- `Skill` 返回 `Launching skill: <name>` 短确认；
- `Workflow` 返回异步启动结果（runId/taskId），不返回完整日志。

#### GA 要改哪些

**P0：Skill 正文与 tool_result 分离（本阶段必做）**

1. `skills_runtime.py`
   - `load_skill_content()` 继续负责读正文，但调用方不再把正文当 tool_result；
   - 增加 `content_chars` 等元数据，正文与元数据分离。
2. `ga.py::do_load_skill`
   - `outcome.data` 只保留短元数据：
     `status`、`name`、`description`、`source`、`path`、`base_dir`、
     `allowed_tools`、`content_chars`；
   - 把 `content` 放进 `outcome.next_prompt`，作为下一轮独立 user 内容；
   - 相同正文重复加载时去重，只注入短提示，不重复注入全文。
3. `agent_loop.py`
   - 保持现有 `tool_results` 与 `next_prompt` 分通道结构；
   - 不把 `next_prompt` 合并进 tool_result。
4. `skills/workflow-authoring/SKILL.md`
   - 瘦身到 `< 5KB`；
   - 详细 API/示例/测试/恢复内容放 `references/`，正文只留契约和索引。

**P1：通用 tool_result 预算（对齐 CC `m0297`）**

1. 在 `agent_loop.py` 增加统一的 tool_result 大小归一化：
   - 小结果：保持 JSON/text；
   - 超阈值：写入 `temp/tool-results/<tool_use_id>.txt|json`，返回
     `<persisted-output>` preview + 路径；
   - 无法持久化：返回 `<truncated-output>` + 前 N 字符。
2. 默认阈值建议先取 50K–100K 字符；对已有自身分页/截断的工具
   （`file_read`、`code_run` 等）可豁免或设 `Infinity`。
3. 不全局禁用 JSON；只限制大 content。

**P2：继续对齐 CC**

- `invoked_skills` 压缩后回注；
- `name-only` / `off` / `disable-model-invocation` 等覆盖状态；
- 目录作用域 skill 命名；
- `/skills` 风格的上下文成本展示。

#### 实施状态

- **2026-10-17：P0 已实施。** `ga.py::do_load_skill` 现在把 SKILL.md 正文从 tool_result 中移除，改为放入独立 `next_prompt`；tool_result 只保留短元数据；同一 skill 相同正文重复加载时去重。focused 测试：`tests/test_load_skill_tool.py` + `tests/test_skills_runtime.py` 共 10 passed。
- 待做：`workflow-authoring/SKILL.md` 瘦身 + `references/` 拆分；`agent_loop.py` 通用 tool_result 预算/持久化。

#### 验收

1. `load_skill('workflow-authoring')` 的 tool_result 不再是 17.7KB JSON；
2. 正文以独立注入内容出现，且重复加载不重复注入；
3. `workflow-authoring` 正文 `< 5KB`，细节可经 `references/` 按需读取；
4. 其他工具的小 JSON 结果不受影响；
5. 超大 tool result 能持久化/截断，不再直接触发上游 guardrail。

## 2. 实施步骤

### 阶段 1（必做，收益最大）：把 `workflow-authoring` 拆成「瘦正文 + references/」

- **目标**：`load_skill('workflow-authoring')` 返回体从 ≈17.3KB 降到 **< 5KB**。
- **做法**：
  - `skills/workflow-authoring/SKILL.md` 只保留：契约要点、`agent/parallel/pipeline/phase/log` 的最小签名、
    常见坑、以及一张**细节索引表**（指向 `references/*.md`）。
  - 拆出：`references/api.md`（逐 API）、`references/examples.md`（示例）、`references/resume.md`、
    `references/artifacts.md`、`references/testing.md`（test gates / runPythonUnittest / repairAndRetest）。
  - 正文里显式写：`需要 X 时读 references/x.md（用 file_read，路径相对本 skill 的 base dir）`。
- **验收**：单次 `load_skill` tool_result < 5KB；那条"并行调研三件事"的 workflow 仍能端到端完成。

### 阶段 2：L3 约定 + base dir 指引强化

- `load_skill_content` 已给 `Base directory for this skill: ...`；在其后补一句显式指引：
  `本 skill 的附带文件在该目录下；需要细节时用 file_read 读取 references/... ，不要一次性读完。`
- 目录约定：`references/`（文档）、`scripts/`（可执行）。

### 阶段 3：压缩后回注（对齐 CC `invoked_skills`）

- compact 之后，把本会话**已 load 过**的 skill 的 **L1 清单行 + 一句话摘要**重新注入（**不注入全文**），
  避免 compact 后模型忘了 skill 约定。
- 注意 CC 的措辞：明确"这是**早先**调用的上下文，不要重复执行、不要当成新请求"。

### 阶段 4（可选）：覆盖状态

- frontmatter 支持 `disable-model-invocation` / `user-invocable`；settings 支持 `name-only` / `off`。

## 3. 验收标准

1. 系统提示里是**清单**（名字 + 一行描述），**不含正文**。
2. `load_skill` 单次返回体显著下降（`workflow-authoring` < 5KB）。
3. 需要细节时，模型能按 base dir **分段读取**并完成任务。
4. compact / 续跑后 skill 指南仍在（回注）。
5. 端到端：workflow 任务不再触发上游渠道 guardrail。
