## 1. 目标、非目标与发布原则

### 1.1 目标

| 编号 | 目标 | 验收判据 |
| --- | --- | --- |
| G1 | 用户从项目 A/B 启动 GA，默认只看到各自 session | `/resume` 不混入另一项目 |
| G2 | workflow run/artifact 按项目隔离 | A 的 `/workflows` 不出现 B 的 run |
| G3 | 主会话工具写出的相对路径落到用户项目 | A 中写 `notes.md` 得到 `A/notes.md` |
| G4 | 普通 subagent 使用同一项目上下文 | cwd、项目文档、项目角色、状态根均正确 |
| G5 | workflow child 使用正确项目文档与隔离 workspace | child 不读错 `GA_AGENTS.md`，不发散写路径 |
| G6 | Agent Team 的 board/mailbox/worktree 始终同源 | lead/teammate 共享，A/B 不串板 |
| G7 | 旧 session/workflow/team 数据只读可见 | 不自动搬迁、覆盖或删除 |
| G8 | resume 回到会话所属项目 | 从 B 目录恢复 A 会话后，上下文回到 A |

### 1.2 非目标

- 不做 transcript 物理压缩或删除。
- 不自动迁移旧 `temp/`。
- 不新增图片读取能力。
- 不把用户项目变成 GA 的数据目录。
- 不要求 CC 的 `.claude` 命名完全一致；GA 使用 `.ga` 作为产品命名层。
- 不同时重构 workflow 业务算法、team 协议或 UI 交互。

### 1.3 发布原则

1. **先契约后接线**：P0 只增加路径 API 和单测。
2. **先拆根后搬家**：P1.5 先修语义，P2/P3 才切换磁盘布局。
3. **同版本切换**：session、subagent registry、workflow store、workflow workspace 的 writer 与 reader 必须同版本。
4. **旧数据只读**：迁移只能是显式 `dry-run/apply`，且不删除源。
5. **UI 协议不变**：control plane 继续输出 `worktreePath`、`transcriptRef`、team/task 字段；只改变解析来源。
6. **每一步可回滚**：启动、布局、工具 cwd 分别保留开关。

## 2. 目标路径模型

### 2.1 核心路径根

| 名称 | 定义 | 是否跨项目共享 | 典型消费者 |
| --- | --- | --- | --- |
| `PACKAGE_ROOT` | GA 包安装目录 | 是，只读 | prompts、bundled skills、assets |
| `PROJECT_ROOT` | 用户启动项目的规范化真实路径 | 否 | 工具 cwd、项目文档、项目角色、workflow 定义、git worktree |
| `DATA_ROOT` | GA 用户级数据根 | 是 | projects、teams、tasks、logs、media、mcp、memory |
| `PROJECT_DATA_DIR` | `DATA_ROOT/projects/<projectKey>` | 否 | session、subagent transcript、workflow run/workspace |
| `SESSION_DATA_DIR` | 当前 session 的 project-local 数据 | 否 | `<sessionId>/subagents`、`<sessionId>/workflows` |
| `WORKSPACE_ROOT` | 一次 workflow run 或隔离 job 的工作副本 | 否 | workflow shared/isolated workspace |

另外保留三个“工作目录/定义库”概念，不能与数据桶混淆：

- `TOOL_CWD`：主会话直接操作的用户项目目录，默认 `PROJECT_ROOT`；
- `WORKTREE_ROOT`：真 git worktree 容器，必须是 `<PROJECT_ROOT>/.ga/worktrees`；只服务 subagent/Agent Team；
- `WORKFLOW_DEFINITION_ROOTS`：project `<PROJECT_ROOT>/.ga/workflows`、user `<DATA_ROOT>/workflows`、legacy `<DATA_ROOT>/temp/sessions/named-workflows`。

### 2.3 项目身份与 projectKey（GA 产品增强）

CC 的 transcript bucket 实际由会话 `sessionProjectDir`，否则由 `originalCwd` 派生；`projectRoot` 是独立的项目/隔离边界；`cwd` 又是当前执行目录。GA 不应把这三个值混成一个 `cwd`，建议新增以下不可变身份（`launch_cwd` 不是 CC 原生字段，是 GA 用于解释启动来源的增强）：

```python
ProjectIdentity(
    original_cwd=...,   # CLI 启动时的原始目录，仅审计/恢复
    project_root=...,   # 项目边界：docs/roles/workflows/worktree/tool cwd
    launch_cwd=...,     # --cwd 或原始启动子目录，用于可解释诊断
    cwd=...,            # 当前会话/子任务执行目录
    project_key=...,    # 数据桶 key，稳定且可复现
)
```

GA 的 `project_key` 生成规则必须写成产品增强，而不是 CC 原样算法：

1. 对 `project_root` 做 `expanduser + resolve(strict=False)`；Windows 路径做大小写不敏感归一（`casefold()`），但 key hash 和显示路径分别保留规范化结果；Unicode 做 NFC；长路径不依赖 `Path.resolve(strict=True)`；
2. 优先找到项目边界：`GA_PROJECT_ROOT` 显式覆盖 > 独立 CLI `--project-root`（若实现）> 向上查找 `.git` / `.ga` / `pyproject.toml` / 明确的 `GA_AGENTS.md` 项目根 > 启动 cwd；
3. 可读前缀取项目目录名的 basename，清洗为 `[A-Za-z0-9_-]`，截断到安全长度；Windows 设备名（`CON`/`NUL` 等）加前缀避开；
4. 计算规范化后的完整路径 SHA-256，取前 12~16 位；hash 输入必须包含大小写/UUID-casefold 后的规范值，不能只 hash basename；
5. key 形如 `<readable-name>-<hash>`，避免 CC 有损清洗造成的撞车；hash 是碰撞判定的唯一依据，不能依赖可读前缀；
6. 同一项目不同子目录启动必须得到同一 key；不同真实项目即使同名也必须不同 key；
7. `original_cwd` 不能替代 `project_root` 进入 key；workflow 的 `withProject(cwd=workspace)` 更不能新建 projectKey。

需要专门测试的非显然边界：

- 从 `A/src/deep` 启动仍写 `A` 的项目桶；
- `A` / `a` 在 Windows 上同桶；Linux 上是否同桶以平台语义为准；测试不能把 Windows 规则硬套到 Linux；
- NFC/NFD 中文或组合字符不会创建两个桶；
- 非 git 目录仍能用显式项目根工作，但需要诊断信息；
- git worktree / 子模块必须在 P0 做真实探针后写清策略，默认建议：`.git` 指向公共 git common dir 的 worktree 仍归主项目，除非显式 `--project-root`；`--separate-git-dir` 不得误判；
- 长路径超过 Windows 常见限制时仍返回可复现 key，不因截断撞车；
- `Path.resolve()` 对不存在子目录/断链的失败路径只允许落到已存在的最近祖先，不允许静默回退到当前进程 cwd。

### 2.4 teamKey 设计

CC 303 原生 team/task namespace 是全局层，不带 projectKey。GA 为了满足多项目同名 team 不串板，增加项目作用域：

```text
teamKey = <sanitized-projectKey>--<sanitized-teamName>
```

约束：

- `teamKey` 只进入目录名与 team identity，不改变 UI 显示的 team name；
- lead 与所有 teammate 必须继承同一个 `teamKey`；
- process child 注入 `GA_TEAM_KEY`；`GA_TEAM_NAME` 保留显示语义；
- task board、共享 swarm ledger/roster、bridge reader 使用同一 `teamKey`；
- **subagent registry 不使用 `teamKey`**：它是项目运行数据，位于 `PROJECT_DATA_DIR/subagents`；`teamKey` 不能替代项目桶，也不能让不同 agent 各建一份；
- 每个 agent 的 `mailbox.jsonl` 仍位于自己的 `task_dir`；只有 mailbox ledger 这类跨 agent bookkeeping 按 teamKey/project data 处理；
- 旧 team 若没有 `teamKey`，按 session 元数据只读兼容，不自动合并。

### 2.5 named workflow 定义库与运行 artifact 分离

这是本次目录改造最容易漏掉的兼容点。GA 当前 `WorkflowStore.root` 同时承担两类职责：

```text
run journal/artifact: <root>/<session>/workflows/<runId>/
named definition:     <root>/named-workflows/<slug>.json
```

如果只把 `root` 换成 `PROJECT_DATA_DIR`，定义库会随项目桶移动；现有全局 named workflow 会“消失”，nested `workflow({name})` 也会断。必须把它拆成“运行 artifact root”和“定义库 roots”。

#### 2.5.1 目标 scope

| scope | 读/写位置 | 默认 | 说明 |
| --- | --- | --- | --- |
| project | `<PROJECT_ROOT>/.ga/workflows/<slug>.json` | 保存默认 | 跟项目走；项目 A/B 同名不互相覆盖 |
| user | `<DATA_ROOT>/workflows/<slug>.json` | 显式选择 | 跨项目共享，类似 CC `<configHome>/workflows` |
| legacy | `<DATA_ROOT>/temp/sessions/named-workflows/<slug>.json` | 只读 | 迁移期兼容，当前 GA 全局库 |

运行 journal/artifact 仍永远写到 `PROJECT_DATA_DIR`：

```text
<PROJECT_DATA_DIR>/<sessionId>/workflows/<runId>/
```

定义库不是 run state；不能放在 `<sessionId>`、`<runId>` 或 `named-workflows` 旧根下再靠“猜”迁移。

#### 2.5.2 解析与冲突规则

`WorkflowStore` 新增显式字段或独立 `NamedWorkflowRegistry`：

```python
WorkflowStore(
    root=project_data_dir,          # run artifact only
    project_workflows_dir=...,      # PROJECT_ROOT/.ga/workflows
    user_workflows_dir=...,         # DATA_ROOT/workflows
    legacy_workflows_dir=...,       # DATA_ROOT/temp/sessions/named-workflows
)
```

加载优先级固定为：

```text
project > user > legacy
```

同 scope 同名文件冲突：列出来源并报错，不静默覆盖。不同 scope 同名：project 覆盖 user，但列表仍应显示 `scope`/`source`，方便用户理解为什么实际执行的是项目版本。legacy 只读、可见、可显式复制/迁移；不自动写回，也不自动复制到每个项目。

保存规则：

- `save_named_workflow(..., scope="project")` 默认保存到 `PROJECT_ROOT/.ga/workflows`；
- `scope="user"` 必须显式指定，写入 `DATA_ROOT/workflows`；
- 非 git/不可写项目根等失败要返回可诊断错误；不能 fallback 到用户库；
- 同 scope 未 `overwrite` 必须报 `FileExistsError`；
- 写入仍用原子替换，不删除旧版本。

读取规则：

- `load_named_workflow(name)` 按 project > user > legacy 查找；
- `list_named_workflows()` 返回合并列表，附 `scope`、`source`、`path`、`shadowed_by`（若适用）；
- nested `workflow({name})` 在 `WorkflowRuntime._resolve_nested_workflow_script()` 中必须调用同一个 resolver；不能直接 `store.load_named_workflow()` 绕过 scope；
- `workflow({scriptPath})` 继续遵守当前 workspace 硬边界，不再额外解析 named definition；
- 测试注入的 `workflow_root=` 保留并把 artifact root 与 definition roots 都指向测试目录，避免 500+ 现有测试失效。

#### 2.5.3 兼容与迁移

- 旧 `<DATA_ROOT>/temp/sessions/named-workflows/*.json` 在首次列表/读取时可见；
- 写入新定义绝不覆盖 legacy；
- 可选 `ga workflows migrate --dry-run` 只列出来源、目标、冲突，不默认 apply；
- apply 只 copy、不删除 legacy；若目标存在则停；
- 旧 `sourceRunId` 指向的 artifact 仍按 run 的绝对 `artifactDir` 读；
- 如果旧 run 已不存在，定义仍可单独加载。

### 3.6 Agent Team 身份传播链（teamName 与 teamKey 分离）

当前 GA 只有显示/派生层 `team_name`，很容易在目录改造后出现“lead 看到自己的板、teammate 看另一个板”：

```text
manager.team_name = "default"
child env: GA_TEAM_NAME only
handler._team_name(): team_name_for(parent.session_id)
task store: <state_root>/temp/teams/<list_id>
bridge reader: state_root/temp/subagents + SubagentTaskStore(...)
teammate idle: 从 task_dir 反推 root_dir，再按 parent_session_id 派生 team_name
```

方案要求同时存在：

```text
team_name = "session-xxxxxxxx"          # UI 显示与 CC 语义
team_key  = "<projectKey>--<team_name>" # GA 的目录/身份隔离 key
```

`team_key` 是 GA 产品增强，因为 CC 303 原生 `teams/<name>`、`tasks/<name>` 是全局层，不带 projectKey。实施时必须保持“全局 `DATA_ROOT/teams`、`DATA_ROOT/tasks` 目录层 + teamKey 项目隔离”，而不是把这两个根搬到 `PROJECT_DATA_DIR`。

传播点必须逐项核对：

| 传播点 | 必须写入/传递 | 验收 |
| --- | --- | --- |
| `SubagentManager.__init__` | `team_name`、`team_key`、`project_root`、`project_data_dir`、`state_root` | 四者独立，禁止再靠 temp_dir 反推 |
| `Manager._child_popen_kwargs` | `GA_PROJECT_ROOT`、`GA_PROJECT_DATA_DIR`、`GA_DATA_DIR`、`GA_TEAM_NAME`、`GA_TEAM_KEY` | child 不根据自己的新 session 重新派生 team |
| `GenericAgentHandler._team_name` / task tools | 以 `team_key` 选板、以 `team_name` 显示 | 任务 create/update/list/claim 全部同一个 key |
| `core/app.py` child worker / teammate idle | 从 state/env 读 `team_key` 和显式 `task_dir` | 不靠 `task_dir` 向上两级猜项目 |
| `SubagentTaskStore` | 新路径接受 `team_key` 或显式 task root；旧参数只做 legacy adapter | `DATA_ROOT/tasks/<team_key>` |
| `SubagentTeam` / roster | registry 与 task board 使用同一个 project identity；registry 本身仍是 project runtime state | roster 不串项目 |
| `swarm` / mailbox / receipt ledger | 共享 ledger 按显式 project-data/team scope；消息仍落各 agent 的 `mailbox.jsonl` | 不把所有 mailbox 内容混写到一个 JSONL |
| Ink bridge `_team_roster_payload` | writer 同一套 `team_name_for` + `team_key_for` + path API | UI reader 不手拼 `temp` |
| manager `task_store()` / handler `_get_task_store()` | 必须显式传 task root/team key，不能从 `self.state_root/temp` 推导 | A/B 同名 team 不串板 |
| hooks `TeammateIdle` | 传显示名和 team_key | hook 可区分项目但 UI 仍显示短名 |

特别说明 mailbox：当前消息文件是各 agent `task_dir/mailbox.jsonl`，而 swarm 的共享 ledger/roster 在 `<state_root>/temp/subagents/`。目录改造不能笼统写成“mailbox 改到 teamKey”；正确做法是：

- 共享 ledger/roster 与任务板：按 `teamKey` 或显式 project-data 作用域；
- 每个 agent 的 inbox/outbox、mailbox 文件和 transcript：继续跟 `task_dir`/session project bucket；
- bridge 的 team panel：registry 从 `PROJECT_DATA_DIR/subagents` 读，任务板从 `DATA_ROOT/tasks/<teamKey>` 读，两个来源都必须显式；
- 禁止让一个 `teamKey` 同时成为 registry 根和 task-board 根，否则会把“项目运行数据”和“团队身份”再次揉成一个变量。

旧兼容：

- 旧 team/task 没有 `team_key`：用 session/project metadata 只读映射；
- 新写入不可把旧全局板当作某个项目的板进行写入；
- UI 若显示 legacy 来源，必须标注，不能只显示短 team name 导致误认；
- 迁移不自动合并同名 old/new 板。

### 3.7 workflow 隔离子代理与 git worktree 不是同一机制

已复核源码后必须明确区分：

```text
普通 subagent / Agent Team isolation=worktree
  → create_subagent_worktree()
  → 真 git worktree
  → <PROJECT_ROOT>/.ga/worktrees/<runId>

workflow job isolation="worktree"
  → workflow/child_agent.py 的私有工作副本
  → 复制 shared workflow workspace
  → <PROJECT_DATA_DIR>/workflow_child_agents/<runId>/<jobId>
```

当前 GA 实现：

- `agents/manager.py:850-855` 创建真 git worktree，但位置在旧 `state_root/temp/subagents/worktrees`；
- `workflow/child_agent.py:28-39` 的 “worktree” 实际是 `TEMP_DIR/workflow_child_agents`；
- `workflow/workspace.py` 的 run workspace 是 `TEMP_DIR/workflow-runs/<runId>`。

因此 P4 只能迁 git worktree 到用户项目 `.ga/worktrees`；P3 只能迁 workflow workspace/child copies 到 `PROJECT_DATA_DIR`。两者不能共用 `WORKTREE_ROOT`，也不能互相做 recursive cleanup。

项目文档也要显式传 identity：

- `core/app.py:515` 目前 `build_ga_project_instructions(script_dir, os.getcwd())`；
- `workflow/child_agent.py:1191-1206` 目前同样的 `PROJECT_ROOT + os.getcwd()`；
- 改造后 root agent、普通 child、workflow child 都显式传 `project_root` 和受控 `current_dir`；
- workflow child 的 current_dir 可以是项目内当前子目录或 workspace 映射，不能拿私有 workflow workspace 当项目文档根；
- 任何 `os.getcwd()` 只允许作为 CLI 启动捕获或诊断，不允许再次决定项目身份。

### 5.2 身份对象

@dataclass(frozen=True)
class RuntimePaths:
    package_root: Path

### 5.3 子进程协议

原则：child env 是“身份快照”，不是重新推导入口。凡是无法从 parent 明确传入的路径，child 必须失败并带诊断，而不是用 cwd/安装目录兜底。

新增并持久化：

```text
GA_PROJECT_ROOT=<用户项目>
GA_PROJECT_DATA_DIR=<项目桶>
GA_DATA_DIR=<全局数据根>
GA_TEAM_KEY=<projectKey--teamName>
GA_TEAM_NAME=<显示名>
GA_TASK_DIR=<显式任务目录>
GA_SESSION_ID=<父/当前 session>
GA_ORIGINAL_CWD=<启动目录，仅审计/恢复>
GA_TOOL_CWD=<当前执行目录>
GA_PROJECT_KEY=<稳定 projectKey>
GA_WORKTREE_ROOT=<项目 .ga/worktrees>
GA_SESSION_DATA_DIR=<当前 session project-local 数据目录>
```

兼容规则：

- 新 child 优先 `--task_dir`；
- 无 `--task_dir` 时用 `--state_root` + 新项目桶规则；
- 旧 `--task_root` 仅按 legacy 规则解析，不能当作新 project root；
- child 启动时校验 `GA_PROJECT_ROOT`、`GA_PROJECT_DATA_DIR`、`GA_PROJECT_KEY` 三者一致；不一致直接报 `project_identity_mismatch`；
- child 的 `GA_TEAM_KEY` 必须由 parent 传入；若缺失且 `team_mode=true`，禁止自行按 session 派生新 key；
- 启动诊断日志记录 original/project/launch/tool/data/project-data/worktree 的 resolved 值，并脱敏完整 home 路径；
- 新 child 不读取 `GA_LAUNCH_CWD` 重建 key；该变量只供顶层诊断/恢复。

### 5.4 关键接口契约

先写接口和失败语义，再改调用点；否则各模块会各自补一套“差不多”的拼接逻辑。

```python
class WorkflowStore:
    def __init__(
        self,
        root=None,                       # run artifact only; test workflow_root maps here
        *,
        project_workflows_dir=None,
        user_workflows_dir=None,
        legacy_workflows_dir=None,
        named_workflow_resolver=None,    # optional injected resolver
    ): ...

    def save_named_workflow(
        self, name, script, *, scope="project", overwrite=False,
        source_run_id=None, description=None,
    ) -> dict: ...

    def load_named_workflow(self, name, *, scope="auto") -> dict: ...
    def list_named_workflows(self, *, include_shadowed=False) -> list[dict]: ...
```

失败语义：

| 情况 | 结果 |
| --- | --- |
| project definition 不可写 | 明确 `PermissionError`/`ProjectScopeUnavailable`；不 fallback 到 user |
| 同名 project 文件已存在且未 overwrite | `FileExistsError`，保留原文件 |
| 同名 user 已存在，project 新建 | 允许，project 覆盖 user；列表标记 `user_shadowed=true` |
| project 文件损坏 | 报错并保留 user 候选，不能静默 fallback 导致执行错版本 |
| legacy 损坏 | 跳过并记录诊断，不影响新 project/user |
| `workflow({name})` 找不到 | `FileNotFoundError` 带 candidate scopes，不扫描整个 DATA_ROOT |

Team/task 接口：

```python
team_name_for(session_id, env=None) -> str       # 显示名 / CC 兼容
team_key_for(project_key, team_name) -> str      # GA 目录身份
task_store_for(team_key, data_root) -> SubagentTaskStore
```

`SubagentTaskStore` 新构造器至少接受显式 `tasks_root`（或 `data_root + team_key`），旧 `root_dir/state_root/list_id` 只作为 legacy adapter。`tasks_root` 必须与 `DATA_ROOT/tasks` 一致；不能从 child cwd 反推。

### 5.5 session 启动事件的最小兼容字段

v2 `session_start` 当前只有 `cwd/frontend` 的基础字段。目录改造要保持 legacy parser 可读，同时让 resume 能恢复项目身份：

```json
{
  "version": 2,
  "type": "session_start",
  "session_id": "session_...",
  "created_at": "...",
  "original_cwd": "D:\work\A",
  "project_root": "D:\work\A",
  "launch_cwd": "D:\work\A\src",
  "cwd": "D:\work\A",
  "project_key": "A-4f2c...",
  "data_root": "D:\ga-data",
  "layout": "project-v1",
  "frontend": "ink"
}
```

规则：

- 新字段 additive，旧 reader 忽略未知字段；
- 旧 v1/v2 session 没有字段时，不能把当前 cwd 当项目身份；只能按 legacy/用户认领流程；
- `load_session()` 应把 identity 放进 `LoadedSession`（或单独 `SessionIdentity`），不要靠 consumer 再读第一行；
- `restore_agent_session()` 先恢复 identity，再让 bridge/handler 用它构造 `RuntimePaths`；
- `ensure_agent_session()` 新建 session 时显式传 identity，不允许 `cwd=os.getcwd()` 兜底；
- session 的 `cwd` 保留旧语义，新增 `original_cwd`/`project_root` 避免改名破坏旧数据。

- 输出诊断时区分 `writer_path`、`reader_path` 与 `source_scope`。

**DoD**

- writer/reader 对 session、subagent、workflow、task 的位置完全一致；
- UI 列表、详情、resume、workflow 进度树在 A/B 双项目下无串数据；
- 旧会话仍能在 legacy 视图中列出，不会因 reader 统一而消失；
- 任一新增手拼路径都能被静态检索门禁发现。

**回滚**

- 保留旧 reader 适配器，但只作为读取 fallback；回滚时恢复旧 reader 接线，不删除新桶。

### P7：显式迁移、`--all` 与 legacy 认领

**改动**

- 新增迁移 CLI，默认 `--dry-run`，输出 source、target、冲突、预计字节数；
- `--apply` 才复制数据，禁止删除源；
- named workflow 支持 project/user/legacy 三 scope 迁移；
- `/resume --all`、`/workflows --all` 可显示跨项目 legacy 条目和来源；
- 用户显式认领后，只追加 identity 元数据，不移动或重写原 transcript；
- 增加迁移报告文件，记录时间、操作者、source/target、hash、结果。

**DoD**

- 无身份旧 session 默认不进入项目主视图，只在 `--all` 出现；
- 认领前后原 JSONL 字节不变；
- 同名冲突停止，不覆盖任何目标；
- 迁移可中断、可重跑，已复制且 hash 一致的目标可跳过；
- 迁移完成后旧 `temp/` 仍可读，删除与否必须由用户另行决定。

**回滚**

- 迁移只产生副本和元数据，可停止使用新副本并回到 legacy reader；
- 不提供自动反向删除，避免误删用户数据。

## 8. 新旧兼容与迁移

### 8.1 规则

- 新写入只使用新布局；
- 旧布局只读，路径来源标记为 `legacy`；
- 旧 session 的 `cwd` 不能被自动当作可靠项目归属；
- 迁移必须由用户显式运行，默认 dry-run；
- apply 只 copy/link/update metadata，不删除源；
- 任何同名冲突停止并打印 source/target。

### 8.2 legacy 查找顺序

session：

1. 当前 project bucket；
2. session metadata 的 `legacy_project_root`；
3. 旧 `temp/sessions` 全局目录，但只用于显式“全部项目”或用户认领；
4. 没有 identity 的旧 session 默认不出现在项目 `/resume` 主列表，只出现在 `--all`/认领视图。

workflow：

1. run/state 中的绝对 `artifactDir`；
2. 当前 project bucket；
3. 旧 `temp/sessions`，按 session/run 匹配，不做无约束扫描。

named workflow：

1. `<PROJECT_ROOT>/.ga/workflows/<slug>.json`；
2. `<DATA_ROOT>/workflows/<slug>.json`；
3. `<DATA_ROOT>/temp/sessions/named-workflows/<slug>.json`；
4. 任何 legacy 命中都只读，写入新建定义时不得覆盖它；nested `workflow({name})` 与顶层使用同一顺序。

subagent：

1. 当前 `<session>/subagents`；
2. 旧 `<temp>/sessions/<session>/subagents`；
3. registry 中的 `task_dir`/`transcript_ref` 绝对路径；
4. 旧 workflow transcript 的 `workflow-runs`/workflow subdir 形式按 registry 记录回读，不按新 base 重拼。

### 8.3 不允许

- 自动把旧 session 搬到当前项目；
- 用 `session_start.cwd` 猜测历史归属后静默合并；
- 自动删除旧 `temp/`；
- 把 legacy 与当前桶同名文件覆盖；
- 只迁移 JSONL 而忽略 `subagents/`、workflow artifact、named workflow 定义和 team task；
- 把 legacy named workflow 当作当前项目定义并允许 overwrite；
- 对旧 session 的 `cwd = GA 仓库/Ink UI` 做“看起来像”自动修复。

## 10. Go / No-Go

### Go

- P0/P1 的单测与 CLI 冒烟通过；
- P1.5 的拆根测试通过；
- P2/P3 的双项目隔离、legacy、workflow resume 全部通过；

- P6 writer/reader 同源测试通过；
- P7 dry-run/apply、legacy 认领与冲突门禁通过。

### No-Go

- 任一 reader 仍手拼旧 `temp/sessions`；
- workflow 的 store 与 workspace 仍分裂；
- team board 仍无法证明跨项目隔离；
- worktree 清理没有 containment；
- legacy 读取会覆盖新数据；
- 项目角色/文档随 DATA_ROOT 改变。

## 11. 回滚策略

| 层 | 开关/策略 |
| --- | --- |
| 启动身份 | `GA_PROJECT_LAYOUT=legacy` |
| 数据布局 | 新旧 reader 同时保留，writer 按版本切回 |
| 工具 cwd | `GA_TOOL_CWD=temp` |
| Agent Team | 保留旧 `teamName` 解析路径，teamKey 不写回旧 board |
| workflow | 优先使用 run 内绝对 `artifactDir/workspacePath` |
| worktree | 只清理 registry 登记且 containment 通过的路径 |

回滚不得删除新桶中的用户数据；只停止写入并恢复旧 writer。

## 12. Definition of Done

目录改造只有在以下全部成立时才完成：

- 普通会话、subagent、workflow、Agent Team、resume、worktree 六条链路都通过；
- `original_cwd`、`project_root`、`launch_cwd`、`cwd` 四者语义清楚且持久化；
- project/config/data/tool/worktree 根在日志中可核验；
- A/B 数据严格隔离；
- named workflow 的 project/user/legacy scope 与 nested 执行全部通过；
- 项目配置和项目文档始终来自用户项目；
- legacy 数据只读可见；
- 无自动搬迁、无原始 JSONL 删除、无物理压缩；
- 图片读取能力未被夹带进入本次改造。
