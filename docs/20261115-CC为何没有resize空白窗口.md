# 为什么 CC 没有 GA 的 resize 空白窗口

**日期**：2026-11-15
**问题**：GA 在终端宽度变化后有约 140ms 的历史空白窗口（见
`frontends/ink/ui/probes/resize_blank_window.ts`）。CC 有没有同样的问题？为什么？

**结论**：CC 没有这个问题，而且不是因为它把延迟调得更准 —— 是**写入模型不同**。
GA 沿用 ink 的「相对擦除 + 分多次写」，CC 早已改成「屏幕缓冲区 diff + 一帧合并成一次写」。
GA 那个 120ms 延迟是给前一种模型的补丁；换成后一种模型，这个补丁连同空白窗口一起消失。

> 证据来源：`claudecode319/modules/m0701_0x122b603a.js`（378 KB，CC 的渲染器）。
> 引用时给的是该模块内的函数名与代码片段，模块编号不可跨版本平移（见 AGENTS.md §3.2）。

---

## 1. GA 现在的写入模型（ink 的）

`node_modules/ink/build/log-update.js`：

```js
let previousLineCount = 0;                    // ← 上一次写出的行数
stream.write(ansiEscapes.eraseLines(previousLineCount) + output);
previousLineCount = output.split('\n').length;
```

每帧的动作是：**按上一次的行数，用相对光标移动往上擦 n 行，再写全量 output。**

这个模型把两个数字绑在了不同的时间点上：

- `previousLineCount` 是**上一次写帧时**算出来的
- 而终端在宽度变化时会 reflow，那一帧在屏幕上**实际占用的行数**已经变了

于是 resize 之后第一次写，擦除用的行数是旧宽度下的，擦不干净 → 残留或误擦。
GA 的应对是整屏重置 + 重挂 `<Static>` 全量重发历史。

更麻烦的是 ink 把这层包了两个 `throttle`（`ink.js:39,45`）：

```js
this.rootNode.onRender = throttle(this.onRender, 32, {leading: true, trailing: true});
this.throttledLog      = throttle(this.log,      undefined, {leading: true, trailing: true});
```

resize 那一刻节流窗口里可能挂着一次**延迟执行的尾帧**，它捕获的 output 是 resize 之前的
（只有 live 区）。它晚于「整屏重置 + 重挂」落地时，就按旧行数擦一遍、只重画 live ——
刚重发的历史被擦掉。

`probes/resize_write_timeline.ts` 抓到的正是这一幕：

```
失败轮  t+ 77ms  含 static 的帧（历史回来了）
        t+123ms  eraseLines(10) + 只写 live   ← 用旧行数擦，历史被抹掉
通过轮  t+130ms  陈旧 tail 帧先落地
        t+245ms  含 static 的重挂帧之后才发生   ← 安全
```

因为结果取决于**谁先谁后**，而不是延迟的绝对值，所以通过率对延迟值不单调
（48ms 7/10、64ms 4/10、120ms 12/12）。这就是为什么调小延迟救不了。

## 2. CC 的写入模型：屏幕缓冲区 + diff + 一帧一次写

CC 的渲染器（`m0701`）里，`render()` 拿到的是**上一帧的屏幕缓冲区 `n` 与这一帧的 `u`**，
两者都是逐格（cell）的网格，而不是字符串：

```js
render(n, u, c = !1, m = !0) {   // n = prev screen, u = next screen
  ...
  if (u.viewport.height < n.viewport.height
      || u.viewport.height > n.viewport.height && A
      || n.viewport.width !== 0 && u.viewport.width !== n.viewport.width)
    return Nl(u, "resize", g, c, O);
```

`Cg(n.screen, u.screen, callback)` 逐格比对两帧，**只对真正变化的格子**发操作
（`cursorTo` / `stdout` / `styleStr`）。没有「按上一次行数整体擦掉再全量重画」这一步，
所以**根本不存在「上一次行数」这个会过期的状态**。

resize 走 `Nl`：

```js
function Nl(n, u, c, m, p, g) {                        // u = "resize"
  let E = m ? 0 : Math.min(p, Math.max(0, n.screen.height - n.viewport.height + 1)),
      A = new rf({x: 0, y: E}, n.viewport.width);
  return Hb(A, n, E, n.screen.height, c),
    [{type: "clearTerminal", reason: u, altScreen: m, viewportRows: n.viewport.height, debug: g},
     ...A.diff];                                        // ← 清屏 + 整屏重绘 = 同一个数组
}
```

`Hb` 把第 `E` 到 `n.screen.height` 行**逐格**写进同一个 diff 缓冲区。关键在返回值：
`[clearTerminal, ...整屏重绘的 ops]` 是**一个**数组。

然后 `E$o` 把这个数组拼成**一个字符串、一次 write**：

```js
function E$o(r, n, o = !1, u, s = "") {
  ...
  for (let c of n) switch (c.type) {
    case "stdout":        d += c.content; break;
    case "clear":         if (c.count > 0) d += Adn(c.count); break;
    case "clearTerminal": d += c.altScreen ? ... : uEt(c.viewportRows); break;
    ...
  }
  J5n(r, d);                                            // ← 整个帧只有这一次 stdout.write
}
```

**清屏和重绘之间没有任何时间窗口。** 终端先收 `clearTerminal`，紧接着就是完整的历史行，
中间不会插进一个「只写 live 的陈旧帧」—— 因为陈旧帧这个概念在 CC 里不存在：
CC 没有 32ms 的 `throttle(log)`，每帧的 ops 都是基于**当时的**屏幕缓冲区算的，
不存在「先捕获 output、稍后再写」的二段式。

## 3. 对照表

| | GA（ink） | CC（自研渲染器） |
| --- | --- | --- |
| 帧状态 | 字符串 output | 逐格屏幕缓冲区（cell grid） |
| 擦除依据 | `previousLineCount`（上次写帧时算的） | 无此概念；逐格 diff |
| resize 处理 | 整屏重置 + 延迟 120ms 重挂 `<Static>` | `clearTerminal` + 整屏重绘，同一 ops 数组 |
| 一帧写入次数 | 多次（`log.clear` / `static` / `log` 各自 write） | **一次**（`E$o` 合并后 `stdout.write`） |
| 有无延迟节流 | 有，32ms 双重 `throttle` | 无 `throttle(log)`（渲染按帧驱动） |
| 陈旧尾帧 | **存在**，是空白窗口的成因 | **不存在**（无二段式写） |
| 空白窗口 | ~140ms | 0（清屏与重绘同一次写） |

## 4. GA 想消掉这 140ms 意味着什么

不是「把 120 调小」（已证否，见 §1 的不单调性），而是**改写入模型**。按代价从低到高：

**A. 接管 stdout 写入，在写之前合并成一个 chunk。**
最贴近 CC 的 `E$o` 思路，但只做「合并」不做 cell diff。GA 的 `cursorPark` 已经是一个
stdout 包裹层（`src/stdoutCursorPark.ts`），同一个位置可以做。难点：ink 是分多次
`write` 的（`log.clear()` → `static` → `log(output)`），要在一个微任务内全部缓冲、
合并、一次写出。`cursorPark` 现在已经是「缓冲 + microtask flush」的模型，**这条最可行**。
但要注意：它不能消掉 32ms 节流尾帧 —— 尾帧是**时间上更晚**才产生的 write，不是同一批。

**B. 让 resize 之后的那次陈旧尾帧无效。**
`ink.js` 把 `throttledLog` 存在实例内部、没暴露，所以只能 fork/patch ink，或
在包裹层做识别（问题：包裹层看到的只是字符串，很难可靠判断「这是 resize 前的 output」）。

**C. 像 CC 一样自研渲染器。**
彻底、也最贵。除非 GA 还要解决更多 ink 结构性限制，不值得。

**D. 接受这 140ms。**
它只在**宽度变化**时发生，用户拖窗口时看到一次整屏重绘，而不是持续抖动。
CC 值得学的是模型，不是「CC 没有这个窗口所以我们必须现在也有」—— 因为对 GA 来说，
A/B 都要动 ink 的边界，风险显著高于收益。

## 4.5 方案 A 已实测：只成功一半，不足以消掉常量

2026-11-15 实现了 A 的前半部分并实测，结论是**不能**靠它把 `RESIZE_REMOUNT_DELAY_MS` 降到 0。

**做了什么**：`cursorPark.resetViewport` 原先直接 `sink(sequence)` 立即写出重置，然后
App 再延迟 120ms 重挂 `<Static>`。改成把重置**放回缓冲区**，与紧随其后的整屏重绘合并成
一次写出（缓冲里属于旧几何的内容直接丢弃）。

**成功的一半**：重置不再单独冒出来，因此「重置之后、重绘之前屏幕全空」这个中间态消失了。
单测 `resetViewport waits for the repaint instead of leaving a blank screen` 能稳定证明这一点。

**失败的一半**：ink 的 32ms trailing throttle 留下的**陈旧尾帧**仍在。它晚于整屏重绘落地，
擦除计数属于旧几何、内容只有 live 区。实测（`probes/resize_write_dump.ts`）：

```
[1] t+ 21ms  擦 10 行 + 15 行内容（含 static 历史）   ← 正确
[2] t+122ms  擦 10 行 +  9 行内容（只有 live 区）     ← 把历史抹掉
```

只做原子化之后，`probes/resize_blank_window.ts` 连续 5 次的结果是 2 次干净、3 次在
t+73~126ms 处历史消失 —— 即**没有**解决问题。

**为什么包裹层挡不住**：那个写入在**时间上更晚**才产生，且内容**已经算错**（ink 在 resize
前就捕获好了 output 字符串）。`cursorPark` 能看到它，但要「修正」它必须知道这一帧本该有
哪些历史行 ——`prevRows` 确实记着，于是试过「用 `prevRows` 补全前缀」的修复，但实现时
改动了 `computeLineDiff` / `recognizeFrame` 的契约，一次性弄红 3 个不相关测试
（`unpark before next write`、`up=0 park`、`line diff falls back when frame shrinks`），
说明影响面比预期宽，已回退。

**所以正确的结论是**：要走 A，必须连**陈旧帧的源头**一起处理（fork/patch ink 的
`throttledLog`，或接管 `onRender` 调度），单改 `cursorPark` 不够。当前保留 120ms。

---

## 5. 一句话

GA 的 140ms 空白窗口不是延迟没调好，是 ink「相对擦除 + 二段式写」与终端 reflow 的结构性
冲突造成的；CC 因为用「屏幕缓冲区 diff + 一帧一次写」，这个冲突不存在，所以它不需要那
120ms。要消掉它，正确方向是 A（在 `cursorPark` 这一层合并写入），不是继续调常量 ——
但 §4.5 的实测补充：**A 只做包裹层合并只能解决一半**，还要处理陈旧尾帧的源头。

## 6. 一条方法论教训（同一轮踩到）

排查过程中我把「延迟扫描 0~120ms 全绿」当成了「机制修好了」，并在代码注释里写下了
「空白窗口降到 4~7ms」。那是错的：延迟扫描每档只观察 `delayMs + 600`，判据是**最终屏幕**，
它看不见 t+120ms 附近那个陈旧帧。

`probes/resize_blank_window.ts`（连续采样时间线）才暴露真相：5 次里 3 次失败。

教训与 `CLAUDE.md` 的硬规则 5 是同一件事，但这次犯在新维度上：**不只是「采样次数不够」，
还有「采样窗口太窄」**。验证「某段窗口消失了」时，观察窗必须覆盖到**比该窗口更晚**的
所有可疑事件，否则那个更晚的事件正好落在窗外。
