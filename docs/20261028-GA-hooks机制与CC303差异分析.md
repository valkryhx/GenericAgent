# 20261028-GenericAgent hooks 机制与 Claude Code 2.1.303 差异分析（只读）

> 只读分析：不改任何源码。对照 GA `genericagent/hooks/` + `core/{loop,handler,app}.py` 的现状，
> 和 CC 303 hooks（`claudecode303/extracted/20261020-hooks入口分析.md` 的权威坐标：33 事件 m0062:501、五类型 m0062:2636、
> 输入输出 m0120:6808-7203、执行 m0459）逐条核对。
> 本文是你的提问“GA 当前 hook 实现需不需要优化”的结论：**需要，且有好几处会直接影响你要复刻的 goal 模式。**

---

## 1. 结论先行

GA 的 hook 实现**底子不错但离 CC 303 还不一致，主要差在两层**：

1. **“执行/事件面”基本对齐**：33 事件词表、5 种 handler、`matcher` + handler 级 `if` 过滤、http 目标策略、
   `onFailure` 忽略集、`$ARGUMENTS/$HOOK_EVENT/$SESSION_ID/$CWD` 替换、五种执行器、audit 日志——这些做得很细、坐标也常对得上 CC。
2. **“语义/生命周期面”明显偏薄**：关键的阻塞/继续闭环、会话级动态 hook、并发、守卫 fail-closed、prompt 求值结构化、
   大量事件实测从未发射——这些正是 CC 高阶能力（goal / asyncRewake / 权限守卫 / 复杂编排）的根基，GA 目前对不上。

一句话：**GA 是“能跑通的简化版 events + 五种 executor”，但还没有 CC 那套“带决策闭环的 hook 语义”。**
goal 模式（以及任何“hook 决定回合是否继续”的能力）目前搭不上——这正是上一份 goal 方案里 `goal_guard`
必须另起炉灶的原因之一，也是本文要讲清楚的根本矛盾。

## 3. 差异清单（按严重度排序）

### 3.1 P1 · `Stop`/`StopFailure`/`SubagentStop` 是“观察式发射”，没有阻塞/继续闭环 —— 最不一致

`core/app.py:1263-1274`、`:1298-1309`、`:2007-2028` 只是**把 `Stop`/`StopFailure`/`SubagentStop` 事件跑一遍，
返回值不检查**：

```python
# app.py:1263（用户回合收尾）
run_hook_event(self, 'Stop', { 'stop_hook_active': False,
                               'last_assistant_message': final_assistant_text,
                               'exit_reason': ..., 'source': ... }, emit=...)
```

- 无论 hook 返回 `{decision:"block"}` 还是 `{preventContinuation:true}`，结果都被丢弃；
- 触发点固定在 `GenericAgent.run()` 收尾（整个用户回合结束），**不是 CC 的 `blockable_turn_end` / `loop_tick` /
  `fork_dispatch`**（m0671:3167、:3351-3471）那种“模型这轮想停”的时刻；
- CC 里 Stop hook 可以阻塞并让回合继续（goal 机制就是靠 `blockingError` + `preventContinuation` 实现的，见
  `m0459:154492-154533`、`m0671:3419-3458`）；
- GA 里 Stop hook **只能被“听到/记录”，永远无法阻止回合结束**。

补充：`.blocked` / `prevent_continuation` 的消费其实已经在别处做过了——
`PreToolUse`（`handler.py:567`）、`UserPromptSubmit`（`app.py:1064`）、`PermissionRequest`（`handler.py:489`）、
`PreCompact`（`app.py:1002`）、空闲(`TeammateIdle`，`app.py:1928`)都读取了 aggregate 的 `blocked`。也就是说 GA 已经有“看结果”的机制，
唯独 **`Stop` / `StopFailure` / `SubagentStop` 这条链路没接上**，所以是“单点缺失”而非“全无基建”。

影响：除了 goal 模式，任何“hook 决定要不要收尾/续跑”的能力（Stop 守卫、异步唤醒续跑兜底）都搭不上。
这是 P1，因为它直接决定 CC Stop 语义是否成立。

### 3.2 P1 · 没有运行时“会话级动态 hook”注册/移除能力

CC 支持向**当前会话**运行时注册带 `agentId` 的 Stop hook（goal 用它，见 `m0274` 的 `sessionHooksRegistry.add(sessionId,"Stop",...)`）。
GA 的 `HookRegistry`（`hooks/config.py:10-21`）**只从文件加载静态 entries**，只有 `for_event()`/`add_issue()`，
没有任何运行时 `add/remove` 入口。

影响：goal、临时守门、会话内一次性 hook（CC 的 `once` 会有，但这是配置级 once）都无法在 GA 现结构上实现周中增减。
这也是让 `goal_guard` 只能单独造状态机、而不能直接复用“加一条目标 Stop hook”的根本原因。

### 3.3 P2 · 并发模型不同：GA 串行执行，CC 非 prompt/agent 并行 + 上限 12

`hooks/runtime.py` 的 `run_event` 是**顺序 for 循环**：`for entry ...: for handler ...: execute_handler(...)`（非 async 走同步）。
CC 是 **非 prompt/agent 可并行，prompt/agent 串行；整体并发上限 12；结果按完成顺序 yield**（权威坐标
`m0459:155268-155275`，见 `20261020-hooks入口分析.md` §11）。

影响：多个独立 command/http hook 在 GA 里只能串行排队，延迟累加、且不满足 CC 的“并行+12 上限”契约。
对要并行校验多条件的场景（安全校验、多路通知）差别明显（属性能/契约差异，非安全）。


### 3.4 P1 · 守卫事件配置错误是 fail-open，而 CC 是 fail-closed

`hooks/config.py:_parse_handler` 对非法 handler 一律 `add_issue(...)` + `return None`（**静默跳过**）；
`load_hook_registry` 也只收集 issues，不做 fail-closed。于是：

- 一个写错的 `PreToolUse` / `PermissionRequest` 守卫 hook，在 GA 里会被直接忽略，工具照常放行；
- CC 对 `PreToolUse` / `PermissionRequest` 的配置/运行错误是 **fail-closed**（`m0062:2815`、`:2893`；
  `m0459:55453-55475`）：坏守卫可能就是权限门，不能静默放行，构造 `blockingError`、`PermissionRequest` 还返回 deny。

影响：这是**安全相关的放行缺口**——守卫写坏 = 门被拆掉而不告警。GA 需要至少对 `PreToolUse` / `PermissionRequest`
的配置错误与运行错误 fail-closed。

### 3.5 P2 · 16 个事件“只进词表、从不发射”（其中 3 个被误标为 integrated）

实测 GA 只真正发射 **17 / 33** 个事件（见 §4 表）。

`event_status()` 诚实标记为 `contract-only`（能配置/校验但从不触发）的有 13 个：`Notification`、
`UserPromptExpansion`、`Setup`、`Elicitation`、`ElicitationResult`、`ConfigChange`、`WorktreeCreate`、
`WorktreeRemove`、`InstructionsLoaded`、`CwdChanged`、`FileChanged`、`DirectoryAdded`、`MessageDisplay`
（`runtime.py:298-326`）。

**另有 3 个被误标为 `integrated` 但实际从不发射**：`SessionEnd`、`PreModelSwitch`、`PostModelSwitch`。
（`app.py` 只发 `SessionStart`；模型切换/会话结束时没有对应 hook 调用点。）也就是说 GA 的
`event_status()` **自报并不完全准确**，比“诚实承认未实现”更值得修——会误导依赖它判断覆盖度的调用方。

影响：用户在这些事件上配的 hook 会**静默无效果**；且 `event_status()` 会高估已覆盖度。建议要么补发射点，
要么把这三个改标为 `contract-only` 并对齐文档。

### 3.6 P2 · prompt/agent handler 结果语义宽松，缺结构化求值

CC 的 prompt hook 求值器走**结构化 `json_schema`**，对 stop-condition 返回 `{ok, reason, impossible?}` 三态
（`m0459:154360-154560`），非法 JSON 判为失败。GA 的 `_prompt_execute`（`runner.py:201-231`）把任意输出当
`allow_text=True` 解析：**普通文本也接受**，且不做 schema 校验。

影响：goal 求值器、以及任何“prompt hook 返回结构化决策”的能力，在 GA 上要协议上的适配；且宽解析会掩盖 prompt 求值错误。
这也呼应 goal 方案 §6——需要给 prompt hook 加“结构化 / schema”支持。

### 3.7 P2 · `prompt/agent` 的 `onFailure=block` 只对 3 个守卫事件生效，与 `command/http` 不一致

`hooks/runtime.py:387-395` 把 `prompt/agent` 的失败转 `blocking` 只在 `event in GUARD_EVENTS`
（`UserPromptSubmit` / `PreToolUse` / `PermissionRequest`）时发生；而 `command/http`（`runner.py:188,287`）对
**所有非忽略事件**都按 `onFailure=block` 转换。同一 `onFailure` 配置在不同 handler 类型下的行为不一致。

影响：一个 `prompt` 型 `PostToolUse` 守卫配了 `onFailure=block`，在 GA 里不会阻塞，行为与 CC 语义（除非在忽略集，
否则 onFailure=block 通用）不一致。

### 3.8 P3 · `PermissionRequest` 显式拒绝 `agent` handler（需进一步核验是否与 CC 一致）

`hooks/config.py:151-157` 对 `PermissionRequest` 的 `agent` handler 直接报 unsupported 并跳过。CC 的五类型是
事件通用的（`m0062:2636`），需要核验 CC 是否允许 `PermissionRequest + agent`；若允许，这是能配不许用的差异。

### 3.9 P3 · 守卫输入 JSON 上限未对齐（输出预算不是差异）

CC 只对 `PreToolUse` / `PermissionRequest` 的输入 JSON 设有上限（约 `MAX_STRING_LENGTH/2`，`m0459:55449-55450`、
`157689-157690`）。GA 侧未看到对等上限/截断逻辑（`runner.py`/`runtime.py` 无对应）——极端输入可能打爆
hook 或模型上下文，属韧性差异。

更正：**输出预算并不是已证实的 CC 差异。** CC 文档明确**撤回** “hook 输出上限 24576（`Yqs`）已证实”的说法，
并建议 GA **自建可配置输出预算**（`maxOutputChars` + 持久化 preview，见 `20261020-hooks入口分析.md` §11）。
因此本条只保留“输入 JSON 上限”这一项已证实的差异。

## 5. 对 goal 模式复刻的影响（与上一份方案联动）

goal 方案里 `goal_guard` 之所以要“另起炉灶”，根因正是上述 P1 差异：

1. **没有会话级动态 Stop hook**（§3.2）→ goal 不能像 CC 那样“加/摘一条目标 Stop hook”，只能自己维护 `active_goal` 状态；
2. **Stop 没有阻塞/继续闭环**（§3.1）→ goal 的“未满足就继续”无法靠现有 Stop 表达，必须在 `agent_runner_loop`
   break 前插 `goal_guard`（这正对应 goal 方案第 4 节）；
3. **prompt 求值不结构化**（§3.6）→ goal 求值器需要 `{ok, reason, impossible?}`，而不是 GA 现在“任意文本都可”的 prompt hook，
   方案 §6 需要加结构化支持。

也就是说：**先补 hook 语义，goal 就能顺带简化；不补，goal 就只能靠旁路状态机硬做。** 两者并不互斥。

## 6. 优化建议（按性价比 / 依赖排序）

### 第一优先（安全 + goal 依赖，建议先做）
1. `PreToolUse` / `PermissionRequest` 守卫 **fail-closed**：配置/运行错误必须阻塞或显式报错，不许静默放行（§3.4）；
2. 增加**会话级动态 hook 注册/移除 API**（`HookRegistry.add_session(event, handler)` / `remove`），
   并让 `run_event` 能消费动态 entries（§3.2）；
3. 给 **Stop / SubagentStop 加“结果可阻塞”语义**：识别 `{decision:block}` / `{preventContinuation:true}`，
   在 turn-end 处把它们接回“继续/续跑”（§3.1）——这是 goal 与许多守卫的公共底座。

### 第二优先（对齐 CC 语义）
4. **并发**：非 prompt/agent handler 并行执行、prompt/agent 串行、全局上限 12、按完成序合并（§3.3）；
5. **prompt/agent 结构化输出**：支持 `json_schema` 校验（至少 stop-condition 三态），并把 `onFailure=block` 对齐成
   全事件语义（§3.6 / §3.7）；
6. **补齐 16 个未发射事件的发射点**（含 3 个误标；至少先做 `Notification` / `Elicitation` / `MessageDisplay` 等高价值项），并修正 `event_status()` 自报（§3.5）。

### 第三优先（边界与一致性）
7. 核验并落实 `PermissionRequest + agent`（§3.8）；
8. 输入/输出预算与截断（§3.9）。

> 优先级建议：先做第 1、2、3 条；它们既是安全/正确性底线，也是 goal 模式能“少造轮子”的关键。
