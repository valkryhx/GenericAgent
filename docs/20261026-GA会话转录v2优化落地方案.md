# GA 会话转录 v2 优化落地方案

> 配套源码分析：`docs/20261026-CC303会话转录与compact实现源码分析.md`。
> GA 仓库：`D:\git_codes\GenericAgent`（本次实际校验的工作副本）。
> 目标：修复“每轮保存整份 `backend_history_before` / `backend_history_after`”带来的存储、加载、deepcopy、分支推断和恢复问题。
> 本文是设计与实施计划，不代表相关代码已经完成。
> 原则：不删减 GA 现有能力；v1 旧会话只读兼容，新会话使用 v2。用户已确认不再依赖旧会话继续写入。

## 0. 结论先行

GA 当前 v1 的根本问题不是“transcript 文件里多存了几个字段”，而是把**每轮完整 backend history 当成会话事实源**：

```python
"backend_history_before": copy.deepcopy(backend_history_before or []),
"backend_history_after": copy.deepcopy(backend_history_after or []),
```

这导致：

1. 第 k 轮写入约 k 条历史，整体写入量接近 O(n²)；
2. `copy.deepcopy` 也随轮数重复，CPU 和峰值内存接近 O(n²)；
3. `load_session()` 要逐行 JSON 解析并 deepcopy 两份快照；
4. `_scan_session_summary()` 虽不 deepcopy，也要解析完整快照；
5. 用“上一轮 after 与下一轮 before 深度相等”推断 rewind，任一 trim / tool 修复 / 结构变化都会让推断失效；
6. `trim_messages_history()` 原地修改 backend history，使 before/after 不再严格等于真实轮次边界；
7. compact 直接把 backend history 替换成两条摘要消息，没有 boundary、preserved UUID、逻辑父链；
8. Ink rewind 在 RAM 里另存完整 history 快照，接近重复一份 O(n²) 内存；
9. restore 只恢复 backend history，不恢复 handler 工作记忆、last_usage 等运行状态。

v2 的目标是改成：

- **canonical transcript = 增量事件流**；
- **每条消息有 UUID / parent_uuid / turn_id**；
- **turn 结束只写 turn_end 元事件，不写完整 history**；
- **compact/rewind 写显式 boundary 事件**；
- **backend history 是 canonical entries 的派生投影**；
- **UI 消息是 canonical entries 或 UI 事件的另一套投影**；
- **所有硬裁剪只作用于投影副本**；
- **恢复按 UUID/锚点重建，不靠整段 JSON 深度相等**。

`restore_agent_session()` 当前恢复：

- `backend.history`；
- `agent.history=[]`；
- `client.last_tools=""`；
- `agent.handler=None`；
- session id/path/turn_id。

没有恢复：

- `handler.working.key_info`；
- active skill / `_loaded_skill_records`；
- `last_usage_tokens`；
- 必要的 tool replay / last tool state；
- canonical branch/boundary；
- rewind snapshots。

因此 resume 后首轮很可能丢失工作记忆，或者把“显示历史”与“模型上下文”再次分叉。

## 2. 设计目标与非目标

### 2.1 目标

1. 新会话每轮写入量近似 O(1)（与该轮新增消息量成正比），不再复制此前所有消息。
2. resume 时能从 canonical transcript 重建 API history 和 UI 消息，不依赖完整快照。
3. compact 后能保留可追溯的 boundary、summary、preserved 消息和工具配对。
4. rewind 后旧分支不进入 API 视图；新分支可继续写入同一 canonical 事件流。
5. hard trim 不再原地破坏 canonical 历史；只影响本次请求的投影副本。
6. restore 能恢复足够的工作记忆和运行状态，使 resume 后首轮行为接近不中断会话。
7. 列表页只扫描轻量元事件，不解析大段消息正文/完整历史。
8. v1 旧文件继续可读；不要求旧会话能继续写 v2。

### 2.2 非目标（本阶段不做）

- 不追求 100% 复制 CC 的 v5 storage、remote mirror、fork context、API replay blob 等内部能力。
- 不在第一阶段引入跨机器存储后端。
- 不立即实现 CC 式“低收益 compact 跳过”和复杂 byte ledger。
- 不删除旧 v1 transcript 文件，也不对旧文件做不可逆迁移。
- 不把 UI 显示的完整历史直接等同于 API 请求历史。

## 3. v2 canonical 数据模型

### 3.1 文件格式

继续使用 JSONL，一行一个事件，UTF-8、LF、无 BOM。文件顶部仍是 `session_start`，但版本升级为 `version:2`。

### 3.2 事件类型

最小可行集合如下：

```jsonc
{"version":2,"type":"session_start","session_id":"session_...","created_at":"...","cwd":"D:/...","frontend":"ink","schema":2}

{"version":2,"type":"message","uuid":"...","parent_uuid":"...","turn_id":1,"role":"user","origin":{"kind":"human"},"created_at":"...","blocks":[{"type":"text","text":"..."}],"text":"..."}

{"version":2,"type":"message","uuid":"...","parent_uuid":"...","turn_id":1,"role":"assistant","created_at":"...","blocks":[{"type":"text","text":"..."},{"type":"tool_use","id":"call_1","name":"file_read","input":{...}}],"text":"..."}

{"version":2,"type":"message","uuid":"...","parent_uuid":"...","turn_id":1,"role":"user","origin":{"kind":"tool_result","tool_use_id":"call_1"},"blocks":[{"type":"tool_result","tool_use_id":"call_1","content":"...","is_error":false}]}

{"version":2,"type":"turn_end","turn_id":1,"first_uuid":"...","last_uuid":"...","created_at":"..."}

{"version":2,"type":"compact_boundary","uuid":"...","parent_uuid":null,"logical_parent_uuid":"...","trigger":"auto|manual","pre_tokens":123,"post_tokens":45,"duration_ms":1200,"summary_uuid":"...","preserved_uuids":["..."],"preserved_segment":{"head_uuid":"...","anchor_uuid":"...","tail_uuid":"..."},"created_at":"..."}

{"version":2,"type":"summary","uuid":"...","parent_uuid":"...","text":"...","is_compact_summary":true,"visible_in_transcript_only":true,"created_at":"..."}

{"version":2,"type":"rewind","uuid":"...","anchor_uuid":"...","keep_turn_id":2,"head_uuid":"...","tail_uuid":"...","created_at":"..."}

{"version":2,"type":"working_state","handler_working":{...},"last_tools":"","last_usage_tokens":{...},"created_at":"..."}
```

字段说明：

| 字段 | 必需 | 作用 |
| --- | --- | --- |
| `version` | 是 | 顶层 schema 版本；与事件内部字段演进分开 |
| `type` | 是 | 事件类型 |
| `uuid` | 消息/边界/摘要必需 | 稳定身份、去重、分支锚点 |
| `parent_uuid` | 消息/摘要必需 | 事件链父指针 |
| `logical_parent_uuid` | boundary/rewind 可选 | 物理根与逻辑父分离 |
| `turn_id` | 消息/ turn_end 必需 | 把消息归属到用户轮次 |
| `origin.kind` | user message 必需 | 区分 human、tool_result、hook、system |
| `blocks` | 消息事件必需 | 保留结构化 content block；不要只存扁文本 |
| `text` | 可选 | UI 快速预览；不是 canonical 唯一内容 |
| `turn_end` | 每轮一个 | 表示一轮完成，不携带整份 history |
| `working_state` | 可选 | 恢复 handler/working 状态 |

### 3.3 UUID 生成与去重

- 每条待写事件生成 UUID，建议使用 `uuid.uuid4().hex`。
- 写入函数接收可选 `uuid`，便于测试和导入。
- 读取器维护 `seen_uuids`，重复 UUID 只保留第一次或按明确规则覆盖：
  - 消息：first-wins，因为消息不可变；
  - `working_state`：last-wins；
  - `turn_end`：last-wins；
  - `compact_boundary` / `rewind`：按 UUID 去重，按事件顺序决定当前分支。
- 不在每个 turn 里写 `before/after history`。

### 3.4 事件顺序与分支关系

仅靠文件顺序不能表达 rewind 产生的分支。v2 使用：

- `parent_uuid`：消息链父指针；
- `turn_id`：用户轮次归属；
- `rewind` 事件：显式记录返回锚点；
- `head_uuid` / `tail_uuid`：可选，帮助校验分支。

读取时可以构建：

```text
events_by_uuid
children_by_parent
turn_events
boundaries
rewinds
working_states
```

当前视图从最后一个有效 `rewind` / `compact_boundary` 和当前 leaf 开始回溯。

### 3.5 与 v1 的关系

- `version:1` 旧文件只读。
- v2 writer 不复用 v1 `turn` 完整快照字段。
- `load_session(path)` 根据首行 `version` 或逐行版本分流到 `load_v1` / `load_v2`。
- 不允许把 v2 事件混合写入 v1 文件。
- 旧会话如果用户继续输入，GA 可新建一个 v2 分支文件，并记录 `resumed_from`；默认不迁移、不覆盖旧文件。

## 4. 写入链路设计

### 4.1 写入粒度

新会话中，以下事件分别追加：

1. 用户消息：`message(role=user, origin=human)`；
2. 模型 assistant 消息：`message(role=assistant)`；
3. 工具调用：作为 assistant message 的 `tool_use` block，或独立 tool_call 事件（二选一，推荐前者，保持与 Anthropic content block 对应）；
4. 工具结果：`message(role=user, origin=tool_result)`；
5. 一轮结束：`turn_end`；
6. compact：`compact_boundary` + `summary`；
7. rewind：`rewind`；
8. 必要的 working snapshot：`working_state`。

### 4.2 写入 API 草案

```python
def append_message(path, *, session_id, role, blocks, origin=None, parent_uuid=None,
                   turn_id=None, text="", uuid_value=None):
    ...

def append_turn_end(path, *, session_id, turn_id, first_uuid, last_uuid):
    ...

def append_compact_boundary(path, *, session_id, trigger, pre_tokens, post_tokens,
                            duration_ms, summary_uuid, preserved_uuids,
                            preserved_segment=None, logical_parent_uuid=None):
    ...

def append_rewind(path, *, session_id, keep_turn_id, anchor_uuid,
                  head_uuid=None, tail_uuid=None):
    ...

def append_working_state(path, *, session_id, handler_working,
                         last_tools="", last_usage_tokens=None):
    ...
```

所有 append 都沿用现有 `append_event()` 的 UTF-8/LF 单行写入，并增加：

- 进程内 `seq`；
- 事件 UUID；
- 可选写入锁或 per-file queue；
- 写入失败不吞异常（由调用方决定降级）。

### 4.3 调用点改造

| 现有调用 | v2 改造 |
| --- | --- |
| `app.py` 的 `transcript_history_before` 捕获 | 删除；改为在用户消息进入时写 `message(user)` |
| `app.py:1198` / `1233` 的 `record_agent_turn()` | 改为写 assistant/tool 消息 + `turn_end`，不再传完整 history |
| `app.py:992` 的 `record_compact()` | 改为写 `compact_boundary` + `summary` |
| `bridge.py:2325` 的 `_record_compact_transcript()` | 同上；不 deepcopy backend history |
| `bridge.py:2438` 的 rewind 记录 | 改为写 `rewind(anchor_uuid, keep_turn_id)` |
| `bridge.py:2497` resume 重建快照 | 改为从 v2 transcript 构建轻量 rewind index，不复制完整 history |

### 4.4 写入顺序与崩溃一致性

一轮的推荐顺序：

```text
message(user)
message(assistant)      # 可能多条
message(tool_result)    # 可能多条
turn_end
```

崩溃恢复规则：

- 没有 `turn_end` 的轮次视为“进行中/未完成”；
- 已写入的 user/assistant 消息仍可显示；
- 不把未完成轮次冒充为已完成轮次；
- `turn_end` 缺失时，下一轮可以用 `turn_id` 继续或新开 turn，按 UI 语义决定；
- compact boundary 或 rewind 写入后，立即影响后续投影，不等待物理压缩。

## 5. 读取链路设计

### 5.1 统一入口

```python
def load_session(path):
    if is_v2_transcript(path):
        return load_v2(path)
    return load_v1_readonly(path)
```

`load_v2()` 输出可以是：

```python
@dataclass
class LoadedSessionV2:
    path: str
    session_id: str
    events: list[dict]
    messages: list[dict]
    turns: list[TurnMeta]
    ui_messages: list[dict]
    backend_history: list[dict]
    working_state: dict | None
    boundaries: list[dict]
    rewinds: list[dict]
    warnings: list[str]
```

但“LoadedSession”里的 `backend_history` 应由投影函数生成，不是原样读某个快照字段。

### 5.2 轻量列表扫描

`list_sessions()` 对 v2 只解析：

- `session_start`：session_id/cwd/frontend；
- 第一条 human user message：preview；
- `turn_end`：rounds；
- 最后 `seq` / mtime；
- 可选 `summary` 标题。

不需要解析每条 assistant/tool_result 的完整 blocks。可以按行前缀快速过滤，或者维护 `.listing_cache.json`。

### 5.3 详情加载

详情加载分两级：

1. **索引级**：读所有事件，只保留 uuid/parent/turn_id/type/timestamp 等轻字段；
2. **内容级**：只为当前分支、当前视口需要的消息读取 blocks/text。

短会话可以一次读全；长会话必须支持分页或按 boundary 裁剪。

### 5.4 旧 v1 reader

保留现有 `load_session` 的 v1 逻辑作为 `load_v1_readonly()`：

- 不改 v1 文件；
- 继续支持旧的 `turn/compact/rewind` 事件；
- 但 v1 的深度相等推断只作为旧数据兼容，不能成为 v2 设计基础。

## 6. backend history 投影

### 6.1 新函数

建议在 `genericagent/core/transcripts.py` 或新模块 `genericagent/core/projection.py` 提供：

```python
def build_backend_history(entries, *, boundary=None, max_messages=4096,
                          include_turn_id=None):
    """Return a request-safe copy. Never mutate entries or backend.history."""
```

返回的是 API messages，不是 GA 内部 UI 消息，也不是完整 canonical events。

### 6.2 投影步骤

1. 从 canonical entries 选出当前分支：
   - 从最后一个 `rewind` 找到 anchor；
   - 从最后一个 `compact_boundary` 找到起点；
   - 沿 `parent_uuid` / `turn_id` 选择当前 leaf 路径。
2. 按 UUID 去重。
3. 收集 `message` 事件，按链顺序展开。
4. tool_use / tool_result 按 id 配对：
   - 缺失 tool_result：在请求副本补明确的 error/placeholder；
   - 孤立 tool_result：在请求副本转为 text 或丢弃，并记录 warning。
5. 截取尾部窗口（建议保留 4096 条上限，与 CC 的 `Rx` 对齐，可配置）。
6. 从窗口内第一条真实 user 消息开始，避免从 tool_result 开头。
7. 应用 compact summary：
   - summary 作为 compact 后 system/context message；
   - preserved 消息按 UUID 顺序保留；
   - 不把 boundary 当普通对话消息发给模型。
8. 最后复制成请求对象，交给现有 LLM backend。

### 6.3 与现有 `trim_messages_history()` 的关系

短期：

- 保留 `trim_messages_history()` 作为最后兜底；
- 但调用前先 `history = build_backend_history(...)`；
- 绝不在 canonical entries 上 `pop`。

长期：

- hard trim 只对请求副本生效；
- canonical entries 永不因为请求裁剪而丢失；
- `backend.history` 可继续作为当前工作上下文缓存，但必须注明它是 projection，不是 canonical。

### 6.4 与 `_fix_messages()` 的关系

`_fix_messages()` 的补齐/转换行为应留在“请求构造副本”：

```python
request_messages = _fix_messages(copy.deepcopy(projected))
```

不能直接修改 `backend.history` 或 canonical entries。若确实需要修正持久化状态，应单独记录 `projection_repair` 事件。

## 7. compact v2

### 7.1 compact 流程

1. 记录 compact 前当前分支的 leaf_uuid。
2. 生成 summary。
3. 计算 preTokens / postTokens / durationMs。
4. 计算 preserved 消息：
   - 优先保留当前 turn 的 human user、最近未完成工具调用及其结果；
   - 保留必要的系统/技能上下文；
   - 不把其他分支消息放入当前 preserved 集合。
5. 追加 `compact_boundary`。
6. 追加 `summary` 消息。
7. 更新 `backend.history` 为新的 projection。
8. 可选：后台执行 physical compaction。

### 7.2 boundary 字段

```jsonc
{
  "version": 2,
  "type": "compact_boundary",
  "uuid": "b-...",
  "parent_uuid": null,
  "logical_parent_uuid": "last-message-uuid",
  "trigger": "auto",
  "pre_tokens": 120000,
  "post_tokens": 18000,
  "duration_ms": 2300,
  "messages_summarized": 84,
  "summary_uuid": "s-...",
  "preserved_uuids": ["u-1", "a-2", "t-3"],
  "preserved_segment": {
    "head_uuid": "u-1",
    "anchor_uuid": "b-...",
    "tail_uuid": "t-3"
  },
  "created_at": "..."
}
```

### 7.3 与 summary 的关系

summary 是独立事件，不是 boundary 内嵌的一大段正文：

```jsonc
{
  "version": 2,
  "type": "summary",
  "uuid": "s-...",
  "parent_uuid": "b-...",
  "text": "...",
  "is_compact_summary": true,
  "visible_in_transcript_only": true,
  "created_at": "..."
}
```

这样：

- summary 可以单独投影/替换；
- boundary 可以只保存元数据和 UUID；
- UI 可以选择显示“Conversation compacted”提示，而不把 summary 当普通用户发言。

### 7.4 物理压缩（已评估，暂不实施）

CC 303 中确有 `performCompactTranscript()`，但它由
`CLAUDE_CODE_TRANSCRIPT_LOCAL_GC` / `tengu_transcript_local_gc` 控制，默认关闭，
并非普通 `/compact` 的默认行为。GA 当前明确不实施 transcript 物理压缩：

- 不删除原始 JSONL 行；
- 不重写或原子替换 transcript；
- 不接自动 GC；
- 不提供 `GA_TRANSCRIPT_GC*` 生产开关。

GA 的 compact 只做语义压缩：追加 `compact_boundary + summary`，由 projection
控制后续模型上下文。原始 transcript 始终保持 append-only，便于审计、回溯和
故障恢复。若未来确有磁盘裁剪需求，应单独立项、默认关闭并完成 dry-run、
并发校验、原子替换和回滚设计；不纳入本次 Phase C/D。

## 8. rewind v2

### 8.1 显式事件

```jsonc
{
  "version": 2,
  "type": "rewind",
  "uuid": "r-...",
  "anchor_uuid": "turn-2-last-uuid",
  "keep_turn_id": 2,
  "head_uuid": "turn-3-first-uuid",
  "tail_uuid": "turn-3-last-uuid",
  "created_at": "..."
}
```

### 8.2 恢复规则

- `anchor_uuid` 指定保留到的消息；
- `keep_turn_id` 是 UI 轮次边界，便于快速恢复；
- `head_uuid` / `tail_uuid` 用于校验被丢弃的分支；
- 读取时从 anchor 回溯，不把 keep_turn 之后的事件纳入当前投影；
- 旧分支事件可以保留在 canonical 文件中供审计/UI 查看，但不进入 API view；
- 后续新消息的 `parent_uuid` 指向 anchor，而不是旧分支 leaf。

### 8.3 内存快照替代

短期保留 `_rewind_snapshots`，但只保存轻量索引：

```python
{
  "text": visible_text,
  "anchor_uuid": "...",
  "keep_turn_id": 2,
  "last_tools": ...,
}
```

需要恢复时：

1. 从 v2 transcript 读 anchor 前的分支；
2. 用 `build_backend_history()` 重建；
3. 从最近的 `working_state` 恢复 handler 工作记忆；
4. 不再 deepcopy 整份 backend history。

如果 v2 尚未完全接入 rewind，可先保留 v1 快照作为回滚路径，但必须与新接口隔离。

## 9. restore v2

### 9.1 恢复内容

`restore_agent_session()` v2 应恢复：

- `backend.history = build_backend_history(...)`；
- `agent.history`：由 UI projection 或内部 agent history 投影生成；
- `session_id` / `session_path` / `session_turn_id`；
- `last_tools`；
- `handler`：
  - 重建 `GenericAgentHandler`；
  - 恢复 `working.key_info`；
  - 恢复 active skill / `_loaded_skill_records`（只恢复必要元数据，不注入完整 skill 正文）；
- `last_usage_tokens`（如果 v2 transcript 有保存）；
- 必要的 `tool replay` / `last_tool_result` 状态；
- rewind 索引（从 transcript 派生，不复制完整 history）。

### 9.2 恢复顺序

1. 读取 v2 canonical entries；
2. 解析当前 branch / boundary / rewind；
3. 构建 UI messages；
4. 构建 backend_history；
5. 恢复 working_state；
6. 创建 handler；
7. 恢复 client/backend 的轻量状态；
8. 设置 session_turn_id；
9. 返回 RestoreResult。

### 9.3 失败策略

- canonical transcript 损坏一行：跳过该行并 warning，不影响其他事件；
- boundary 指向的 summary 缺失：降级为不应用 compact，保留完整可用历史并提示；
- preserved UUID 缺失：安全降级，不要把该 UUID 当普通消息强行重建；
- working_state 缺失：恢复 backend history，但明确标记“工作记忆未恢复”；
- rewind anchor 缺失：拒绝恢复分支，回退到最后一个可验证 boundary/turn_end。

## 10. API 与 UI 分层

### 10.1 API view

来源：当前分支的 `message` + `summary` + `preserved` 事件。

约束：

- 最多 4096 条（可配置，建议常量 `MAX_PROJECTION_MESSAGES = 4096`）；
- 从真实 human user 开始；
- tool_use / tool_result 配对；
- compact 后 summary 作为 context；
- 只读投影，不修改 canonical entries。

### 10.2 UI view

来源：当前分支的 `message` 事件（可包含被 API 窗口裁掉的历史）。

约束：

- 不应用 API 的 4096 条硬窗口，或使用单独更大的 UI 窗口；
- 显示 tool_use / tool_result 合成行；
- 跳过 `is_meta` / `is_virtual`；
- rewind 后旧分支不显示为当前分支；
- 如需显示旧分支，必须明确标注为历史分支。

### 10.3 列表 view

来源：`session_start`、第一条 human user、`turn_end`、摘要/标题元事件。

约束：

- 不解析完整 blocks；
- 不构建 backend history；
- 不 deepcopy；
- 文件 mtime/size + cache 仅作为性能优化，不是语义依据。

## 11. 文件大小与性能目标

### 11.1 写入目标

- 单轮新增写入量与该轮新增消息内容成正比；
- 不随历史轮数增长而重复写入此前消息；
- 同一 UUID 不重复写；
- compact boundary 只写元数据 + UUID，不写完整旧历史。

### 11.2 读取目标

Phase 0 先测现有 v1：

- 50 / 200 / 500 / 1000 轮；
- 每条消息 1KB / 10KB / 100KB；
- 记录 JSONL 大小、加载耗时、deepcopy 峰值、列表扫描耗时。

v2 验收建议：

- 1000 轮、每轮 2 条普通消息的 transcript 大小，不应因轮数平方增长；
- `load_session()` 的 peak memory 主要随当前投影窗口增长，而不是随整个文件所有历史快照增长；
- 列表扫描只解析轻量字段；
- resume 到首屏的耗时与文件总大小近似线性，至少不出现 O(n²) 级别。

具体阈值需要在 GA 实测后写死，避免凭空制定不现实指标。

## 12. 分阶段实施计划

### Phase 0：基线与保护网（先做）

1. 为 v1 增加性能/行为基准测试：
   - 写入 N 轮后的文件大小；
   - load_session 耗时与 peak memory；
   - list_sessions 首次扫描耗时；
   - compact 后恢复结果；
   - rewind 后 API/UI 分支。
2. 为现有调用点增加结构化日志：
   - `session_id` / `path` / `turn_id`；
   - 写入字节数；
   - load_session 事件数/耗时；
   - compact boundary/摘要消息数。
3. 确认现有 listing cache 与 seq 行为不被破坏。
4. **不改协议**，只建立基线。

### Phase A：v2 writer + v1 只读兼容

1. 新增 `version:2` 事件写入 API。
2. 新会话写 v2；旧会话只读。
3. 实现 `load_v1_readonly()` 与 `load_v2()` 分流。
4. v2 先只支持普通 user/assistant/tool 消息 + turn_end。
5. 保留 v1 `load_session()` 作为兼容路径，不删除旧快照字段解析。
6. 增加回滚开关：`transcript_schema=v2|v1`，默认新会话 v2、旧会话 v1 read-only。

DoD：

- 新会话不再出现 `backend_history_before/after`；
- 单轮日志只包含该轮新增消息；
- 旧 v1 会话可打开、可显示、可恢复（至少只读/兼容模式）；
- 所有现有测试通过。

### Phase B：projection adapter

1. 实现 `build_backend_history(entries, ...)`。
2. 把请求前的 history 构造改为投影副本。
3. `trim_messages_history()` 改为只接受 projection copy，或增加 `mutate=False` 模式。
4. resume 使用 projection 生成 backend.history。
5. 保留 v1 fallback。

DoD：

- hard trim 不再改变 canonical entries；
- tool_use/tool_result 配对正确；
- API 视图不会从孤立 tool_result 开头；
- v1 旧会话仍能工作。

### Phase C：compact boundary v2

1. `compact_agent_context()` 生成 boundary + summary。
2. `record_compact` 写 boundary/summary，不写完整 backend history。
3. resume 从最后 boundary 之前/之后正确投影。
4. 加入 preserved UUID / preserved segment。
5. 暂不做物理压缩，只验证追加式 compact。

DoD：

- compact 后恢复不会把摘要当真实用户发言；
- preserved 消息可恢复；
- 缺 summary/缺 UUID 时安全降级；
- 与 CC 的 boundary 语义对齐但保留 GA 简化实现。

### Phase D：rewind / restore / working_state

1. rewind 写显式 `rewind` 事件和轻量 anchor。
2. `_rewind_snapshots` 使用轻量索引，不复制整份 backend history。
3. restore 恢复 backend history、working_state、last_tools 和
   last_usage_tokens。
4. resume 时按 branch `turn_id` 恢复每个 checkpoint 对应的状态。
5. UI 正确处理旧分支隐藏和 rewind 目标位置。

DoD：

- rewind 后旧分支不进入 API 视图；
- rewind 恢复的 backend history、working memory、last_tools 和 usage 一致；
- resume 后每个 checkpoint 使用该 turn 自己的 working_state，而不是最新状态；
- 缺失 anchor 时安全失败，不猜测或部分截断；
- transcript 保持 append-only，不执行物理删除。

## 14. 回滚策略

1. **协议回滚**：保留 v1 reader；v2 writer 可通过配置关闭，新文件不再写 v2。
2. **compact 回滚**：v2 boundary 写入失败时，保留原 backend history，不替换内存状态。
3. **rewind 回滚**：无法解析 anchor 时回退到最后一个 turn_end，不强行截断。
4. **恢复回滚**：working_state 解析失败时恢复 backend history，并显示 warning，不让 session 进入不可用状态。
5. **物理压缩**：当前不实施，因此不存在 transcript 原地改写回滚路径；原始 JSONL 始终保留。
6. **旧文件保护**：v1 文件默认只读；不在原文件上做不可逆升级。

## 17. 需要用户确认的产品选择

以下不是阻塞调研，但会影响实现细节：

1. 旧 v1 会话默认是“只读展示”，还是“继续输入时另开 v2 分支”？建议后者。
2. compact 后是否要在 UI 显示 compact 提示行？建议显示简短提示，不显示完整 summary 正文。
3. rewind 后旧分支是否允许在 UI 中查看？建议默认隐藏，高级模式可查看。
4. v2 是否保留 `agent.history` 与 `backend.history` 两个概念？建议保留，但都标记为 projection/working cache，不成为 canonical。
5. physical compaction 是否在 Phase D 开启？**已确认不开启**：CC 中该能力默认关闭，GA 当前继续保留 append-only transcript。

## 18. 最终建议

先做 **Phase 0 + Phase A + Phase B**，不要一开始同时改 compact/rewind/物理压缩。

原因：

- Phase A 直接消灭 O(n²) 写入和完整快照事实源；
- Phase B 直接解决 hard trim 破坏分支推断；
- Phase C/D 才涉及 compact boundary、preserved、rewind 和 working_state，风险更高；
- transcript 物理压缩不属于当前实施范围，继续保持 append-only；
- 这样每一步都能独立验证、独立回滚，不需要一次性重写整个会话系统。

最终目标不是“照搬 CC 代码”，而是采用 CC 已经证明有效的四条原则：

1. **事件是事实源**；
2. **边界是锚点**；
3. **API/UI 是投影**；
4. **裁剪只作用于副本**。
