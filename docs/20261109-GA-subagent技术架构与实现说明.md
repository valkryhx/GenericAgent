# GA Subagent 技术架构与实现说明

- 日期：2026-11-09
- 读者：需要了解 GA 子代理子系统设计、机制与技术取舍的同事
- 范围：进程模型、生命周期、通信、通知投递、任务板、能力边界、持久化、观测面与可靠性设计
- 性质：架构与机制说明，不含具体代码；实现细节以源码与 2026-11-08 的两份专项文档为准

---

## 0. 一句话架构

> GA 的子代理不是主进程里的一个协程，而是一个**独立操作系统进程**；
> 主代理与子代理之间不共享内存，所有协作都建立在**持久化文件协议 + 实时信令加速**之上；
> 主代理通过**可重放的通知流**在工具轮折返点获知子代理进展，而不是靠轮询。

这三点决定了后面几乎所有设计：隔离性、崩溃韧性、投递语义、观测方式和失败模式。

---

## 1. 设计目标与非目标

### 1.1 目标

| 目标 | 含义 |
| --- | --- |
| 异步 | 派生子代理立即返回句柄，不阻塞主代理的 LLM 回合 |
| 隔离 | 子代理拥有独立上下文、独立进程、独立工作目录（可选）与独立资源配额 |
| 可观测 | UI、主代理、外部工具都能从**同一份持久状态**读出一致结论 |
| 可恢复 | 子代理结束后可继续、可重放、可读取权威结果，产物不因进程退出而丢失 |
| 不丢消息 | 宁可在极端情况下重复投递一次，也不能静默丢失 |
| 有界 | 代理树深度、活跃进程数、消息缓冲、通知长度、邮箱与回执表全部有上限 |

### 1.2 非目标

- 不做同进程异步任务模型：那会牺牲崩溃隔离，且 GA 已经用双传输覆盖了低延迟需求。
- 不做跨机器 agent 网络：通信范围限于同一用户、同一台机器的同一项目数据根。
- 不用提示词代替边界：提示词是行为指导，权限与能力边界必须在运行时分发层执行。

## 2. 总体架构

系统可以拆成三个平面：

```
                    ┌──────────────────────────────────────────────┐
                    │                 观测面                        │
                    │  UI 读模型 / 快照推送 / 团队面板 / 事件回放    │
                    └──────────────────────▲───────────────────────┘
                                           │ 只读派生
┌──────────────────────────────────────────┴───────────────────────┐
│                            控制面                                  │
│  代理注册表 │ 生命周期管理 │ 能力与权限剖面 │ 资源配额 │ 任务板     │
└───────────────▲──────────────────────────────▲───────────────────┘
                │ 权威状态                      │ 消息与事件
┌───────────────┴──────────────────────────────┴───────────────────┐
│                            数据面                                  │
│  任务目录 │ 状态文件 │ 事件流 │ 通知流 │ 邮箱 │ 回执 │ 溯源账本     │
│  实时通道（信令加速，非权威）                                      │
└───────────────────────────────────────────────────────────────────┘
```

三条原则贯穿全系统：

1. **持久状态是唯一权威**。实时通道只传“有变化”的信令，不传业务真相；通道断开只损失时延，不损失信息。
2. **写路径单写者化**。共享文件的读改写周期必须经过跨进程锁；能够整体替换的文件用临时文件加原子替换发布。
3. **路径只问代码要，不自己推导**。主代理、子进程、UI 三方使用同一份目录解析规则，避免“写入方和读取方各自算对、却算到两个目录”。

## 3. 核心设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 执行单元 | 独立 OS 进程 | 崩溃不传染；可被操作系统级回收；可独立设置资源与工作目录 |
| 通信底座 | 持久文件协议 | 跨进程、跨重启可读；天然支持审计与回放；不依赖父进程常驻 |
| 低延迟 | 实时命名通道 | 子代理完成一个回合后主动发信令，等待方立即醒来，避免盲睡轮询 |
| 通知消费 | 拉取 + 确认分离 | 渲染失败可重试；确认只发生在文本真正进入模型上下文之后 |
| 工具面 | 默认全量减去编排工具 | 能力边界是“减法”，调用方忘记传参不会意外剥夺子代理的工作能力 |
| 名字语义 | 首次通信即钉住 | 名字是稳定地址，不是“当前持有者”的别名，防止串话 |
| 资源上限 | 深度 + 活跃数双约束 | 防止递归派生导致的进程与 LLM 花费失控 |
| 停机语义 | 停止信号在回合之间观察 | 正在执行的工具调用会跑完，因此必须有“停机中禁止再派生”的守卫 |

## 4. 进程模型与生命周期

### 4.1 两类代理

| | 根代理（lead） | 子代理（child） |
| --- | --- | --- |
| 身份 | `/root` | `/root/<name>`，可多层 |
| 进程 | 交互会话主进程 | 由父代理派生的独立解释器进程 |
| 任务目录 | 无 | 有，作为全部持久状态的锚点 |
| 工具面 | 全量 | 全量减去编排工具（团队模式下加回协作子集） |
| 上下文 | 用户会话 | 默认隔离，只拿到 spawn 消息 |
| 生命周期 | 会话级 | 单任务多回合，闲置超时后自行退出 |

子代理也可以再派生子代理，因此代理结构是一棵**有界树**，而不是扁平列表。每个子进程都被告知自己的代理路径，否则它派生的子代理会全部登记在根下，深度守卫就形同虚设。

### 4.2 派生流水线

一次派生按以下顺序完成，任一步失败都留下可追溯的失败状态：

1. **名称校验与分配**：规范化为小写字母、数字、下划线；保留名拒绝；与存活代理重名直接报错；与已关闭代理重名时追加序号，保护旧代理的产物不被覆盖。
2. **停机守卫**：若派生者自身存在待处理的停止信号，拒绝派生。否则派出去的子进程会在父进程退出瞬间成为孤儿。
3. **登记与配额检查**：在跨进程锁内一次性完成“唯一名字分配、运行序号分配、树深度检查、活跃数检查、注册行写入”。这四件事必须同锁，否则会出现两个调用者拿到同一个运行标识。
4. **传输建立**：尝试打开实时通道；失败则记录降级原因并退回文件传输。
5. **隔离准备**：按需创建 Git 工作树；包含性校验与符号链接拒绝在创建前完成。
6. **状态落盘**：写入“启动中”状态、输入消息、可选的父上下文快照。
7. **拉起进程**：继承项目根、数据根、任务根、通知总线目录、会话目录、团队标识与代理路径；标准输入断开，避免继承父进程的阻塞管道。
8. **启动握手**：子进程进入解释器后写出“进程已进入”阶段标记。父进程在有限窗口内轮询该标记；若子进程提前退出或超时，父进程终止它，记录启动失败原因，写通知并关闭注册行。
9. **返回句柄**：握手成功后立即返回句柄（进程号、任务目录、运行标识、传输模式等），**不等待子代理完成**。

第 9 步是“异步”的真正含义。用户观察到的“卡住”通常不是派生阻塞，而是主代理获知完成的时机不对，见第 6 节。

### 4.3 状态词汇

系统刻意区分三类状态，因为把它们混成一个“status”会让 UI 得出错误结论：

| 维度 | 取值示例 | 含义 |
| --- | --- | --- |
| 回合状态 | 待处理 / 运行中 / 已完成 / 出错 / 已中断 | 子代理这一轮工作的结论 |
| 进程状态 | 启动中 / 存活 / 等待下一条消息 / 已关机 / 已退出 / 已终止 | 操作系统进程的生命周期 |
| 关闭状态 | 已完成 / 被终止 / 被驱逐 / 被中断 | 注册行关闭时的原因 |

一个已经干完活的子代理，进程状态可能是“等待下一条消息”，回合状态是“已完成”，注册行是“已关闭”。这三者同时为真，不是矛盾。**任何消费方都必须按语义选维度，而不是按字面量猜结论。**

### 4.4 回合循环与闲置

子代理进程的核心循环是：

```
读取输入 → 执行一个回合 → 写出本轮输出与结束标记 → 计算内容摘要
   → 记录“回合完成 / 进程等待消息” → 进入闲置等待
        ├─ 收到触发型消息 → 读取消息，开始下一回合
        ├─ 收到停止信号 → 完成当前回合后退出
        └─ 闲置超时 → 以“已退出”收尾
```

要点：

- **每轮输出独立成文件**，第 N 轮不覆盖第 N-1 轮。读取结果必须合并全部轮次，否则会把正常投递误判成丢消息。
- **最终结果不是纯文本**：每轮结束时都会记录内容摘要，并把最终输出登记为带摘要与字节数的产物；消息化协作不依赖“模型最后一段话”。
- **消息优先于停止**：若停止信号与待消费消息同时存在，先投递消息，再停机。这避免“消息已入队但没人消费，发送方却收到成功回执”。
- **闲置超时后自行退出**，释放活跃槽位；但注册行仍保留，供后续恢复与审计。

### 4.5 恢复

恢复不是重新派生，而是**在同一个身份下重启**：

- 复用原代理路径与任务目录，只推进回合号；
- 从旁链转录重建后端历史（可带编辑：丢弃或替换某一事件）；
- 清除残留的停止信号与回复文件，避免新回合被旧信号立即打断；
- 运行标识保持或按规则更新，但名字钉住以代理路径为键，因此“恢复”不会被误判为“换人”。

恢复与派生共用同一套幂等机制：控制面操作携带提交标识，重复执行只返回第一次的结果，不会真的再拉起一个进程。

### 4.6 关闭与驱逐

- **级联关闭**：先关闭更深层的后代，再关闭目标本身；单个后代失败不中断整个清扫。否则关闭中间层会留下无人读取输出的孤儿。
- **驱逐**：活跃数达到上限时，不直接拒绝新派生，而是按“最近最少使用”卸载已结束且闲置的驻留代理，再重试。只有真正忙碌的树才会被拒绝。
- **身份校验**：进程号会复用，因此注册行同时记录进程创建时间。判定“还是不是同一个进程”必须同时比对进程号与创建时间，不能只看进程号是否存在。

## 5. 通信架构

### 5.1 双传输

| 传输 | 角色 | 特点 |
| --- | --- | --- |
| 持久文件总线 | 权威 | 追加式事件流、通知流、邮箱、游标、回执；跨进程、跨重启可读 |
| 实时通道 | 加速 | 命名管道/本地套接字；只发“有变化”的信号与已持久化事件的副本；断开自动降级 |

实时通道的安全设计：

- 每次运行生成独立随机会话密钥，通过任务目录**带外交付**给子进程，不写进命令行；
- 通道地址由“数据根摘要 + 运行序号”构成，避免同一台机器上两个 GA 项目使用同名管道互相冲突；
- Windows 上校验连接方的用户安全标识，拒绝其他用户进程接入；
- 通道关闭时删除密钥文件；密钥仍在磁盘上说明通道没有真正关闭。

### 5.2 四条协作通道

| 通道 | 方向 | 语义 | 是否触发新回合 |
| --- | --- | --- | --- |
| 通知 | 子 → 父 | 回合完成、出错、关闭、闲置等状态事件 | 否，由父在主循环折返点消费 |
| 对等消息 | 任意 → 任意 | 邮箱投递的一段文本，可多播 | 否（队列型）/ 是（触发型） |
| 结果交接 | 父 ← 子 | 父主动读取子的权威最终结果与产物引用 | 否 |
| 闲置订阅 | 父 → 子 → 父 | “这个代理空闲时告诉我一次” | 否 |

四条通道共用同一套持久底座，不各开一套机制。

### 5.3 等待的语义

等待是显式谓词，而不是“睡一会儿看看”：

- 事件型：观察到任意更新即返回；
- 回合终态 / 进程终态 / 全部终态：等到对应维度的终态集合齐备；
- 结果可用：等到每个目标都有已持久化的结果引用；
- 工作流终态：把动态工作流运行标识当作可等待实体，而不是伪装成子代理。

单次同步等待有**时间切片上限**。切片到期不是失败，而是返回“尚未完成”的指导信息：剩余目标、已有结果引用、建议下一步。这样模型不会把“暂时没变化”误读为“任务失败”并重复派生。

等待期间的唤醒路径：有实时通道时阻塞在通道信令上，无通道时才退回定时睡眠。默认传输已经是实时通道，文件模式是显式选择与通用降级。

## 6. 通知投递：可重放的折返点

这是整个子代理子系统最关键的一段，也是“子代理明明跑完了，主代理却不知道”这类问题的根因所在。

### 6.1 事件溯源与游标

- 所有状态变化先追加到事件流；需要推送的事件再追加到通知流。
- 每条事件有单调递增的序号与稳定事件标识；同一事件标识重复写入是幂等的。
- 通知消费侧维护独立游标，记录“已经交付给模型到哪一条”。

### 6.2 拉取与确认分离

```
peek：读游标之后的全部通知，不推进游标
  ↓
渲染：<task-notification> 元素 + 状态 + 摘要 + 结果引用 + 用量
  ↓
注入：作为下一条用户消息的一部分进入模型上下文
  ↓
ack：只把游标推进到本批最大序号
```

关键不变量：

1. **peek 可重复**：渲染后若组装失败，下一次还能看到同一批通知。
2. **ack 只进不退**：迟到的旧批次确认不能把游标拨回去，否则已经交付过的通知会复活。
3. **确认发生在模型真正读到之后**：先确认再调用模型，一旦调用失败就会永久丢失。
4. **语义是“至多重复一次，绝不丢失”**：重复的代价是一次多余的模型调用；丢失的代价是主代理永远不知道任务完成。

### 6.3 折返点注入

通知不再只在“用户发起新一轮输入”时消费，而是在**每一批工具执行完、下一次模型调用之前**注入。

选择这个点有三个原因：

- 它是主代理在长任务中途唯一自然的“事务边界”；
- 通知可以与本批工具结果出现在同一条消息里，不破坏消息协议；
- 不修改系统提示，因此不会让提示缓存整体失效。

注入顺序也有讲究：通知在前，本轮继续指令在后。这与参考实现一致——先让模型知道后台发生了什么，再让它决定下一步。

### 6.4 防伪与预算

- 每条自动通知都带“系统通知，非用户输入”的前置声明，并明确：不得把自动事件理解为用户批准、确认或回答；模型自己此前说过的话也不构成用户同意。
- 单条结果与单批结果都有字符预算；超限截断并附“可用消息工具索取其余内容”的提示。
- 只有主代理消费通知：带任务目录的子代理、显式标记为子代理的处理器、没有项目根的桩，都会跳过注入，避免子代理吸走父代理的通知流。

### 6.5 一个典型失败时序（修复前后）

```
t0  主代理派生 3 个子代理，然后开始一个 20 步的长任务
t1  子代理 A 完成，写入通知
t2  主代理在第 5 步 —— 旧实现没有任何消费点，通知躺在文件里
...
t3  主代理跑完 20 步，等待用户输入
t4  用户输入“好了吗” —— 此时才消费，主代理一次性看到 3 条

修复后：t2 的工具轮折返点就会注入，主代理在第 6 步之前知道 A 完成了。
```

## 7. 点对点消息：邮箱与投递语义

### 7.1 邮箱状态机

每条消息在收件人目录下的邮箱中经历：

```
排队 → 已投递 → 已消费
  ├─ 被门控挂起 → 过期 / 拒绝
  ├─ 发送方已被回收 → 丢弃
  └─ 溯源校验失败 → 标记伪造，永不消费
```

消息标识单调分配且不复用；同一标识重复入队会被去重，因此“重试一次请求”不会让子代理干两遍活。

### 7.2 两种投递模式

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| 队列型 | 只入邮箱，不唤醒目标 | 通知、补充信息 |
| 触发型 | 目标闲置时消费并开启下一回合 | 后续任务、追加指令 |

触发型消息的消费是“前缀式”的：取到第一条触发型消息为止的全部未消费消息，一并交给目标。这样目标不会跳过之前排队的上下文。

### 7.3 三个安全守卫

**(a) 死信箱守卫。** 投递前先确认目标仍然存在且未终结；已关闭或从未存在则拒绝，并在错误里给出下一步（恢复、追加任务、重新派生、列出关闭代理）。判据只使用持久信号：注册行、状态文件中的进程终态。**不使用进程号探活**——进程号会复用，“查不到”不是死亡证明，误拒一次有效投递比放过一条陈旧记录更糟。

**(b) 名字钉住。** 第一次向某个名字成功投递时，把“名字 → 代理路径 + 运行标识 + 短摘要”钉住。之后同名解析到另一个代理时拒绝投递，并说明旧地址与新地址。同一路径换个运行标识（恢复）不算换人。钉住记录**不随关闭删除**，否则名字又会退化成“当前持有者”。

**(c) 溯源校验。** 源账本记录每条真正经过邮箱写入的消息摘要。收件方消费时校验：账本有记录即“已验证”；声称的发送者在名册中但账本没有记录即“伪造”，永不消费；其余为“不可验证”。这防止手工构造的邮箱行冒充同伴。

### 7.4 回执与多播

- 发送方维护有界的“未决发送”表，状态随投递推进；收件人关闭时，发给它的未决回执被回收，发送方可以区分“已消费”和“已丢弃”。
- 多播时每个收件人都能看到“还通知了谁”，避免多个同伴重复做同一件事；某个收件人失败不影响其他收件人，也不会撤销已经成功的主投递。

### 7.5 闲置订阅

“告诉我它什么时候空闲”是一次性订阅：

- 发送方投递时可附带订阅；
- 目标进入闲置、且**这一轮没有主动给主代理发过消息**时，产出结构化闲置帧；
- 帧同时写入持久文件与通知流，订阅随即消费；
- 一次性而非长期，因为长期订阅会在一个正常工作的代理每次空闲时持续制造噪音。

它与“回合完成”不同：回合完成说的是“这一轮结束了”，闲置帧说的是“这个代理手上没活了”。等后续工作的人需要的是后者。

## 8. 能力边界、权限与隔离

### 8.1 工具面是数据，不是提示词

能力剖面是纯数据：允许集、拒绝集、是否允许再委派、是否团队模式。同一份剖面同时用于：

- 生成模型可见的工具模式（看不见的工具无法被选择）；
- 运行时分发（即使模型幻觉出工具名，也会被拒绝）。

子代理默认拿到**本进程全部具体工具减去编排工具**。编排工具包括派生、等待、关闭、任务板与团队状态等；团队模式会把“对等消息 + 任务板 + 团队状态”这个协作子集加回来，但**不会**加回派生与等待。

一个刻意的决定：**角色不限制工具**。角色只影响提示词（做什么、怎么报告）。历史上角色带有空工具白名单，导致“选了一个角色就什么都干不了”。当前语义是“能力默认全量，调用方显式做减法”，忘记传参不会让子代理失去工作能力。

### 8.2 权限剖面

- 继承当前权限：把父代理的权限模式映射到子代理的工具判定；
- 只读、受限 MCP、显式批准等剖面；
- 每次派生还可以进一步允许/拒绝普通工具、MCP 服务器、MCP 工具。

权限判定与能力边界是两层：能力先决定“这个工具有没有出现在工具面里”，权限再决定“这次调用是否允许”。内部哨兵工具（无工具调用的终态信号）永远放行——它是子代理交付最终回答的通道。

### 8.3 隔离

| 隔离 | 内容 |
| --- | --- |
| 上下文隔离 | 默认不继承父代理对话，只拿 spawn 消息 |
| 进程隔离 | 独立解释器进程，独立退出与资源回收 |
| 文件系统隔离（可选） | Git 工作树；创建前做包含性校验、拒绝符号链接；关闭时输出变更摘要，清理需显式开启 |
| 传输隔离 | 每次运行独立密钥与独立通道 |

文件系统隔离是**可选**的：默认共享工作目录。共享时，父代理必须在 spawn 消息里明确“你不是一个人在这个工作区，不要回滚别人的改动”，并给每个子代理分配互不重叠的写入路径。

## 9. 上下文模型

| 模式 | 机制 | 适用 |
| --- | --- | --- |
| 隔离 | 只把 spawn 消息写入输入文件 | 默认；自包含的旁路任务 |
| 显式分叉 | 父代理选择若干轮后端历史，序列化为一次性上下文快照，子进程消费后删除 | 需要延续父代理已有对话的任务 |
| 恢复 | 从旁链转录重建历史，可对单事件做丢弃或替换 | 继续已结束的代理 |

上下文快照只消费一次：子进程读取后删除，避免下一轮误把旧上下文再插一遍。

结果侧同样有契约：最终输出登记为产物（路径、摘要、字节数、轮次），并写入转录；父代理读取的是权威结果字段，而不是原始输出流水。这样即使进程退出，结果仍可定位、校验与恢复。

## 10. 团队协作与任务板

### 10.1 隐式团队

- 每个会话天然有一个团队，根代理是协调者，名字固定；
- 子代理名即团队成员名，保留名（主代理、用户、系统等）不可占用；
- 团队标识随派生环境传给子进程；子进程不能从自己的会话标识重新推导，否则它会操作**另一个**任务板。

### 10.2 任务板语义

- 一个团队一份任务板，整体原子替换，跨进程锁保护读改写；
- 任务状态：待处理 / 进行中 / 已完成；
- **归属是软锁**：同一任务同时只能有一个归属者；第二个认领者被拒绝；
- 依赖门控：存在未完成前置任务时不可认领；
- 任务标识单调分配，删除后不复用；
- 未完成任务同主题重复创建时复用已有任务，避免模型重试造出重复任务。

### 10.3 派生与任务的绑定

团队模式下，派生必须先绑定一个可认领任务：

1. 解析本次派生实际会得到的名字（可能因历史目录追加序号）；
2. 找到指定任务或确定性匹配一个可认领任务；
3. 认领成功后才派生；
4. 把任务协议作为消息前缀交给子代理。

顺序不能反：如果先按裸名认领、再因重名得到带序号的名字，子代理的更新会被判为“非归属者”，协调者就会误以为失败并派第二波。

### 10.4 回收与自驱动

- 子代理关闭时，名下未完成任务回到任务板，并通知父代理“哪些任务被释放”；
- 团队模式子代理在回合结束后会尝试认领下一项可认领任务；没有可认领任务时才报告闲置；
- **回合完成不等于任务完成**：子代理必须显式把任务标为完成。一个被阻塞的同伴即使结束了回合，也不能让任务板出现假的“已完成”。

### 10.5 团队视图

团队视图是**报告**，不是工作队列：

- 默认包含已关闭成员；否则“打开面板看团队干得怎么样”时，恰恰因为所有成员都已关闭而显示 0 人；
- 每行同时携带关闭前状态与关闭原因，否则“完成”和“出错”都只显示为“已关闭”；
- 回合状态单独透出，避免后台同伴在两轮之间一直显示为“运行中”。

## 11. 持久化与并发

### 11.1 文件角色

| 类别 | 作用 | 写模式 |
| --- | --- | --- |
| 代理注册表 | 全树索引：路径、父路径、运行标识、进程身份、状态、关闭原因 | 整体原子替换 + 跨进程锁 |
| 任务状态 | 单个代理的回合/进程/结果状态、输入输出路径、产物引用 | 整体原子替换 |
| 事件流 | 该代理或该总线的全部状态变化 | 追加式 JSONL |
| 通知流 | 需要推送给父代理的事件子集 | 追加式 JSONL |
| 邮箱 | 点对点消息与投递状态 | 整体原子替换 + 跨进程锁 |
| 回执账本 | 发送方未决发送与终态 | 整体原子替换 + 跨进程锁 |
| 溯源账本 | 已写入邮箱的消息摘要 | 追加式 JSONL |
| 提交日志 | 控制面操作的幂等身份与结果 | 有界整体替换 |
| 启动阶段日志 | 启动握手的阶段标记，用于超时与失败归因 | 追加式 |
| 旁链转录 | 可恢复的请求、工具调用、工具结果、最终输出、关闭事件 | 追加式 JSONL |
| 产物清单 | 最终输出的摘要、字节数、轮次 | 整体原子替换 |
| 实时通道密钥 | 带外交付的通道凭据 | 任务目录内独立文件，关闭时删除 |

### 11.2 并发与原子性

- **跨进程锁**：Windows 用首字节文件锁自旋，POSIX 用阻塞文件锁；所有共享文件的读改写周期都在锁内。
- **原子替换**：先写同目录临时文件，再原子替换目标。Windows 上读句柄会阻塞替换，因此读写双方都使用同一套退避预算：读者退避重试，写者延长重试，避免“读一下文件就能让写失败”。
- **追加式日志**：事件流与通知流只追加，不重写；解析遇到坏行时跳过，不让一行坏数据毁掉整条流。
- **游标文件**：事件序号与通知游标各自独立存储，避免消费通知影响事件回放。

### 11.3 目录解析的单一真相

持久化布局有两种形态：

- 产品形态：项目数据桶 / 会话 / 子代理总线 / 任务；
- 源码或旧调用形态：状态根 / 临时目录 / 子代理总线。

主进程、子进程、UI 三方都必须从**同一份解析规则**得到目录，并通过环境变量把结果交给子进程。子进程不允许从自己的任务目录层级反推总线位置——在产品形态下，反推会落到一个没人读的“孤儿总线”。

## 12. UI 观测面

UI 不直接读子代理的标准输出，而是读桥接层投影出的权威读模型：

| 通道 | 触发 | 内容 |
| --- | --- | --- |
| 事件推送 | 事件序号之后有新事件 | 逐条事件，带去重标识 |
| 快照推送 | 注册表或任一任务状态文件的修改时间变化 | 全量记录 + 游标 + 错误 |

实现要点：

- **纯 stat 轮询**：后台观察者每半秒只比对文件签名，不解析可能达到兆字节的事件流；签名变化才重建读模型。
- **指纹去重**：快照内容不变不发第二帧；看不到重复帧是正确行为，不是丢帧。
- **游标播种**：新会话从当前尾部开始，不重放历史事件；需要历史时显式从零读取。
- **结论词表**：UI 判定“子代理到底干完没有”时，必须区分进程生命周期词与工作结论词。进程进入“等待消息”不等于失败；正确顺序是：完成状态元数据 → 回合状态 → 进程状态（仅当它不是生命周期词）→ 通用状态。
- **最新结论胜出**：同一执行标识只保留一行，新结论替换旧结论。第一次终态往往产生于真正的回合结论落地之前，是最不可靠的那一次。
- **团队名册**：默认包含已关闭成员，并用关闭前状态渲染结论字形；未知结论显式显示问号，而不是伪装成空闲。

## 13. 可靠性机制清单

| 失败模式 | 防护机制 | 不变量 |
| --- | --- | --- |
| 父进程退出留下孤儿 | 停机中禁止派生；级联关闭 | 子代理不会在没有读者的情况下继续占用槽位 |
| 进程号被复用 | 进程号 + 创建时间双重身份 | 旧行不会被新进程误认为仍存活 |
| 活跃槽位泄漏 | 启动宽限期后回收；关闭/驱逐/自愿释放 | 崩溃或重启不会永久耗尽配额 |
| 无限递归派生 | 深度上限 + 活跃数上限 + 子代理默认无编排工具 | 代理树有界 |
| 通知丢失 | 拉取/确认分离；失败不确认 | 至多重复一次，绝不丢失 |
| 通知刷屏 | 单条与整批字符预算 | 单次注入有界 |
| 自动事件被当成用户批准 | 防伪前置声明 | 模型不会把自动通知读成授权 |
| 消息投给死信箱 | 持久状态守卫 + 明确下一步 | 不会出现“回执成功但无人消费” |
| 名字串话 | 首次通信钉住 + 换人拒绝 | 名字是稳定地址 |
| 伪造同伴消息 | 溯源摘要账本 + 伪造标记 | 非账本消息永不被消费 |
| 重复控制面操作 | 提交标识三元组幂等 | 重放不会二次执行 |
| 启动静默失败 | 阶段标记握手 + 超时终止 + 失败通知 | 启动失败可归因 |
| 通道名跨项目冲突 | 数据根摘要 + 运行序号 | 两个项目不会抢同一管道 |
| 通道线程泄漏 | 管理器级统一关闭 + 关闭时释放通道 | 长驻进程不累积线程 |
| 读取方与写入方目录分裂 | 单一目录解析 + 环境变量下发 | 三方读同一棵树 |
| 大事件流拖慢观察 | 只 stat 签名 + 指纹去重 | 观测开销与事件量解耦 |

## 14. 与 Claude Code 的对齐与有意偏离

对齐的部分：

- 子代理异步、启动即返回句柄；
- 完成事件以结构化通知推送，带防伪前置与结果预算；
- 对等消息带来源标注与多播同伴列表；
- 名字首次通信钉住，换人拒绝；
- 停止中的派生者不能派新代理；
- 任务板软锁、依赖门控、关闭回收；
- 闲置帧与“本轮已给主代理发过消息”去重。

有意偏离的部分：

| 项 | 参考实现 | GA | 理由 |
| --- | --- | --- | --- |
| 执行模型 | 同进程任务 | 独立进程 | 崩溃隔离与操作系统级回收 |
| 消息路由 | 内存直写 | 持久文件 + 实时信令 | 跨进程；断线只损失时延 |
| 输入队列 | 统一三档队列 | 直接在主循环折返点注入 | 避免为单一用途引入无人使用的中间层 |
| 角色语义 | 部分角色携带能力限制 | 角色只影响提示，能力默认全量 | 防止“选了角色反而干不了活” |
| 结果交接 | 子主动交回 | 父主动读取持久结果 | GA 的结果是持久状态，误用代价低 |

## 15. 验证方法论

子代理子系统最容易出现的不是逻辑错误，而是**验证假通过**：

1. **路径分裂**：测试自己按旧公式算目录，产品按新规则算目录；两边都健康，队列永远空。因此测试必须调用与产品相同的目录解析。
2. **桩上全绿、真实链路已死**：单测替换了模型与处理器，无法证明通知真的进了模型可见的上下文。
3. **累积输出冒充当前状态**：读取终端历史字节流会把“修复前的一帧”和“修复后的一帧”同时看到，让正确实现看起来像重复。

因此采用四层证据模型，由便宜到贵：

| 层 | 驱动 | 能证伪什么 |
| --- | --- | --- |
| 探针 | 只构造对象、只读磁盘产物 | 路径分裂、落盘位置错误 |
| 单元 | 真实模块 + 假模型 | 分支、契约、序列化 |
| 真实子进程 | 真实操作系统进程 + 真实模型 | 工具面、启动握手、真实回合 |
| 真实 UI 桥 | 真实桥接 + 真实事件流 | 通知是否到模型、UI 是否实时 |

后两层不可互相替代：真实子进程证明“干得了活”，真实桥证明“主代理知道它干完了”。

另外两条硬规则：

- **反向确认**：测试必须在修复前的代码上变红，否则无法证明它抓得住缺陷；
- **不对固定输出做断言**：只断言不变量与结构证据（例如通知与工具结果出现在同一条消息、子进程能复述只存在于消息中的随机令牌）。

## 16. 已知边界与演进方向

| 项 | 现状 | 方向 |
| --- | --- | --- |
| 传输 | 同机、同用户 | 跨机器需要新的传输层与身份体系，当前不做 |
| 团队任务回收 | 关闭时回收；被中断的进行中任务没有超时回收 | 可考虑超时降级或显式回收策略 |
| 团队面板 | 代码级与桩级验证充分，真实面板仍需人工观测一次 | 纳入常规自测清单 |
| 通知流 | 只增不减，读取侧已可优化为尾部扫描 | 可引入定期压缩，但保留审计价值 |
| 手工交接 | 前台/后台切换当前只记录状态与事件，不接管交互终端 | 若需要真正接管，需重做终端所有权模型 |
| UI 测试 | 存在既有并发抖动，与子代理改动无关 | 单独排查共享计时器与时序竞争 |

## 17. 术语表

| 术语 | 含义 |
| --- | --- |
| 根代理 / 协调者 | 交互会话的主代理，代理路径为根 |
| 子代理 / 同伴 | 由派生创建、拥有独立进程与任务目录的代理 |
| 代理路径 | 树形稳定地址，根之下逐级命名 |
| 任务目录 | 一个子代理全部持久状态的锚点 |
| 运行标识 | 一次执行实例的标识，派生时单调分配 |
| 总线 | 会话级子代理数据目录，存放事件、通知、注册表、邮箱与账本 |
| 折返点 | 一批工具执行完、下一次模型调用之前的注入时机 |
| 拉取 / 确认 | 通知消费的两步：先读不推进，交付后再推进游标 |
| 钉住 | 首次通信时把名字绑定到具体代理，之后拒绝同名换人 |
| 死信箱 | 已关闭代理留下的邮箱目录，没有进程会消费 |
| 软锁 | 任务归属的并发控制：可被拒绝，但不能被抢占 |
| 驻留驱逐 | 活跃数满时优先卸载已结束且闲置的代理 |
| 能力剖面 | 允许/拒绝工具集合与委派/团队开关的纯数据描述 |
| 幂等提交 | 携带提交标识的控制面操作，重放只返回第一次结果 |
