# 诊断文件与诊断经验：为什么必须留下，以及怎么留

**日期**：2026-11-15
**触发**：Claude Code 在修 `ready`/`running` 测试竞态时，用完诊断脚本就删掉了。
用户指出这是错误行为，要求改正并沉淀经验。

---

## 1. 错误是什么

在 2026-11-15 那轮修复里，我写了三个一次性诊断文件：

- `src/diagRunningPark.test.ts` —— 确认 `Running ·` 到底有没有到达捕获流
- `src/diagRepeat.test.ts` —— 同进程重复挂载 12 次，抓偶发失败
- `src/diagCompletion.test.ts` —— 打印完成摘要的真实帧与 chunk

它们分别定位出了"帧尾是 `idle` 而不是 `running`"这个根因。**然后我把它们全删了。**

删的理由是"用完的一次性脚本不该留在仓库里"。这个理由错得很具体：

1. **诊断文件是根因的唯一可复现证据。** 断言失败信息说的是"等不到 Running"，
   但根因是"晚到的 `ready` 把状态重置了"。这两者之间的距离，就是这三个文件的价值。
   删掉之后，下次同一个 bug 回来，只能从头再猜一遍。
2. **诊断文件承载的是"怎么想到的"，不是"结论是什么"。** 结论可以写进文档，但
   "打印捕获流里真实到达的每一帧"这个方法本身，才是可复用的部分。
3. **仓库里早就有它该待的地方。** `frontends/ink/ui/probes/` 存在已久，
   `tests/probes/README.md` 明确写着"它们是结论的可复现证据……**不删除，只归类**"。
   我既没查目录约定，也没看 README，凭"一次性脚本"的字面意思就删了。

---

## 2. 正确做法

### 2.1 诊断脚本一律落到 `probes/`，不删

| 内容 | 落点 |
| --- | --- |
| Ink UI 侧（TypeScript，可 import `../src/*`） | `frontends/ink/ui/probes/` |
| PTY / 抓屏 / pyte 回放（Python） | `tests/probes/python/` |
| 探针产出的原始抓包 | `tests/probes/captures/`（已 gitignore） |

诊断过程中写在 `src/*.test.ts` 的临时文件，**结论确认后不是删掉，而是搬进 `probes/`**：
去掉 `node:test` 包装，改成一个可直接 `npx tsx probes/xxx.ts` 跑的脚本。

### 2.2 探针必须是**确定性**的，否则不配当证据

这是这次最关键的教训。第一版 `ready_race.ts` 我按真实时序写，结果跑了 24 轮
`failures=0` —— 它抓不到 bug，因为能否复现取决于事件循环当时有多忙。

一个"平时全绿、偶尔红"的探针**不能证明任何事**：绿的时候你不知道是修好了还是没触发。
所以探针要**显式构造**能触发 bug 的条件，给出两种模式：

| 模式 | 构造 | 期望 |
| --- | --- | --- |
| `stale-order` | 先让 running 落地，50ms 后再发 ready | 复现 bug（failures = 轮数） |
| `correct-order` | 等 ready 落地，再发 running | 干净（failures = 0） |

前者证明根因存在，后者证明修法有效。两者都成立，探针才算有效；脚本末尾会自己判定
并打印 `✔ 探针有效` 或 `✖ 宿主行为变了，需要复核`。

### 2.3 探针顶部写清四件事

```ts
/**
 * 探针：<一句话说测什么>
 * 手动跑：`npx tsx probes/xxx.ts`（不参与 npm test）
 *
 * ## 它测什么        —— 症状 A / 症状 B
 * ## 根因            —— 具体到文件:行号
 * ## 为什么确定性     —— 为什么不是靠运气采样
 * ## 为什么值得留     —— 结论离表现有多远
 */
```

"为什么值得留"那一节是给未来的自己看的：它回答"这个文件为什么不能删"。

## 3. 这次的根因（留作范例）

**症状 A**：`composerDuringRun.test.ts` 的 `the native cursor stays visible while
the agent is running` 偶发 15s 超时，等不到 `Running ·`。

**症状 B**：`App.test.ts` 的 `App shows a Codex-style completion summary only after
each turn ends` 偶发失败，`Worked for 1s` 出现但 token 段 `↑12k ↓1k Σ13k` 丢了。

**根因**：`src/state.ts:107` 的 `ready` 处理会把 `status → idle`、`activityLabel → null`、
`tokenUsage → null`。测试 harness 普遍写 `setTimeout(() => onEvent({type:'ready'}), 0)`，
测试却在捕获到 emit 的瞬间就发 `running` / `token_usage`。晚到的 `ready` 把已建立的状态清掉。

- 症状 A 里，晚到的 `ready` 把 `running` 打回 `idle`，`Running ·` 再也不出现。
- 症状 B 里，晚到的 `ready` 把 `tokenUsage` 清空，完成摘要只剩时间戳。

**修法**：harness 里加 `readyEmitted` 标志，**在 emit 之后**置位，`setRunning()` 先等它。
`App.test.ts` 同理，加了 `waitForCondition(() => bridge.ready, ...)`。

## 4. 顺带记下的另一类假绿

同一轮里还发现两个等待原语超时后**静默返回**：

```ts
// 超时直接 return —— setRunning() 在 Running · 从未出现时也"成功"
async function waitUntil(predicate: () => boolean, timeoutMs = 2000): Promise<void> {
  const deadline = Date.now() + timeoutMs
  while (Date.now() < deadline) {
    if (predicate()) return
    await delay(10)
  }
}   // ← 什么都不做就返回了
```

```ts
// 超时返回最后一个（不匹配的）帧，常常是空串
lastFrame = frames.at(-1) ?? ''
...
return lastFrame     // ← 调用方的 assert.doesNotMatch('', /x/) 在空串上恒真
```

前者让失败信息指向离根因很远的断言（"submitted instead of queueing"）；后者是一条
**实打实的假绿通道**：`assert.doesNotMatch('', ...)` 永远通过。

**规则**：等待原语超时必须**抛错并说明等的是什么**，绝不静默返回。
超时时长按"是不是真卡住了"来定（这里放宽到 15s —— 8 核跑 90 个测试文件时，
2s 是负载预算，不是卡死判据）。

## 5. 检查清单

写完任何诊断脚本，过一遍：

- [ ] 结论确认后，**搬进 `probes/`**，不是删掉
- [ ] 去掉了 `node:test` 包装，可直接 `npx tsx probes/xxx.ts` 跑
- [ ] 顶部写清：测什么 / 根因（文件:行号）/ 为什么确定性 / 为什么值得留
- [ ] 能**确定性复现** bug（有对照组，不是靠运气采样）
- [ ] 脚本自己判定并打印结论（`✔` / `✖`），不要求人肉解读输出
