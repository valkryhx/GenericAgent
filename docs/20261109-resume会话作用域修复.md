## 1. Claude Code 319 的做法（源码坐标）

CC 不是靠"内容启发式"区分，而是**靠目录结构**：

| 事实 | 源码坐标（`reconstructed319/deminified/`） |
| --- | --- |
| 子代理转写写在**父会话自己的目录**下：`<sessionsDir>/<sessionId>/subagents/agent-<id>.jsonl` | `m0279_0x11749cfa.js:73` `lht()` = `i(gee(), z(), "subagents")`（`z()` 是当前 session id，`gee()` 是会话根） |
| 顶层会话文件长这样：`<sessionsDir>/<sessionId>.jsonl` | 同文件 `bp()` = `i(gee(), \`${z()}.jsonl\`)` |
| 会话列表**只枚举顶层常规文件**：`isFile()` + `.jsonl` | `m0591_0x11be624e.js:33509`：`if (!S.isFile() \|\| !S.name.endsWith(".jsonl")) continue;` |
| 项目目录发现同样只认顶层文件 | `m0103_0x1135412a.js:803` 同一判据 |
| 路径解析显式区分两种形状：两层 = 用户会话；≥4 层且 `subagents/agent-*.jsonl` = 子代理 | `m2488_0x13f25e54.js:945` |
| 迁移/落盘时按 `agentId` 生成 `subagents/agent-<id>.jsonl` | `m0771_0x12408585.js:11`：`n = ["subagents", ...(e.agentRelPath ?? []), \`agent-${e.agentId}${t}\`]` |
| 历史扫描还额外跳过 `isSidechain === true` 的记录 | `m0860_0x125252e9.js:642`、`m0670_0x12268a3c.js:487` |

也就是说 CC 有三层保证：**目录嵌套（结构）+ 顶层枚举（列表）+ isSidechain（历史扫描）**。
GA 的等价物本来就存在——子代理侧写 `SubagentTranscriptStore` 写到
`<projectData>/<parent>/subagents/<run_id>.jsonl`（`genericagent/agents/transcript.py:234`），
**唯独子进程自己的会话文件被写到了顶层**，于是一模一样地混进了 `/resume`。

## 2. GA 的三个根因

1. **子进程会话落在顶层。** `GenericAgent.__init__` 在构造时就调用
   `ensure_agent_session()`（`genericagent/core/app.py:794`），那时
   `run_task_worker_loop` 还没跑（`agent.is_subagent = True` 在 `app.py:2685`），
   所以没有任何"我是子代理"的信息可用；会话就按项目桶顶层创建。
   `session_start` 与用户会话**schema 完全一致**，事后无法区分。
2. **没有子会话标记。** 子进程环境里其实已经有 `GA_PARENT_SESSION_ID` 与
   `GA_SESSION_DATA_DIR`（`genericagent/agents/manager.py:470-478`），但
   `identity_from_environment()` 没读，也没写进 `session_start`。
3. **老会话默认不可见。** `continue_cmd.list_sessions()` 支持 `session_roots`，
   但 Ink 桥的 `_resume_exclusion_kwargs()` 只在 `include_legacy=True`
   （即 `/resume --all`）时才把 legacy root 加进去。真实的 10 个老会话
   （最早 2026-10-27、最多 7 轮）因此一直躺在
   `%LOCALAPPDATA%\GenericAgent\temp\sessions` 里没人看得到。

> 补充核查：`D:\git_codes\GenericAgent\temp\sessions`（源码仓库本地运行时根）里另有
> 2208 个文件，逐个看过：全部是 e2e / 单测 / 图像冒烟产生的开发噪声（`do the task`、
> `[WORKFLOW OPT-IN]` 等），**没有**用户真实对话。真实启动（`ga.cmd` → `ga_cli`）
> 会注入 `GA_PROJECT_ROOT`，用户会话始终写项目桶。因此这个目录**故意不并入**
> `/resume`——并进去只会把 1128 条测试噪声塞给用户。

| # | 文件 | 改动 |

| 1 | `genericagent/core/transcripts.py` | `identity_from_environment()` 读取 `GA_PARENT_SESSION_ID` / `GA_SESSION_DATA_DIR`，产出 `parent_session_id` / `agent_kind="subagent"` / `session_data_dir` |

| 4 | 同上 | `list_sessions(..., include_subagents=False)`：默认跳过 `agent_kind=subagent` 与**首个用户消息**以 `[TEAM TASK PROTOCOL]` 开头的历史文件 |
| 5 | `genericagent/core/listing_cache.py` | `VERSION 1 → 2`：旧缓存条目没有 `agent_kind`，而 freshness 只比 mtime+size，不升版就永远刷不出来 |

| 7 | `genericagent/core/session_scope.py` + `scripts/migrate_child_sessions.py` | 历史残留迁移器：只在**证据精确**时移动（见 §4） |

### 3.1 为什么历史过滤只用"首条消息前缀"

历史子会话没有标记，只能靠内容。选定的唯一文本判据是 `[TEAM TASK PROTOCOL]`
（`genericagent/agents/tasks.py:438` 生成，只由 GA 写给 teammate），且**只看第一轮**——
用户完全可能在后续轮次打出这个词（已加测试证明不会被误藏）。
其余历史子会话（首条就是普通任务文本）交给迁移器用**逐字节相等**证明，绝不猜。

## 4. 历史残留迁移（`scripts/migrate_child_sessions.py`）

### 4.1 证据

`SubagentManager` 派生每个子代理时，会把 spawn message 原样写进
`<project>/<parent>/subagents/tasks/<name>/input.txt`；子进程自己的转写**首条用户消息
就是这段文字**。本机逐条核对：

- 130 条可见会话中，**77 条**以 `[TEAM TASK PROTOCOL]` 开头，**32 条**首条消息与某个
  `input.txt` 逐字节相等 → 合计 **109**，与用户看到的"一堆多智能体会话"吻合；
- 剩下 **21 条**与任何 `input.txt` 都不相等，逐条看过全是真实用户对话
  （"你好"、看图、`[WORKFLOW OPT-IN]`、真实问题）；
- 歧义（同一 prompt 对应多个父会话）**0 条**。

### 4.2 行为

- 默认 **dry-run**；`--apply` 才移动；**不删除**、**不覆盖**（目标已存在则跳过并记录）。
- **2 分钟新鲜度护栏**：mtime 在 120 秒内的文件一律不移动（可能还有活着的子进程在追加，移动会把一份转写劈成两半：下一次 append 会在旧路径重建文件）。这类文件计入 `ambiguous`。
- 目标路径：`<project>/<parent>/subagents/sessions/<session>.jsonl`，与新增子会话同一目录。
- 输出 `planned / kept / ambiguous / moved` 计数与逐条 `-> 文件 parent=... (reason)`。

实测：

```
genericagent-75a8dbce4ad4b6da：planned=109 moved=109 kept=66 ambiguous=0
20261028ai-l2-d54e8e13a88a6711：planned=2   moved=2   kept=4  ambiguous=0
其余 16 个项目桶：planned=0（无残留）
```

`kept=66` = 21 条用户会话 + 45 条空壳（只有 `session_start`，本来就被 `include_empty=False` 过滤）。

## 5.5 执行期验证：新位置可用、中间结果不受影响（2026-11-09 夜）

问题不是"会话文件换个地方"就完了：agent-team / dynamic-workflow **执行中**的
中间结果（`send_message`、任务板、`read_agent_result`、workflow handoff）会不会因为
位置变化而断链？逐个查过。

### 5.5.1 谁真的读子会话文件（静态审计）

| 子系统 | 读的是什么 | 是否受位置影响 |
| --- | --- | --- |
| 子进程自己记账（`record_agent_turn` / `append_event`） | 自己持有的 `agent.session_path` | 不受（拿到哪个路径就写哪个） |
| 子代理 durable 转写 / `send_message` / 通知 | `<父会话>/subagents/<run_id>.jsonl`（`SubagentTranscriptStore`） | 不受（`sessions/` 是它的同级新目录） |
| 任务板 / 状态 / 产物 | task dir 下的 `state.json` / `output*.txt` | 不受 |
| 子代理 resume（`resume_source=sidechain_transcript`） | 上面那条 durable 转写 + `output*.txt` | 不受 |
| workflow 子代理 | `<父会话>/workflows/<runId>/agents/<job>/transcript.jsonl` + handoff | 不受（在 `workflows/` 下） |
| `/resume` 列表 | 顶层 `session_*.jsonl` 才扫 | 正是本次要的效果 |
| 全仓 glob 检索 | 只有 `transcripts.list_sessions` 一处 `session_*.jsonl` | 已确认 |

结论：**没有任何消费者按"项目桶顶层 + 子会话 id"去找子会话文件**；
子会话自己的转写只被它自己追加。

#### 两次"失败"其实是测试脚本的时序假设，不是产品缺陷

| 运行 | 断言结果 | 真实原因（证据） |
| --- | --- | --- |
| A | `w2:interrupted` | 板 15/15 后 lead 关闭团队，w2 此时**仍在写收尾总结**：`output.txt` 停在半句、`last_round_end_at=None`、`round=0`；它已完成 11 个任务、发了 12 次 `send_message` |
| B | `w3:running` | 同一时序：断言在板满瞬间读取，w3 当时在写总结；2 分钟后它 `turn_status=completed`、`[ROUND END]` 落盘（事后核对 state.json） |

根因是脚本"板满即断言成员回合已完成"，而 `task_update` 发生在回合**内部**，
回合结束在其后。已在 `real_ink_team_scale_e2e.ts` 加**有界等待**
`waitForTeammatesToSettle()`（默认 180 s，`GA_TEAM_E2E_SETTLE_MS` 可调）：
等每个 teammate 的 `turn_status` 进入终态再断言；真卡死的 worker 仍会让测试失败。

## 6. 未做 / 边界

1. **不清理**旧 registry/任务板数据；迁移只动会话文件，且可逆（文件还在父会话目录下）。
2. **不并入**源码仓库本地运行时根 `<repo>/temp/sessions`：实测 1128 条非空会话全是开发噪声
   （见 §2 补充核查），并进去等于把测试垃圾倒进用户列表。安装版无此问题
   （`RUNTIME_ROOT == user_data_dir`，两条路径合一）。
3. 终端（非 Ink）前端的 `/resume` 仍走 `continue_cmd` 的历史默认扫描；本次只改 Ink 桥的
   作用域。若终端前端仍在用，可按同一 `session_roots` 改法对齐。
4. 历史会话检测依赖 `[TEAM TASK PROTOCOL]` 字面量；若将来改协议前缀，需要同步
   `transcripts.TEAM_TASK_PROTOCOL_PREAMBLE` 与迁移器（迁移器本身是按 `input.txt` 精确匹配，
   不受影响）。
