
# GA 与 Claude Code 上下文压缩机制对比（2026-11-10）

> 用户问：CC 的压缩机制（自动压缩 / 手动压缩）和我们调研过的那套，GA 有没有可以优化的地方？
> 本文先如实记录 GA 现在到底有什么（代码坐标），再逐项对照 CC 319 的实现
> （依据 `claudecode283_hack/docs/20261108-CC319上下文压缩机制调研.md`），最后给缺口与优先级。

---

## 1. GA 现有的压缩机制（代码坐标）

GA 的压缩分两条线，都在 `genericagent/llm/config.py` 里可配：

| 线 | 触发 | 行为 | 坐标 |
| --- | --- | --- | --- |
| 软线（摘要压缩） | 估算 token > `auto_compact_tokens`（默认窗口 × **0.90**） | LLM 摘要替换整段历史 | `core/context.py:48` / `:69` |
| 硬线（裁剪兜底） | 估算 token > `hard_limit_tokens`（默认窗口 × **0.95**） | 丢最旧消息，压到 **60%** 水位 | `llm/core.py:115` / `_HARD_TRIM_RECOVER_RATIO=0.6` |

### 1.1 触发时机

- **软线只在"用户提交新请求之前"判定**：`frontends/ink/bridge.py:574` → `:2701 _auto_compact_if_needed(text)`。
  **CLI / TUI 前端没有自动压缩**（`app.py` 只有手动 `/compact`）。
- **长工具循环中途不会触发摘要压缩**；中途超窗口时只有硬线裁剪兜底（每次请求前都会跑，
  `llm/core.py:883` / `:1026`），它直接丢最旧消息。

### 1.2 摘要用的 prompt（`core/context.py:355`）

五句话：保留目标 / 当前状态 / 决策 / 约束 / 重要文件路径 / 工具结果 / 未完成任务 / 下一步，
不要废话、不要调用工具、只返回摘要；有 `[image]` 标记时不得编造像素细节。
支持 `/compact <instructions>` 追加用户指令。**没有**分段模板（没有"必填小节"）。
摘要模型 = 当前会话模型（不升级）。

### 1.3 压缩后的历史结构（`_summary_history_pair`，`core/context.py:326`）

```text
user:      The previous conversation has been compacted. Continue from this context.
           <compact_summary>…</compact_summary>
assistant: <summary>loaded compact context</summary>
```

只有两条消息：**最近若干轮全部被摘要，不再逐字保留**。同时：

- `agent.handler = None`（`context.py:108`）—— 丢掉 handler 的 working 状态（读过的文件、cwd 等）；
- `client.last_tools = ""`（`:106`）；
- `invoked_skills` 以 `<invoked_skills>` 块**追加到摘要末尾**（`:169`），只带 name/description/base_dir；
- 压缩前的 `working_state`（handler working + last_tools + last_usage）**只写进 transcript**，供 `/resume` 用（`bridge.py:2749`、`transcripts.py:423`）。

### 1.4 微压缩（`compress_history_tags`，`llm/core.py:56`）

每 **5 次**请求执行一次：把除最近 10 条以外消息里的 `<thinking>/<tool_use>/<tool_result>`
按 800 字符**中间截断**，`<history>/<key_info>/<earlier_context>` 直接清空。
不看内容、不看路径是否重要，纯按字符切。

### 1.5 失败与回滚

摘要为空或抛错 → 完整回滚历史、`last_tools`、`agent.history`（`context.py:119`）。
Ink 前端连续失败 **3** 次后，本会话停用自动压缩（`bridge.py:202`），硬线兜底继续生效。
**没有**"缩小输入重试"或"换模型重试"。

### 1.6 其它已经对齐的

- token 计量：真实 usage 锚点 + 未发送增量字符估算 + 会话校准 cpt（`core/tokens.py`），图片块固定 1500 token。
- `PreCompact` / `PostCompact` hooks 已接（`app.py:1614`、`bridge.py:1006`）。
- transcript 侧已有 CC 风格的 `compact_boundary` + summary + `preserved_uuids` / `preserved_segment` + `working_state`。
- 摘要源文本：每条消息 6000 字符、总量 `min(2×窗口, 800K)`（`context.py:190`）；图片转 `[image]`，绝不带 base64。

## 2. 逐项对照（CC 依据 `20261108-CC319上下文压缩机制调研.md`，坐标取自该文档）

| 维度 | CC 319 | GA 现状 | 差距性质 |
| --- | --- | --- | --- |
| 窗口与水位 | `effectiveWindow = window − min(maxOut, 20000)`；四档：`warn ≥ S−20000`、`compact ≥ S−13000`、`blocked ≥ 窗口−输出预留−3000`（`m0591:82455/82466`） | 固定比例：软线 `0.90×window`、硬线 `0.95×window`（`llm/core.py:800`），无输出预留、无 warn/blocked 分档 | 口径不同：大窗口偏保守、小窗口偏激进；没有"快满了"提示 |
| 触发时机 | **每次请求前**由主循环判定（`m0848:7651`），另有 idle 预计算与 PTL 反应式 | **只在 ink 用户提交前**（`bridge.py:574`）；CLI 无自动压缩；工具循环中途只有硬线 | 长任务/大工具结果会先撞硬线 |
| 溢出兜底 | 反应式阶梯（`nPe`）：按 `actual−limit` 反推保留轮数、4 种步长、媒体降级、最后一招略过超大 tool_result（`m0591:104367`） | 硬线 `trim_messages_history`：pop 最旧消息到 `0.6×hard`（`llm/core.py:115`） | 断崖式丢 ~35% 且丢的是最早的（可能是任务目标） |
| 微型压缩 | 只清旧 `tool_result` 正文（白名单、保留最近 12 个、**省 ≥20000 token 才动手**、无 LLM 无 boundary，`m0591:81455`） | `compress_history_tags`：每 5 次请求，把最近 10 条以外的 thinking/tool_use/tool_result **按 800 字符中间截断**（`llm/core.py:56`） | GA 会伤到 tool_use 参数；无"值不值得"门槛；执行时机由计数器决定，不可预测 |
| 压缩后历史 | `[boundary, ...summary, ...replacement, ...messagesToKeep, ...attachments]`，**保留尾部逐字**（`m0591:114726`） | 只替换成 2 条消息（summary + 假 ack），**最近轮次全部变成摘要**（`context.py:326`） | 丢细节：文件路径、刚跑过的命令、当前任务原话 |
| 状态重建 | `aPe` 20 项：最近读过的文件、plan、skill 列表、MCP delta、后台任务、输出风格…（`m0591:115685`） | 只回注 `<invoked_skills>`；`agent.handler = None`、`client.last_tools = ""`（`context.py:106-109`） | 连 GA 自己叮嘱 `update_working_checkpoint` 存下的 `key_info` 都会丢 |
| 摘要 prompt | 9 个小节 + `<analysis>/<summary>` + **3 条注入防护** + TEXT ONLY 双保险 + `maxTurns:1`（`m0591:103472/103430`） | 5 句话（`context.py:355`），无小节、无注入防护 | 摘要质量与抗注入能力偏弱 |
| 手动 `/compact` | 与自动共用 `Ers/nPe/ayn/vno`；带指令、前置校验（turn in flight）、失败提示 | 与自动共用 `compact_agent_context`；带指令；已接 `PreCompact/PostCompact` hooks | 基本对齐，GA 少"轮次进行中禁止压缩"的校验 |
| 失败处理 | 熔断 3 次 + 阶梯重试 + 媒体降级 + thrashing 检测（`m0848:4810`、`m0591:116207`） | 回滚 + ink 连续 3 次熔断（`bridge.py:202`）；无重试阶梯 | GA 失败后只能等下一次，不会换个粒度再试 |
| 遥测 | boundary 带 `preTokens/postTokens/durationMs/cumulativeDroppedTokens`（实测 28/28 都带） | `record_compact_v2` 有这些字段，但 bridge 调用时传的是 0/默认（`bridge.py:2749`） | 已有管道，没接数据 |
| 预计算 / 换模型 / partial | 都有（`hOo` 6 道校验、`_xr`、`Qki`） | 无 | 属加分项，不是痛点 |

**一句话**：GA 的"压缩核心"（token 计量、软/硬线、摘要、回滚、hooks、transcript boundary）是齐的；
**缺的是"压缩得太狠 + 触发太晚"这两件事的周边**：不保留近期原文、不恢复工作状态、微压缩太粗暴、没有溢出反应式。

## 3. 优化建议（按性价比排序）

### P0：建议下一轮就做（都是小改动、不动整体架构）

**P0-1 压缩后保留最近一轮原文**（对齐 CC 的 `messagesToKeep`）

- 问题：现在 `_summary_history_pair()` 把整段历史换成 2 条消息，用户刚说的话、刚跑的命令、
  刚读到的报错全部变成摘要里的一句话。
- 做法：`compact_agent_context()` 里在摘要 pair 之后追加"最近 N 轮"原消息（N=1 起步）：
  从尾部倒推，遇到第 2 个 `role=user`（非 tool_result 承载）就停；开头若是孤立 `tool_result`
  则丢弃并加一行 `[earlier tool result omitted]`；pair 后加一句
  `The following recent turns are kept verbatim so you do not repeat work.`
- 验收：单测——12 条含 tool_use/tool_result 的历史压缩后，最后 1 轮完整保留、摘要在前；
  首条被丢弃时不留孤立 tool_result；压缩后 token 明显下降。

**P0-2 压缩后恢复工作状态**（对齐 CC `aPe` 的 A 类）

- 问题：`context.py:108` 直接 `agent.handler = None`，GA 自己叮嘱的
  `update_working_checkpoint(key_info=…)`、`related_sop`、`active_skill`、`in_plan_mode`
  全部丢出模型视野（只写进了 transcript）。
- 做法：把已有的 `_lightweight_handler_working()` 结果渲染成
  `<working_state>` 附件（key_info / related_sop / active_skill / in_plan_mode / last_tools），
  追加到摘要之后；重建 handler 时把这些字段回填到 `handler.working`。
- 验收：压缩前设置 `key_info` 与 plan 模式 → 压缩后系统上下文里能看到；
  重新进入工具循环时 `handler.working["key_info"]` 仍在。

**P0-3 CLI / TUI 也启用自动压缩**

- 问题：自动压缩只写在 `frontends/ink/bridge.py:2701`，CLI 用户只能手动 `/compact`，
  否则一路撞硬线被裁剪。
- 做法：把 `_auto_compact_if_needed` 的逻辑下沉到 `core/context.py`（或 app.py 的请求入口），
  bridge 与 CLI 共用；熔断计数放进 agent 对象而不是前端。
- 验收：CLI 单测——构造超软线 backend，提交请求前触发一次摘要压缩并发出提示；
  连续失败 3 次后本会话不再尝试。

**P0-4 微压缩改成"有压力才动、只清 tool_result"**

- 问题：`compress_history_tags` 每 5 次请求就动手，截断的是 thinking/tool_use/tool_result
  三种块，工具调用参数被中间截断后模型会照着半截参数重试。
- 做法：① 只清 `tool_result` 正文（`thinking`/`tool_use` 保留）；
  ② 先估算"能省多少"，低于阈值（建议 `max(20000, 0.05×window)`）不动；
  ③ 保留最近 10~12 个 tool_result，其余替换成 `[old tool result cleared]`；
  ④ 去掉 `_cd % 5` 计数器，改为按 token 水位触发，行为可预测、可幂等。
- 验收：未到阈值时历史字节不变；超阈值时只清 tool_result、tool_use 原样；
  同一历史跑两次结果一致。

### P1：做完成本更低、收益可观

**P1-1 溢出反应式压缩**：捕获 provider 的 `context_length` / 413，先强制摘要再重试一次
（保留轮数按"上次摘要后新增的轮数"折半），仍失败才交给硬线。对应 CC `nPe` 的最小版。

**P1-2 摘要 prompt 结构化**：换成 CC 的九个小节（Primary Request / Key Technical Concepts /
Files and Code Sections / Errors and fixes / Problem Solving / All user messages /
Pending Tasks / Current Work / Optional Next Step），并加三条注入防护：
用户约束逐字保留；只有真正的 user 消息算用户请求；tool_result 不覆盖用户消息。

**P1-3 阈值口径**：从"0.90/0.95 固定比例"改成"窗口 − 输出预留 − 13000 / − 3000"，
并保留旧配置的兼容；`warn` 档只用于 UI 提示（"上下文已用 90%，下一轮将自动压缩"）。

**P1-4 遥测接上**：`record_compact_v2` 已经有 `pre_tokens/post_tokens/duration_ms/trigger`，
bridge/CLI 调用时把估算值填进去（现在是 0），以后才能统计"压缩一次省了多少、花了多久"。

### P2：加分项，不急

- 预计算（idle 时先算好摘要，到线直接 swap）：CC 为此写了 6 道复用校验，复杂度最高。
- 摘要换更大模型、partial compact（只压某一段）。
- `XMe` 那 12 项全局重置：其中一半是 CC 自己的缓存，GA 不必照抄（CC 文档 §77.3 也这么说）。

## 4. 不建议照抄的部分

- **双引擎**（`Ino` 同步摘要 / `mfr` 反应式）：CC 文档明确说正常会话只走 `mfr`，复刻写一套就够。
- **`hOo` 6 道校验**：那是预计算复用的正确性校验，不做预计算就不需要。
- **20 项状态重建里的 CC 特有项**（agent_listing_delta、MCP delta、sticky beta、classifier 缓存）：
  GA 没有对应概念，抄了只会增加死代码。
- **失败文案**：CC 的三条 `Could not compact…` 在 319 里实际不会弹出（`zoe()` 恒 false），
  没有参考价值。

1. **单元层**：`tests/test_compact_context.py` 里加 P0-1/P0-2/P0-4 用例；
   反向确认（去掉实现后必须变红）。
2. **真实模型层**：用 `temp/prompt_ab_probe.py` 跑一个"长工具循环"任务（例如让它连续 grep/read

   （尤其 `preserved_uuids` / `working_state` 的 transcript 契约）。

## 6. 结论

- GA 的压缩**不是"很原始"**：token 计量、软硬双线、摘要、回滚、hooks、transcript boundary
  都与 CC 对齐；真正落后的是**压缩策略的细腻度**——一次压太狠（全摘要、无尾部保留）、
  状态恢复太少（handler 直接丢）、微压缩太粗暴（盲截 tool_use）、触发点太少（只有 ink）。
- 四个 P0 都是几百行以内的改动，做完后最直观的变化是：**压缩后模型还知道"刚才在干什么"**，
  而不是从一段摘要重新猜。

### 7.2 真实模型端到端（`temp/compact_e2e_probe.py`，zhanlu-ds）

脚本流程：turn1 让模型 `update_working_checkpoint(key_info=CODE=SENTINEL-7391)` 并读文件；turn1b 再读一个文件；然后把软线压到 500 token 制造"下一轮必须压缩"；turn2 只问"刚才让你记的 CODE 是什么"。

```text
system notes: ['Auto Compacted 6 messages into summary context. (auto, before this request)']
checks: auto_compact_happened=True, summary_is_the_first_message=True,
        summary_kept_sentinel=True, answer_recalled_sentinel=True,
        tail_present=True, second_compaction_did_not_fire=True
RESULT: PASS
```

即：压缩由核心触发、摘要头部正确、`SENTINEL-7391` 通过摘要/working_state 传到了下一轮、模型直接答对、且没有二次压缩。

### 7.3 仍需注意

- `maybe_auto_compact` 与 Ink 前端的 `_auto_compact_if_needed` 目前是两条入口（Ink 在提交时压、核心在消费时压）。第二次判定会因为"刚压过且 usage 锚点已重置"而自然跳过，端到端已验证；后续可以把 Ink 改成直接调核心入口，彻底去掉重复实现。
- 硬线裁剪仍是一次丢到 60% 水位（本次没动）。
- P1（溢出反应式、九小节摘要 prompt、阈值口径、遥测）尚未实施。

### 8.1 回合内重试（可重试的请求边界）

上一版只能"检测 + 压缩 + 提示用户重发"，因为 GA 把上游错误当普通文本（`!!!Error: ...`）
yield 出去，tool loop 里没有异常可捕、也没有回滚点。现在补上了：

1. `core/errors.py`：`ContextOverflowError` + 特征匹配（`context_length` / `maximum context length` /
   `prompt is too long` / `too many tokens` / `413 Request Entity Too Large` …），四个解析点在命中时**抛异常**，
   其余错误保持原来的文本行为。
2. `core/loop.py`：每次 `client.chat()` 外层是一个可重试帧——调用前记下 `history` 长度、
   `client.last_tools`、`_pending_tool_ids`；捕获 `ContextOverflowError` 后先**回滚**（截掉本次
   append 的 user 消息、恢复计数、清 `last_provider_error`），再压缩，然后**只重发这一次模型调用**，
   重试预算 1 次；第二次仍失败就把异常抛给上层。
3. 由此得到的语义：用户消息恰好一条、已经执行过的工具不会重放、`UserPromptSubmit` 等 hook 不会二次触发、
   UI 不会出现两条用户消息。

残留限制（如实说明）：如果失败那次已经往界面上吐了一部分文本，那段文本无法撤回（一般上游是在开头就拒，
还没产生 token）；要彻底避免得把流先缓冲到首个 chunk 再放行，本轮没做。

测试：`tests/test_overflow_retry.py` 7 条——一次溢出后压缩并原地重试、历史只剩一条新 user 消息、
二次溢出不再重试、普通异常不重试不压缩、正常回合不压缩、解析层把溢出升级成异常而非文本。
反向确认：stash 掉 `loop.py` 后 2 条重试测试变红。

## 11. 预计算压缩（P2 最后一项）

目标：把端到端测到的 **同步压缩 13.8 秒**等待变成 0——摘要提前算好，到线时只是一个 swap。

### 11.1 机制

- **何时算**：回合结束、任务队列为空时（`app._precompute_compaction()`），且估算用量 ≥ 软线 × **0.8**
  （`PRECOMPUTE_WATERMARK_RATIO`）。
- **算什么**：只摘要**前缀**——`coverage_len = len(history) − 最近一轮`，尾轮留原文；结果存
  `agent._precomputed_compact = {summary, coverage_len, fingerprint}`，其中 `fingerprint` 是前缀的 sha256。
  只产生文本：不改历史、不写 transcript、不动会话状态。
- **何时用**：`compact_agent_context(reuse_precomputed=True)` 在真正压缩时先尝试复用——
  前缀指纹一致就直接用缓存摘要，尾段 = `history[coverage_len:]`（包括预计算之后新加的所有消息）；
  `result.precomputed_reused=True`，并打印 `[Compact] reused the precomputed summary`。
- **何时作废**：指纹不一致（压缩、`/resume`、编辑过前缀）、缓存缺失/损坏、或 `instructions` 非空
  （`/compact 指令` 要的是另一种摘要）→ 丢弃缓存，走同步摘要。

### 11.2 三条容易踩的坑（都已按约束实现）

1. **`<invoked_skills>` / `<working_state>` 在 swap 时现生成**，缓存里只存纯摘要——否则会把预计算那一刻的
   过期计划、过期 checkpoint 塞回模型。
2. **transcript 按 coverage 记**：`CompactResult.summarized_messages` 记的是被摘要的条数（不是原始总条数），
   `kept_turns` 记保留了几轮，`record_compact_v2` 用它们填 `messages_summarized` / `keep_recent_turns`，
   这样 `/resume` 拼回的位置才正确。
3. **并发安全**：`_summarize_with_backend` 在一次摘要期间**持有 backend 锁**（`threading.Lock` 改成 `RLock`，
   因为内部 `ask` 还会再拿一次），否则预计算换历史的同时有请求进来，会把新消息写进临时空历史并丢失；
   另外 `_precompute_compaction` 在队列非空时直接跳过。

### 11.4 真实模型结果（`temp/precompute_e2e_probe.py`）

脚本：turn1 记 SENTINEL 并读文件 → 把软线调到"当前用量/0.85"（低于 80% 水位不会立刻压缩、高于则触发预计算）
→ turn1b 再读文件（回合末应预计算）→ 把软线压到当前用量以下 → turn2 触发压缩（应复用缓存）→ 问回 SENTINEL。

```text
[Precompute] summarized 8 messages ahead of time.
fingerprint match right after precompute: True | history len: 12 | coverage: 8
[Compact] reused the precomputed summary for 8 messages.
{ "precompute_happened": true, "compaction_reused_cache": true,
  "only_one_compaction": true, "cache_cleared_after_use": true,
  "answer_recalled_sentinel": true }
RESULT: PASS
```

过程中发现并修掉了一个真问题：缓存是**和摘要 prompt 绑定的**。最初把复用条件写成
「instructions 为空才复用」，结果自动压缩自己带了一句 `Automatic compact before the
next user request.`，永远命不中缓存——端到端第一次跑就是「预计算成功、复用失败」。
改成缓存里存下 `instructions`、swap 时逐字比对，并把自动压缩的指令抽成常量
`AUTO_COMPACT_INSTRUCTIONS`，问题消失；带自定义指令的 `/compact` 因为 prompt 不同，
依然不会复用（有单测钉住）。
