
# GA 输入框看图优化设计与实施方案

> 依据：`claude_hack/docs/20261024-CC-输入框看图链路实现调研.md`（Claude Code 2.1.303 源码级调研）
> 对照对象：`frontends/ink/ui/src/{clipboardImage,imagePathDetect,imageAttachments,inputController}.ts`、
> `frontends/ink/bridge.py`、`genericagent/core/app.py`、`genericagent/media/{image_codec,image_gc}.py`
> 日期：2026-10-24　状态：设计稿（未实施）

---

## 0. 一句话结论

GA 的输入框看图链路**主干已经通了**：剪贴板捕获 → `[Image #N]` 占位 → 路径附件 → 后端编码 → 原生 image block。
与 CC 303 对比后，真正的差距集中在 **10 个点**，其中 3 个（O1/O2/O3）属于"吞输入/误导模型"的正确性问题：

| 编号 | 优化项 | 优先级 | 一句话 |
|------|--------|--------|--------|
| O1 | 剪贴板无图时回退为文本粘贴 | **P0** | 当前 Ctrl+V 命中贴图分支后，剪贴板是文字就什么都不发生（`App.tsx:702` 直接 return） |
| O2 | 补尺寸/坐标说明（对齐 CC `Lee`） | **P0** | 图被缩到 2048 后模型不知道原始尺寸，给坐标/点击位置必错 |
| O3 | 收紧后端路径自动扫描 | **P0** | `_extract_image_paths` 扫描整段文本（含代码块/URL），可能"意外附图" |
| O4 | 长边预算 2048 → 1568（可配） | P1 | CC 用 1568；2048 多花约 70% 图片 token，多数 provider 还会再缩一次 |
| O5 | token 估算与 O4 联动 | P1 | `IMAGE_BLOCK_TOKENS=1500` 在 1568 下是准的，在 2048 下偏低 |
| O6 | 单图失败对用户可见 | P1 | 目前失败只写进模型文本，用户界面无提示 |
| O7 | 前端路径存在性前置校验 | P1 | 不存在的路径也会生成 `[Image #N]`，后端才报错 |
| O8 | 占位符高亮 / 可点击 | P2 | CC 渲染成 chip + OSC-8 链接；GA 是纯文本 |
| O9 | 快捷键策略收敛 | P2 | Ctrl+V 同时承担"贴图"和"文本粘贴"，语义要写死 |
| O10 | 多前端一致性 | P2 | 目前只有 ink 与飞书桌面端会传 `images`，其余前端靠后端扫路径 |

**推荐落地顺序**：O1 + O3（安全/正确性）→ O2 + O4（质量/成本）→ O6 + O7（体验）→ 其余。

## 2. CC 303 输入框链路里值得借鉴的 6 个设计

只列与 GA 有差距的部分，完整链路见 CC 调研文档。

### 2.1 统一归一化函数（`jb`，`m0396:609`）

剪贴板、路径粘贴、拖拽、Read 工具**全部**走同一个 `jb`：格式嗅探 → 缩放 → 重编码 → 返回 `{buffer, mediaType, dimensions}`。
GA 目前也是统一的（`image_codec.encode_image_for_prompt`），这点**已经对齐**，不需要改。

### 2.2 尺寸说明作为独立 meta 消息（`Lee`，`m0396:993`；`gs`，`m0683:2737`）

CC 在缩放或带源路径时生成：

```text
[Image: source: <path>, original 3024x1964, displayed at 1568x1018.
        Multiply coordinates by 1.93 to map to original image.]
```

并作为**独立 `isMeta` 消息**追加，不混进用户正文。
GA **完全没有**这类说明（全仓库无 `original ... x ...` / `Multiply coordinates` 字样）。

### 2.3 剪贴板读图失败回退读文本（`mue` 失败 → `D()`，`m0549:85` / `:117`）

CC 的粘贴处理是"先试图，失败再试文本"，两条路都在同一个组件里。
GA 只有读图（`captureClipboardImage`），没有读文本；失败即静默丢弃。

### 2.4 路径粘贴的双重校验（`Ods`，`m0549:149`）

CC 先按扩展名/绝对路径判定，再**确认文件存在**，才生成附件。
GA 前端只做正则判定（`imagePathDetect.ts:65`），不检查存在性；存在性检查推迟到后端编码。

### 2.5 附件 store 的条数上限与生命周期（`m0681:62`，200 条；`m0863:2161`，90s/45s 草稿 GC）

CC 的磁盘 store 有 200 条 LRU，粘贴草稿有 90s/45s 两级回收。
GA 有磁盘 GC（`image_gc.py:21` 7 天 / `:22` 200 条），**已对齐**；但内存 store 只在提交时剪枝。

### 2.6 占位符不剥离（`m0683:2352` 全程不删 `[Image #N]`）

GA 也是保留占位符（`inputController.ts:349-377` 只把**路径**替换成占位符，不删占位符）。
**已对齐**，无需改。

### 3.6 后端路径二次扫描

`_extract_image_paths`（`app.py:89`）对整段用户文本做三轮回溯：

```python
# 1) 引号包裹的路径
r'"([^"]+\.(?:png|jpe?g|webp|gif|bmp))"|\'([^\']+\.(?:png|jpe?g|webp|gif|bmp))\''
# 2) 绝对路径
r'(?:[A-Za-z]:[\/]|/)[^\r\n"\']+?\.(?:png|jpe?g|webp|gif|bmp)'
# 3) 任意非空白 token 以图片扩展名结尾
r'\S+\.(?:png|jpe?g|webp|gif|bmp)'
```

命中后要求 `os.path.isfile`，并去重。**没有**跳过代码块、URL、`key=value` 里的路径。

### 3.7 非原生后端的降级

`app.py:1081-1120`：当 `supports_image_input` 为假时，

1. 把附件真实路径补进 `raw_query` 文本；
2. 追加 `[系统] ...无原生图片输入能力...上述 [Image #N] 仅是占位符...`；
3. 通过 `display_queue` 给用户一条 `[image] ...` 提示。

这条降级**做得比 CC 细**（CC 默认模型都支持图，不需要），保留。

## 5. 优化项详解

### O1（P0）剪贴板无图时回退为文本粘贴

**现状**

`handleInput` 一旦命中 `isImagePasteShortcut` 就返回 `pendingImagePaste`（`inputController.ts:300`），
App 侧捕获失败时直接 `return`（`App.tsx:702`）：

```ts
void applyClipboardImagePaste(baseValue, baseOffset, imageStore)
  .then((pasted) => {
    if (seq !== imagePasteSeqRef.current) return
    if (!pasted.ok) return          // ← 这里什么都没发生
```

**问题**

- Windows：Ctrl+V 通常被终端截获，应用收不到，所以影响小；**Alt+V 是主快捷键**，剪贴板是文字时同样被吞。
- macOS / Linux：Ctrl+V 会到达应用，剪贴板是文字时**用户按了粘贴但没有任何反应**。
- 用户会认为"粘贴坏了"，而不是"剪贴板没有图"。

**CC 的做法**

`mue`（`m0549:85`）读图失败后，同一个粘贴处理器会调用 `D()`（`m0549:117`）读剪贴板文本并插入。
即"先试图，失败再试文本"，两条路在一个组件里。

**方案**

1. 新增 `readClipboardText()`（建议放 `frontends/ink/ui/src/clipboardText.ts`）：

   ```ts
   // win32:  powershell -NoProfile -Command "Get-Clipboard -Raw"
   // darwin: pbpaste
   // linux:  wl-paste --no-newline || xclip -selection clipboard -o
   ```

2. `applyClipboardImagePaste` 的失败结果补一个 `reason`：

   ```ts
   type ClipboardPasteResult =
     | { ok: true; value: string; cursorOffset: number }
     | { ok: false; reason: 'no-image' | 'too-small' | 'timeout' | 'tool-missing'; error?: string }
   ```

3. App 侧在 `reason === 'no-image'` 时回退：

   ```ts
   if (!pasted.ok) {
     if (pasted.reason !== 'no-image') return   // 有图但坏了：保持静默
     const text = await readClipboardText()
     if (!text) return
     // 插到"完成瞬间"的光标处，复用现有 current.value !== baseValue 分支
     insertTextAtCurrentCursor(text)
     return
   }
   ```

4. **防重复粘贴**：终端若同时把文本以 bracketed paste 送进来（`paste.ts:10` 的 `\u001b[200~`），
   会出现"插两次"。加 150ms 去重窗口：记录本次回退插入的文本，
   若 `pasteStore` 在 150ms 内收到内容相同/包含关系的 paste，丢弃后者。

**边界**

- `reason === 'too-small'`（剪贴板里是 1x1 占位图）：**不要**回退成文本，保持静默。
- `reason === 'timeout'`：保持静默，避免慢剪贴板导致文本插入滞后。
- 环境变量 `GA_CLIPBOARD_TEXT_FALLBACK=0` 可关闭回退。

**验收**

- 剪贴板放文字 → Ctrl+V（macOS/Linux）/ Alt+V（Windows）→ 文本出现在光标处。
- 剪贴板放图片 → 出现 `[Image #N]`，不出现文本。
- 连续按两次 → 只插一次。

### O2（P0）补尺寸/坐标说明

**现状**

`EncodedImage` 已经带 `width/height/resized/source_path`（`image_codec.py:30-40`），
但 `build_image_block`（`:256`）只输出 `type/source`，**尺寸信息在发给模型前被丢弃**。

模型拿到的只有像素，不知道原始尺寸、不知道自己看到的是缩放版、也不知道坐标要乘多少。

**影响场景**

- "点这个按钮" / "这个元素在屏幕什么位置"——模型给出的坐标基于缩放后的图，与用户屏幕坐标不一致。
- 3024x1964 的浏览器全屏截图被缩到 2048x1330，误差约 1.48 倍。

**CC 的做法**

`Lee`（`m0396:993`）生成：

```text
[Image: source: <path>, original 3024x1964, displayed at 1568x1018.
        Multiply coordinates by 1.93 to map to original image.]
```

只在"缩放"或"有源路径"时生成；作为独立 `isMeta` 消息由 `gs`（`m0683:2737`）追加。

**方案**

GA 没有 `isMeta` 概念（全仓库无此字段），因此**不新增消息**，把说明追加到 user content 的**第一个 text block**。

前置改动：`EncodedImage` 增加 `orig_width/orig_height`，在 `encode_image_for_prompt` 缩放前记录。
否则说明会写成"original == displayed"，等于没写。

```python
def display_note(enc: EncodedImage) -> str:
    """只在缩放或带源路径时生成，对齐 CC Lee 的触发条件。"""
    if not enc.resized and not enc.source_path:
        return ""
    parts = []
    if enc.source_path:
        parts.append(f"source: {enc.source_path}")
    parts.append(f"original {enc.orig_width}x{enc.orig_height}")
    if enc.resized and enc.width > 0:
        scale = enc.orig_width / enc.width
        parts.append(f"displayed at {enc.width}x{enc.height}, multiply coordinates by {scale:.2f}")
    return "[image] " + ", ".join(parts)
```

`build_user_content_with_images` 收集所有 note，追加到 `content[0]["text"]` 末尾：

```python
notes = [n for n in (display_note(e) for e in encoded) if n]
if notes:
    content[0]["text"] = (content[0]["text"] or "").rstrip() + "\n\n" + "\n".join(notes)
```

**为什么不新加 text block**

`_msgs_claude2oai`（`llm/core.py:733`）把同一 user 消息里的 text/image 按出现顺序平铺；
末尾的独立 text block 会变成 `[text, image_url, image_url, text]`，
部分 OpenAI 兼容代理只接受固定的文本位置。合并进第一个 text block 最稳。

**为什么不学 CC 用独立 meta 消息**

`_fix_messages`（`llm/core.py:945`）会把连续同 role 消息合并，独立 user 消息会被拼回去，
既拿不到 CC 的"meta 不参与用户意图"效果，还多一条无意义消息。

**验收**

- 3024x1964 截图 → 文本出现 `[image] source: ..., original 3024x1964, displayed at 1568x1018, multiply coordinates by 1.93`。
- 800x600 的图 → 只有 `[image] source: ...`。
- 非原生后端（`supports_image_input=False`）→ 不重复输出（该分支已有路径列表，见 `app.py:1115-1122`）。

### O3（P0）收紧后端路径自动扫描

**现状**

`_extract_image_paths`（`app.py:89`）对**整段** `raw_query` 做三次正则：

```python
r'"([^"]+\.(?:png|jpe?g|webp|gif|bmp))"|\'([^\']+\.(?:png|jpe?g|webp|gif|bmp))\''
r'(?:[A-Za-z]:[\/]|/)[^\r\n"\']+?\.(?:png|jpe?g|webp|gif|bmp)'
r'\S+\.(?:png|jpe?g|webp|gif|bmp)'
```

命中后要求 `os.path.isfile` 并去重，**没有**跳过代码块、URL、`key=value`。

**问题**

1. **代码块误伤**：粘贴日志/配置/代码，里面出现 `assets/logo.png` 且文件存在 → 被当成附件发出去。
2. **URL 误伤**：`https://x.com/a.png` 会被切出 `//x.com/a.png`；若本地恰好有同名相对路径就误命中。
3. **`key=value` 误伤**：`ICON=assets/a.png` 单独出现时会被第 3 条捕获。
4. **数量无上限**：50 个路径 → 50 张图一起发，直接撑爆上下文。

**方案**

扫描前做三步预处理，并加上限：

```python
MAX_AUTO_IMAGE_PATHS = 8

_FENCE_RE = re.compile(r"```[\s\S]*?```|~~~[\s\S]*?~~~")
_INLINE_CODE_RE = re.compile(r"`[^`\n]+`")
_URL_RE = re.compile(r"https?://\S+")

def _strip_non_path_regions(text: str) -> str:
    text = _FENCE_RE.sub(" ", text)
    text = _INLINE_CODE_RE.sub(" ", text)
    text = _URL_RE.sub(" ", text)
    return text
```

- 三条正则只作用于 `_strip_non_path_regions(raw_query)`。
- 第 3 条（裸 token）要求不以 `=`、`:`、`(`、`[` 开头：
  `r'(?<![\w=:([])\S+\.(?:png|jpe?g|webp|gif|bmp)'`。
- 结果截断到 `MAX_AUTO_IMAGE_PATHS`，超出时在文本里留一行：

  ```text
  [image] 其余 N 个路径未自动附图（上限 8），如需请单独粘贴
  ```

- 环境变量 `GA_IMAGE_AUTO_PATHS=0` 完全关闭后端自动扫描（前端附件不受影响）。

**为什么保留第 3 条正则**

CLI 与非 ink 前端（`frontends/web`、`frontends/terminal`、`frontends/acp`、`frontends/bots`）不传 `images`，
用户只能靠"把路径写进文本"附图。删掉第 3 条会让这些前端失去能力。

**验收**

- 代码块里出现 `assets/logo.png` → 不附图。
- 文本里 `D:\shots\a.png`（存在）→ 附图。
- 12 个存在的路径 → 只附前 8 个，并出现截断提示。
- `GA_IMAGE_AUTO_PATHS=0` → 完全不附图。

### O4（P1）长边预算 2048 → 1568（可配）

**现状**

`MAX_DIMENSION = 2048`（`image_codec.py:14`），超长边才缩，缩到 2048。

**为什么改**

1. **成本**：图片 token ≈ `w*h/750`。2048 方图约 5590 token，1568 方图约 3278 token，单图差约 2300。
2. **收益为零**：Claude 视觉编码器内部会把长边压到约 1568，再大也是被降采样。
3. **与 token 估算一致**：GA 固定按 1500 token/图估算（`tokens.py:31`）；
   1568 长边的真实值接近这个数，2048 则明显低估，压缩时机判断偏晚。
4. **与 CC 对齐**：CC 输入链路长边就是 1568（`m0396:205-206`），且额外做 token 目标二分。

**方案**

```python
MAX_DIMENSION = int(os.environ.get("GA_IMAGE_MAX_DIMENSION", "1568"))
# 夹紧到 512..2048；2048 保留给"某些 provider 明确要求更大"的场景

MAX_IMAGE_AREA = MAX_DIMENSION * MAX_DIMENSION
```

再加**面积上限**（CC `q()` 的简化版）：

```python
if width * height > MAX_IMAGE_AREA:
    ratio = math.sqrt(MAX_IMAGE_AREA / (width * height))
    new_w, new_h = max(1, int(width * ratio)), max(1, int(height * ratio))
    # 交给 Pillow 重采样
```

面积上限比"只卡长边"更贴近 token 预算：4000x500 的长条图长边没超但面积很大，只卡长边会放过它。

**风险**

- 极小字号截图在 1568 下可能糊。提供 `GA_IMAGE_MAX_DIMENSION=2048` 按需放开。
- `MAX_BASE64_CHARS=5_000_000` 不需要跟着改（1568 的 PNG 远小于此）。

**验收**

- 3024x1964 截图 → 编码后长边 1568。
- 4000x500 长条图 → 编码后约 1568x196。
- `GA_IMAGE_MAX_DIMENSION=2048` → 回到旧行为。

### O5（P1）token 估算与 O4 联动

**现状**

`IMAGE_BLOCK_TOKENS = 1500`（`tokens.py:31`），只统计顶层 image block（`:93`）。

**结论：O4 落地后，1500 是合适的，不需要改公式。**

- 1568 长边的图按 `w*h/750` 算约 3278 token，但 Anthropic 对图像有单图上限，
  实际计费通常落在 1500-1600 区间。
- 保守估计（少算）比高估好：高估会导致过早压缩，丢上下文。
- 真正的问题不是公式，而是**尺寸上限与估算不匹配**——2048 时真实成本可能是估算的 3 倍以上。

**要做的小改动**

1. 在 `tokens.py:31` 的注释里写清"该值的前提是 `MAX_DIMENSION <= 1568`"。
2. 增加一条断言式测试：编码任意大图后，`len(data_b64)` 对应的估算不应超过 `IMAGE_BLOCK_TOKENS * 4`。
3. 可选：`IMAGE_BLOCK_TOKENS` 改为读环境变量，方便极端场景调参。

**不改的部分**

`_msg_image_count` 只数顶层 block——这是**正确的**：输入框链路里图都在顶层；
`tool_result` 里的图属于"agent 自主读图"，届时需要递归计数（见自主读图设计文档 §6.5），
但那是另一个改动，不要混在本次。

### O6（P1）单图失败对用户可见

**现状**

`build_user_content_with_images` 在单图失败时把错误写进文本（`image_codec.py:331`）：

```python

```

模型能看到，**用户看不到**——除非模型主动复述。

**方案**

1. `build_user_content_with_images` 增加可选参数收集失败：

   ```python
   def build_user_content_with_images(text, images=None, *, extra_paths=None, failures=None):

       except Exception as e:
   ```

**验收**

- 粘一个被删除的文件路径 → 界面出现 `[image] 图片附件读取失败: ...`，模型也收到同一行。

### O7（P1）前端路径存在性前置校验

**现状**

`asImageFilePath`（`imagePathDetect.ts:65`）只做"绝对路径 + 扩展名"判定；
`insertImagePlaceholdersAtCursor`（`inputController.ts:197`）无条件 `attachImage`。
路径不存在时，输入框照样出现 `[Image #N]`，直到提交后后端编码才报错。

**CC 的做法**

`Ods`（`m0549:149`）在生成附件前**确认文件存在**，失败直接归类为"不是图片路径"，不产生占位符。

**方案**

在 `insertImagePlaceholdersAtCursor` 与路径分支（`inputController.ts:349-363`、`:401-410`）里：

```ts
import { existsSync, statSync } from 'node:fs'

function isUsableImagePath(p: string): boolean {
  try {
    const st = statSync(p)
    return st.isFile() && st.size > 0
  } catch { return false }
}
```

- 不可用 → **不 attach**，原文保持不变（用户能看出没被转换），并设置一条 2s 自动消失的提示：

  ```text
  [image] 找不到文件：<path>
  ```

- 纯路径输入且不可用 → 不做任何转换，按普通文本发送（与 CC 一致）。

**注意**

- 前端只校验"存在且非空"，**不做格式/尺寸校验**——那仍然由后端 `image_codec` 负责，
  避免前端引入图片解码依赖。
- Windows 路径大小写不敏感，`existsSync` 已处理。

**验收**

- 输入一个不存在的 `D:\nope.png` → 不生成占位符，出现提示。
- 输入存在的图 → 正常生成占位符。
- 路径指向目录 → 不生成占位符。

## 7. 代码骨架

### 7.1 `clipboardText.ts`

```ts
import { spawnSync } from 'node:child_process'

export function readClipboardText(): string {
  const r = process.platform === 'win32'
    ? spawnSync('powershell', ['-NoProfile', '-Command', 'Get-Clipboard -Raw'], { encoding: 'utf-8', timeout: 2000 })
    : process.platform === 'darwin'
      ? spawnSync('pbpaste', [], { encoding: 'utf-8', timeout: 2000 })
      : spawnSync('bash', ['-lc', "wl-paste --no-newline 2>/dev/null || xclip -selection clipboard -o 2>/dev/null"], { encoding: 'utf-8', timeout: 2000 })
  if (r.status !== 0) return ''
  return (r.stdout || '').replace(/\r\n/g, '\n')
}
```

### 7.2 policy 化

```ts
export type ImagePastePolicy = 'image-only' | 'image-then-text'

export function imagePastePolicy(key: InputKey, rawInput: string): ImagePastePolicy | null {
  if (!isVChar(key, rawInput)) return null
  const alt = Boolean(key.alt || key.meta)
  const ctrl = Boolean(key.ctrl)
  if (alt && ctrl) return 'image-only'        // Ctrl+Alt+V
  if (alt) return 'image-only'                // Alt+V / Meta+V
  if (ctrl) return 'image-then-text'          // Ctrl+V
  return null
}
```

5. 粘贴含 `assets/logo.png` 的代码块 → 不附图。
6. 粘贴 12 个存在的路径 → 只附 8 个，有截断提示。

## 11. 不照搬 CC 的部分

| CC 做法 | 为什么不照搬 |
|---------|-------------|
| `isMeta` 独立说明消息 | GA 的 `_fix_messages` 会合并连续同 role 消息，达不到"不污染用户意图"的效果 |
| 读文件权限门 `VWt` | GA 的路径来自用户主动输入/前端附件，不是模型自行决定；加门会打断正常流程 |
| 磁盘 store 200 条 LRU + 0600 | GA 已有 `image_gc`（7 天 / 200 条），且临时图不是长期资产 |
| chip + OSC-8 默认开 | 终端兼容性参差，默认开容易出乱码 |
| 28px patch token 公式 | GA 的固定 1500 在 1568 预算下已足够，引入公式收益低于维护成本 |
| WSL 路径转换 | GA 当前不面向 WSL 场景，先不做 |

## 13. 一句话总结

GA 的输入框看图**不缺能力，缺三样东西**：

1. **失败时的第二选择**（O1）——剪贴板没图就什么都不做，用户以为坏了；
2. **给模型的尺寸事实**（O2）——缩放了却不告诉模型原始尺寸，坐标类任务必错；
3. **扫描的边界**（O3）——后端把整段文本当路径清单，代码块里的文件名也会被附图。

O4/O5 把成本与估算对齐到 1568，O6/O7 让失败可见、让无效路径不产生占位符，
O8-O10 属于体验打磨。按 S1→S4 顺序落地，每一步都能单独回滚。
