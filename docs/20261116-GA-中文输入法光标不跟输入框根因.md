# GA 中文输入法光标不跟输入框 —— 根因与修复（2026-11-16）

**状态：** ✅ 已修复并真机验证（862 tests + typecheck PASS）
**主修复：** `frontends/ink/ui/src/stdoutCursorPark.ts`（park 段每帧重发 SHOW）
**相关：** `docs/ga_ui_ime_visible_native_cursor_root_cause_2026-07-16.md`（上一轮的「可见性」根因）

---

## 0. 结论先行

> **`stdoutCursorPark.ts` 用 `cursorShown` 记账来决定「要不要发 `ESC[?25h`」，只在
> 「不可见 → 可见」的那一次发。但在 ConPTY 上，终端会在 DEC 2026 同步输出
> （BSU/ESU）事务边界自行插入 DECTCEM HIDE，于是 writer 的记账与终端的真实状态
> 脱钩：整个会话只 SHOW 了 1 次，原生光标停在屏幕右下角 `(39,119)`。**

- park 的相对移动算术**从头到尾都是对的**（真机 SINK 日志：帧末确实发出 `ESC[4A ESC[10G`，
  行/列与输入行、反显块精确吻合）；
- 缺的也不是「可见性开关」本身（2026-07-16 已经加了 SHOW）；
- 缺的是**每一帧都重新声明可见性**——因为终端会在事务边界把可见性重置掉。

修法 = 把 `needShow` 从「只在记账为不可见时发」改成「**每帧都发**」。不发 HIDE，
所以不会闪；闪烁来自 HIDE/SHOW 成对翻转，而这条链路上一次 HIDE 都没有。

---

## 1. 症状

用户描述（Windows Terminal，中文输入法）：

| 场景 | 现象 |
|---|---|
| 中文合成 | 拼音 preedit 与候选框出现在**屏幕下方**，不跟随输入框里的深色光标；输入框光标不横向扩展 |
| 切换英文（Shift） | 正常，字符出现在反显块光标左侧 |
| 整体观感 | 输入时光标「左右晃」 |

「英文正常、中文异常」这个对照组在 2026-07-16 的文档里已经被解读过一次（英文靠反显块顶替可见光标，中文需要系统级锚点）。那一轮把根因定在「原生光标被隐藏」。本轮的问题是：**修复之后症状仍然存在**。

## 2. 真机测量（这是本轮的关键，也是上两轮缺失的部分）

### 2.1 真机探针的建立

在真 PTY（`winpty.PtyProcess` + `pyte`）里跑 `./ga`，逐字输入后采样三样东西：

1. composer 输入行的行号（`────…` 上边框的下一行）；
2. 该行里**反显块**的列（pyte 的 `reverse` 属性）——这是用户看到的深色光标；
3. **原生光标**的绝对 `(row, col)` 与 DECTCEM 状态——这是输入法锚定的位置。

### 2.2 测量结果（修复前）

```
composer 输入行 = 35   反显块列 = 8
该行内容       = ' > abcde'
原生光标       = (39, 119)    ← 屏幕右下角
DECTCEM        = show 1 / hide 2
```

**整个会话只 SHOW 了 1 次**。光标在屏幕最后一行最后一列，而用户看到的深色光标在
第 35 行第 8 列。两者相差 4 行、111 列——这就是「拼音跑到屏幕下方」的准确距离。

### 2.3 一次伪证（必须记下来）

第一版探针用 `console.error` 打调试日志，结果 ink 的 `patchConsole` 把每条日志写进
stdout 并重画上一帧 → 每条日志又触发一次渲染 → 又产生一条日志，13 秒刷出 **8265 条**、
每帧退化成 1 行。在那个自反馈里我一度读到 `spec=null`（park 从未发生），那是**假的**。

改成写文件旁路（`GA_UI_PARK_LOG`）后重测：

```
SINK 1144B "...\x1b[39m\n\x1b[4A\x1b[9G\x1b[?2026l"
                                            ^^^^^^^^^^
                                  ?2026l = ESU，事务在此结束
```

park 段 `ESC[4A ESC[9G` **确实存在且正确**。所以「park 没发生」这个假设被推翻，
真正的问题在 SHOW 上。

## 3. 定位（A/B/C 三配置对照）

只改一个环境变量，各跑一次，读回原生光标：

| 配置 | 原生光标 | DECTCEM | 判定 |
|---|---|---|---|
| **A 默认**（park + 同步输出） | `(39,119)` | show=1 / hide=2 | ✖ 偏离（4 行 110 列） |
| **B 关同步输出** `GA_UI_SYNC_OUTPUT=0` | `(35,9)` | show=17 / hide=17 | ✓ 在 caret |
| **C 关 park** `GA_UI_CURSOR_PARK=off` | `(39,119)` | show=0 / hide=1 | ✖ 偏离（对照组） |

**B 正确、A 错误**，两者唯一的差别是同步输出。而 B 配置里 DECTCEM 是 17/17 ——
因为 `syncOutput` 为 false 时 `needHide` 恒为 true，每帧都在 HIDE→SHOW 翻转，
**翻转反而让 SHOW 每帧都被发出**，于是光标始终可见。

这一段是整条排查链的转折点：**关掉同步输出之所以「修好」了光标，不是因为它关掉了
BSU/ESU，而是因为它把 SHOW 的频率从「一次」变成了「每帧」。**

### 3.1 排除 BSU/ESU 本身

为确认「不是 BSU/ESU 破坏了光标语义」，做了最小隔离实验（不带 App、不带 ink）：

- A 无 BSU/ESU、B 移动在事务内、C 移动在事务外、D 移动+SHOW 都在事务内

四种形态下 pyte 读到的光标**全部正确**。所以 BSU/ESU 与相对光标移动**不冲突**，
`docs/20261112-ga-ink-cursor-smoothness-fix-design.md` 当时的前提没被推翻。

结论收紧为：**是「SHOW 只发一次」这个记账，不是同步输出本身。**

---

## 4. 根因（精确表述）

`stdoutCursorPark.ts` 原代码：

```ts
// 只在「需要变可见」时发 SHOW：同步输出生效时光标全程可见，这里通常一次都不发。
const needShow = !this.cursorShown
suffix = `${up}\x1b[${spec.col + 1}G${needShow ? SHOW_CURSOR : ''}`
if (needShow) this.cursorShown = true
```

这段的前提是一句写在注释里的断言：**「同步输出生效时光标全程可见」**。

真机实测证明它是**假的**：ConPTY 在 BSU/ESU 事务边界会重置 DECTCEM。于是
`cursorShown` 与终端真实状态脱钩，`needShow` 永远为 false，SHOW 整个会话只发一次
（在首次 park 那一刻）。此后每一帧的 park 都在**移动一个不可见的光标**——算术正确，
但输入法看不见它。

这与 2026-07-16 那次修的是**同一类错误的第二个实例**：那一次是「全程不 SHOW」，
这一次是「只在第一次 SHOW」。两次都栽在「把外部终端的行为当成已知常量写进注释」。

---

## 5. 修复

```ts
// 必须**每帧**重发 SHOW，不能靠 cursorShown 记账省略。
suffix = `${up}\x1b[${spec.col + 1}G${SHOW_CURSOR}`
this.cursorShown = true
this.parkedUp = spec.up
```

不变量不变（**光标可见 ⟺ 它正停在 caret 上**），只是把「可见」的维护周期从
「状态变化时」改成「每帧」。

### 5.1 为什么不会重新引入闪烁

2026-11-12 的 `docs/20261112-ga-ink-cursor-smoothness-fix-design.md` 记录过：
旧实现每帧 `HIDE → SHOW` 翻转，实测流式中 8.4~11.2 次/秒，肉眼即「光标一直在闪」。
本次修复**只加 SHOW、不加 HIDE**：

- 同步输出生效（默认）：`needHide = cursorShown && (!syncOutput || !willPark)` → 本帧要 park 时为 false，**不发 HIDE**；
- 结果：每帧只有一次 SHOW，没有翻转。

### 5.2 连带修正的测试

| 文件 | 改动 |
|---|---|
| `stdoutCursorPark.test.ts` | 「每帧只 SHOW 一次」改为「SHOW 必须每帧都发」，并在注释里写明真机证据；`resetViewport` 用例末尾补上 `\x1b[?25h` |

## 7. 方法论（给后续排查）

1. **注释里的因果断言，第二次骗人。** 2026-07-16 骗了一次（「IME 跟随隐藏光标」），
   2026-11-16 又骗了一次（「同步输出时光标全程可见」）。**关于外部系统（终端/输入法/
   ConPTY）行为的断言，一律视为待验证假设**——写注释时若拿不出探针，就标 `待验证`。

2. **「关掉 X 就好了」不等于「X 是根因」。** B 配置关掉同步输出后光标正确，但真正
   起作用的不是关掉 BSU/ESU（隔离实验证明 BSU/ESU 无害），而是**关掉它带来的副作用
   ——每帧翻转使 SHOW 每帧都被发出**。从「相关」走到「因果」必须再做一次只改被测变量
   的隔离实验。

3. **调试输出本身会污染被测系统。** ink 的 `patchConsole` 让 `console.error` 变成一次
   渲染，于是「打日志」这个动作改变了产品行为，探针测到的是自反馈。**诊断旁路必须出
   进程**（写文件），不能走被测的 I/O 通道。

4. **一个 `show=1 / hide=2` 的计数就能定位。** 绝对位置、列号、布局模型都可以争论，
   但「整个会话只 SHOW 了一次」是无可争辩的。**先找一个无法争辩的计数**，再往它下面挖。

5. **真机 vs headless 的路径已经分叉。** 2026-11-16 之后仓库默认 **fullscreen/alt-screen**
   （`mouseWheel.ts:112` 恒返回 true），而 `probes/park_absolute_row.ts` 等 headless 探针
   走的还是主屏 + `CaptureWriteStream` 路径。**在 ConPTY 行为上，headless 探针给不出
   结论**——探针里 park 正常（`ESC[4A ESC[7G` 每帧都有），真机上却看不到光标。

## 9. 分析边界

- 真机验证在 **Windows Terminal / ConPTY** 上完成。「ConPTY 在 BSU/ESU 边界重置
  DECTCEM」是**行为观测**（show=1/hide=2 与位置证据），未查阅 Windows Terminal 源码确认机制。
- **未在**其它终端（WezTerm / Alacritty / iTerm / kitty）验证。每帧重发 SHOW 在所有
  这些终端上都是无害的（多发一次幂等序列），但「ConPTY 是否真的重置 DECTCEM」这一点
  未在别处复现。
- 修复只改 SHOW 的发送频率，未改 park 的几何算术，也未改同步输出的启用条件。
