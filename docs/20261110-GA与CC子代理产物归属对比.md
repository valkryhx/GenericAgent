# GA 与 CC 的子代理产物归属对比（2026-11-10）

> 缘起：`tests/test_workflow_child_agent.py` 一条偶发超时（已修）暴露出 GA 用「整目录快照 + diff」
> 判断子代理产出了哪些文件，而 `snapshot_workspace` 到了 20,000 条会**静默截断**。
> 这里记录 CC 319 是怎么做的，以及本次采用的折中方案。

## 1. GA 现状

`NativeGPTChildAgentRunner._run_tool_job`（`genericagent/workflow/child_agent.py`）：

```python
workspace_before = snapshot_workspace(workspace_root)        # 跑前全量扫描
...
written = diff_workspace(workspace_before, snapshot_workspace(workspace_root))  # 跑后再扫一次
```

优点：不依赖工具自报，`code_run` / 脚本里写的文件也能被 diff 出来。
代价：每个子任务固定两次全扫（本仓库 2 万文件、单次约 0.9s），且上限内**漏哪些不确定**。

## 2. CC 319 的做法：编辑自报，从不扫目录

| 环节 | 实现 | 坐标 |
| --- | --- | --- |
| 编辑前登记 | `fileHistoryTrackEdit`（导出名 `Rdt`）在 Edit / Write / NotebookEdit 落盘前调用 | `m1868_0x131deb6b.js:465` 导出；实现在 file-history 模块 |
| 落库事件 | `insertFileHistoryDelta({type:"file-history-delta", messageId, snapshotMessageId, trackingPath, backup, timestamp})` | `m0591_0x11be624e.js:27000` |
| 快照 | `fileHistoryMakeSnapshot` 按消息打 checkpoint，最多保留 100 个 | 见 `claudecode283/extracted/rewind-internals.md` §2–§3 |
| “这轮改了什么” | `fileHistoryGetTurnDiffStats` 遍历 `state.trackedFiles` 与 backup 比对，产出 `filesChanged/insertions/deletions` | `m0591:71988`（`HZo`） |
| 时间预算 | `TURN_DIFF_COUNTING_MS = 1000` | 同模块导出 |

关键点：**路径来自工具调用的入参**（`file_path`），所以不需要枚举工作区；
diff 的规模与实际改了多少个文件成正比，与仓库多大无关。

### 2.1 CC 的盲区：shell 写盘

Bash 工具的 `G.begin({...})` 不是文件跟踪，是**重复命令计**（`BashRepeatMeter`）：

```js
// m2320_0x13b9f7dd.js:135
export { GOn as BashRepeatMeter, lus as isBashRepeatMetered };
```

Bash 结果允许出现的字段也没有任何文件清单（`stdout` / `stderr` / `interrupted` /
`timedOutAfterMs` / `noOutputExpected`，见 `m0252_0x116efdb7.js:709`）。
所以 **CC 不知道 shell 里创建或修改了哪些文件**，除非那条命令后来又被 Edit/Write 打开过。

### 2.2 CC 的子代理结果里没有文件清单

Task / `local_agent` 的结果只有文本 + `agentId` / `subagent_type` / 状态类元数据
（`m0165_0x1145c609.js:8740`、`:11286` 的 `filesChanged` 是 **rewindFiles** 的预览字段，
不是子代理产物）。子代理的编辑同样走 file-history（同一个编辑工具链路），
所以父会话能 rewind 到它改之前，但拿不到「这个子代理产出了哪些文件」的列表。

## 3. 结论：GA 的路子更宽，代价是更贵

| | CC | GA |
| --- | --- | --- |
| 依据 | 编辑工具自报路径 | 前后两次目录快照 diff |
| 覆盖 | 只有 Edit/Write/NotebookEdit | 含 `code_run` / 脚本写盘 |
| 成本 | 与改动文件数成正比 | 与工作区大小成正比（有上限） |
| 大仓库 | 无影响 | 命中上限后**静默漏报** |

## 4. 本次改动（方案 A：可见化 + 确定化）

1. `snapshot_workspace(root, *, max_entries=20000, meta=None)`：
   - `meta` 回填 `entries` / `max_entries` / `truncated`；`truncated=True` 表示产物归属是“尽力而为”；
   - 遍历改为 **BFS + 目录内按名称排序**，重复扫描未变化的工作区返回同一子集
     （`os.scandir` 的顺序被文档定义为任意，NTFS 恰好是名字序，换文件系统就不保证了）；
   - `max_entries <= 0` 视为不限。
2. `child_agent`：新增 `GA_WORKFLOW_SNAPSHOT_MAX_ENTRIES`（默认 20000，非法值回退默认）；
   任一快照被截断时，`tool_summary` 带 `artifactScanTruncated` 与 `artifactScanLimit`，
   父会话/UI 能看见“这份产物清单不完整”。
3. 测试：`test_snapshot_reports_truncation_instead_of_silently_capping`、
   `test_child_result_flags_a_truncated_artifact_scan`（stash 实现后都变红）、
   `test_snapshot_order_is_deterministic`（回归护栏，见 §5）。

## 5. 还没做

- **双通道**（方案 B）：让 `file_write` / `file_patch` 自报路径，扫描只做 `code_run` 的兜底并可关闭。
  这是最接近 CC 的模型，但要动工具层与子任务结果结构。
- 截断时的“优先保留哪些文件”还没有策略（当前是 BFS 名称序，顶层文件先被收进快照）。
