# GA 事件→帧节流（对齐 Codex schedule_frame()）收益测量（2026-10-14）

> 背景：遗留项「事件 → 帧节流（对齐 Codex `schedule_frame()`）」，
> 见 `docs/20261014-ga-workflow-异步background-task-实施记录.md` §9 /
> `docs/20261014-GA-workflow列表轻量payload对齐CC.md` §6。
> 上游分析：`docs/20261010-ga-ink-workflow-progress-ui.md` §3（Codex 对照）。
> **云端不复刻：复刻时暂时不需要参考 claudecode 云端会话的实现。**

**结论先行：在当前架构下收益可忽略（最坏 ~3% CPU，合并只省 ~1–2%），建议暂不实施。**

---

## 1. 要验证的假设

Codex 的 `schedule_frame()` 把「状态变更」与「画一帧」解耦：多个请求**合并**成一次 draw，
并用 `FrameRateLimiter` 把帧率钳到 ≤120 FPS（`MIN_FRAME_INTERVAL ≈ 8.33ms`）。

GA 侧假设是：**每个 bridge 事件都触发一次全树 Ink render**，事件一多就会卡。
本测量就是验证「一次 render 有多贵」「事件有多密」→ 值不值得合并。

---

## 2. 测量方法

探针脚本：`frontends/ink-ui/scripts/_probe_workflow_frame_cost.ts`

```bash
cd frontends/ink-ui && npx tsx scripts/_probe_workflow_frame_cost.ts
```

做法：用真实 `<App>` 组件 + 假 bridge client，构造「大 transcript + 运行中 workflow」
的稳态，然后逐个注入事件并**直接计时 `emit()` 调用**（实测 Ink 是同步 flush，
所以 `emit()` 的耗时就是这一帧的成本），同时统计 stdout 的写次数（= 帧数）。

---

## 3. 关键发现

### 3.1 Ink 每个 `dispatch` 同步写一帧

- 一次 burst 里同步注入 20 个事件 → **20 次 write**（不是 1 次）。
- 即：**N 个事件 = N 帧**，React/Ink 在这里**没有**自动合并。
- ⇒ 原理上「合并」确实能把 N 帧降到 ⌈N/帧⌉ 帧。

### 3.2 `<Static>` 让 transcript 长度不影响单帧成本

- 20 条 vs 1500 条历史消息，单帧成本几乎一样（±0.3ms）。
- 原因：transcript 走 `<Static>`，只在挂载时写一次；后续每帧只重绘 **live chrome**
  （状态条 / 打开的 workflow 面板 / composer），每帧只有 ~440–590 B。

### 3.3 单帧成本（median / p90）

| 场景 | 帧/事件 | 单帧 median | 单帧 p90 | 每帧字节 |
| --- | --- | --- | --- | --- |
| `workflow_progress`（状态条） | 1 | **1.3–1.8 ms** | 2.6–4.1 ms | ~443 B |
| `workflow_live`（面板打开） | 1 | **4.2 ms** | 7.6 ms | ~584 B |

### 3.4 事件速率

运行期唯一的高频 emitter 是 `frontends/ink_bridge.py::_watch_workflow_progress`
（`interval = 0.25`）：每 tick 最多 emit `workflow_live` + `workflow_progress` 两个事件。
⇒ **≤ 8 事件/秒**（`agent_event`/`agent_snapshot` 只在控制命令时发，非常态）。

### 3.5 换算

| 场景 | 现状 CPU（8 事件/s） | 合并 4:1 后 | 节省 |
| --- | --- | --- | --- |
| 状态条更新 | 1.3–1.8ms × 8 ≈ **1.1–1.5%** | ~0.4% | ~1% |
| 面板实时刷新（最坏） | 4.2ms × 8 ≈ **3.3%** | ~0.8% | ~2.5% |

---

## 4. 结论

- **收益可忽略**：最坏也就 ~3% CPU，合并只省 1–2.5%；而实现要引入
  「事件分类（立即 vs 可合并）+ 保序缓冲 + 帧调度器」，**复杂度/风险 > 收益**。
- **真正解决之前「卡」的**是已经修掉的几条（都不是重绘频率问题）：
  1. workflow 占用会话 `running` → composer 锁死（已修，见异步 background-task 文档）；
  2. `workflow_detail`/`list` 携带 2.3 MB payload、单次 7.5–16.8s（已修）；
  3. `_watch_workflow_progress` 每 tick 调 `load_run` + 全量 `json.dumps`（已修，改为 mtime/size + fingerprint 门控）；
  4. `workflow_list` 全量 run payload（已修，改轻量摘要，−97.9%）。
- **触发重估的条件**（任一出现再做）：单帧 > 20ms、或常态事件 > 50/s、
  或引入「每帧重绘大 transcript / 大表格」的新 UI。届时再上帧节流。
