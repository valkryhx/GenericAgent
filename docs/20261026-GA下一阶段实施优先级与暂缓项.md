# GA 下一阶段实施优先级与暂缓项

> 日期：2026-10-26
> 状态：实施决策记录
> 本文不重复完整设计，只记录推荐顺序、提交边界、排序依据与暂缓项。详细设计以第 6 节列出的文档为准。

> - `docs/20261026-CC303项目目录与高级特性路径机制调研.md`
> - `docs/20261026-GA-CC风格项目目录改造实施方案.md`

## 1. 结论

下一阶段按以下顺序实施：

1. **目录方案 P0**：在 `genericagent/paths.py` 增加项目桶路径 API，不修改业务调用方，只增加纯路径单测。
2. **目录方案 P1**：CLI 在 `os.chdir(ui_dir)` 之前捕获并注入 `GA_LAUNCH_CWD`，修正“启动项目根”的来源。
3. **目录方案 P1.5**：拆开 subagent / Agent Team 的 project root 与 state root，锁定 `.ga/subagents`、`GA_AGENTS.md` 等项目配置归属；只修语义，不切换磁盘布局。
4. **目录方案 P2 + P3**：session、workflow store、subagent registry 与 workflow workspace 同时切换到项目桶；team/task 保留全局层，用 project-scoped `teamKey` 隔离。必须同一版本上线，旧 `temp/` 只读兼容。
5. **目录方案 P4**：Agent Team 的 `teamKey`、task board 与真 git worktree 切到项目层，`team_name` 仅保留显示语义。
6. **目录方案 P5**：主会话工具 cwd / `workspace_root` 切换到用户项目；这是用户可感知行为变化最大的一步，放最后。
7. **目录方案 P6-P7**：前端统一路径、迁移工具、named workflow scope 迁移、`--all` 查询与 `_legacy` 认领。

P0 与 P1 可以作为同一个评审批次，但建议保留两个逻辑提交，便于独立回滚。P0 只建立路径契约，P1 才开始改变启动上下文。P1.5 是 P2/P3 的强制前置：详细影响见第 8 节。

**本次目录改造是独立发布线，不包含、不依赖 Agent 自主读图、输入框看图或任何 image block 链路。** 读图能力另立任务线，目录改造的测试与验收不得以读图功能为前提。

**一句话结论：目录改造按 P0 → P1 → P1.5 → P2/P3 → P4 → P5 → P6-P7 独立推进；Agent 自主读图不进入本次目录改造，也不作为其前置或验收条件。transcript 物理压缩、执行中继续输入和 prompt suggestion 当前均暂缓。**

## 2. 排序依据

### 2.1 当前目录现状是基础性缺口

当前运行值仍把 GA 安装仓库当作默认项目：

```text
PROJECT_ROOT  = D:\git_codes\GenericAgent
RUNTIME_ROOT  = D:\git_codes\GenericAgent
TEMP_DIR      = D:\git_codes\GenericAgent\temp
SESSIONS_DIR  = D:\git_codes\GenericAgent\temp\sessions
```

本地数据已经形成明显规模：

```text
temp/sessions             1869 个 JSONL，约 209 MB
temp/workflow-runs        6365 个目录，约 17 MB
temp/workflow_child_agents 约 9 KB
```

旧 session 的 `cwd` 统计显示，约 149 个 session 被 Ink UI 目录污染：

```text
1711  D:\git_codes\GenericAgent
 113  D:\git_codes\GenericAgent\frontends\ink-ui
  36  D:\git_codes\GenericAgent\frontends\ink\ui
   6  D:\git_codes\GenericAgent\.worktrees\ink-unified-terminal-layout
   2  临时 process 目录
   1  无法解析
```

关键代码现状：

- `genericagent/core/app.py:1070` 使用 `paths.TEMP_DIR` 作为 handler 的默认 cwd，并把 `paths.PROJECT_ROOT` 作为 `workspace_root`。
- `genericagent/core/transcripts.py:18` 使用 `paths.SESSIONS_DIR` 作为默认根目录。
- `create_session` 仍使用 `cwd or os.getcwd()`。
- `ga_cli/cli.py` 源码运行时优先把 GA 仓库当作项目根。
- 当前没有 `GA_LAUNCH_CWD`。

因此目录 P0/P1 的收益不是“整理文件夹”，而是建立正确的项目身份、会话归属和生成物落点。P0 单独可测、无业务行为变化；P1 才修复 UI 子目录污染启动 cwd 的根因，二者风险低且为后续迁移提供基础。

### 2.2 Agent 自主读图不属于本次目录改造

Agent 自主读图是独立功能线，虽然也涉及 `handler.py`、`loop.py` 和 `llm/core.py`，但它的改动目标是 tool result 的 image block 协议，与目录归属无关。

本次明确规定：

- 目录 P0-P5 与迁移阶段 P6-P7 都不包含 `StepOutcome.images`、`file_read` 图片识别、tool_result image block 或 OpenAI 图片抬升；
- 目录改造不以读图实现作为前置；
- 目录改造的测试、Go/No-Go 和提交不引入图片读取用例；
- 读图完成后再单独评估输入框看图链路。

### 2.3 执行中继续输入暂不适合插队

当前实现是明确拒绝忙碌提交，而不是排队：

- Ink 输入控制器在 `running / stopping / connecting` 时直接返回；
- `bridge.submit()` 对忙碌提交返回 `busy`；
- 没有全局命令队列、轮内 fold、轮末 drain、Esc 清队列和上箭头编辑协议。

要正确实现必须同时修改：

- 输入控制器；
- bridge 协议；
- agent loop；
- transcript；
- UI 队列状态。

这是跨层状态机改造，回归面显著大于目录 P0/P1。CC 的 `now / next / later` 队列、`queued_command` attachment 和轮末 drain 可以作为后续设计依据，但当前不应为了“输入体验”打断已经明确的目录改造主线。

## 3. 推荐阶段与提交边界

### 阶段 1：目录 P0

**范围**

- 在 `genericagent/paths.py` 新增路径 API。
- 明确 project root、runtime root、session、workflow、temp 等路径的解析职责。
- 不修改任何业务调用方。
- 只新增纯路径单测。

**完成标准**

- 不传环境变量时保持现有路径行为。
- 路径 API 的输入、输出和默认值均有单测。
- `pytest` 相关路径测试通过。
- 业务行为零变化，可独立回滚。

### 阶段 2：目录 P1

**范围**

- CLI 在 `os.chdir(ui_dir)` 之前捕获启动 cwd，并注入 `GA_LAUNCH_CWD`。
- 项目根优先级明确为：`GA_PROJECT_ROOT > GA_LAUNCH_CWD > 启动 cwd`。
- 保留 `GA_PROJECT_LAYOUT=legacy` 回退开关。

**完成标准**

- 从任意目录启动时，项目身份不再取决于 UI 子目录。
- `legacy` 模式仍能回到旧行为。
- 有覆盖源码运行与安装运行的 CLI 测试。
- 与 P0 分开提交，便于定位“契约新增”与“调用接线”的问题。

### 阶段 3：目录 P1.5

**范围**

- 拆开 `SubagentManager` 的 `project_root` 与 `state_root`。
- 拆开 `start_task_background()` 的 `task_root` 语义，兼容旧参数但不再让它同时代表项目和状态。
- `SubagentTaskStore` 明确 `teamKey`；A/B 同名团队不得串板，但路径仍位于 `DATA_ROOT/tasks/<teamKey>` 全局层。
- `.ga/subagents`、`GA_AGENTS.md`、`mcp.json` 继续绑定用户项目，不跟随 `DATA_ROOT`。
- 只修语义和测试，不修改 `TEMP_DIR` / `SESSIONS_DIR` 默认值，不迁移数据。

**完成标准**

- 现有测试全部通过。
- 新增 project root / state root 拆根测试。
- 双项目同名 team board 隔离测试通过。
- 普通 subagent cwd 与 Agent Team git worktree 都以用户项目为基准。
- 旧 `--task_root`、旧 session、旧子代理状态仍可运行。
- 详细影响矩阵见第 8 节。

### 阶段 4：目录 P2 + P3

**范围**

- session 与 workflow store 切换到项目桶。
- subagent registry、workflow workspace、workflow child agents 同时切换项目桶；team board 保持 `DATA_ROOT/tasks/<teamKey>` 全局层。
- 旧 `temp/` 只读兼容。
- 不自动搬迁历史数据。

**上线纪律**

- P2 与 P3 必须同一版本上线，避免 session 指向新桶而 workflow 仍写旧桶，或反之。
- 旧路径读取失败时给出可诊断错误，不静默回退到错误项目。
- 不在此阶段改变主会话工具 cwd。
- 第 8.7 节的 subagent / workflow / Agent Team 隔离测试必须作为合并门禁。

### 阶段 5：目录 P4（Agent Team）

**范围**

- `team_name`（显示）与 `team_key`（项目隔离）分离；
- task board 切到 `DATA_ROOT/tasks/<teamKey>`；
- 真 git worktree 切到 `<PROJECT_ROOT>/.ga/worktrees`；
- child env、teammate idle、bridge reader、swarm/roster 同源；
- workflow 私有工作副本不进入本阶段。

**上线纪律**

- 必须先有 P0-P3 的路径契约、项目桶和只读兼容。
- 必须证明 A/B 同名 team 不串板，且 teammate 不按自己的新 session 重派生 team。
- `.ga`、`.ga/worktrees`、目标路径 symlink 必须拒绝。
- worktree 清理必须有 containment/registry 检查；失败不得无条件 `rmtree`。
- 回退时只停止写新 board/新 worktree，不删除已有数据。

### 阶段 6：目录 P5（主会话工具 cwd）

P5 单独做“工具落点切换”，仍是用户可感知行为变化最大的一步：

- 主会话工具 cwd / `workspace_root` 切到 `PROJECT_ROOT`；
- `code_run` fallback 同步切；
- prompt 精确描述 project root、project data、tool cwd；
- 保留 `GA_TOOL_CWD=temp` 回退；
- 先完成 P0-P4，再单独提交与真实 CLI 冒烟。

### 阶段 7：目录 P6-P7（控制面统一与显式迁移）

P6-P7 可以在 P5 稳定后按需求逐步推进，不与 P0-P5 捆绑：

- P6：前端、control-plane、registry 全部统一走 `RuntimePaths`；
- P7：迁移脚本支持 `dry-run` 与 `apply`；
- P7：named workflow 定义迁移（project/user/legacy、冲突检测）；
- P7：`/resume --all`、`/workflows --all`；
- P7：`_legacy` 认领流程。

迁移脚本默认只 `dry-run`，不得自动删除、覆盖或递归清理历史数据。

## 4. 暂缓项

### 4.1 明确暂停，不排入当前阶段

以下项目当前明确暂缓，不应在目录改造主线中顺手加入：

1. **transcript 物理压缩 / local GC**
   - 当前 transcript 保持 append-only。
   - 已有 compact boundary、projection resume、轻量 rewind checkpoint。
   - 在没有独立容量指标、保留策略和可恢复验证前，不删除原始 JSONL，也不做物理压缩。

2. **执行中继续输入命令队列**
   - 需要输入控制器、bridge、agent loop、transcript、UI 状态共同改造。
   - 等目录改造稳定后单独立项。

3. **prompt suggestion / ghost text**
   - 依赖输入状态、焦点、请求预算、缓存和接受协议。
   - 不是当前影响最大的使用阻塞项。

4. **目录 P6-P7**
   - 迁移、全量查询、前端统一路径、named workflow 定义迁移和 `_legacy` 认领后置。
   - 不得自动迁移或清理旧 `temp/`。

5. **Agent 自主读图的任何变体**
   - 包括 `StepOutcome.images`、`file_read` 图片分支、tool_result image block、OpenAI 兼容图片抬升。
   - 与项目目录归属无关，本次不做，也不作为高级特性路径改造的验收依赖。

6. **自动迁移旧 `temp/`**
   - 历史 session 和 workflow 数据只读兼容。
   - 任何迁移必须由用户显式执行，并提供 dry-run。

7. **`GA_PROJECT_NAME` 写入型自定义名**
   - 暂不引入额外的写入型项目命名来源。
   - 先以 `GA_PROJECT_ROOT > GA_LAUNCH_CWD > 启动 cwd` 建立稳定优先级。

8. **Agent 自主读图与输入框看图**
   - 包括 `StepOutcome.images`、tool_result image block、`file_read` 图片识别、OpenAI 图片抬升，以及 O1-O10 输入侧能力。
   - 全部作为独立功能线推进，不进入本次目录改造。

### 4.2 独立功能线的边界

Agent 自主读图、输入框看图、目录改造分别验收、分别提交：

1. 目录改造只处理项目身份、运行时状态、工作区和迁移兼容；
2. Agent 自主读图只处理模型消费图片；
3. 输入框看图只处理图片采集和交互；
4. 任一功能线的完成，不得以另一条功能线未完成作为阻塞条件。

## 5. 风险控制

- **每次只改变一层**：P0 只加契约，P1 才接启动上下文，P5 才改主会话工具落点。
- **P2/P3 原子发布**：session 与 workflow 的项目桶切换不能拆成两个版本。
- **旧数据只读**：任何阶段都不自动删除、覆盖或递归清理历史 transcript、workflow 和临时文件。
- **开关可回退**：P1 保留 `GA_PROJECT_LAYOUT=legacy`，P4 保留 `GA_TOOL_CWD=temp`。
- **先测试再迁移**：路径测试、CLI 冒烟测试、resume/rewind 回归必须分别覆盖。
- **目录与读图解耦**：目录改造不包含图片协议改动，也不以读图测试作为验收门禁。
- **不做隐性兼容承诺**：旧会话和旧路径出现歧义时明确报错或给诊断信息，不猜测项目归属。

## 8. 目录改造对 subagent、workflow、Agent Team 的影响分析

> 本节是 2026-10-26 对原目录方案的复核补充。结论：**原 P2/P3 不能只改 `SESSIONS_DIR`、`TEMP_DIR` 和 `WorkflowStore` 默认根后直接上线。** subagent、workflow 和 Agent Team 同时依赖“项目身份”和“运行时状态”两类路径；当前实现经常把它们混用，必须先把语义拆开并补兼容测试。

### 8.1 总体结论

目录改造必须拆成四种不同身份：

| 路径身份 | 含义 | 典型消费者 | 可否跨项目共享 |
| --- | --- | --- | --- |
| `PROJECT_ROOT` | 用户启动时所在的真实项目 | 工具 cwd、项目文档、git worktree | 否 |
| `PROJECT_DATA_DIR` | 当前项目的会话、workflow、subagent 状态 | session、workflow store、subagent state | 否 |
| `DATA_ROOT` | 本机 GA 的全局运行时根 | logs、media、MCP、全局锁 | 是 |
| `PACKAGE_ROOT` | GA 安装目录，只读资源来源 | prompts、skills、assets | 是 |

现有代码最危险的假设是：

```text
root_dir == state_root == 当前项目 == GA 安装仓库
```

源码模式下这个等式碰巧成立，因此测试容易通过；一旦 `PROJECT_ROOT` 改成用户项目、`RUNTIME_ROOT` 改成全局数据根，这个隐式等式会同时影响子代理启动、任务板、workflow 状态和 git worktree。

### 8.2 Subagent 影响

| 位置 | 当前行为 | 改造风险 | 必须补的措施 |
| --- | --- | --- | --- |
| `agents/manager.py:250-263` | `root_dir` 默认 `PROJECT_ROOT`；`state_root` 默认 `root_dir`；`temp_dir = state_root/temp` | 若只改 `PROJECT_ROOT`，subagent 状态会错误写进用户项目 | 明确传入 `project_dir` 与 `state_root` 两个参数；生产路径禁止依赖默认值 |
| `agents/manager.py:382-393` | 子进程 `GA_PROJECT_ROOT=root_dir`、`GA_DATA_DIR=state_root`，cwd 为 `worktree_path or root_dir` | 项目目录与数据目录一旦混用，子代理会读错项目状态或把状态写进项目 | 子进程环境同时传 `GA_PROJECT_ROOT` 与 `GA_PROJECT_DATA_DIR`；cwd 只由项目/worktree 决定 |
| `agents/manager.py:370-396` | `cwd=root_dir` 是普通子代理的默认目录 | `root_dir` 若误设为 `PROJECT_DATA_DIR`，Agent Team worktree 将不是用户 git 项目 | 普通 subagent 的 cwd 和 worktree repo 必须是 `PROJECT_ROOT` |
| `agents/manager.py:813` | `task_dir = temp_dir/task_name` | `temp_dir` 来源必须改为项目桶下的 subagent 状态目录 | 新增 `project_data_dir()/subagents` 语义，并保留旧 `temp/subagents` 只读兼容 |
| `agents/manager.py:848-855` | `isolation=worktree` 调 `create_subagent_worktree(self.root_dir, ...)` | `root_dir` 不是 git repo 时 Agent Team 的隔离写入会直接失败 | 加显式 preflight：检查 `.git`、目标路径属于真实项目；失败信息必须可诊断 |
| `agents/manager.py:1008-1009` | 子进程 `--task_root` 传 `root_dir` | 子进程会从 `root_dir/temp/task_name` 推导任务目录 | 增加独立 `--state_root` 或显式 `--task_dir`，不能继续用 `task_root` 同时表达两个根 |

### 8.6 持久化与 resume 兼容

目录改造后，旧 session 仍可能包含：

- `session_start.cwd` 指向 GA 仓库或 Ink UI 子目录；
- 子代理转录在旧 `temp/sessions/<parent>/subagents/`；
- workflow state 的 `artifactDir` / `workspacePath` 是旧绝对路径；
- team board 在旧 `temp/teams`；
- `worktree_path` 指向旧 `temp/subagents/worktrees`；
- named workflow 定义在旧 `temp/sessions/named-workflows`，不能随 run bucket 搬走。

因此 P2/P3 必须满足：

1. **新写入只进新桶；旧读取按元数据定位。**
2. **不能根据当前 `PROJECT_ROOT` 猜测旧 session 所属项目。**
3. **resume 后工具根与 project docs 使用 session 持久化的 `project_root`/显式 identity，而不是当前启动目录；旧 `cwd` 不能独自当作项目归属。**
4. **workflow run 按 state 中的绝对 `artifactDir`/`workspacePath` 读取，不按新 base 重新拼。**
5. **子代理转录按父 session 的 project bucket 查找，找不到再查 legacy。**
6. **team board、subagent registry、worktree 清理都不能跨项目扫描。**
7. **旧路径只读兼容期不自动迁移、不自动删除。**

### 8.8 对原实施顺序的修订

目录改造的独立顺序是“P0 → P1 → P1.5 → P2/P3 → P4 → P5 → P6-P7”，不插入 Agent 读图阶段。P2/P3 的范围要扩大，不能只当作 session/workflow 存储迁移：

1. **P0**：新增路径 API；同时增加 `project_dir`、`project_data_dir`、`project_state_*`、`legacy_temp_dir` 的单测。暂不改调用方。
2. **P1**：CLI 注入 `GA_LAUNCH_CWD`；明确 `PROJECT_ROOT` 是用户项目；增加从 UI 子目录启动的测试。
3. **P1.5（新增，必须先做）**：拆开 subagent/team 的 `root_dir` 与 `state_root`，补 P2/P3 所需测试；**不改磁盘布局**，只修隐式等式。此阶段可以保持旧默认值，确保现有行为不回归。
4. **P2**：session 与 workflow store 切换项目桶；保留旧 `temp/sessions` 只读兼容。
5. **P3**：subagent registry、workflow workspace、workflow child agents 切换项目桶；task board 留到 P4，但 API/测试在 P1.5 先锁定。与 P2 同版本发布。
6. **P4**：Agent Team 的 teamKey、task board、真 git worktree 切到项目层。
7. **P5**：主会话工具 cwd/workspace_root 切到用户项目。
8. **P6-P7**：前端统一、迁移 dry-run/apply、named workflow 定义迁移、`--all` 视图和 `_legacy` 认领。

关键点：**P1.5 是不能省略的防回归层。** 如果直接把 `RUNTIME_ROOT` 改成 `DATA_ROOT`，subagent/team/workflow 会同时换根，出问题时很难判断是路径契约、状态迁移还是 worktree 语义导致的。

### 8.8.1 named workflow 与高级特性的跨阶段边界

目录改造不能只验证“run 能启动”，还要验证定义库和高级特性身份没有被错误搬走：

| 对象 | 归属 | 所属阶段 | 必须验证 |
| --- | --- | --- | --- |
| 主 session transcript | `PROJECT_DATA_DIR/<sessionId>.jsonl` | P2 | A/B 列表隔离、resume identity |
| subagent transcript | `PROJECT_DATA_DIR/<sessionId>/subagents/` | P2 | legacy 回读、workflow subdir |
| workflow run/artifact | `PROJECT_DATA_DIR/<sessionId>/workflows/<runId>` | P3 | resume 绝对路径 |
| workflow shared workspace | `PROJECT_DATA_DIR/workflow-runs/<runId>` | P3 | A/B 隔离、cleanup |
| workflow isolated child | `PROJECT_DATA_DIR/workflow_child_agents/...` | P3 | 私有副本、不调用 git |
| project named workflow | `<PROJECT_ROOT>/.ga/workflows` | P3/P6 | project > user > legacy；nested 一致 |
| user named workflow | `<DATA_ROOT>/workflows` | P3/P6 | 显式 user scope |
| legacy named workflow | `<DATA_ROOT>/temp/sessions/named-workflows` | 兼容 | 只读、可见、不覆盖 |
| Agent Team task board | `<DATA_ROOT>/tasks/<teamKey>` | P4 | lead/teammate 同板 |
| 真 git worktree | `<PROJECT_ROOT>/.ga/worktrees/<runId>` | P4 | symlink、containment、清理 |
| project roles/docs | `<PROJECT_ROOT>/.ga/subagents`、`GA_AGENTS.md` | P1.5/P5 | 不随 DATA_ROOT 改变 |

named workflow 的推荐实现原则：

1. `WorkflowStore.root` 只负责 run artifact；
2. 新增 `NamedWorkflowRegistry`（或等价 resolver）负责 project/user/legacy 三 scope；
3. 顶层加载和 nested `workflow({name})` 必须共用 resolver；
4. 列表输出 `scope/source/path/shadowed_by`，冲突显式提示；
5. 旧 `workflow_root=` 测试注入继续可用，作为“所有 scope 都指向该测试根”的兼容短路；
6. 不把 legacy 定义自动复制到所有项目，不做无界扫描。

### 8.9 目录改造的 Go / No-Go 条件

#### Go

- P0/P1 测试通过；
- P1.5 明确记录每个 manager 的 `project_root`、`state_root`、`task_root`；
- subagent、team board、workflow 的新桶隔离测试全部通过；
- 旧 session、旧 workflow、旧 worktree 至少完成一次 resume/close 冒烟；
- prompt 中不再出现错误的 `cwd = temp` 合同；
- 子 agent 的 cwd 与 workflow workspace 的定义在代码、skill、测试三处一致；
- named workflow 的 project/user/legacy 与 nested 解析通过；
- teamKey 在 child env、task store、idle hook、Ink reader 四处同源；
- 真 git worktree 与 workflow 私有副本没有共用 root/cleanup。

#### No-Go

- `RUNTIME_ROOT` 被直接整体替换为 `DATA_ROOT`，但没有逐个消费方确认；
- 只改 `PROJECT_ROOT`，没有同时拆 `root_dir/state_root`；
- 只改 `WorkflowStore`，没有改 workflow workspace 和 child cwd；
- 只改后端路径，没有更新 child prompt、workflow-authoring skill 和 `/team` roster；
- 只改 named workflow 列表，nested `workflow({name})` 仍读旧全局库；
- 只传播 `GA_TEAM_NAME`，没有 `GA_TEAM_KEY` 或显式 task store root；
- 把 workflow 私有工作副本误当 git worktree，或相反；
- 旧 `temp/` 被自动迁移、覆盖或删除；
- 没有 cross-project 隔离测试就宣称 P2/P3 完成。

### 8.10 补充入口：旧 background task 与角色目录

#### `core/app.py` 的一次性 background task

`start_task_background()` 是另一条独立于 `SubagentManager.spawn_agent()` 的启动链：

- `core/app.py:2002-2024` 把 `root_dir` 默认为 `paths.RUNTIME_ROOT`，并直接拼 `root_dir/temp/<task>`；
- `core/app.py:2079-2080` 把同一个 `root_dir` 作为 `--task_root` 传给子进程；
- `core/app.py:2100` 把 `cwd` 也设为 `root_dir`；
- `core/app.py:2196-2201` 子进程再次按 `task_root/temp/<task>` 定位任务目录。

这条链不能只改 `PROJECT_ROOT`，否则会出现：

- 用户项目目录被当成 `temp` 的父目录；
- 子进程 cwd 落进用户项目，但状态仍按 `root_dir/temp` 读写；
- 旧调用方传 `--task_root` 时无法区分“项目根”和“任务状态根”。

**修订要求：**

1. `start_task_background()` 接受显式 `project_root` 与 `state_root`，二者不得再共用一个参数。
2. 新增 `--project_root`、`--state_root`、`--task_dir` 中至少两个语义清晰的参数；旧 `--task_root` 只作为兼容别名，解析时给出 warning。
3. 子进程 cwd 使用 `project_root`；任务输入输出和 state 使用 `state_root`。
4. `_startup_task_dir_from_argv()` 不得再从 `task_root/temp` 猜路径；优先使用显式 `--task_dir`，否则由新的 state root 计算。
5. 旧 `--task_root` 在兼容期按旧规则解析到 legacy 目录，不得把它误解释成用户项目。

#### 角色目录 `.ga/subagents`

`SubagentRoleRegistry(root_dir)` 当前把项目角色放在：

```text
<root_dir>/.ga/subagents/
```

这是**用户项目配置**，不是 GA 运行时状态。目录改造后：

- 它必须继续从 `paths.project_dir()` 读取；
- 不能跟着 `state_root` 或 `project_data_dir()` 搬到 `DATA_ROOT`；
- 否则用户的角色文件会突然消失，`spawn_agent(role=...)` 会退回内置角色或报错。

需要补的测试：

- 项目 A 的 `.ga/subagents/reviewer.md` 能被 A 的 spawn_agent 发现；
- 项目 B 看不到 A 的 project role；
- 切换 `GA_DATA_DIR` 不改变 project role 的查找位置；
- legacy session resume 时仍按 session 所属项目查找角色。

#### 其他同类“项目配置而非运行时状态”路径

P1.5 应顺手列出并锁定以下分类，避免 P2/P3 时再次混淆：

| 路径 | 正确归属 | 说明 |
| --- | --- | --- |
| `<project>/.ga/subagents/` | 用户项目 | project roles |
| `<project>/GA_AGENTS.md` | 用户项目 | project instructions |
| `<project>/mcp.json` | 用户项目 | `mcp/runtime.py` 当前按 `script_dir/mcp.json` 解析；P1.5 锁定其 project root 参数 |
| `PROJECT_DATA_DIR/subagents/` | 项目运行时桶 | registry、event bus、submission log、共享 swarm ledger |
| `PROJECT_ROOT/.ga/workflows/` | 用户项目 | project-scoped named workflow definitions |
| `DATA_ROOT/workflows/` | 全局层 | user-scoped named workflow definitions |
| `DATA_ROOT/temp/sessions/named-workflows/` | legacy | 旧全局 named workflow；只读兼容 |
| `DATA_ROOT/teams/<teamKey>/` | 全局层 + GA 项目作用域 key | team config |
| `DATA_ROOT/tasks/<teamKey>/` | 全局层 + GA 项目作用域 key | Agent Team task board |
| `PROJECT_DATA_DIR/<sessionId>.jsonl` | 项目运行时桶 | 主会话转录（无额外 `sessions/` 层） |
| `PROJECT_DATA_DIR/<sessionId>/subagents/` | 项目运行时桶 | 子代理转录 |
| `PROJECT_ROOT/.ga/worktrees/` | 用户项目 | 真 git worktree（subagent/team）；不进数据桶 |
| `PROJECT_DATA_DIR/workflow-runs/` | 项目运行时桶 | workflow 共享 workspace |
| `PROJECT_DATA_DIR/workflow_child_agents/` | 项目运行时桶 | workflow 隔离工作副本 |
| `DATA_ROOT/logs/` | 全局运行时 | hooks、MCP、bridge 日志 |
| `DATA_ROOT/media/` | 全局运行时 | 前端媒体 |
| `DATA_ROOT/mcp/` | 全局运行时 | MCP cache 等 |

### 8.11 修订后的 P1.5 详细任务

P1.5 只做“语义拆根 + 兼容测试”，不切换磁盘默认布局。建议拆成以下逻辑提交：

1. **P1.5a：SubagentManager 参数拆根**
   - 保留 `root_dir` 作为兼容入口；
   - 新增 `project_root`、`project_state_root`（或 `state_root` 的明确别名）；
   - 内部统一记录 `self.project_root`、`self.project_state_root`、`self.task_root`；
   - 所有新建子进程显式传 project root 与 state root。
   - 现有默认值保持不变，测试应全绿。

2. **P1.5b：task store 与 registry 拆根**
   - `SubagentTaskStore` 不再从 `state_root/temp/teams` 推导项目身份；
   - 保持旧默认路径，但允许显式 `project_data_dir`；
   - team board 使用 `DATA_ROOT/tasks/<teamKey>`；项目归属由 teamKey 明确表达，不由 state root 决定。
   - 增加双项目同名 team 测试，即使暂时仍使用旧根，也要证明 API 能隔离。

3. **P1.5c：background task 参数拆根**
   - `start_task_background()`、`_startup_task_dir_from_argv()`、`--task_root` 兼容解析一起改；
   - 新旧参数都能启动同一测试任务；
   - 旧参数路径必须与改造前完全一致。

4. **P1.5d：project role、project docs 与 named workflow 定义根锁定**
   - `.ga/subagents`、`GA_AGENTS.md`、`mcp.json` 明确绑定 `project_dir()`；
   - `.ga/workflows` 明确绑定 `project_dir()`，不能跟随 `state_root`；
   - `DATA_ROOT/workflows` 与 legacy named workflow 根先以显式参数传入，不切 writer；
   - 增加“切换 DATA_ROOT 不影响项目配置/项目 workflow 定义”的测试；
   - 在 prompt builder 中显式传 project root 与受控 current dir，不依赖 cwd。

5. **P1.5e：Team 身份传播链锁定**
   - 引入 `team_name`（显示）与 `team_key`（项目隔离）双字段；
   - child env 同时注入 `GA_TEAM_NAME`、`GA_TEAM_KEY`；
   - `SubagentTaskStore` 支持显式 `tasks_root`，旧临时目录仍作为兼容 adapter；
   - teammate idle、handler、manager、Ink reader 全部接受显式 team/project identity；
   - 先保持旧磁盘布局，测试证明 A/B 同名 team 的 API 已能隔离。

6. **P1.5f：workflow isolation 语义锁定**
   - 明确 workflow `isolation="worktree"` 是私有工作副本，不是 git worktree；
   - `workflow-runs` 与 `workflow_child_agents` 先参数化，不切默认值；
   - 新增“workflow isolation 不调用 `create_subagent_worktree`”测试；
   - 新增“普通 subagent isolation 仍使用真 git worktree”测试。

P1.5 完成标准：

- 所有现有测试通过；
- 新增拆根测试通过；
- 旧路径行为完全不变；
- 没有修改 `TEMP_DIR` / `SESSIONS_DIR` 的默认值；
- 没有开始数据迁移；
- 代码中每个 root 都有唯一语义，不再出现“同一个变量既当 repo 又当 state”的新代码。

### 8.12 最终修订结论

**目录 P0/P1 仍应先做，但 P2/P3 前必须插入 P1.5。**

subagent、workflow、Agent Team 的风险不在 UI 层，而在三个隐式约定：

1. **项目身份**：用户项目目录不能被运行时数据桶替代；
2. **状态归属**：session、workflow、subagent 按项目桶隔离；team/task 保持全局目录层，用 `teamKey` 隔离；
3. **工作区边界**：workflow workspace、isolated child workspace、Agent Team git worktree 是三个不同概念，不能共用一个 `root_dir`。

只要 P1.5 先把这三类语义拆开，并用跨项目、legacy、worktree、prompt 四组测试锁住，P2/P3 才适合进入实施。否则“目录改造完成”很可能表现为：普通会话正常、单个 subagent 正常，但 Agent Team 的 worktree、workflow 隔离子代理或旧 resume 在真实使用中失败。
