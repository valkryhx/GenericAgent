# GA 提示词优化第 2 轮：让"隐性任务"也触发 skill（2026-11-10）

> 第 1 轮（`docs/20261110-GA提示词与工具使用优化-第1轮.md`）解决了"专用工具没到手 / 太慢"。
> 本轮针对用户反复提的第二件事：**GA 很少调用 skill**。第 1 轮只是把措辞加强了一点，
> 没有量化；这一轮先量，再改，再量。

---

## 0. 结论先行

| 指标（真实模型 zhanlu-ds） | 改前 | 改后 |
| --- | --- | --- |
| 隐性任务命中 skill（诊断性能 / 设计新功能） | **0 / 2** | **2 / 2**（`diagnose`、`brainstorming`） |
| 诊断任务的答案质量 | 搜几处代码就下结论 | 分段实测（`ga.EXE` 299/318/409ms、`import` 563–631ms），给出两个入口的不同慢点 |
| 无匹配 skill 的代码任务 | 24.6s，12 调用，结果正确 | 23.9s，11 调用，结果正确，**没有乱加载 skill** |
| 显式点名的 skill 任务 | 加载 `workflow-authoring` | 仍加载，并且这次真的运行了 `workflow` 工具 |

代价（如实说明）：隐性任务变慢了很多——诊断 19.8s → 202.4s，设计 12.5s → 101.5s。
原因是 skill 本身是一套流程（reproduce → measure → evidence），加载后模型按流程走。
**这是本轮想要的取舍**：复杂任务要的是结论质量，不是最快出字。

---

## 1. 证据：先证明"隐性任务不加载 skill"

`temp/prompt_ab_probe.py`（进程内真实 Agent，记录每次 tool call）跑两个**不点名 skill**的任务：

```text
任务 A: "GA 最近有时候启动要两三秒。先定位时间花在哪一步，别急着改代码，把证据给我。"
任务 B: "我想给 GA 加一个 /plan 命令：先只做设计，不写代码。给我一个方案，说明取舍。"

改前（第 1 轮后的提示词）:
  A: 19.8s  {file_grep:4, file_read:5, file_glob:1}   load_skill = 0
  B: 12.5s  {file_grep:2, file_glob:1, file_read:1}   load_skill = 0
```

两个任务分别对应 `diagnose`（"Disciplined diagnosis loop for hard bugs and performance
regressions"）和 `brainstorming`（"You MUST use this before any creative work"），
但模型一次都没加载——列表里明明写着。

### 1.1 对照：代码任务本来就没问题

同一时间在同一份提示词下，两个代码任务都做对了（所以问题不是"GA 不会写代码"）：

```text
修失败测试: 19.9s, 8 调用 → 先跑 pytest、读两个文件、file_patch、再跑 pytest → 4 passed
给 CLI 加 --json: 24.6s, 12 调用 → 读文件、补测试、跑 pytest、实际执行 `calc.cli --json` → 6 passed
```

两者都没有对应 skill，不加载是**正确**行为——这也给本轮设了一条不能破坏的红线：
**加强 skill 引导后，不能对没有匹配的任务滥加载。**

## 2. CC 319 的依据与差异

CC 的 skills 引导其实很少：

- 系统提示里只有一行 `When the user types \`/<skill-name>\`, invoke it via Skill. Only use skills
  listed in the user-invocable skills section — don't guess.`（`m0274_0x117329cf.js:393`，
  `m0591_0x11be624e.js:109991` 引用）；
- 列表本身是 `The following skills are available for use with the Skill tool:` + 名称/描述
  （`m0591:228783`）；
- 其余靠模型自身的习惯。

GA 不能照抄这个"少说"策略：CC 面向的是被专门训练过会用 skill 的模型；GA 的用户常用
zhanlu-ds / deepseek 这类模型，**不点名就不会想到**。所以本轮给 GA 加的是 CC 没有的
"任务类型 → skill 类别"映射，同时保留"真的要相关才加载"的门槛。

## 3. 本轮改动

### 3.1 base prompt（zh/en，75 → 77 行）

技能条目拆成两条：

```text
- 开工前先做一次技能扫描：把任务类型与 Available Skills 的描述对照，而不是等用户点名。常见对应关系：
  排查 bug / 性能回退 → diagnose 类；设计新功能或方案 → brainstorming 类；代码审查 / review → review 类；
  写或改 dynamic workflow 脚本 → workflow-authoring；画架构图 / 流程图 → archify 类；做幻灯片 → slide 类。
  只要某个 skill 与任务领域、仓库、流程或产物形态部分相关，就先 load_skill 读全文再动手；……
- 用户用 /<skill-name> 点名时必须 load_skill，且只用 Available Skills 里出现过的名字；
  扫描后确实没有匹配就不用加载，不要为了显得守规矩乱加载。
```

`# 验证纪律` 增加一条（对齐 CC `# Doing tasks` 的 UI 验证要求）：

```text
- 前端 / CLI / 可视化产物要亲手跑一次再汇报：启动 dev server、执行命令、打开页面或看截图，
  确认黄金路径和边界情况；确实跑不了就明说"没有实际验证 UI"，
  不要用"类型检查通过 / 测试通过"冒充功能验证。
```

英文版逐条对应（`assets/sys_prompt_en.txt`）。

### 3.2 skills 段落（`genericagent/core/skills.py`）

```text
Before starting a task, scan this list and match by *task type* (diagnosis, design, review,
workflow authoring, diagrams, slides), not only when the user names a skill. ...
```

### 3.3 测试

- `tests/test_skills_runtime.py`：skill 提示必须包含 `task type` 这一判据；
- `tests/test_ga_agents_runtime.py`：base prompt（zh/en）必须包含"任务类型"扫描规则与
  "没有实际验证 UI"的诚实汇报要求。

## 4. 复测（同一模型、同一组提示词）

| 任务 | 改前 | 改后 |
| --- | --- | --- |
| A 诊断启动慢（隐性） | 19.8s，10 调用，`load_skill` **0** | 202.4s，39 调用，`load_skill=diagnose` |
| B 设计 /plan（隐性） | 12.5s，4 调用，`load_skill` **0** | 101.5s，23 调用，`load_skill=brainstorming` |
| CLI 加 --json（无匹配 skill） | 24.6s，12 调用，正确 | 23.9s，11 调用，正确，`load_skill` 0 |

## 5. 观察与下一轮候选

1. **加载 skill 会让任务变慢**：这是流程成本，不是回归。下一步可以给"轻量问题"划一条线
   （例如纯查询类不加载流程型 skill），避免用户问一句简单的也触发完整诊断 SOP。
2. **隐性匹配的样本仍然太少**（2 个）。下一轮把 5–8 个不同任务类型（review / 重构 / 迁移）
   跑一遍，统计加载率与误加载率。
3. **skill 扫描目前不可观测**：只有 load_skill 调用能当证据。可以在 transcript/hook 里
   记一条"skill scan"决策（加载 / 不加载 + 原因），方便事后统计。
4. **8KB skills 列表**仍未裁剪（本机 53 个 skill）；下一轮考虑按 cwd/仓库相关性收敛。
5. 探针局限：`temp/prompt_ab_probe.py` 的 `final` 取的是显示队列的 done 文本，
   不是完整最终答案；本轮质量判断改用会话 transcript 里的最后一条 assistant 消息。
