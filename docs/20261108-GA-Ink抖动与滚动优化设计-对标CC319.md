## 0. 结论

**用户现象**：整体没有 CC CLI 平稳，agent 输出时整个画面**偶尔轻微上下位移**。

**根因（真机确证）**：

> **内联模式下，画面不是「整体平移」，而是「向下生长」。**
> 画面上边界恒为 0，整体平移事件 **0 次**；下边界随流式内容一路下推，
> 输入框被顶着往下走。终端没撑满之前，画面每长一行，输入框就下移一行。

关键证据（`tests/probes/python/screen_shift.py`，40×120 终端，真 PTY + pyte）：

| 指标 | 测量结果 |
| --- | --- |
| 画面上边界（首个非空行） | **恒为 0**，变化 0 次 |
| 画面下边界（末个非空行） | 5 → 21，变化 7 次 |
| 画面高度 | 5 → 21 行（终端 40 行，**从未滚动**） |
| 整体平移事件（上下边界同向等量） | **0 次** |

对照测量（`tests/probes/python/short_vs_long.py`）把两段行为分得很清楚：

| 场景 | 输入框行号 | 移动次数 | 是否撑满终端 |
| --- | --- | --- | --- |
| 短答案（1 段） | 4 → 13 | 7 次 | 否 |
| 长答案（40+ 行） | 4 → 37 | 25 次 | 是 |

**撑满终端后出现 ±1 来回摆动**（长答案里 `36→37→36` 出现 3 次），
这才是用户说的「**偶尔**轻微上下位移」——位移集中在两处：
① 每轮输出撑满屏幕前的那几秒（持续下推）；
② 撑满之后末行宽度临界时的 ±1 抖动。

## 1. 四条被真机实测否决的方案

全部已 `git checkout` 回滚，代码零改动。

| 方案 | 想法 | 实测结果 | 为什么不行 |
| --- | --- | --- | --- |
| **A. 固定 live 槽位** | 把 live 视口高度钉死 | `[3,3,3]` → `[3,3,3]`，零改善 | 只钉了槽位，内容在 tail 内仍把帧高从 7 顶到 13 |
| **B. 批量提交 Static** | 攒 8 行再提交 | 提交 53→5 次，但**单次跳变 1→8 行** | 优化了频率，恶化了幅度 |
| **C. 合并多次 write** | 把 ink 一帧的 3 次写合并 | 空窗 5.13%→4.70% | ConPTY 已缓冲，感知不到 |
| **D. 关闭中途 Static 提交** | tail 设成 100000（永不提交） | 移动 5 次、总下移 32 行（基线 34 行） | **Static 提交不是位移源**，此路彻底排除 |
| **E. live 区返回满高** | `height = room`，输入框一开始就贴底 | 总下移 33 行，**单次幅度 30/32 行** | 启动屏只有 4 行，切到满高时一次跳 30 行，更糟 |

### 1.1 为什么「固定 live 槽位」注定无效

CC 文档 §3.1 的「固定高度」解决的是**底栏被正文挤压**，GA 早已做对
（`BottomChrome` 有 `flexShrink: 0`）。它不解决**正文自身在长**。

在 inline 模式（Ink `<Static>` + 动态帧）下，画面总高 =
`Static 历史 + 动态帧 + 底栏`。Ink 的 `<Static>` 只保证「已写出的行不再改」，
**不保证 frame 高度封顶**。只要内容还在动态区，每多一行，帧就高一行。

### 1.2 为什么「减少提交次数 / 合并写入」也没用

方案 D 是最干净的对照：把中途提交**完全关掉**，画面照旧移动 5 次、
总下移 32 行。说明位移根本不来自「提交」这个动作，而来自
「**动态帧的高度在增长**」这一件事本身。

## 2. 与 CC 的关键差异

CC 的 inline 模式（CC 文档 §2.2）**不试图让整帧高度恒定**，它靠两件事：

1. **已滚出行水位 `scrolledOutRows`**：内容超出一屏后，溢出部分交给终端
   scrollback，屏幕上 frame 高度就此封顶；
2. **同步输出 `CSI ?2026h…?2026l`**：一帧的多次 write 原子可见，不闪。

GA 的差异：

| 能力 | CC 319 | GA 现状 |
| --- | --- | --- |
| 溢出行交给终端 scrollback | ✅ `scrolledOutRows` 水位 | ⚠️ 有 `<Static>`，但只在 tail 超 8 行时提交，且提交不减少**当前帧**高度 |
| 同步输出 `?2026h` | ✅ 使用 | ❌ **本机 ConPTY 丢弃并重排该序列**（3 对全为空对），改了无法验证 |
| 底栏固定 | `flexShrink: 0` | ✅ 已做对 |
| 帧高封顶 | 由 scrollback 水位自然达成 | ❌ 未做 |

**ConPTY 这条要特别记：** `CSI ?2026h/?2026l` 在 Windows ConPTY 下被丢弃，
所以「靠同步输出消除闪烁」这条路在本机**无法验证也无法使用**。

## 3. 为什么代码一直没改

五个方案全部实测否决，且它们分别针对：槽位高度、提交频率、写入次数、提交开关、
live 满高。这五个维度穷举完，剩下的唯一可行方向是**改变渲染层次结构**——
让画面高度不再随内容增长。这不是调参，是要么接受现状、要么重写渲染层。

按用户「确定能解决问题再改」的要求，在没有真机验证可行方案之前不动代码。

> **方案 E 的教训尤其重要**：它看似最接近 CC 的「固定高度」，实测却是单次
> 幅度最大的一种（30/32 行）。原因是 GA 启动时屏幕只有 4 行，一旦切到满高
> 就是一整屏跳变。**「最终稳定」不等于「过程平稳」**——用户抱怨的正是过程。

## 4. 下一步（按代价排序，都需先做真机 A/B）

### 4.1 方案 F：接受现状 + 减少被注意到的次数（改动小，唯一务实方向）

方案 E 已否决（见 §1 表与 §3 的注），说明「钉死高度」这条路在 GA 的启动形态下
走不通。剩下的务实方向不是消除下移，而是**降低它被感知的程度**：

- **抑制撑满后的 ±1 摆动** ✅ 已定位到成因（见下）
- **让底栏提示行高度恒定**（`Running · …` 与 `Enter send · …` 都是 1 行，
  但切换瞬间会同时改动边框位置）

#### 4.1.1 ±1 摆动的成因（已抓到整屏 diff）

`tests/probes/python/osc_diff.py` 抓到了摆动前后的完整屏幕差异，成因明确：

```
--- [1.43s] 34 -> 35 (+1) ---
  + ────────────────（新的上边框）
  +  Enter send · Alt+Enter newline · PgUp/PgDn · Ctrl+O tools · Ctrl+C exit
  +  （空行）
  - 37. 服务端的 QUIC 性能受单核处理能力影响，因为加解密在用户态完成。
  - ────────────────（旧的上边框）
  -  Running · Enter keeps draft · PgUp/PgDn · Ctrl+O tools · Esc stop
```

`BottomChrome` 本身是固定高度（`flexShrink: 0` + `height: metrics.bottomRows`
+ `overflow: hidden`），`ActivityView`/`ActivityPlaceholder` 也都是 1 行。
所以底栏**不是** ±1 的来源。逐层归因（`frontends/ink/ui/probes/layer_attribution.ts`）指向
`MessageViewport`：

| 阶段 | plan | 视口高 | 底栏 | 帧高 |
| --- | --- | --- | --- | --- |
| D. done 已到、status 仍 running | `live/1` | 1 | 5 | **6** |
| E. status 转 idle | `none/0` | 0 | 5 | **5** |

**turn 结束这一刻，视口从 1 行塌成 0 行**，整帧高度 6→5。
终端已撑满时，这 1 行就是一次整体上移。

#### 4.1.2 已实施的修法（方案 A，代码已落地）

只改一处：idle 且有历史时不再塌成 `none`，保持 1 行。

```ts
// src/messageViewportPlan.ts
-  return { kind: 'none' }
+  return { kind: 'live', height: 1 }
```

验收（三条独立证据）：

| 证据 | 结果 |
| --- | --- |
| `frontends/ink/ui/probes/layer_attribution.ts` 逐层高度 | turn 边界 `视口 1 -> 1`，**变化 0**；帧高 6→6 |
| `tests/probes/python/osc_diff.py` 真机 ±1 次数 | 基线 2 次 → **1 次**（剩下那次是 turn 开始的正常内容增长，基线也有，方向相反） |
| `npm test` | **520/520 通过**（含 `resizeReflow` 不重复回归） |

代价：idle 状态多占 1 行，`MessageViewport` 的 `ready` 属性为真，会显示
`Ready.`。这是 `live/1` 的既有行为（`ready={liveTranscriptRows.length === 0}`），
不是新引入的。**试过把它改成空白，会让 `resizeReflow` 回归失败**
（`BRAVO=0`，见 §7 第 8 条），因此保留现状。

### 4.2 方案 G：`GA_INK_MOUSE=full`（备用屏，改动小，但是产品决策）

备用屏下帧高实测恒为 39（`frontends/ink/ui/probes/frame_jitter.ts`，只有 1 种高度），
位移为零。代价是失去终端原生 scrollback，历史只能靠 GA 自己滚。

**这是唯一能做到「零位移」的现成开关**，属于产品取舍而非技术问题。

## 7. 方法学教训

1. **先确认「画面在移动」还是「画面在长高」。** 这是两回事。
   前者靠 scroll region / 整体平移解决，后者只能靠高度封顶。
   前几轮一直按「平移」找原因，方向错了。

2. **先做 A/B 基线，再写代码。** 方案 A 写完才发现零改善；
   先花 10 分钟测基线，本可在动手前否掉。

3. **端到端指标优先。** 方案 A 单测断言「槽位高度恒定」全绿，
   但用户指标「输入框移动次数」纹丝不动。**测试断言了错误的量。**

4. **优化「频率」还是「幅度」，先想清楚。** 方案 B 把提交次数降 90%，
   却让单次跳变放大 8 倍。用户感知的是幅度。

5. **不要用「看起来合理」代替「测过」。** 本轮先后判断错五次
   （live 区 / 提交频率 / 屏幕刷新率 / delta 粒度 / 整体平移），全靠实测纠正。

6. **测量工具的 debug 模式与缓冲边界都会污染结果。**
   Ink `debug:true` 时每帧写全量 Static（`ink.js:108`），帧高测出 6→53（9 种）；
   `debug:false` 才是真实的 6→14。按单次 write 数行数也会因缓冲切分而系统性偏差
   （`tests/probes/python/write_attribution.py` 因此被判定不可靠）。

7. **pyte 在宽字符边界会 `IndexError`。** 采样线程崩溃会让样本数骤降
   （89 → 9），据此得出的 A/B 结论不可信。绕开 `screen.display`、
   直接读 `screen.buffer` 可避免。

8. **「更干净」的写法可能踩坏回归测试。** 修完 `live/1` 的 `Ready.` 副作用时，
   先后试过三种写法（`spacer` 类型空白行 / `ready` 加 `staticTranscriptRows`
   条件 / `readyLabel` 传空格），**三种都让 `resizeReflow` 从绿变红**
   （`frontends/ink/ui/probes/resize_rows.ts` 复现 `BRAVO=0`，基线是 `BRAVO=1`）。
   原因：这些写法都改变了某个状态下的**实际帧行数**，而那个测试断言的正是
   「resize 后每行只出现一次」——帧行数一变，24 行窗口的边界就跨过去了。
   最终保留 `live/1` 原样（`Ready.` 是它的既有行为，不是本次引入）。
   **教训：能用「不改行为」的方式达成目标时，不要顺手「顺便美化」。**
