# CC 303 项目目录与高级特性路径机制调研

> 日期：2026-10-26
> 调研对象：Claude Code 2.1.303 已完成去混淆源码，以及 GenericAgent 当前实现
> 目的：为 GA 改造成 CC 风格“按项目分目录”提供可信边界，重点回答 subagent、workflow、Agent Team 为什么不能只靠替换一个根目录完成迁移。
> 证据等级：**S** = 303 去混淆源码或 GA Python 源码逐行直读；**A** = 多调用点互相印证但未找到唯一声明；**B/C** = 推断，本文不作为结论依据。

## 1. 结论先行

CC 303 并不是“把所有状态都塞进 projectKey”。它至少分成四个层次：

1. **全局配置根**：`CLAUDE_CONFIG_DIR` 或 `~/.claude`，承载跨项目的全局状态。
2. **项目桶**：`<configHome>/projects/<projectKey>`。CC 的 transcript 路径实际使用会话 `sessionProjectDir`；否则用 `originalCwd` 派生 key。`projectRoot` 是独立的项目/隔离边界，不能把三者当成同一个 cwd。
3. **用户项目根**：真实 cwd。工具执行、项目级 `.claude/agents`、`.claude/workflows`、git worktree 都围绕这个根，而不是围绕 projectKey 数据桶。
4. **会话项目身份**：同时记录 `originalCwd`、`projectRoot`、`cwd`；resume 时优先回到会话绑定项目，而不是“当前碰巧所在的目录”。

因此 GA 改造的核心不是“移动 temp”，而是拆开以下等式：

```text
旧：PROJECT_ROOT == RUNTIME_ROOT == 当前项目 == GA 安装仓库

新：PACKAGE_ROOT != PROJECT_ROOT != DATA_ROOT != PROJECT_DATA_DIR
```

高级特性能否继续使用，取决于实现是否始终区分：

- **项目身份根**：项目文档、项目角色、项目 workflow 定义、工具 cwd、git worktree；
- **项目运行数据桶**：session、subagent transcript、workflow run/artifact；
- **全局运行数据根**：teams、tasks、mailbox、logs、media 等；
- **GA 安装资源根**：内置 prompts、skills、assets、workflow JS。

关键限制：清洗是**有损**的。`a/b`、`a_b`、`a-b` 可能得到相同 key，所以 GA 若采用类似 key，必须：

- 照抄 CC 的撞车检测；或
- 使用“可读前缀 + 路径 hash”的稳定 key。

设计上推荐后者，因为实现更简单，且不会在迁移时把两个项目合并。

### 2.3 会话项目身份不是单一 cwd 字段

`m0017_0xe4565fb.js:3199-3208` 把项目身份定义成三项：

```js
{
  originalCwd: normalize(originalCwd),
  projectRoot: normalize(projectRoot),
  cwd: normalize(cwd)
}
```

`m0017:3303-3307` 的 `withProject()` 允许为 workflow/worktree fork 一个带新 cwd 的会话视图；`m0017:4734-4756` 则分别解析 `sessionProjectDir` 和 `projectRoot`。

| 事实 | 等级 | 坐标 |
| --- | --- | --- |
| 会话项目身份同时含 `originalCwd`、`projectRoot`、`cwd` | S | `m0017:3199-3208` |
| fork 可用 `withProject({cwd})` 临时改变工作 cwd | S | `m0017:3303-3307` |
| projectDir 优先 `sessionProjectDir`，否则当前 identity | S | `m0017:4734-4736` |
| projectRoot 优先会话绑定值 | S | `m0017:4751-4756` |

GA 方案必须把这组信息持久化到会话元数据，否则在 B 目录 resume A 的会话时，无法同时恢复“显示/列表项目身份”和“工具实际工作目录”。

| 阶段 | CC 的实际值 | 说明 |
| --- | --- | --- |
| 初始身份 | `originalCwd = projectRoot = cwd` | `m0017:4605-4613` 的 `Qi()` |
| project bucket | 优先 `sessionProjectDir`，否则 `originalCwd` | `m0017:4734-4736` + `m0282:42-68` |
| 项目配置/worktree 边界 | `projectRoot`，可与会话 `cwd` 不同 | `m0017:4751-4756` |
| workflow/worktree 执行 | `withProject({cwd})` 改变执行视图 | `m0017:3303-3307`、`m1064:2554-2559` |

因此 CC 的 projectKey 更准确地说是“会话原始 cwd / sessionProjectDir 派生的数据桶 key”，不是“任意时刻当前 cwd”，也不是“projectRoot 的同义词”。GA 若希望从项目子目录启动仍落到同一桶，可以基于规范化 `project_root` 生成 key，但必须明确标注为 **GA 产品增强**，不能冒充 CC 原算法。

### 4.2 workflow 定义

`m1607_0x101b69c6.js:356-363,413-425`：

- project scope 从 cwd 向上发现 `.claude/workflows`；最近的项目目录最终覆盖更高层目录；
- 找不到现成目录时，默认保存到 `<cwd>/.claude/workflows`；
- user scope 保存到 `<configHome>/workflows`；
- project scope 与 user scope 同名时，project scope 覆盖 user scope；无效 project workflow 不应静默覆盖有效 user workflow；
- 使用 `--project-config-root` 启动的会话禁用 project-scope 保存，而不是偷偷写回 user scope。

| 事实 | 等级 | 坐标 |
| --- | --- | --- |
| project workflow 定义来自用户项目的 `.claude/workflows` | S | `m1607:356-363`；发现链 `m0459:40341-40380` |
| user workflow 定义来自 `<configHome>/workflows` | S | `m1063:133-135,189-255,257-292` |
| 项目定义覆盖用户定义，最近目录覆盖更远目录 | S | `m1063:267-277` |
| 默认保存 project scope，可切换 user scope | S | `m1607:435-510` |

这说明 project workflow 定义必须绑定 `PROJECT_ROOT`，不能绑定 `PROJECT_DATA_DIR`；否则用户把项目复制到另一台机器后，workflow 定义不会跟着项目走。

### 4.3 workflow 子代理的项目上下文

`m1064_0xf9ee4cd.js:2554-2559`：

```js
let V = U.session.withProject({ cwd: Fn });
return vmn(vo(V).cwd, () => Or(V, ...));
```

`Fn` 是 worktree path；没有 worktree 时沿用原项目 cwd。workflow 改变的是该次执行的工作目录，不是另造一个新的 projectKey。

结论：

- workflow run 的 projectKey 仍来自父会话项目；
- child cwd 可以是项目根或 `.claude/worktrees/...`；
- transcript 仍归父项目的 session 数据桶。

## 5. git worktree

`m0459_0xecff32a.js:102191-102228`：

```js
function R_(e) { return join(e, ".claude", "worktrees") }
```

创建前依次 lstat：

1. `<repo>/.claude`
2. `<repo>/.claude/worktrees`
3. `<repo>/.claude/worktrees/<name>`

任何一层是 symlink 都拒绝，原因是 symlink 可能把 worktree 写到仓库外。

workflow 的 `isolation:'worktree'` 走同一机制：

- `m1064:2138-2145` 生成 run/job 名并创建 worktree；
- `m1064:2555-2559` 在 worktree cwd 下执行；
- `m1064:2765-2777` 在 finally 中清理或保留。

| 事实 | 等级 | 坐标 |
| --- | --- | --- |
| Agent Team/workflow worktree 容器是 `<projectRoot>/.claude/worktrees` | S | `m0459:102191-102233` |
| 三层 symlink preflight | S | `m0459:102210-102228` |
| workflow 用 worktree 作为临时 cwd | S | `m1064:2138-2145,2554-2559` |
| worktree 有独立清理/保留语义 | S | `m1064:2765-2777` |

GA 若采用 `<DATA_ROOT>/.../worktrees`，`git worktree add -C <用户项目>` 虽然技术上可能成功，但 worktree 会落在用户仓库之外，无法沿用项目级 `.gitignore`，也不符合 CC 的归属。正确落点是：

```text
<PROJECT_ROOT>/.ga/worktrees/<runId>
```

GA 使用 `.ga` 而不是 `.claude` 是产品命名差异；**路径归用户项目**这一点必须一致。

### 6.2 namespace 不带 projectKey

`m0037_0xe4aad18.js:199-213,327-351` 进一步确认命名空间：

```js
team: team => ({ namespace: "team", team }),
mailbox: (team, teammate) => ({ namespace: "mailbox", team, teammate }),
```

在 key 序列化里只有：

```js
case "team": return [e.namespace, e.team];
case "mailbox": return [e.namespace, e.team, e.teammate];
```

对照同一文件的 `sidecar(projectKey, sessionId, relPath)` 与 `agentMemory(..., projectKey, ...)` 可以确认：CC 明确知道哪些 namespace 要带 projectKey；team/mailbox 并不带。`m0391_0xec86091.js:178-195` 的 task list 也以 sanitize 后的 `teamName/listId` 直接定位 `<configHome>/tasks/<id>`。

这带来一个真实的产品边界：

- CC 允许不同项目使用同名 team，因此 board 可能共享；CC 用 session 派生/显式 team name 管理身份，而不是 projectKey 路径隔离。
- GA 若要求“A/B 同名 team 不串板”，不能声称这是 CC 原生行为；应在保留全局 `teams/`、`tasks/` 层级的前提下，由 GA 增加 project-scoped `teamKey`。

## 8. CC 的不变量与 GA 应遵守的映射

| CC 不变量 | GA 对应目标 |
| --- | --- |
| config home 与安装位置、用户项目分离 | `DATA_ROOT`、`PACKAGE_ROOT`、`PROJECT_ROOT` 分离 |
| transcript bucket 使用会话 `originalCwd`/`sessionProjectDir` | `project_key` 基于规范化 `PROJECT_ROOT` 是 GA 增强；会话同时保存 `original_cwd`、`project_root`、`cwd` |
| 主会话与子代理转录在项目桶 | `PROJECT_DATA_DIR/<session>/subagents/...` |
| workflow journal 绑定 project + session + run | `WorkflowStore(root=PROJECT_DATA_DIR)` |
| workflow 定义按 project/user 分层 | project: `<PROJECT_ROOT>/.ga/workflows`；user: `<CONFIG_ROOT>/workflows`；legacy 只读 |
| worktree 位于用户项目 | `<PROJECT_ROOT>/.ga/worktrees` |
| team config/task 是全局层 | `<DATA_ROOT>/teams`、`<DATA_ROOT>/tasks` |
| 项目角色/文档来自用户项目 | `<PROJECT_ROOT>/.ga/subagents`、`GA_AGENTS.md` |
| resume 绑定会话项目 | session 元数据持久化三根并优先恢复 |

## 9. 反模式

以下做法会“看似完成目录改造，实际破坏高级特性”：

1. 把 `PROJECT_ROOT` 直接定义成 `PROJECT_DATA_DIR`。
2. 让 subagent 的 `root_dir` 同时承担 repo、cwd、state root。
3. 把 Agent Team worktree 建到 `DATA_ROOT`。
4. 把 `.ga/subagents` 或 `GA_AGENTS.md` 跟着数据桶迁移。
5. 只迁移 session JSONL，不迁移或兼容 workflow artifact 的绝对路径。
6. 只改 writer 的路径，不改 registry/roster/control-plane reader。
7. 根据当前 cwd 猜测旧 session 所属项目。
8. 在 team name 中直接拼未清洗的 Windows 路径。
9. 让 workflow child 的项目文档继续从 `os.getcwd()` 加载。
10. 把 CC 的全局 teams/tasks 说成按 projectKey 分目录。
11. 把 `originalCwd`、`projectRoot`、当前 `cwd` 当成同一个字段，或宣称 CC 的 projectKey 一定来自 `projectRoot`。
12. 把 named workflow 定义放回某个 run 的项目数据桶，导致定义随 run/会话删除而消失。
13. 只实现 workflow 列表 reader 的 project/user scope，却让 nested `workflow({name})` 继续读旧全局库。
