# 并行 / 满负载跑 pytest 时哪些用例会偶发失败

> 日期：2026-11-16
> **2026-11-16 更新：§3.4 的 MCP 两条已修，负载下 6/6 全绿。结论表见 §2。**
>
> 结论：**6 条里 4 条是"预算小于固定开销"，属于测试侧缺陷；2 条（MCP）的等待上限
> 比冷启动成本还短，其中一条空闲状态也稳定失败。没有一条是产品缺陷。**
>
> 复现测量脚本：`tests/probes/python/_probe_test_flakiness_under_load.py`

---

## 1. 为什么必须有这份文档

排查 0.6.1 安装版的多智能体问题时，出现过这样的对话：

> "有几条偶发失败，单独复跑均通过 —— 是我同时跑多个 pytest 进程互相干扰造成的。"

这句话**当时是错的**。其中一条（workflow 0.2 s 预算）的根因是**预算低于固定启动成本
的下限**，也就是说它失败的原因与它声称要测的东西完全无关，而且它并不是"只在并行时才红"。
把"负载下的偶发"当成既有噪声、不追到底，已经在这个仓库里掩盖过两次真实缺陷。

所以这份文档要固定三件事：

1. 哪些用例会**因负载**而偶发失败，具体机制是什么；
2. 哪些用例**空闲也失败**，即真正的缺陷（不是 flake）；
3. 每条各自的正确处置，以及"不要怎么做"。

判定方法见 §4：每个格子都是 **N 轮通过率**，不是单次采样。

---

## 3. 每条的机制与处置

### 3.1 已修的两条 workflow 用例

`WorkflowRuntime` 的 deadline 在**node 子进程存在之前**就开始计时：

```python
# genericagent/workflow/runtime.py:284
deadline = time.monotonic() + self.timeout_seconds
```

所以 `timeout_seconds` 还要覆盖 `spawn` + `ready` 握手。实测该开销：

| 条件 | spawn → 脚本第一行 |
| --- | --- |
| 空闲 | 145–525 ms（均值 ~250 ms） |
| CPU 负载满 | 最高 1.4 s |

- `test_runtime_timeout_cancels_running_child_agents` 原来用 **0.2 s**，低于启动成本的下限
  → deadline 在脚本第一行之前就到期，**job 从未启动**，而测试断言的是
  `cancelled_job_ids == {"agent_1"}`（要求 job 已启动过）。失败原因与"取消"无关。
  **0.6.2 已修**：预算提到 2.0 s，并新增
  `assertTrue(runner.started_job_ids, ...)` —— 把"deadline 早于任何子 agent 启动"
  变成一条指名道姓的失败，而不是伪装成"取消没生效"。
- `WorkflowCancellationSemanticsTest.CANCELLATION_DEADLINE_SECONDS` 已经是 2.0 s，
  注释里写明了同一机制，空闲与负载下均通过。

> 这两个是**测试侧**缺陷。runtime 严格执行它收到的 deadline，行为是对的。

### 3.2 `test_run_git_timeout_kills_pipe_holding_descendants` —— 仅负载下偶发

```python
with self.assertRaises(subprocess.TimeoutExpired):
    _run_git([sys.executable, "-c", child], timeout=0.2)
self.assertLess(time.monotonic() - started, 1.5)   # ← 实测 2.97 s
```

断言"0.2 s 超时后，清理必须在 1.5 s 内完成"。这个用例要杀的是一个**持有管道句柄的
孙进程**；调度器饱和时，连 kill + 等待退出这一步本身都会被饿到 1.5 s 之外。

**处置**：暂无需求改。它测的行为（不让孙进程拖住管道）是真的，只是阈值贴着实测值。
若要修，方向是放宽到 3 s 或改为断言"句柄最终被释放"而不是耗时。

**不要做**：不要因为它在满负载下红就把阈值一路放大到失去意义。

### 3.3 `test_a_stalled_subscriber_does_not_delay_delivery_to_a_healthy_one` —— 极低频

```python
deadline = time.time() + 3
...
self.assertGreaterEqual(len(seqs), 100, ...)   # 曾实测 72
```

200 个事件里必须至少 100 个在 3 s 的 drain 窗口内到达。发送线程被饿住时会掉到 100 以下。

实测：串行 20 轮 **0 失败**；20 轮前的一次 4 轮测量里出现过 1 次。即失败率远低于 5%，
属于真正的低频抖动，**不是**稳定的预算不足。

**处置**：暂无需求改。若将来频繁出现，方向是放宽 drain 窗口或降低 100 这个下限。

### 3.4 MCP 两条 —— **已修**（原来不是 flake，是等待上限设得太短）

这两条最容易被误判成"负载抖动"，因为它们在**整文件运行时是绿的**，单独跑才红。
真实机制是**首次 `import fastmcp` 的冷启动成本**：

```
冷 import fastmcp: 4.53 s
热 import fastmcp: 4.03 s
```

MCP fixture 子进程的第一步是 `import time` → 写 starts 文件（0.15 s），但 GA 这一侧
要先把 fastmcp 拉起来才能启动 server。而测试只等 **3 s**：

```python
# tests/test_mcp_runtime.py:695（修复前）
deadline = time.monotonic() + 3
while not starts_path.exists() and time.monotonic() < deadline:
    time.sleep(0.02)
self.assertTrue(starts_path.exists(), "shared startup fixture did not launch")
```

实测 5 轮：`3.39s / 0.23s / 0.15s / 0.17s / 0.17s`。**只有第一轮撞上冷启动**，此后模块
已缓存，全部 0.2 s 以内。这解释了两个现象：

- **整文件跑是绿的**：文件里前面的用例已经把 fastmcp 预热了；
- **单独跑必红**：它是进程里的第一个 fastmcp 使用者。

**决定性验证**：在父进程先 `import fastmcp`（耗时 3.95 s）再跑同一段逻辑，
4/4 轮全部落在 3 s 以内（0.17–0.21 s）。假设成立，且这 4 秒确实是暖机成本，
不是被测行为的一部分。

```python
# 对照组：撞冷启动
trial 0: 3.39s  <- 唯一一次失败
trial 1: 0.23s
trial 2: 0.15s

# 实验组：父进程先 import fastmcp（3.95s），再跑
trial 0: 0.18s
trial 1: 0.21s
trial 2: 0.20s
trial 3: 0.17s   <- 全部 < 3s
```

#### 修复（2026-11-16）

`genericagent/mcp/runtime.py` 新增一个常量，把"冷启动要花多少"这件事**写进产品侧**，
让测试从它派生预算，而不是在每个调用点重新猜一个数字：

```python
MCP_IMPORT_COST_ESTIMATE_SECONDS = 5.0
```

`tests/test_mcp_runtime.py` 据此定义：

```python
FIXTURE_START_BUDGET_SECONDS = 3.0 * _MCP_IMPORT_COST_ESTIMATE_SECONDS  # = 15s
```

改动点（都是"等待预算覆盖冷启动"，不是无脑放大）：

| 位置 | 修复前 | 修复后 |
| --- | --- | --- |
| 4 处 waits-for-start-marker | `+ 3` / `+ 3` / `+ 3` / `+ 5` | `+ FIXTURE_START_BUDGET_SECONDS` |
| `discover_mcp_tools(timeout=…)` | `5` | `FIXTURE_START_BUDGET_SECONDS` |
| 对应 `worker.join(timeout=…)` | `8` / `10` | `FIXTURE_START_BUDGET_SECONDS + 5` 等 |
| `GA_MCP_CALL_TIMEOUT` | `10` | `FIXTURE_START_BUDGET_SECONDS * 2` |

配套加了一条守卫测试 `test_fixture_startup_budget_covers_a_cold_mcp_import`：
断言 `FIXTURE_START_BUDGET_SECONDS > MCP_IMPORT_COST_ESTIMATE_SECONDS * 2`。
**这样以后谁把预算改小回去，测试会直接指出原因**，而不是重新变成一条偶发红。

反向确认：把预算强制改回 3.0 s，`test_cancelled_waiter_...` 立刻重新失败，报错与修复前
逐字一致；改回派生预算则通过。

**不要做**：不要因为"反正测试慢"就把预算改成 60 s 一次性了事。15 s = 3 × 实测冷启动，
留了 3 倍余量已经足够覆盖慢机器；再放大只会让"server 真的起不来"这种故障也拖到同样久
才暴露。

## 4. 判定方法（为什么不能靠"单独复跑一次就通过"）

「单独复跑一次通过」**不能**证明它是负载抖动：

- 冷启动类失败（§3.4）恰恰是第一次跑失败、后面全过；
- 0.2 s 预算类失败（§3.1）在空闲时通过率 12/12，加负载才开始红。

正确做法是**分条件测通过率**：

```bash
# 空闲 vs 负载，每格 N 轮
python tests/probes/python/_probe_test_flakiness_under_load.py --rounds 6 --hogs 6
```

判据：

| 空闲 | 负载 | 结论 |
| --- | --- | --- |
| 全过 | 偶红 | 预算小于调度噪声 → 放宽预算，或改为断言机制而非耗时 |
| **红** | 红 | **真实缺陷**，不是 flake |
| 全过 | 全过 | 该用例对此条件不敏感 |

同时要记录**实际测量值**（耗时、事件数、seq 数），而不是只记 pass/fail：`72 not >= 100`
和 `2.97 not less than 1.5` 这两个数字本身就是判断依据。

## 5. 结论

| 类别 | 条数 | 处置 |
| --- | --- | --- |
| 测试侧缺陷，已修 | 5 | 2 条 workflow 预算 + 2 条 MCP 冷启动等待上限 + 1 条 ink bridge 阶段预算 |
| 负载抖动，暂不改 | 2 | worktree 1.5 s 阈值、IPC 3 s drain 窗口 |

修复后 6/6 在空闲与 6×CPU 负载两种条件下均 4/4 通过；`test_ink_bridge.py` 173/173；
全量套件 2791 passed。

**满足以下条件时，请把对应条目升级处理**：

- worktree / IPC 两条的失败率超过约 10% → 按 §4 重新测量并放宽。

### 5.1 ink bridge：一条"差 30 毫秒"的预算（2026-11-16 已修）

`test_workflow_resume_cache_hit_replays_prefix_without_restarting_cached_child`
用 `runner.second_started.wait(timeout=3.0)` 等 workflow 跑到第二个 `agent()`。
全量套件连跑时偶发失败，单独跑 3/3 通过。

实测两个数（探针 `_probe_ink_bridge_stage_budget.py`）：

| 条件 | approve → 第二个 agent() 启动 |
| --- | --- |
| 自然条件（含首轮冷启动） | 0.32 s，最坏 **2.38 s** |
| 注入 4 s 启动延迟（对照组） | **4.45–4.61 s** |

自然最坏值 2.38 s 距 3.0 s 上限只剩 0.6 s。也就是说这个预算**不是错，是太紧**——
机器一忙就漂过 3.0 s，而失败信息只是 `assertTrue(False)`，看起来像"resume 逻辑坏了"。

修法：`WORKFLOW_STAGE_BUDGET_SECONDS = 15.0`，替换该测试里 5 处等待
（`workflow_approve` / `second_started.wait` / 两处 `wait_for_workflow_idle` /
`workflow_resume`），并加一条守卫测试断言它 ≥ 10 s。这些都是 poll 等待而不是固定
sleep，所以放宽不影响通过时的耗时。

#### 这一条踩到的坑：`Event.wait(timeout=N)` 不是秒表

第一版探针用 `event.wait(timeout=3.0)` 的**返回值**判断"3 秒够不够"。结论是错的：
工作流线程在做 node 启动和 IPC（CPU 密集），等待线程被 GIL 饿住，
`wait(timeout=3.0)` 实际**在 4.5 s 后才返回 True** —— 它早就超出了超时，然后看到了一个
已经被置上的事件。于是探针把"4.5 s 的阶段"报告成"3.0 s 预算够用"。

正确做法是**记时间戳再相减**，不依赖任何线程等待语义的返回值：

```python
stage = runner.second_started_at - approved_at       # 纯算术
covered = stage <= budget
```

同理，第一次反向确认（6 个 CPU hog + 旧预算，期望变红）也是 5/5 绿 —— 那也是假绿：
负载不可控，说明不了任何事。改成**注入固定延迟**构造慢条件之后，对照组 4/4 稳定超出。

### 一条通用教训

这 5 条修法都是同一个形状：**等待预算必须覆盖"与被测行为无关的固定开销"**，
并且这个开销应该由**一处**定义、测试从它派生，而不是在每个调用点各写一个数字。
否则下次机器慢一点，就会有人逐个把 3 调成 5、把 5 调成 8，而没人说得清为什么。

第二条教训：**判断"预算够不够"必须用时间戳，不能用 `wait()` 的返回值**。
CPU 密集的邻线程会让等待方拿不到 GIL，返回值既可能过冲也可能失真。
