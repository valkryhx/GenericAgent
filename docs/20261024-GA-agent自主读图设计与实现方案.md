# 20261024-GenericAgent agent 自主读图设计与实现方案（对标 Claude Code 2.1.303）

> 目标：让 GA 的 agent 在执行过程中**自己**读取一个图片路径并真正"看见"像素，
> 与「用户把图片贴进输入框」走同一套原生多模态通道。
> 适用范围：本地会话（Ink / CLI / desktop / bots）、workflow 子 agent、subagent。
> **不包含**：用户输入侧（已由 `docs/ga_image_input_research_2026-07-20.md` 覆盖）、
> 云端会话、OCR / vision_api 旁路。
> 依据：CC 侧源码事实见 `D:\git_repos\claude_hack\docs\20261024-CC-view-image实现调研.md`；
> GA 侧结论均带 `文件:行号`，可直接回查。

---

## 0. 一句话结论

GA 的**图像编码管线、三个后端的 image 块序列化、token 计量、压缩占位**都已经写好了，
真正卡住"agent 自己看图"的只有**三个管道口径**：

| # | 断点 | 位置 | 后果 |
|---|------|------|------|
| 1 | `do_file_read` 没有图像分支，把 PNG 当 UTF-8 文本读 | `genericagent/core/handler.py:848` | 模型看到的是一堆 `\ufffd` |
| 2 | `loop` 把**所有** tool 结果 `str()` 成字符串 | `genericagent/core/loop.py:258-272` | 即使工具返回了 image block 也会被拍平 |
| 3 | OpenAI 兼容适配器把 tool_result 的数组内容只取 `text` | `genericagent/llm/core.py:762-767` | 图在 OAI 后端被静默丢弃 |

补上这三处（外加一处 token 计量的嵌套计数），agent 就能像 CC 的 Read 工具一样，
用一个已经存在的工具、零新增工具 schema 的方式读图。

## 1. 需求边界

### 1.1 两条看图入口，一条终点

```text
入口 A（已实现）  用户粘贴 / 拖入 / 路径 → 前端附件 → app._build_user_content_with_images
                                                              ↓
入口 B（本文）    agent 调 file_read("x.png") → do_file_read 图像分支
                                                              ↓
                                          tool_result.content = [text, image]
                                                              ↓
                         Claude native: 直接发 / OAI native: 抬到 user message / 文本后端: 降级
```

两条入口最终都是同一个 Anthropic image content block：
`{"type":"image","source":{"type":"base64","media_type":"image/png","data":"..."}}`。
CC 也是这个结构，且 CC **没有** `view_image` 工具——读图是 Read 工具的一个分支。

### 1.2 与既有文档的关系

- `docs/ga_image_input_research_2026-07-20.md` 解决的是**入口 A**（用户贴图），Slice A–D 已落地。
- 该文档 §5.7 把「agent 截 UI / 读本地图」划给 `vision_api` / OCR，**本文改写这条边界**：
  当后端支持原生图时，工具读图应直接产出 image block，而不是再绕一层 vision API。
  理由见 §1.3。
- `memory/vision_sop.md` 仍然有效，但它降级为**后端不支持原生图时**的兜底。

### 1.3 为什么不继续用 vision_api / OCR 包装

1. **多一次模型往返**：`vision_api` 返回的是一段自然语言描述，agent 拿到的是"别人转述的图"，
   细节（按钮位置、报错文字、UI 布局）在转述里已经丢了。
2. **依赖 agent 自觉**：模型必须先想到调 `vision_api`，而不是"读这个文件"。
   原生通道把「看」变成读文件的副作用，不需要额外决策。
3. **系统提示更脏**：vision SOP 要教窗口枚举、截图边界、禁止全屏，都是旁路成本。
4. CC 与 Codex 都选了原生块：CC 的 Read 工具、Codex 的 `view_image` 共用同一套 codec。

### 1.4 非目标

- 不做新的 `view_image` 工具（理由见 §4.1）。
- 不改前端附件协议、不改用户输入路径。
- 不做视频 / PDF 页面渲染（PDF 仍按文本读）。
- 不做"图片内容索引"或向量检索。

## 2. CC 303 的事实（本文只引用结论）

详细坐标见 `claude_hack/docs/20261024-CC-view-image实现调研.md`，这里只留实现所需的四条：

| 事实 | CC 的做法 | 对 GA 的约束 |
|------|-----------|--------------|
| 没有独立读图工具 | Read 工具内部按扩展名 / magic bytes 分流 | GA 扩 `file_read` 即可，不加工具 |
| 图挂在 tool_result 里 | `content: [{type:"image", source:{...}}]`，**数组**才带图 | `tool_result.content` 必须是 list |
| 结果旁有可读元信息 | 另发一条 `isMeta` 消息写 `[Image: ...]` 尺寸/路径 | GA 用同一 tool_result 的 text 块即可 |
| 预算有硬上限 | 长边 1568、base64 ≤ 5 MiB、超限 JPEG q20 兜底 | GA codec 已有 2048 / 5 MB / Pillow 缩放 |

关键一句：**字符串 content 只当文本，模型永远看不到图。** 这是所有坑里最贵的一个。

## 3. GA 现状（带坐标）

### 3.1 回顾：输入框看图链路（入口 A，已实现）

> 这一节是"已有能力"的现状快照，用来对比入口 B 缺什么。
> 一句话：**前端把图变成 path + `[Image #N]` 芯片，bridge 只透传 path，
> Python 在发请求前才编码成 image block，挂到第一条 user 消息上。**

#### ① 前端采集：两个入口，都落成芯片

#### ② 提交：按 placeholder 顺序收集

`inputController.ts:370` → `attachmentsForSubmit()` 扫 `[Image #N]`，按出现顺序输出
`[{path, placeholder, source}]`，随命令发给 bridge：

#### ③ bridge：透传

`frontends/ink/bridge.py:353` `submit(text, display_text, images)` → `:426`
`agent.put_task(text, source="user", images=images)`。bridge 不碰图。

#### ④ 后端：编码成原生 image block

```python
# genericagent/core/app.py:1080

initial_content = _build_user_content_with_images(raw_query, images) if can_image else None
```

`_build_user_content_with_images`（`app.py:129`）还会用 `_extract_image_paths`（`:89`）
从文本里再抽一遍路径，再进 `image_codec.build_user_content_with_images`（`image_codec.py:300`）：

```python
[{"type": "text", "text": query},
 {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "..."}}]
```

编码器 `encode_image_for_prompt`（`image_codec.py:175`）：magic bytes 嗅探 → 2048 长边缩放 /
BMP 转 PNG（Pillow）→ base64 ≤ 5 MB、原始 ≤ 40 MB → 32 条 LRU 缓存。

#### ⑤ 进模型与配套

- `loop.py:201-205`：`initial_user_content` 直接作为第一条 user 消息的 `content`。
- Claude native 原样收；OAI 必须 `native_image_input: true`（`llm/core.py:1041`）。
- 后端不支持视觉时（`app.py:1081-1120`）：不发明图，把真实路径补进 query，
  并明确告诉模型"[Image #N] 只是占位符，你看不到像素"。
- 提示词补丁：`should_inject_vision_direct_answer`（`app.py:273`）+
  `build_vision_direct_answer_sys_prompt`（`:239`），强制第一轮直接看图，禁止搜仓库/OCR。
- 计量按 1500 token/图（`tokens.py:31`），压缩时打 `[image]` 占位（`context.py:227`）。

#### 对入口 B 的启示

入口 A 的终点是 `initial_user_content`，**只覆盖"用户这一轮"**。
agent 执行中调 `file_read` 走的是 `tool_results`，那条路今天还是纯字符串——
这正是 §3.3 缺口 1/2 的来源：不是编码器不会做，而是**另一条管道没接上**。

### 3.3 缺口逐条

#### 缺口 1：`do_file_read` 是纯文本读

```python
# genericagent/core/handler.py:848
def do_file_read(self, args, response):
    path = self._get_abs_path(args.get("path", ""))
    yield f"\n[Action] Reading file: {path}\n"
    ...
    result = file_read(path, start=start, keyword=keyword, count=count, show_linenos=show_linenos)
```

`file_read`（`handler.py:295`）用 `open(path, 'r', encoding='utf-8', errors='replace')` 打开，
PNG 会变成一长串替换字符，随后被 `smart_format` 截断成几千字符的乱码。
**这不是"图没传过去"，是"从来没读过图"。**

#### 缺口 2：loop 把 tool 结果无条件字符串化

```python
# genericagent/core/loop.py:258-272
structured = type(outcome.data) in [dict, list]
datastr = json.dumps(outcome.data, ensure_ascii=False, default=json_default) if structured else str(outcome.data)
...
datastr = budget_tool_result(handler, tool_name, persist_key, datastr, structured=structured)
...
tool_results.append({'tool_use_id': tid, 'content': datastr})   # ← 永远是 str
```

即使 `do_file_read` 想返回 image block，这里也会被 `str()` 吃掉。
`budget_tool_result`（`core/tool_results/budget.py:149`）签名也只接受 `str`。

#### 缺口 3：OAI 适配器丢掉 tool_result 里的图

```python
# genericagent/llm/core.py:762-767
tr = b.get("content", "")
if isinstance(tr, list):
    tr = "\n".join(x.get("text", "") for x in tr if isinstance(x, dict) and x.get("type") == "text")
result.append({"role": "tool", "tool_call_id": ..., "content": tr if isinstance(tr, str) else str(tr)})
```

非 text 的块（image）被过滤掉。OpenAI Chat Completions 的 `role:"tool"` 消息本来也不能带图，
所以正确做法不是"塞进去"，而是**抬到紧随其后的一条 user 消息**（见 §4.5）。

#### 缺口 4：token 计量漏算嵌套图

```python
# genericagent/core/tokens.py:93-101
def _msg_image_count(msg):
    content = msg.get("content")
    if not isinstance(content, list): return 0
    return sum(1 for b in content if isinstance(b, dict) and b.get("type") in ("image","image_url","input_image"))
```

只数**顶层**。图放进 `tool_result.content` 后，`_msg_chars` 里 tool_result 分支也只累加 `text`
（`:79-83`），于是这张图被算成 **0 token**。上下文压缩会因此低估水位。

#### 缺口 5：没有工具级 capability gate

`supports_image_input` 只在 `app.py:1080` 用于**入口 A**。工具侧如果无脑返回 image block，
在纯文本后端上会被 `_to_responses_input` / 文本协议路径变成 `str(list)` 塞进 prompt —— 既浪费又可能 400。

#### 缺口 6：工具描述没告诉模型"能读图"

`assets/tools_schema.json:14` 与 `assets/tools_schema_cn.json:14` 的 `file_read.description`
只有"读取文件内容 / 修改前先读"。模型不会主动拿它去读截图。

### 3.4 现状数据流（读一张 PNG）

```text
agent: file_read("shot.png")
   ↓
do_file_read → file_read() → open(..., encoding='utf-8', errors='replace')
   ↓  乱码字符串
StepOutcome(str)
   ↓
loop.py:258  str(...)  → budget_tool_result → tool_results[].content = str
   ↓
NativeToolClient.chat → tool_result{content: "<乱码>"}
   ↓
Claude: 模型看到乱码；OAI: 同样是乱码
```

目标数据流：

```text
agent: file_read("shot.png")
   ↓
do_file_read → 嗅探 magic bytes → encode_image_for_prompt → build_image_block
   ↓
StepOutcome(note_text, images=[block])
   ↓
loop.py: content = [{"type":"text","text":note}, block]
   ↓
Claude: tool_result.content=[text,image]  → 模型直接看图
OAI   : tool 消息(text) + user 消息(image_url) → 模型直接看图
文本后端: 只发 note，并明确告诉模型"后端不支持原生图"
```

## 4. 设计

### 4.1 扩 `file_read`，不新增工具

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 新增 `view_image` 工具 | 语义直白 | 工具表 +1，每轮 prompt 多一份 schema；模型还要先判断"这是图吗" | ❌ |
| 扩 `file_read` 自动分流 | 零新增 schema；与 CC Read 同构；模型只需"读这个路径" | `file_read` 语义变宽 | ✅ |

CC 的 Read 工具描述里就写着 "Reads images (PNG, JPG, …) and presents them visually"，
没有单独的读图工具。GA 沿用这个形状。

**分流判据用 magic bytes，不只看扩展名**：扩展名可伪装，且 `.bmp` 需要转码。
`image_codec._sniff_media_type` 已经有这套逻辑，工具侧只需读前 16 字节做一次快速判定，
避免把 40 MB 的二进制先当文本读进来。

### 4.2 数据契约：`StepOutcome` 增加 `images`

```python
@dataclass
class StepOutcome:
    data: Any
    next_prompt: Optional[str] = None
    should_exit: bool = False
    images: Optional[list] = None      # 新增：原生 image content block 列表
```

- 追加在末尾，102 处 `StepOutcome(...)` 调用点**全部按关键字/两参使用**，不破坏。
- `images` 只放**已经构造好的 block**（`build_image_block` 的输出），
  工具层不负责决定后端形态 —— 适配是 `llm/core.py` 的事。
- `data` 仍然是纯文本（人类可读的元信息），继续走 `budget_tool_result`。
  **图片永远不进 `data`**，否则会被 stringify。

### 4.3 loop 组装：只在有图时改变形状

```python
# genericagent/core/loop.py，替换 :272 附近
images = getattr(outcome, 'images', None) or []
if images:
    tool_content = [{"type": "text", "text": datastr}, *images]
else:
    tool_content = datastr
tool_results.append({'tool_use_id': tid, 'content': tool_content})
```

要点：

1. **只有 `images` 非空时才变成 list**。无图路径字节级不变，现有测试不会抖。
2. `budget_tool_result` 只作用在 `datastr` 上，图片不受影响。
3. 并行批次（`_run_parallel_tools`）按原始 index 返回，图不会串位。
4. `turn_end_callback` 收到 `tool_results` 但不做序列化（`handler.py:2291` 只读 `tool_calls`），
   所以不需要额外改动。

### 4.4 `do_file_read` 图像分支

判定顺序（**先嗅探，后读文本**）：

```text
path = _get_abs_path(args.path)
  ↓
os.path.isfile? 否 → 走原逻辑（让 file_read 给出 FileNotFound + 相似文件建议）
  ↓ 是
读前 16 字节 → PNG / JPEG / GIF / WEBP / BMP ?
  ↓ 否 → 原逻辑（文本读取）
  ↓ 是
后端支持原生图?
  ├─ 否 → 返回文本提示（不加载像素）
  └─ 是 → encode_image_for_prompt
            ├─ 异常 → 返回 [Image could not be processed: ...]
            └─ 成功 → StepOutcome(note, images=[block])
```

文本提示（capability 关闭）：

```text
[Image] <path> (image/png) — 当前后端不支持原生 image 输入，未加载像素。
可用 code_run + Pillow / OCR 处理，或改用支持视觉的模型。
```

失败提示（codec 抛错）：

```text
[Image could not be processed: <path>: <reason>]
（常见原因：文件过大 > 40 MB、base64 超 5 MB 且无 Pillow、BMP 无 Pillow、边长 < 8px）
```

成功时的 text 块（**必须短**，它会计入字符预算）：

```text
[Image: shot.png | 1280x720 | image/png | ~142 KB]
图片已作为原生 image block 附在本条 tool_result 中，直接观察像素作答；
不要再 file_read 同一路径，也不要为了理解它去搜仓库。
```

参数语义：

| 参数 | 对图片的行为 |
|------|--------------|
| `start` / `count` / `keyword` / `show_linenos` | **忽略**（图片没有行） |
| `path` | 必需，经 `_get_abs_path` 解析（受 workspace 约束） |

其他副作用保持：`log_memory_access(path)`、`_get_anchor_prompt(...)` 照常调用，
否则 `next_prompt` 为空会被 loop 判定为 `CURRENT_TASK_DONE` 提前结束任务。

### 4.5 后端适配矩阵

| 后端 | 序列化位置 | tool_result 形态 | 需要改什么 |
|------|-----------|------------------|-----------|
| `NativeClaudeSession` | `llm/core.py:1422` 透传 → Anthropic Messages | `[{text},{image}]` | 无（透传已支持） |
| `NativeOAISession`（chat_completions） | `_msgs_claude2oai` `:733` | `role:"tool"` 只放 text；图抬到紧随的 `role:"user"` | **改 `:762-767`** |
| `NativeOAISession`（responses） | `_msgs_claude2oai` → `_to_responses_input` `:692` | `function_call_output` 只放字符串；图在 user 的 `input_image` | 随上一条自动生效 |
| `ToolClient`（文本协议） | `_build_protocol_prompt` 拼纯文本 | 无法带图 | capability gate 关闭即可 |

**抬图算法（OAI）**：一条 user 消息内，tool_result 块是连续的，后面才跟 text。
把每个 tool_result 里的 image 块收集到 `deferred`，在该条消息处理结束时
`text_parts = deferred + text_parts` 再 flush —— 这样顺序是
`tool, tool, user[image..., text]`，满足 OpenAI「tool 消息必须紧跟 assistant tool_calls」的约束。

**绝不能**把图插在两个 tool 消息之间，否则严格代理会 400。

### 4.6 capability gate 的落点（避免循环导入）

`handler.py` 目前不 import `app.py`，也不应 import。做法：

```python
_IMAGE_MAGIC = (
    (b"\x89PNG\r\n\x1a\n", "image/png"),
    (b"\xff\xd8\xff", "image/jpeg"),
    (b"GIF87a", "image/gif"),
    (b"GIF89a", "image/gif"),

)


def _sniff_image_magic(path):
    """前 16 字节判图；不打开整文件，避免把大二进制当文本读。"""
    try:
        with open(path, 'rb') as f:
            head = f.read(16)
    except OSError:
        return None
    if len(head) >= 12 and head[:4] == b"RIFF" and head[8:12] == b"WEBP":
        return "image/webp"
    for magic, media_type in _IMAGE_MAGIC:
        if head.startswith(magic):
            return media_type
    return None
```

```python
    """原生 image 输入能力判定（app.supports_image_input 的唯一实现）。"""
    backend = getattr(backend, 'primary', backend)
    if backend is None:

    if bool(getattr(backend, 'supports_image_input', False)):

    if isinstance(backend, NativeClaudeSession) and not isinstance(backend, NativeOAISession):
        if 'native_image_input' in getattr(backend, '__dict__', {}):
            return bool(getattr(backend, 'native_image_input'))
        return True
    if isinstance(backend, NativeOAISession):
        return bool(getattr(backend, 'native_image_input', False))
    return False
```

## 8. 坑清单

1. **`tool_result.content` 是字符串 = 图不存在。**
   Anthropic 只有数组形态才解析 image block。这是整个改动里唯一"看起来对、实际全错"的坑。
2. **OpenAI 的 `role:"tool"` 不接受图片。**
   必须抬到紧随其后的 user 消息；而且**所有 tool 消息必须连续**，
   不能把 user 插在两个 tool 之间，否则严格代理 400。
3. **不要把 image block 放进 `next_prompt`。**
   那是纯文本通道，`str(dict)` 会变成几 MB 的 Python repr 进 prompt。
4. **不要让图片经过 `budget_tool_result`。**
   它按字符预算截断并可能落盘，签名只收 `str`。图必须走 `images` 字段旁路。
5. **先嗅探再读文本。**
   否则 40 MB 的 PNG 会先被 `open(..., encoding='utf-8', errors='replace')` 读一遍，
   再被 `smart_format` 截断 —— 又慢又脏。
6. **并行 `file_read` 的顺序。**
   `_run_parallel_tools` 按 index 返回，但 `StepOutcome.images` 不能放进共享的 handler 状态里，
   必须是每次调用的返回值，否则两图会串。
7. **重复读同一张图会线性叠加 token。**
   每读一次就是 1500 token + 一份 base64 在 history。P2 用 sha1 去重，
   并在 note 里明确"不要再读同一路径"。
8. **硬裁剪后模型会"失忆"。**
   `trim_messages_history` 丢掉最旧消息时图一起丢，这是与 CC 一致的行为，
   不要试图把 base64 重新塞回去。
9. **尺寸边界与 CC 不同。**
   GA `MAX_DIMENSION=2048`，CC 长边 1568；GA `MIN_DIMENSION=8` 会拒绝极小图标。
   若发现 token 偏贵，再考虑对齐 1568，不要一次改两个变量。
10. **BMP 必须有 Pillow。**
    `image_codec.py:221` 明确：无 Pillow 时 BMP 直接报错。错误文本要原样透给模型，
    不要吞掉。
11. **日志与终端绝不能出现 base64。**
    `_write_llm_log` 已有 `_redact_image_payloads`，但新增代码不要自己 `print(block)`。
12. **workflow child 的 `parent.llmclient` 是假的。**
    `child_agent.py:965` 是 `SimpleNamespace(backend=SimpleNamespace(history=[]))`，
    自动探测必然 False；必须在 `:880` 之后用真实 `client` 显式赋值。
13. **`_fix_messages` 的孤儿 tool_result 会把 content 变成字符串。**
    裁剪导致 tool_use 丢失时，图会跟着丢 —— 这是安全降级，不要"修复"它。
14. **图片 block 不要混进 `outcome.data` 的 dict。**
    `structured=True` 时会 `json.dumps`，base64 会进 tool_result 文本，等于白做。

---

## 9. 验收标准（DoD）

1. Claude native 后端：`file_read("<png>")` 后，下一轮 assistant 能**直接描述图内内容**。
2. OAI native（`native_image_input: true`）后端：同样能描述，且抓包可见
   `role:"tool"` 为字符串 + 紧随 user 含 `image_url`。
3. 不支持视觉的后端：返回明确文本提示，无异常、无 400、prompt 里没有 base64。
4. 文本文件读取行为、`tool_results` 形状、transcript 字节数**零变化**。
5. `python -m unittest tests.test_native_image_input tests.test_agent_image_read` 全绿。
6. `log/` 中 image 的 `data` 一律是 `<redacted base64 len=...>`。
7. 一次会话里连续读 3 张图不触发上下文压缩异常，`estimate_msg_tokens` 每张图计 ≈1500。

## 10. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| 某代理严格校验 tool_result 数组 | 400 | 加 `GA_AGENT_IMAGE_READ=0` 环境变量，`_image_input_enabled` 直接返回 False |
| 大图导致单轮 token 暴涨 | 上下文被裁 | codec 已限 2048 / 5 MB；必要时对齐 CC 的 1568 |
| transcript 体积膨胀 | 磁盘 | §4.8 的 `GA_TRANSCRIPT_IMAGE_MODE=path` |
| 模型反复读同一图 | token 浪费 | P2 sha1 去重 + note 提示 |

回滚粒度：**只回退 Slice 2 即可关闭工具读图**，Slice 1/3/4 是纯结构改动，
无图时行为与改动前完全一致。

## 11. 与 CC 的差异（有意为之）

| 点 | CC 303 | GA 方案 | 理由 |
|----|--------|---------|------|
| 工具 | Read 的 image 分支 | `file_read` 的 image 分支 | 同构 |
| 元信息位置 | 独立 `isMeta` 消息 | 同一 tool_result 的 text 块 | GA 的 loop 只有一条 user 消息，少一条消息更省 |
| OAI 兼容 | 有专门的降级路径 | 抬到 user 消息 | OpenAI 协议限制 |
| 缩放上限 | 长边 1568 | 2048 | 沿用 GA 既有 codec，避免一次改两个变量 |
| 重复读 | 不做去重 | P2 做 sha1 去重 | GA 会话更长、工具循环更多 |

## 13. 一句话总结

**GA 不缺看图的能力，缺的是"把图从工具送到模型"的那三行管道。**
`do_file_read` 出一个 image block、`StepOutcome` 带一个 `images` 字段、
`loop` 在 `tool_result.content` 里保留数组形状 —— 三处改完，
agent 就能像 CC 的 Read 一样，自己打开一张图看见它。
