# GA Ink 首轮大输出遮挡：Bug 分析与修复方案

- 日期：2026-10-23
- 范围：`frontends/ink/ui`（Ink 前端）
- 结论：数据没有丢，问题出在**流式提交把工具头与参数围栏拆开**，叠加**未闭合工具参数被原样绘制**和 **live band 只有 12 行**。修复同时改这三处。
- 说明：本文先于代码修改落盘；修复与测试见后续提交。

---

## 0. 对 GA 原分析的判断

GA 的分析方向基本正确：它抓住了 live band 12 行、fence-safe 提交停滞、相对擦除三个机制，也正确排除了“数据丢失”和“`[omitted long output]` 是 UI 折叠”。

但它把 **H1（12 行上限）当成了主因**，把 **H2（fence-safe 提交停滞）当成放大因素**，这与实际代码链路相反：

1. `findFenceSafeOverflowCount()` 确实会在工具参数围栏未闭合时停滞；
2. 但真正致命的是，它**已经开始提交了，而且把 `⏺ Tool: code_run args:` 这一行单独提交出去**；
3. 于是 Static 里只剩一个 `● code_run`，live 里只剩 ````text` + 大段 JSON；
4. live 段没有工具头，`formatAssistantText()` 无法把它识别成工具参数块，只能按普通 Markdown 代码块整段绘制；
5. 大段 JSON 把 live 行数推高，12 行视口只画尾部，用户就看到“上半部分被盖住/消失”。

所以：

- **H1 是放大器，不是根因。**
- **H2 的机制存在，但描述不完整；真正的 bug 是提交边界把工具调用拆成两半。**
- **H3（cursorPark/相对擦除擦到 Static）没有证据支持。** 最终虚拟终端回放 `missing: 0 / duplicated: 0`；`_probe_firstturn_clobber` 里的重复计数是把“同一帧重绘”按原始字节累计，不能当作屏幕重复或覆盖证据。

## 1. 决定性证据

### 1.1 提交边界把工具头单独切走

用真实状态机逐 delta 复现（70 行 `code_run` 参数）：

```text
delta@1140 commits=1 liveRows=22
commit tails: ["我先执行一个脚本。"]
live starts: "⏺ Tool: `code_run` args:\n````text\n{\n  \"script\": \"const x0 = 0..."

delta@1200 commits=2 liveRows=24
commit tails: ["我先执行一个脚本。", "⏺ Tool: `code_run` args:"]
live starts: "````text\n{\n  \"script\": \"const x0 = 0..."
```

第二次提交后：

- Static：`● code_run`（只有工具头，没有参数围栏）
- live：以 ````text` 开头的大段 JSON

`formatAssistantText()` 的完整工具块正则要求“工具头 + ````text` + 参数 + 闭合 ````”在同一个字符串里。两者被拆开后，live 段永远匹配不上，JSON 就按普通代码块整段显示。

### 1.2 这正好解释截图

截图里看到的是：

```text
● code_run
{
  "script": "import os
  ...
}
```

而不是 CC 风格的：

```text
● code_run(script: import os..., timeout: 60, type: python) (ctrl+o to expand)
```

原因不是 Markdown 解析错了，而是**工具头已经被提交到 Static，参数还留在 live**。

### 1.3 live 12 行上限把后果放大

`planMessageViewport()` 默认 `DEFAULT_MAX_LIVE_ROWS = 12`，而 `liveTranscriptViewportLines()` 在溢出时只保留尾部。于是：

- 大段 JSON 在 live 里持续增长；
- 视口只画最后 12 行；
- 工具头、`Exit Code: 0`、`[Stdout]` 等中段内容在“当前屏幕”上不可见；
- 等整轮进入 Static 后，向上滚动才能看到完整内容。

这与用户描述的“首轮进行中看不到，第二轮后往上翻又能看到完整第一轮”完全一致。

### 1.4 H3 未成立

`_probe_overwrite.ts`（真实 `<App>` + 虚拟终端，120 行输出）：

```text
TOTAL visual rows: 142
missing: 0
duplicated: 0
ExitCode line present: true
```

`_probe_firstturn_clobber.ts` 中 `L010:2 / L040:2` 的来源是：同一段内容在“增量重绘帧”里被写了多次，统计脚本按 `plain.split(needle)` 计数，把重绘帧也算成了重复。它不是最终屏幕重复，也不是 Static 被擦掉的证据。最终虚拟终端回放仍是单份。

`_probe_frame_geometry.ts` 的 `ERASE_MISMATCH` 同样是把 `log.clear()` 纯擦除帧、Static 追加帧都算进“当前帧行数”的粗判，不能直接证明擦到上方历史。至少目前没有可复现的丢失。

## 2. 根因链

```text
assistant_delta 累积
  → commitStreamingAssistantMessages()
  → findFenceSafeOverflowCount() 选切点
  → 切点落在 “工具头” 与 “````text 参数围栏” 之间
  → 工具头进 Static，参数留 live
  → live 段无法被 formatAssistantText() 识别为工具块
  → 大段 JSON 按代码块绘制
  → live 行数 > 12
  → 只画尾部
  → 用户看到“上半部分被覆盖”
```

三个可独立验证的缺陷：

| 编号 | 缺陷 | 角色 |
|---|---|---|
| R1 | 流式提交允许切在工具头之后、参数围栏之前 | **主因** |
| R2 | 流式中的未闭合工具参数不会被折叠，原样进入渲染 | **主因放大器** |
| R3 | live band 固定 12 行，且只保留尾部 | **视觉放大器** |

## 3. 修复方案

### 3.1 提交边界：工具头与参数围栏不可拆

在 `streamCommit.ts` 增加“工具头尾行”判断：如果候选提交段的最后一个非空行是 `⏺ Tool: \`name\` args:`，该切点不安全，继续向前找。

这样：

- 工具头、` ````text`、参数体、闭合围栏作为一个整体保留在 live；
- 围栏闭合后，下一次提交可整块进入 Static；
- Static 中的工具块能被 `formatAssistantText()` 正确折叠成一行摘要。

### 3.2 流式渲染：未闭合工具参数先折叠成工具名

在 `formatAssistantText()` 增加 `streaming` 选项。流式且工具参数围栏未闭合时，把“工具头 + 未闭合参数体”折叠为 `● tool_name`，不把 JSON 原样塞进 transcript。

这样即使某个工具块暂时无法提交，live 也只占 1 行，不会把视口撑爆。

### 3.3 视口：live 使用终端可用高度

`App.tsx` 调用 `planMessageViewport()` 时显式传入 `maxLiveRows: metrics.messageRows`，让 live band 在运行中最多使用当前终端可用的消息区高度，而不是固定 12 行。

保留 `DEFAULT_MAX_LIVE_ROWS = 12` 作为无终端上下文的默认值；真实 UI 不再被它硬截断。

### 3.4 不在本轮修改的部分

- 不引入绝对行锚点或重写 cursorPark：目前没有 H3 的实证，贸然改会引入 IME 光标回归。
- 不改 `handler.py` 的 `max_str_len=600`：`[omitted long output]` 是后端工具结果截断，和本次遮挡不是同一问题。
- 不删除 GA 的探针脚本：它们仍有回归价值，后续统一整理。

## 4. 回归测试

新增/调整测试覆盖：

1. `streamCommit.test.ts`
   - 长参数块流式增长时，任何提交段都不得以工具头结尾；
   - 完整工具块尽量整块提交，不把 ````text 与工具头拆开；
   - 既有 fence-safe 测试继续通过。
2. `messageFormat.test.ts`
   - `streaming: true` + 未闭合工具参数 → 只剩 `● code_run`；
   - 工具头之前的正常文本保留；
   - 完整工具块仍然折叠为一行摘要；
   - 第二个未闭合工具块不会吞掉前面的完整内容。
3. `messageWindow.test.ts`
   - `done: false` 的消息传入 streaming 模式，transcript 行数不随未闭合 JSON 线性增长。
4. `messageViewportPlan.test.ts` / App 集成
   - 运行中 live 高度可使用超过 12 行（由 `messageRows` 限制）；
   - idle 时仍不产生大块空白 spacer。

## 5. 验收标准

- 首轮 `code_run` 大参数流式期间，屏幕只显示一行 `● code_run`，不再出现整段 JSON 代码块。
- 参数围栏闭合后，工具块进入 Static 并折叠为一行摘要。
- 首轮运行中向上翻，不再出现“工具头在 Static、参数在 live”的割裂画面。
- 120 行普通 stdout 探针最终 `missing: 0 / duplicated: 0` 保持成立。
- `npm test`、`npm run typecheck` 全绿。
