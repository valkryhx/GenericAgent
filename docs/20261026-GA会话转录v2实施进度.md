# GA 会话转录 v2 实施进度

> 目标：从当前 v1 的“每轮保存完整 backend history before/after”迁移到 v2 的增量事件模型。
>
> 本文跟踪 **Phase 0 + A + B + C + D**。Phase C 完成 compact boundary；Phase D 完成 rewind 与 working_state。物理压缩明确不在当前范围。

## 1. 范围锁定

本阶段只做三件事：

1. **Phase 0：基线与保护网**
   - 记录现有测试基线；
   - 确认 backend history 的真实追加路径；
   - 增加 v1 兼容和 v2 增量写入测试；
   - 不改现有 compact / rewind 协议。

2. **Phase A：v2 writer + v1 只读兼容**
   - 新会话写 `version: 2`；
   - 普通轮次只追加该轮消息和 `turn_end`；
   - 不再写 `backend_history_before` / `backend_history_after`；
   - v1 reader 保留，旧会话继续可读、可恢复；
   - 通过回滚开关可强制新会话继续使用 v1。

3. **Phase B：projection adapter**
   - 从 canonical v2 events 生成 backend/API history 副本；
   - 从 canonical v2 events 生成 UI messages；
   - 请求前裁剪只作用于 projection 副本；
   - v1 继续走 fallback。

明确**不在本阶段做**：

- 不重构 `record_compact()` 的 v1 快照语义；
- 不重构 `record_rewind()`；
- 不做 transcript 物理压缩；
- 不删除旧 v1 解析逻辑；
- 不迁移、不覆盖旧会话文件。

## 3. 关键源码事实

### 3.1 写入链路

- `genericagent/core/transcripts.py`
  - `create_session()` 默认写 `version: 2`，可用 `GA_TRANSCRIPT_SCHEMA=v1` 回滚 writer；
  - `record_turn()` 保留为 v1-only 兼容入口；
  - v2 `record_agent_turn()` 只持久化本轮新增 message + `turn_end`。

- `genericagent/core/app.py`
  - 每轮开始捕获 `transcript_history_before`；
  - 成功/失败都调用 `record_agent_turn()`；
  - 因此同一轮会保存两份完整 history，且历史长度随轮数增长。

### 3.2 backend history 的真实追加路径

- `BaseSession.__init__()` 初始化 `self.history = []`。
- `BaseSession.ask()` 在请求前原地 `history.append(user_message)`；
- 请求成功后再原地 `history.append(assistant_message)`。
- `trim_messages_history()` 过去会原地 `pop(0)`；Phase B 已改为只操作请求副本。
- `NativeClaudeSession.ask()` 同样直接 append user/assistant，但 trim 只作用于请求副本。

结论：不能简单假定 `handler.history_info` 等于 backend history。Phase A 的增量必须从轮次开始和结束时的 **backend history 实际差异** 得出，并且写入的是可独立重放的 content blocks，而不是整份快照。

### Phase A/B 边界收口（2026-10-26，最终复核）

在主体实现完成后，补做了 5 个边界语义，仍不属于 Phase C/D：

1. **tool_result 来源标记**
   - v2 writer 不再仅按 role 推断 origin；
   - `role=user` 且 content 含 `tool_result` 时写
     `origin.kind=tool_result`；
   - UI 投影不会把工具结果误显示为用户发言。

2. **v1 → v2 分支可再次 resume**
   - v2 分支的 `resumed_from` 现在会被 reader 跟随；
   - 重新 `/resume` 分支文件时，展示源 v1 历史 + 分支新增轮次；
   - 源文件仍只读，不迁移、不覆盖；
   - 分支本地 turn_id 仍从 1 开始；另用
     `LoadedSession.branch_rounds` 作为续写游标，避免与源 v1 轮号冲突。

3. **分支文件目录继承**
   - 从 v1 恢复后创建 v2 分支时，默认继承源 transcript 所在目录；
   - 修复分支写进默认 sessions 目录、但当前 resume 列表扫描另一个 root 时
     “新分支在列表中不可见”的问题。

4. **v2 compact listing 兼容**
   - listing 扫描遇到兼容桥 `compact` 时同步清空轮次；
   - 仅保证 `/resume` 列表和 `load_session()` 一致，
     **没有修改 compact 的数据格式或压缩语义**。

5. **version detection 有界读取 + workflow v2 覆盖**
   - `_detect_session_version()` 改为逐行读取，首条合法事件即停止；
   - 新增 v2 workflow event 不增加轮次、不污染 UI/API projection 的测试。

## 9. 风险与待确认项

1. `handler.history_info` 是 UI/agent 历史，不等同于 `backend.history`。
   - Phase A 必须从 backend history 的轮次开始/结束差异提取增量。
2. hard trim 可能让轮次开始快照不再是轮末 history 的前缀。
   - 增量提取必须容忍“旧前缀已被 trim 掉”；找不到公共前缀时，本轮至少写入实际 user/assistant 消息，不能写整份快照。
3. tool_use / tool_result 必须成组投影。
   - 若投影窗口从一个 `tool_result` 或孤立 assistant tool_use 开始，需要回退/补齐配对。
4. compact、rewind 仍可能出现 v1 事件。
   - 本阶段不允许 v2 writer 静默混写 v1 快照；通过独立兼容入口隔离。
5. 旧 v1 文件只读。
   - 旧会话继续发言时优先新建 v2 会话；本阶段至少不得原地追加 v2 事件污染旧文件。

- v1 恢复后继续输入会创建新的 v2 分支文件，并追加 `resumed_from`；旧 v1 文件

### Phase B

- 新增 `projection.py`：UUID 去重、tool_use/tool_result 配对修复、缺失结果占位、
  孤立结果降级、4096 窗口和真实 user 起点约束。
- `BaseSession.ask()` 与 `NativeClaudeSession.ask()` 先把工作历史复制成请求副本，
  hard trim 只修改副本；请求失败/成功都不会因 trim 丢失 canonical 事件来源。
- v2 resume 从 canonical events 生成 backend history 与 UI messages。
- `app.py` 的 v2 轮次锚点改为“轮次开始前的 history 长度”，不再每轮 deepcopy
  完整 before history；v1 仍保留快照兼容路径。

### 关键约束与剩余风险

- `backend.history` 在 v2 中仍是“当前工作缓存”，不是磁盘 canonical；请求裁剪
  已不再从它删除旧消息。
- 本阶段 compact/rewind 仍复用旧快照桥。后续进入 Phase C 时，必须单独处理
  boundary/summary/preserved，不得把本次 projection 结果误当成 compact canonical。
- v1 分支使用新的本地 turn_id 命名空间；完整恢复展示源历史 + 分支历史时需要
  分别读取 `rounds`（展示轮数）与 `branch_rounds`（本地续写游标）。
- 物理压缩、transcript 原子替换、preserved UUID 清理均未在本阶段启用。
- Phase C/D 已完成 compact boundary、preserved UUID、rewind 和 working_state。
- transcript 物理压缩已明确移出当前范围，原始 JSONL 保持 append-only。

### Phase C（已完成）

- `projection.py` 增加 `compact_boundary` 投影：
  - summary 只进入 API/transcript 视图，不作为普通用户发言进入 UI；
  - boundary 前只恢复 `preserved_uuids` / `preserved_segment` 父链；
  - boundary 后消息全部属于当前分支；
  - summary 缺失时安全回退到线性投影；
  - preserved UUID 缺失时跳过，不从无关内容猜测。
- `record_compact_v2()` 只写 `compact_boundary + summary`，不再复制完整
  `backend_history_after`。
- manual compact 和 auto compact 已接入 v2 写入。
- compact 前会快照轻量 `working`、`last_tools`、usage，并作为
  `working_state` 事件写在该 boundary 的 `turn_id` 下；这样 compact 清空
  handler 后，resume 仍能恢复工作记忆。
- `/resume` listing 遇到 compact boundary 时与 `load_session()` 的轮次语义一致。

### Phase D（已完成，不含物理压缩）

- v2 rewind 使用显式 `rewind` 事件和轻量 anchor，不再写完整
  `backend_history_after`。
- Ink resume 重建 rewind checkpoint 时使用 turn 自己的 branch `turn_id`，
  修复 v1 source 合并后 UI task id 与真实 turn id 不一致的问题。
- `working_state` 按 `turn_id` 持久化；resume 后每个历史 rewind checkpoint
  读取对应 turn 的状态，而不是统一使用最新全局状态。
- 恢复链路覆盖 `backend.history`、`last_tools`、`last_usage_tokens` 和
  `handler.working` 的轻量白名单字段。
- 只保存 skill 元数据和 hash，不保存 SKILL.md 正文或任意大对象。
- 写入增加进程内锁，避免同一进程并发 append 交错。

### 明确不做：transcript 物理压缩

经再次核对 CC 303 源码，`performCompactTranscript()` 确实存在，但属于
`CLAUDE_CODE_TRANSCRIPT_LOCAL_GC` / `tengu_transcript_local_gc` 控制的
默认关闭能力，不是普通 `/compact` 的默认行为。

GA 当前明确不实施：

- 不删除原始 JSONL 行；
- 不做临时文件重写和原地 replace；
- 不接自动 GC；
- 不提供 `GA_TRANSCRIPT_GC*` 生产开关；
- 已移除 Phase D 原型里的物理压缩代码和测试脚本。

原 transcript 保持 append-only；语义 compact 继续通过 boundary + summary
控制模型上下文，不承担磁盘裁剪职责。
