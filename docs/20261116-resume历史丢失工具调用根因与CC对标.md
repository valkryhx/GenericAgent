## 0. 结论先行

> **数据没丢，是转成 UI 消息时被压成纯文本了。**
>
> transcript 里 `tool_use` / `tool_result` / `thinking` 块**完整存在**（含 name、id、
> 完整 input、完整 result）。`load_v2()` 用 `_message_text_from_blocks()` 把 assistant
> 消息折叠成纯文本时，**只收集 `type == "text"` 的块**，其余全部丢弃。`bridge.py` 再拿
> 这个纯文本发 `history_replace`，前端自然只能画出文字。

CC 319 的做法完全不同：它把消息转成 UI 项时**保留 `toolUses` / `toolResults` 两个结构化
数组**，不压成文本。见 §3。

## 2. 根因定位

### 2.1 第一层：折叠成纯文本时丢弃非 text 块

```python
# genericagent/core/transcripts.py:229
def _message_text_from_blocks(blocks):
    parts = []
    for block in blocks or []:
        if isinstance(block, dict) and block.get("type") == "text":
            value = block.get("text")
            if isinstance(value, str) and value.strip():
                parts.append(value)
    return chr(10).join(parts).strip()
```

`load_v2()` 用它填充 `turn.assistant_text`：

```python
# transcripts.py:1085 附近
value = str(event.get("text") or _message_text_from_blocks(event.get("blocks")))
turn_text.setdefault(int(turn_id), {})["assistant_text"] = value
```

`tool_use` / `tool_result` / `thinking` 在这一步全部消失。

### 2.2 第二层：bridge 只把纯文本发出去

```python
# frontends/ink/bridge.py:3578  _resume_ui_messages_with_checkpoints()
for turn in loaded.turns:
    messages.append({"role": "user", "text": turn.user_text, "taskId": task_id})
    ...
    if turn.assistant_text:
        messages.append({"role": "assistant", "text": turn.assistant_text, "taskId": task_id})
```

注意：完整的 `backend_history` **没有被丢弃**，但只进了 `_rewind_snapshots`（供 rewind
回退使用），**没有进 `messages`**。

### 2.3 第三层：协议类型只有 text

```ts
// frontends/ink/ui/src/protocol.ts:102
export type HistoryMessage = {
  role: 'user' | 'assistant' | 'system'
  text: string          // ← 只有纯文本，没有 toolUses / toolResults 的位置
  taskId?: number
}
```

### 2.4 为什么「实时」看起来是对的

前端把工具调用渲染成 `● tool_name(args)` / `  ⎿  result`，走的是**文本行解析**
（`messageWindow.ts:200` `isToolChipRow`：匹配行首 `●` + `name(`）。实时流里这些行由
turn 过程中的进度文本流进 `assistant_delta`。

而 transcript 的 `assistant_text` 取的是**模型回复的 text 块**，本来就不含进度行。
两条来源不同，所以「实时有、resume 没有」。

⚠️ **这说明修复不能只做 `_message_text_from_blocks`。** 即使把 `tool_use` 渲染成文本塞进
`assistant_text`，格式也必须与前端 `isToolChipRow` 认得的形状一致，否则画不出 chip。

## 3. CC 319 的做法

### 3.1 消息 → UI 项时保留结构化数组

```js
// m0591_0x11be624e.js:45435
function jke(e) {
  if (e.type === "assistant") {
    let w = e.message.content, N = [], G = [];
    for (let Y of w)
      if (Y.type === "text") G.push(Y.text);
      else if (Y.type === "tool_use") N.push({
        tool_use_id: Y.id,
        tool: Y.name,
        input: mOn(Y.input)          // 参数摘要
      });
    return { role: "assistant", text: G.join(""), toolUses: N };
  }
  if (e.type !== "user") return;
  ...
  for (let w of n)
    if (w.type === "text") r.push(w.text);
    else if (w.type === "tool_result") s.push({
      tool_use_id: w.tool_use_id,
      text: ZAs(w.content),
      isError: w.is_error === !0,
      ...
    });
  return VVe(r.join(""), s);        // { role:'user', text, toolResults:[...] }
}
```

**关键点：`text` 与 `toolUses` 并列返回，互不吞并。** 纯文本只装正文，工具调用单独成数组。

### 3.2 消费点：把 toolResults 建成 map，供 toolUses 配对

```js
// m0591:46116  zWo(e, n) —— 取最近 N 条历史转成 UI 项
function zWo(e, n) {
  let r = [], s = new Map, h = Xke(s, n);
  for (let y of e.toReversed()) {
    if (r.length === jS) break;
    let S = jke(y);
    if (!S) continue;
    for (let w of S.toolResults ?? []) s.set(w.tool_use_id, w);   // ← 结果进 map
    r.push({ ...S, toolUses: S.toolUses.map(h) });                // ← 调用按 id 关联结果
  }
  return r.reverse();
}
```

即：**调用与结果按 `tool_use_id` 关联，UI 层拿到的是成对的结构化数据**，不需要去猜文本形状。

## 4. 两者差异一览

| 维度 | CC 319 | GA 现状 |
|---|---|---|
| 存储 | 消息级 jsonl，content blocks 原样 | ✅ 相同（v2 也是 blocks 原样） |
| 转 UI | `{text, toolUses[]}` / `{text, toolResults[]}` | ❌ `{text}` only |
| 调用-结果关联 | 按 `tool_use_id` 建 map | ❌ 无 |
| 渲染依据 | 结构化字段 | 解析文本行首 `● name(` |
| thinking 块 | 有独立渲染路径 | ❌ 丢弃 |

**结论：GA 的存储层已经和 CC 对齐了，缺的是「转 UI 消息」这一层。**

## 5. 实现（方案 A 已落地）

按「与 CC 同构」的方向实现，数据全程保持结构化，直到渲染层才变成行。

### 5.1 加载层：`transcripts.py`

`TranscriptTurn` 增加三个字段：

```python
tool_uses: list = field(default_factory=list)       # [{id, tool, input(JSON字符串)}]
tool_results: list = field(default_factory=list)    # [{toolUseId, text, isError}]
thinking: list = field(default_factory=list)        # [str, ...]  每个 thinking 块一条
```

新增 `_tool_blocks_from_message()` / `_thinking_blocks_from_message()` 抽取。
`load_v2()` 按 turn 聚合，**不触碰 `_message_text_from_blocks`**——它是别的调用方的
既有契约，`assistant_text` 仍然只装模型自己的 prose。

`input` 传的是**原始 args 的 JSON 字符串**，这样前端可以复用实时路径的
`formatToolBlock()`：折叠/展开（Ctrl+O）行为与实时完全一致。

`tool_result.content` 既可能是字符串，也可能是 text 块列表（Anthropic 两种形态都合法），
两种都处理。`redacted_thinking` 保留为空字符串标记——推理被隐去，但这一步确实发生过，
UI 应当能表达「有思考但不可读」而不是静默略过。

### 5.2 协议层：`protocol.ts`

```ts
export type HistoryToolUse = { id: string; tool: string; input: string }
export type HistoryToolResult = { toolUseId: string; text: string; isError?: boolean }
export type HistoryMessage = { role, text, taskId?, toolUses?, toolResults?, thinking? }
export type ChatMessage = { ...同上... }
```

### 5.3 转发层：`bridge.py`

`_resume_ui_messages_with_checkpoints()` 把三个数组一并发出。**保留空 prose 但有用具
或思考的 turn**：模型只用工具作答时 `assistant_text` 为空，旧逻辑会让整个 turn 从历史
里消失。

### 5.4 渲染层：`messageWindow.ts`

- `appendStructuredToolRows()`：渲染成与实时**完全相同**的形状

  ```
  ● spawn_agent(task_name: probe_a, fork_turns: none)
    ⎿  {"status": "started", "pid": 34136}
  ```

- `appendThinkingRows()`：复用工具 chip 的折叠开关（Ctrl+O）

  ```
  折叠：▸ ✻ Both spawned successfully. Return ACK line only.
  展开：▾ ✻ thinking
          Both spawned successfully.
          Return ACK line only.
  ```

`formatToolBlock` 从 `messageFormat.ts` 导出以复用，保证 chip 的措辞、截断、
展开逻辑只有一份。结果按 `tool_use_id` 配对（不是数组位置）——与 CC 的 `zWo()` 一致。

### 5.5 未采用方案 B 的原因

方案 B（在 bridge 里合成文本行）虽然只改一处，但依赖前端 `isToolChipRow` 认的文本
形状，形状一改就静默失效，且无法展开/折叠、参数被压平丢结构。方案 A 让数据保持
结构化直到渲染层，与 CC 一致，也让 thinking 等块将来可以走同一条路。

## 7. 分析边界

- **实时路径仍未显示 thinking。** 本次修的是 `resume` 侧（加载 → 转发 → 渲染）。
  实时要显示思考，需要改 `genericagent/llm/core.py` 的 yield 契约：现在
  `_parse_claude_sse` 的 `thinking_delta` 只累加到 `current_block`，**从不 yield**；
  chat_completions 分支的 `reasoning_text` 同样只进 `blocks`。这是一处独立的、
  风险更高的改动（会影响流式文本边界），未在本轮进行。
  用户观察到的「从来没见过 thinking」在实时侧同样成立，原因就是这一段。
- 「实时工具行来自 `assistant_delta` 的进度文本」由前端解析逻辑（`isToolChipRow` 认
  `● name(`）与 transcript `assistant_text` 不含工具名的实测共同推出；**未**逐行追踪
  后端产生进度文本的具体函数（`loop.py` 的 `yield` 链路较长，本轮未走完）。
- CC 侧只读了 `jke` / `zWo` / `lio` 几个函数及其调用点，未通读它的整个渲染栈。
- v1 schema（`turn` 事件）的 `assistant_text` 实测**含**工具行（7915 字符、含 `🔧`），
  与 v2 不同。本次只修 v2 路径；v1 会话本来就能显示工具行（以文本形式），
  行为不变。新增的 Python 测试全部针对 v2。
